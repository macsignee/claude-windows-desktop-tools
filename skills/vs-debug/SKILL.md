# Visual Studio の操作 (開く・前面・ブレークポイント・デバッグ実行)

> **パスの書き方:** `<Skill群>` = この Skill のフォルダ (Base directory) の 1 つ上。ほかの Skill も、そこにある。コマンドでは、実際のパスに置き換える。

Claude (WSL) は、Windows の Visual Studio を、直接操作できない。そこで、**ホスト側のウォッチャーに、操作を依頼する** (`trigger_vs.flag`)。ウォッチャーは、VS の自動化の窓口 (DTE) を、実行中のプロセスの表 (ROT) から、**ソリューションのパスで**探す (「最初の VS」ではない。VS 2022 / 2026 など、版に依らない)。結果は、ファイルで返る。
**自分で `devenv.exe` / `powershell.exe` を実行しない** (WSL のサンドボックスからは、動かない)。同梱のスクリプトを使う。

## 前提
- ユーザーが、対象のソリューションで `run_watcher.cmd` を起動済みであること (ビルドと同じウォッチャー。**`trigger_vs.flag` に対応した版** = `HOST_VERSION` 2.90.0 以降。`--output` / `--inspect` は 2.99.0 以降。`--step` / `--continue` / `--pause` / `--eval` は 2.101.0 以降。古ければ、`install.sh` で配り直して、ウォッチャーを再起動してもらう)。
- `$SLN_DIR` = `.sln` / `.slnx` があるフォルダ。

## スクリプト

```bash
bash <Skill群>/vs-debug/scripts/vs_once.sh "$SLN_DIR" [モード...]
```

| モード | 動作 |
|---|---|
| (なし) | ソリューションを VS で開く。**開いていなければ、引数に渡して VS を起動** (読み込みの完了まで待つ)。開いていれば、**そのウィンドウを前面に出す** (最小化なら戻す) |
| `--status` | 状態だけ。**VS を起動しない**。`OPEN:` / `INSTANCES:` / `DEBUG_MODE:` (design / run / break。`break` のときは `STOPPED:` の場所も) / `DIRTY: <パス>` (未保存) |
| `--changes` | git の差分 (追記・変更した**コードの行**。変更のかたまりごとに 1 つ、最大 10) に、ブレークポイントを置く。先に、このツールが置いたものを消す |
| `--break <相対パス>:<行>` | ブレークポイントを、1 つ置く (複数可。`--changes` と併用可。ソリューションのフォルダからの相対パス) |
| `--clear` | このツールが置いたブレークポイント (Tag で見分ける) だけを消す。ユーザーが手で置いたものは、消さない |
| `--reload` | git で変更したファイルのうち、VS で開いていて、**未保存の編集がない**ものを、開き直す |
| `--debug` | デバッグ実行を始める。アプリの起動後、**ブレークポイントに着くのを、最大 20 秒待つ**。結果に、`DEBUG_MODE:` と、break で止まったときの `STOPPED:` (関数・ファイル・行) |
| `--no-wait` | `--debug` と併用。アプリが起動したら、**ブレークポイントを待たずに**返す (結果は `DEBUG_MODE: run`)。UI テストのアタッチ (下の「UI 操作をきっかけに」) で、きっかけを撃つ前に使う |
| `--inspect` | **ブレークで止まっているときの状態**: `EXCEPTION:` (例外)・`STACK:` (呼び出し履歴。最大 10)・`LOCALS:` (現在のフレームのローカル変数。最大 30。値は 200 文字まで)。読み取りだけ。止まっていなければ `INSPECT_SKIP:`。**`--debug` と一緒のときだけ**、20 秒でブレークに届かず、まだ起動中 (`run`) なら、さらに最大 40 秒、ブレークを待つ (初回の起動が遅いとき。`NOTE: the app was still starting` が付く) |
| `--output [行数]` | **VS の出力ウィンドウの「デバッグ」ペイン** (`Debug.WriteLine`・`Trace`・`OutputDebugString`・MFC の `TRACE`) の、最後の行数 (既定 200、1〜500)。全文は `$SLN_DIR/vs_debug_output.txt` に残り、標準出力には、**最後の 60 行**だけが出る (続きは、ファイルを `Read` する)。まだペインがなければ `OUTPUT_UNAVAILABLE:` (デバッグを、一度も始めていない)。読み取りだけ (ペインを消さない) |
| `--step over\|into\|out [歩数]` | **ステップ実行** (F10 / F11 / Shift+F11)。歩数は 1〜30 (既定 1)。**1 歩ごとに** `STEP n: ファイル:行  ソースの行` と、**変わった変数** (`CHANGED: 名前 = 前 -> 後`) を返す。関数が変わったときは `FRAME:` と `LOCALS:`。終了したら `STEP_END:`、15 秒たっても止まらなければ `STEP_TIMEOUT:` (モーダルダイアログや、入力待ちが原因。ウォッチャーは固まらない)。**止まっているときだけ** |
| `--continue` | 続行 (F5)。次のブレークポイントか終了まで (最大 20 秒待つ)。止まっているときだけ |
| `--pause` | 走っているアプリを止める (ブレークにする) |
| `--eval "<式>"` | 式の値を返す (ウォッチ)。**読み取りだけ: 代入・`++`・`--`・`;` は、`BAD_ARGS` で断られる。** 200 文字まで、1 回に 10 個まで。止まっているときだけ。`EVAL: 式 = 値 (型)` / `EVAL_ERROR:` |
| `--frame <N>` | (v2.107.0) `--inspect` か `--eval` と併用。**N 番目のスタック フレーム (0 = 先頭) を選んで**、`LOCALS:` と `--eval` を、そのフレームで読む。読んだあとは、元のフレームに戻る (VS の画面の選択は、変えたまま残さない)。`--debug` / `--status` / `--step` / `--continue` / `--pause` とは併用できない (`BAD_ARGS`)。範囲外は `FRAME_OUT_OF_RANGE:`、止まっていなければ `FRAME_SKIP:`。選んだフレームは `FRAME: #N …` の行で分かる |
| `--timeout 秒` | 待つ秒数 (既定 240) |

**実行系 (`--step` / `--continue` / `--pause` / `--eval`) は、指定した順に実行する。** 単独で指定したときは、`--status` と同じに、**VS を起動せず、前面にも出さない。** **デバッグの停止 (Shift+F5) の操作は、持たない** (ユーザーの操作)。

`--inspect` / `--output` だけを指定したとき (動作のモードと併用しないとき) は、`--status` と同じに、**VS を起動せず、前面にも出さない** (VS が、このソリューションを開いていなければ、`FAILED`)。`--debug` と併用すると、デバッグを始めて、止まる (または走る) のを待ったあとに、取り込む。

1 行目と終了コード: `OK` (0) / `FAILED` (1。複数の VS・すでにデバッグ中・ファイルなし など) / `BAD_ARGS` (2) / `WATCHER_NOT_RUNNING` (3。起動を依頼して止まる) / `ENV_ERROR` (4。VS が見つからない・開かない) / `TIMEOUT` (5。報告して止まる。**もう一度走らせない**: VS が、ダイアログを出して待っているかもしれない)。

## 依頼ごとの手順

### 「Visual Studio で開いて」「前面に」
`vs_once.sh "$SLN_DIR"` だけ。

### 「ブレークポイントを置いて」(追記・変更した部分)
1. `vs_once.sh "$SLN_DIR" --changes` (置く場所を、自分で決めたいときは、`--break 相対パス:行` を足す)。
2. 結果の `BREAK_SET:` を、報告する。**`NEW_FILE: <パス>`** は、新規ファイルで、行を自動では選べない。**自分で、実行の入口に近い、実質のある行を選び、`--break` で指定する。** `TRUNCATED: <件数>` は、10 件を超えたので、重要な行を `--break` で足すか、報告する。
3. **ブレークポイントを置くだけでは、実行しない。**

### 「デバッグのログを見て」「出力を解析して」「止まっている変数を見て」
1. **いつ読めるか:** `--output` は、**走っている間も、止まっているときも、アプリが終了したあとも、読める** (終了したあとでも、**次のデバッグを始める前なら**、読める。ペインは、新しいデバッグの開始で、クリアされる)。`--inspect` は、**止まっているときだけ** (走行中・終了後は `INSPECT_SKIP:`)。**アプリが落ちた・終了したときは、終了したあとに `--output` を実行する。** 最後のログと、**終了コード** (`プログラム '[...] xxx.exe' はコード N (0xN) で終了しました。`) から、原因を解析できる。取り込みは、その時点の写しで、追いかけ読みはできない (必要なら、何度か実行する)。**次のデバッグを始める前に、読む。**
2. VS で、デバッグが走っている (または、止まっている、終了した) こと。**ユーザーが、すでにデバッグ中なら、実行はしない** (`--debug` は付けない)。
3. `vs_once.sh "$SLN_DIR" --output 200` (ログ)。ブレークで止まっていれば、`--inspect` も足す: `vs_once.sh "$SLN_DIR" --inspect --output 200`。
4. 出力の `=== VS debug output ... ===` 以降が、ログの**最後の 60 行**。**もっと前が要るときは、`vs_debug_output.txt` を `Read` する** (全文は、最大 500 行)。`LOCALS:` / `STACK:` / `EXCEPTION:` は、止まった時点の事実。
5. **解析して、原因の候補と、確かめる次の一手 (ブレークポイントを置く場所、足すログ) を、報告する。** ユーザーが頼んでいないのに、ソースを直さない。
6. **取り込めるのは、VS が受け取る出力だけ:** `Debug.WriteLine`・`Trace`・`OutputDebugString`・`TRACE`。`Console.WriteLine` は、WinForms・WPF では、出力ウィンドウに出ない。アプリが、自分でファイルに書くログは、そのファイルを、直接読む (このスクリプトの対象外)。
7. **ログには、個人情報・認証情報・社外秘が、含まれていることがある。** 報告では、解析に必要な行だけを引用し、全文を貼らない。`vs_debug_output.txt` は、生成するソリューションの `.gitignore` に入れてある (コミットしない)。

### 「原因は、こちらのコードか、外のライブラリか」(v2.107.0。切り分け)
別のソリューションでビルドしたライブラリ (静的ライブラリ、DLL、アセンブリ) を使っているとき、止まった場所の**スタックの仕分け**で、見当をつける。静的な検査 (`mfc-check` など) は、外のソースには広げない (将来の話)。
1. 止まっている状態で `vs_once.sh "$SLN_DIR" --inspect`。`STACK:` の各フレームに、**所有者の印**が付く: `[ours]` (こちらのソース)、`[ext]` (外のライブラリ)、`[sys]` (Windows・MFC・CRT・.NET)、`[unknown]` (シンボルがなく、判定できない)。末尾の `(モジュール名)` は、そのフレームのモジュール。
2. 要約を読む: `OWNER: top=… (frame #n)` は、上から見て、最初の `sys` でないフレームの所有者。`BOUNDARY: #a ours -> ext #b` は、**こちら (#a) が、外 (#b) を呼んでいる境界**。`BOUNDARY: unknown (frame #n has no symbols)` は、境界を、断定できない (間のフレームにシンボルがない)。
3. 境界があれば、`vs_once.sh "$SLN_DIR" --frame <呼ぶ側 (#a)> --inspect` (または `--eval "<式>"`) で、**こちらが、外に何を渡したか** (引数・ローカル変数) を読む。引数が不正なら、こちらの責任の見当。正しいのに、外の中で落ちるなら、外の責任の見当。
4. **ヒントであり、断定ではない。** こちらが誤った引数を渡して、外の中で落ちるときも、`OWNER: top=ext` と出る。外の中の、ロジックの誤りかどうかは、スタックだけでは決まらない (外のソースを、読んで確かめる)。
- **判定の根拠:** ソースファイルのパスを、先に見る (ソリューションのフォルダの下 = `ours`、システム・VS・MFC のソース = `sys`、それ以外 = `ext`)。静的ライブラリは、exe に取り込まれて、モジュールが、こちらの exe になるため、モジュールでは見分けない。ソースがないときだけ、モジュールで判定する (システムのモジュール名か、パスで)。**こちらの出力フォルダにある DLL でも、ソース (PDB) がなければ `unknown`** (配布された外の DLL を、コピーしたものかもしれない。`ours` は、こちらのソースが見えるときだけ)。パスが分からない名前だけのモジュールは `unknown` (誤って `ours` / `ext` と言わない。`System.*` / `Microsoft.*` は、既知のフレームワークの名前だけを `sys` にする。`System.Data.SQLite` などの追加のライブラリは `unknown`)。**ソリューションの直下の `vcpkg_installed` / `packages` / `ThirdParty` / `third_party` / `external` / `vendor` の下のソースは、外のコードとして `ext`** (`add-package` が、ここに外のコードを置く)。.NET のフレームワークは、Source Link などで `/_/src/…` のようなパスになるが、モジュールがシステムなら `sys`。`STACK_TRUNCATED:` のときは、`BOUNDARY: none` に「深いフレームは、見ていない」と付く。`--frame` で選ぶと、VS のエディターが、そのフレームのソースに移る (開いたタブは、戻っても残る。フレーム自体は、`status` の前に、元に戻る)。`SOLUTION:` の行が出ないときは、システムでないものは `unknown`。
- **ネイティブ C++ (v2.107.2。実機で分かったこと):** `STACK:` の各フレームには、**ソースのパスが出ない** (.NET は出る)。そこで、(1) **止まったフレーム**は、`STOPPED:` のファイルを、**同じ関数名のフレーム**に割り当てて、ソースのパスで判定する (PDB がなく、`#0` にソースがないときは、VS が、ソースのある `#1` を現在のフレームにするので、`#1` に付く)。**ファイルがこちらのソリューションの中なら、そのフレームのモジュールが、こちらのプロジェクトの出力で、こちらの出力フォルダにあるときだけ割り当てる** (外の DLL の、同じ名前のフレームに、こちらのファイルを付けて、`[ours]` としない)。(2) ファイルがないフレームは、モジュールが、**こちらのプロジェクトの出力** (`*.vcxproj` / `*.csproj` / `*.vbproj` の名前、`TargetName` / `AssemblyName`。**パスが、こちらの出力フォルダにあるもの。名前だけのモジュールは対象外**) で、関数が、**こちらのソースに、`クラス名::関数名` の定義 (行頭から、`(引数)`、`const` などの後ろに `{` か `:`) がある**ときだけ `[ours]`。**呼び出し (`Lib::Fn(1);`、`return Lib::Fn(x);`)・宣言・コメント・メッセージ マップの `&クラス::関数` は、定義に数えない。** それ以外は `[unknown]` (静的ライブラリの深いフレームを、誤って `[ours]` にしない。`クラス名::` のない関数は、定義を判定できず `[unknown]`)。ソースの走査は、`bin` / `obj` / `x64` / `Win32` / `ARM64` / `Debug` / `Release` (どの深さでも) / `.git` / `.vs` と、外のコードの置き場 (`vcpkg_installed` / `packages` / `ThirdParty` / `third_party` / `3rdparty` / `deps` / `extern` / `submodules` / `external` / `vendor`) を除く。**`src\Debug\` のような、実際のソースのフォルダも除かれ、`unknown` になる (安全側)。****限界:** 止まったフレーム以外の、外のコードのフレームは、ソースが分からず、`[unknown]` のまま。**`EXCEPTION:` (v2.107.3):** ネイティブの例外 (アクセス違反など) は `$exception` が使えない。VS が止まったときにデバッグ出力ペインへ書く 1 行 (`…で例外がスローされました (App.exe 内): 0xC0000005: …` / `Exception thrown at … in App.exe: 0xC0000005: …`) の、**ペインの最後の行**を、例外のコード (`0xC…` / `0xE…` / `0x8…`) がコロンに挟まれた形のときだけ `EXCEPTION:` として出す (言語に依存しない)。**ヒント**: 例外のあとにアプリが出力を続けた、または、古い例外の行が最後に残ったまま、ブレークポイントで止まると、古い行を `EXCEPTION:` と出すことがある (行は、ペインの 1 行そのまま)。
- **日次の配布で、使うときの運用:** (a) **バイナリ・PDB・ソースの世代を揃える。** 揃っていないと、シンボルが読み込まれず、`[ext]` ではなく `[unknown]` が増える。番号を見ない運用 (最新を、バッチで引く) でも、PDB とソースを、同じ配布から取る。(b) シンボルが読み込まれるように、VS の「ツール → オプション → デバッグ → シンボル」に、PDB のフォルダを足す。(c) ソースの場所は、ソリューションのプロパティ → 共通プロパティ → **デバッグ ソース ファイル** (ユーザー単位。プロジェクトには入らない) に足す。(d) .NET のライブラリは、`<EmbedAllSources>true</EmbedAllSources>` と `<DebugType>embedded</DebugType>` で、ソースの場所の設定が要らなくなる。C++ の静的ライブラリは `/Z7` (デバッグ情報を `.lib` に埋め込む)、ソースのチェックサムは `/ZH:SHA_256`。

### 「ステップ実行して」「バグを探して」(ステップ実行で、原因を追う)
**ユーザーが、求めたときだけ** (デバッグの実行と、同じ)。ブレークポイントを置く・ログを見るだけの依頼では、進めない。

1. **仮説を立てる:** 症状・ログ・コードから、「どの変数が、どこで、期待とずれるか」を、先に決める。**ブレークポイントは、ずれる直前に置く** (`--changes` / `--break`)。最初から、1 歩ずつ進めない。
2. **止める:** `vs_once.sh "$SLN_DIR" --break 相対パス:行 --debug --inspect` (止まった場所・変数・履歴)。すでに止まっているなら、`--inspect` だけ。
3. **進める:** `vs_once.sh "$SLN_DIR" --step over 5 --inspect` のように、**まとめて進めて、1 歩ごとの場所と、変わった変数を、トレースで読む** (往復は、1 回に数秒かかるので、1 歩ずつは、遅い)。関数の中を見たいときだけ `--step into`、出たいときは `--step out`、次のブレークポイントまでは `--continue`。**期待する値と、トレースの値を、1 歩ごとに、突き合わせる。**
4. **確かめる:** 疑う値は、`--eval "式"` で、直接、見る (例: `--eval "i"`、`--eval "items.Count"`、`--eval "a <= b"`)。
5. **報告する:** 原因の候補 (どのファイルの、どの行で、どの値が、なぜ、期待とずれるか)、トレースの根拠、直し方の案。**頼まれていないのに、ソースを直さない。直すときは、デバッグを止めてもらってから** (停止は、ユーザーが Shift+F5)。

**守ること:**
- **1 回の依頼で、ステップは、合計 30 歩まで。** 超えそうなときは、ここまでの結果を報告し、**続けてよいかを、ユーザーに聞く。**
- **同じ場所に 3 回戻ったら、そこで止まる** (ループの中を、何周も追わない。ループは、ブレークポイントの条件を絞るか、`--continue` で、飛ばす)。同じ失敗 (`STEP_TIMEOUT:` など) が、続いたら、止まって、報告する。
- **`--eval` は、読み取りだけ** (スクリプトが、代入・`++`・`--` を断る)。**関数の呼び出しは、断られないが、副作用でプログラムの状態を変えうる。ユーザーの了承なしに、使わない** (変数・メンバー・配列の要素・演算の値を、見る)。
- **`STEP_TIMEOUT:` は、モーダルダイアログか、入力待ち** (UI の操作が要る)。再試行せず、ユーザーに、何が出ているかを聞く。**`STEP_END:` は、アプリが終了した** (終了コードは、`--output` で読む)。
- **ステップ実行は、アプリの状態を進める** (ファイルへの書き込み・通信などの副作用も、実行される)。**副作用のある処理の手前では、進める前に、ユーザーに確認する。**
- ローカル変数・式の値には、**個人情報・認証情報が含まれうる**。報告には、必要な行だけを引用する。
- **デバッグ中は、ビルド・テスト・ソースの編集をしない** (従来どおり)。
- **実機で分かった動き (2026-11-24):** (a) **`--step out` は、呼び出しの行 (代入の前) に戻る。** 戻り値は、`LOCALS:` の「〜が返されました」の行。代入された値は、もう 1 歩進めると見える。(b) **1 行の `for` は、F10 のたびに、同じ行に止まる** (初期化・条件・本体・増分)。歩数が増えるので、`--continue` と、ブレークポイントで飛ばす。(c) **`--pause` は、任意のスレッド (タイマーなど) で止まる。** アプリのコードの追跡には、ブレークポイントで止める。(d) `--reload` は、git の差分に頼る。git 管理でないフォルダでは、`NOT_A_REPO` でスキップされる (VS が、自動で読み込み直す)。(e) 外部コードでも、場所は出る (取得したソースのコピー)。最適化されたモジュールの変数は、値が読めない。

### 「デバッグを実行して」
1. **ユーザーが、実行を求めたときだけ。** ブレークポイントを置く・開く・前面に出す、では、実行しない。
2. 先に、**ビルドが、成功していること** (`build-test-loop` / `auto-build`)。VS が、古いまま実行すると、ビルドエラーのダイアログで止まる。
3. `vs_once.sh "$SLN_DIR" --changes --debug` (ブレークポイントも、要るとき) / `--debug` だけ。
4. 結果の `DEBUG_MODE:` を報告する。`break` なら、`STOPPED:` の場所と、そこで確認したいこと。**`run` のままで `NOTE: no breakpoint was hit within 20s` が出たら、ブレークポイントに、まだ着いていない (ユーザーの操作待ちなど) か、効いていない。まず `--status` で、モードをもう一度確かめる** (あとから `break` になっていることがある。`--status` は、`break` なら `STOPPED:` も返す)。`design` のまま (`NOTE:`) なら、VS にダイアログが出ていないか、ユーザーに確認してもらう。**`run` のままなら、アプリの操作は、ユーザーが行う** (自動で操作しない)。
5. **デバッグ中は、ビルド・テスト・ソースの編集をしない** (exe が、ロックされ、`LNK1104` になる。編集は、VS の「編集して続行」と、ぶつかる)。「デバッグを止めて」と頼まれたら、**VS の Shift+F5 を、ユーザーに依頼する** (停止の操作は、持っていない)。

### 「UI の操作をきっかけに、デバッグして」(v2.106.0)
止めたいコード (ロジックなど) に、**画面の操作** (ボタンを押す・文字を入れる) で到達するとき。UI のバグを追うのではない。UI 操作は、**きっかけ**。UI テストの仕組み (FlaUI) が、デバッグ中のアプリにアタッチして、きっかけを撃つ。
前提: `<アプリ>.UITests` があること (なければ `ui-test-first`。古いひな形は `add_ui_tests.py "$SLN_DIR" --refresh-support-files [--app <アプリ名>]`)。ユーザーのデスクトップで動く (実行中は、PC に触らないよう、ユーザーに伝える)。
1. 止めたい場所に、ブレークポイントを置き、アプリを起動する: `vs_once.sh "$SLN_DIR" --break <パス>:<行> --debug --no-wait` (`DEBUG_MODE: run` で返る)。
2. **きっかけ専用のテスト**を書く (数行): `[TestMethod, TestCategory("DebugTrigger")]`。**最後の操作を `Trigger(() => UiDialogs.Click(Find("...")))` にする。その後に UI を読まない・探さない** (止まったアプリは UIA に応答しない。`Trigger` の後の `Find` は、すぐ失敗する)。
3. `uitest_once.sh "$SLN_DIR" --attach <プロセス名>` (ビルド全体も、アプリの強制終了も、しない。UI テストのプロジェクトだけをビルドする)。出力の `ATTACHED:` と `TRIGGERED:` を確かめる。`ATTACH_UNSUPPORTED` なら、上の `--refresh-support-files` で `UiTestBase.cs` を更新して、やり直す。
4. ウォッチャーは空いている: `vs_once.sh "$SLN_DIR" --inspect` / `--step over 5 --inspect` で、止まった場所と変数を調べる (「ステップ実行して」の手順)。
- できないこと: 別のデスクトップでの実行 (VS が起動したアプリは、ユーザーのデスクトップにある)。きっかけの後の UI の読み取り。

## 編集の競合を避ける (VS に、このソリューションが開いているとき)

VS と Claude が、**同じファイルを、同時に編集すると、片方の変更が、消える。** ファイルを書く前に、必ず、次を行う。

1. **編集の前に、`vs_once.sh "$SLN_DIR" --status`** を実行する (VS が開いているときだけ。`OPEN: no` なら、競合はないので、そのまま編集してよい)。
2. 結果で、分かれる:

| 結果 | 行動 |
|---|---|
| `DIRTY:` に、**これから編集するファイル**がある | **編集しない。** 「VS に、未保存の編集がある」と報告し、(a) VS で保存 (Ctrl+S) してもらう (b) そのファイルは、編集せず、ほかを進める、のどちらかを聞く。**VS の編集を、上書きしない。ユーザーの了承なしに、「保存して」と、VS を操作もしない** |
| `DIRTY:` が、別のファイルだけ | 編集してよい (**ユーザーが、VS で編集中だと、知らせておく**) |
| `DEBUG_MODE: run` / `break` | **編集もビルドもしない。** デバッグを止めてもらう (停止は、ユーザーの操作) |
| `INSTANCES: 2` 以上 | 止まる。**どの VS で、続けるか** (ほかを閉じるか)、聞く |

3. **編集のあと**、VS が、変更を取り込むようにする:
   - VS の設定 (ツール → オプション → 環境 → ドキュメント → 「ファイルが外部で変更された場合は、保存されていない変更がない限り、自動的に読み込む」) が、有効なら、何もしなくてよい。**無効でも、勝手に変えない** (推奨するだけ)。
   - 取り込まれないときは、`vs_once.sh "$SLN_DIR" --reload` (**未保存の編集がないドキュメントだけ**、開き直す。未保存のものは、`RELOAD_SKIP_DIRTY:` で、飛ばす)。
4. **ブレークポイントは、編集がすべて終わってから、最後に置く** (行が、ずれる)。編集を重ねたときは、`--changes` を、もう一度 (このツールが置いたものを消してから、置き直す)。
5. 編集の直後にも、もう一度 `--status` で、`DIRTY:` に、同じファイルがないか確かめてよい (ユーザーが、VS で、同時に打ち始めたとき)。

Claude の `Edit` ツールは、読んだあとにファイルが変わっていると、書き込みを断る。これは、VS が保存した変更に対する、最後の安全網で、**上の確認の代わりにはならない** (VS の、未保存の編集は、ファイルに、まだないため)。

## しないこと
- ユーザーが求めないデバッグ実行。ブレークポイントを置くだけの依頼での実行。
- VS の未保存の編集の、上書き。ユーザーの了承なしの、VS の保存・設定の変更・ウィンドウを閉じる操作。
- デバッグ中の、ビルド・テスト・編集。
- 自分で、フラグファイルを置く・`devenv.exe` を実行する。
- ユーザーが手で置いたブレークポイントの削除 (消すのは、このツールが置いたものだけ)。
