# Visual Studio の操作 (開く・前面・ブレークポイント・デバッグ実行)

> **パスの書き方:** `<Skill群>` = この Skill のフォルダ (Base directory) の 1 つ上。ほかの Skill も、そこにある。コマンドでは、実際のパスに置き換える。

Claude (WSL) は、Windows の Visual Studio を、直接操作できない。そこで、**ホスト側のウォッチャーに、操作を依頼する** (`trigger_vs.flag`)。ウォッチャーは、VS の自動化の窓口 (DTE) を、実行中のプロセスの表 (ROT) から、**ソリューションのパスで**探す (「最初の VS」ではない。VS 2022 / 2026 など、版に依らない)。結果は、ファイルで返る。
**自分で `devenv.exe` / `powershell.exe` を実行しない** (WSL のサンドボックスからは、動かない)。同梱のスクリプトを使う。

## 前提
- ユーザーが、対象のソリューションで `run_watcher.cmd` を起動済みであること (ビルドと同じウォッチャー。**`trigger_vs.flag` に対応した版** = `HOST_VERSION` 2.90.0 以降。古ければ、`install.sh` で配り直して、ウォッチャーを再起動してもらう)。
- `$SLN_DIR` = `.sln` / `.slnx` があるフォルダ。

## スクリプト

```bash
bash <Skill群>/vs-debug/scripts/vs_once.sh "$SLN_DIR" [モード...]
```

| モード | 動作 |
|---|---|
| (なし) | ソリューションを VS で開く。**開いていなければ、引数に渡して VS を起動** (読み込みの完了まで待つ)。開いていれば、**そのウィンドウを前面に出す** (最小化なら戻す) |
| `--status` | 状態だけ。**VS を起動しない**。`OPEN:` / `INSTANCES:` / `DEBUG_MODE:` (design / run / break) / `DIRTY: <パス>` (未保存) |
| `--changes` | git の差分 (追記・変更した**コードの行**。変更のかたまりごとに 1 つ、最大 10) に、ブレークポイントを置く。先に、このツールが置いたものを消す |
| `--break <相対パス>:<行>` | ブレークポイントを、1 つ置く (複数可。`--changes` と併用可。ソリューションのフォルダからの相対パス) |
| `--clear` | このツールが置いたブレークポイント (Tag で見分ける) だけを消す。ユーザーが手で置いたものは、消さない |
| `--reload` | git で変更したファイルのうち、VS で開いていて、**未保存の編集がない**ものを、開き直す |
| `--debug` | デバッグ実行を始める。結果に、`DEBUG_MODE:` と、break で止まったときの `STOPPED:` (関数・ファイル・行) |
| `--timeout 秒` | 待つ秒数 (既定 240) |

1 行目と終了コード: `OK` (0) / `FAILED` (1。複数の VS・すでにデバッグ中・ファイルなし など) / `BAD_ARGS` (2) / `WATCHER_NOT_RUNNING` (3。起動を依頼して止まる) / `ENV_ERROR` (4。VS が見つからない・開かない) / `TIMEOUT` (5。報告して止まる。**もう一度走らせない**: VS が、ダイアログを出して待っているかもしれない)。

## 依頼ごとの手順

### 「Visual Studio で開いて」「前面に」
`vs_once.sh "$SLN_DIR"` だけ。

### 「ブレークポイントを置いて」(追記・変更した部分)
1. `vs_once.sh "$SLN_DIR" --changes` (置く場所を、自分で決めたいときは、`--break 相対パス:行` を足す)。
2. 結果の `BREAK_SET:` を、報告する。**`NEW_FILE: <パス>`** は、新規ファイルで、行を自動では選べない。**自分で、実行の入口に近い、実質のある行を選び、`--break` で指定する。** `TRUNCATED: <件数>` は、10 件を超えたので、重要な行を `--break` で足すか、報告する。
3. **ブレークポイントを置くだけでは、実行しない。**

### 「デバッグを実行して」
1. **ユーザーが、実行を求めたときだけ。** ブレークポイントを置く・開く・前面に出す、では、実行しない。
2. 先に、**ビルドが、成功していること** (`build-test-loop` / `auto-build`)。VS が、古いまま実行すると、ビルドエラーのダイアログで止まる。
3. `vs_once.sh "$SLN_DIR" --changes --debug` (ブレークポイントも、要るとき) / `--debug` だけ。
4. 結果の `DEBUG_MODE:` を報告する。`break` なら、`STOPPED:` の場所と、そこで確認したいこと。`design` のまま (`NOTE:`) なら、VS にダイアログが出ていないか、ユーザーに確認してもらう。**`run` のままなら、アプリの操作は、ユーザーが行う** (自動で操作しない)。
5. **デバッグ中は、ビルド・テスト・ソースの編集をしない** (exe が、ロックされ、`LNK1104` になる。編集は、VS の「編集して続行」と、ぶつかる)。「デバッグを止めて」と頼まれたら、**VS の Shift+F5 を、ユーザーに依頼する** (停止の操作は、持っていない)。

## 編集の競合を避ける (VS に、このソリューションが開いているとき)

VS と Claude が、**同じファイルを、同時に編集すると、片方の変更が、消える。** ファイルを書く前に、必ず、次を行う。

1. **編集の前に、`vs_once.sh "$SLN_DIR" --status`** を実行する (VS が開いているときだけ。`OPEN: no` なら、競合はないので、そのまま編集してよい)。
2. 結果で、分かれる:

| 結果 | 行動 |
|---|---|
| `DIRTY:` に、**これから編集するファイル**がある | **編集しない。** 「VS に、未保存の編集がある」と報告し、(a) VS で保存 (Ctrl+S) してもらう (b) そのファイルは、編集せず、ほかを進める、のどちらかを聞く。**VS の編集を、上書きしない。ユーザーの了承なしに、「保存して」と、VS を操作もしない** |
| `DIRTY:` が、別のファイルだけ | 編集してよい (**ユーザーが、VS で編集中だと、知らせておく**) |
| `DEBUG_MODE: run` / `break` | **編集もビルドもしない。** デバッグを止めてもらう (停止は、ユーザーの操作) |
| `INSTANCES: 2` 以上 | 止まる。**どの VS で、続けるか** (ほかを閉じるか)、聞く |

3. **編集のあと**、VS が、変更を取り込むようにする:
   - VS の設定 (ツール → オプション → 環境 → ドキュメント → 「ファイルが外部で変更された場合は、保存されていない変更がない限り、自動的に読み込む」) が、有効なら、何もしなくてよい。**無効でも、勝手に変えない** (推奨するだけ)。
   - 取り込まれないときは、`vs_once.sh "$SLN_DIR" --reload` (**未保存の編集がないドキュメントだけ**、開き直す。未保存のものは、`RELOAD_SKIP_DIRTY:` で、飛ばす)。
4. **ブレークポイントは、編集がすべて終わってから、最後に置く** (行が、ずれる)。編集を重ねたときは、`--changes` を、もう一度 (このツールが置いたものを消してから、置き直す)。
5. 編集の直後にも、もう一度 `--status` で、`DIRTY:` に、同じファイルがないか確かめてよい (ユーザーが、VS で、同時に打ち始めたとき)。

Claude の `Edit` ツールは、読んだあとにファイルが変わっていると、書き込みを断る。これは、VS が保存した変更に対する、最後の安全網で、**上の確認の代わりにはならない** (VS の、未保存の編集は、ファイルに、まだないため)。

## しないこと
- ユーザーが求めないデバッグ実行。ブレークポイントを置くだけの依頼での実行。
- VS の未保存の編集の、上書き。ユーザーの了承なしの、VS の保存・設定の変更・ウィンドウを閉じる操作。
- デバッグ中の、ビルド・テスト・編集。
- 自分で、フラグファイルを置く・`devenv.exe` を実行する。
- ユーザーが手で置いたブレークポイントの削除 (消すのは、このツールが置いたものだけ)。
