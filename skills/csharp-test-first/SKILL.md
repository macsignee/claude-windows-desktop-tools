# C# (WPF / WinForms) テストファースト (Red を作る)

実装の前に、仕様をテストとして書き、**正しい理由で失敗すること (Red)** を確かめるところまでを行う。
実装して通す (Green) 工程は、`build-test-loop` が行う。実行の仕組み (ウォッチャー、フラグ、結果の読み方) は、そちらと同じ (MSTest の失敗も、GoogleTest と同じ形の要約で返る)。
C++ のソリューションは、`cpp-test-first`。**手順の骨格は同じで、C# (.NET) 固有の部分 (層、スタブ、MSTest の書き方) が違う。**

**WPF と WinForms の読み替え (以降の本文は、WPF の用語で書く。WinForms のときは、次の表で読み替える):** 種類は、`CLAUDE.md` の `- メイン:` の行 (`WPF (MVVM)` / `WinForms (MVP)`) で決める。

| 本文の用語 (WPF) | WinForms での読み替え |
|---|---|
| View (`Window` / XAML / code-behind) | `Form` / `*.Designer.cs`。**テストしない** |
| ViewModel と ViewModel 層 (`ViewModels`) | **Presenter** と `IView` (`IMainView` など)。置き場所は、**ロジック層があればそこ** (`LogicLayer`)、なければアプリの `Presenters/` (アプリを参照する `<アプリ名>.Tests` が、テストする)。**WinForms に、ViewModel 層は、ない** (`--kind viewmodel` は、使わない) |
| `PropertyChanged` の通知、コマンドの `CanExecute` / `Execute` | `IView` の **イベント** (`NameChanged` / `ClearRequested` など) を起こして、`IView` の **プロパティ** (表示の結果) と、サービスの Fake が受け取った値を確かめる |
| ViewModel のテストでの、ロジック層のフェイク | Presenter のテストでの、`IView` の **Fake** (イベントを起こす `RaiseXxx()` を持つ) と、`IDialogService` などの Fake |
| WPF の型 (`Window` / `MessageBox` / `Application.Current` / `Dispatcher`) | WinForms の型 (`Control` / `Form` / `MessageBox` / `Application` / `Timer` / `Clipboard`)。Presenter では、使わない (`IDialogService` などに分ける) |
| 組み立てる場所 (`App.xaml.cs` の `OnStartup`) | `Program.cs` (`Form` と Presenter を作って結ぶ。`IDialogService` の実装 (`MessageBox.Show` を呼ぶ) も、ここで渡す) |
| `wpf-check` | `winforms-check` |
| 規約 `~/.claude/rules/wpf-csharp.md` (WPF 固有。`ViewModels/` `*.xaml` などを読むときに、読み込まれる) | `~/.claude/rules/winforms-csharp.md` (WinForms 固有。`Forms/` `Presenters/` `*Presenter*.cs` などを読むときに、読み込まれる)。**C# の共通部分 (`csharp-common.md`) は、どちらでも、`.cs` を読むときに、読み込まれる** |

- **`IView` にイベントや、Presenter に依存 (`IDialogService` など) を足すと、既存のテストが、コンパイルで落ちる** (`IView` の Fake が、新しいメンバーを実装していない / `MainPresenter` のコンストラクターの引数が変わる)。**Fake と、既存のテストの呼び出し箇所 (`new MainPresenter(...)` の引数) だけを、機械的に直す。期待値とアサーションは、変えない。** 直した箇所は、Red の報告 (5.) に、書く。

## 飛ばさない 5 つ (詳細は、5.・6.・「完了時の確認」)
1. **Red を確認したら、「この Red を、仕様として確定してよいか」と聞いて、答えを待つ。** 省いてよいのは、依頼文に「実装まで続けて」とあるときだけ (「機能を追加して」「TDD で」では、省けない)。
2. **Green に進む前に、`test_guard.py snapshot "$SLN_DIR"`。**
3. **実装のあと、報告の前に、`test_guard.py check "$SLN_DIR"`。** `TEST_GUARD:` の行を、報告に含める。
4. Form / XAML / ViewModel / Presenter を触ったら、`wpf-check` (WinForms は `winforms-check`)。
5. **最後の報告の先頭に、テストファイルの一覧と、「期待値が、仕様と合っているか、確認をお願いします」。** Git 管理下でなくても、省かない。

## 前提
- ユーザーが対象ソリューションのフォルダで `run_watcher.cmd` を起動済みであること。
- ソリューションフォルダを `$SLN_DIR` とする (**`.slnx` / `.sln` のファイルのパスではなく、それを含むフォルダ**。スクリプトの第 1 引数も、このフォルダ)。Claude Code は、このフォルダをカレントにして起動されている。
- **作業フォルダ (`solutions.md` があり、`.sln` / `.slnx` がないフォルダ) で起動しているとき** (複数の候補のソリューションを、比べているとき): `$SLN_DIR` は、カレントではなく、対象の候補。`SLN_DIR=$(python3 ~/.claude/skills/new-solution/scripts/new_solutions.py resolve "$PWD" [<候補名>])` で決める (終了コード 2: 候補が複数 → 一覧を示して、ユーザーに質問する。3: 対象がない)。以降の `CLAUDE.md` や `docs/` は、`$SLN_DIR` の下 (その候補のコピー)。**他の候補は、読まない・書かない。** ウォッチャーは、その候補のフォルダで、起動されている必要がある。
- **ソリューションがないとき** (カレントにも、作業フォルダの候補にも、`.slnx` / `.sln` がない): **ここで止まり、テストも、スタブも、書かない。** 「ソリューションがありません。`/new-solution --type wpf` (または `winforms`) を、ご自身で実行してください (例: `--layers data,logic --tests mstest`。ViewModel をテストしたいなら `data,logic,viewmodel`)」と案内する。**種類 (WPF / WinForms / C++) が分からないときは、ユーザーに聞く** (C++ なら、`cpp-test-first` と、`/new-solution` の C++ の種類を案内する)。**空のフォルダで、サンドボックスの内側に、`.gitconfig`・`.idea`・`.vscode`・`.mcp.json`・`.claude/skills` などの、0 バイトのキャラクタ特殊ファイルが見えても、書き込み禁止の目隠しで、プロジェクトのファイルではない。環境の不具合と判断しない** (ソリューションの有無は、`.slnx` / `.sln` の有無だけで決める)。**`/new-solution` を、`Skill` ツールで呼ばない** (`disable-model-invocation` で、エラーになる)。**ASP.NET Core などの Web、MAUI、Linux / macOS 向けの .NET は、このスキルの対象外**。この手順を使わず、そのことを伝える。
- **ソリューションは、次の層 + テストの構成であること** (作り方と規約は、同梱の `PROJECT-LAYOUT.md`)。

  | 層 | プロジェクト | 種類 | テスト |
  |---|---|---|---|
  | View | メインの WPF アプリ | WPF (`net10.0-windows`) | **しない** (画面。ビルドと `wpf-check` と、目視) |
  | ViewModel | `ViewModels` 等 | クラスライブラリ (**WPF 非依存**) | `<名前>.Tests` (MSTest) |
  | ロジック | `LogicLayer` 等 | クラスライブラリ (WPF 非依存) | `<名前>.Tests` (MSTest) |
  | データ | `DataLayer` 等 | クラスライブラリ (WPF 非依存) | `<名前>.Tests` (MSTest) |

  (WinForms のとき: View = メインの WinForms アプリ (`net10.0-windows`)。Presenter / `IView` = `LogicLayer` (WinForms 非依存)。ViewModel の行は、ない。データ層は、同じ。)

- **テストは、ライブラリ単位で作る。** ViewModel のテストは `ViewModels.Tests` に、ロジックのテストは `LogicLayer.Tests` に。テストプロジェクトは、対応するライブラリをプロジェクト参照している。ウォッチャーは、`dotnet test --no-build` で、すべて実行する。
- **テスト対象は、ViewModel (WinForms は Presenter)・ロジック・データ層のクラスだけ。** `Window`・`UserControl`・XAML・code-behind (WinForms は `Form`・`UserControl`・`*.Designer.cs`) は、対象にしない。
  - 対象が View (XAML / code-behind。WinForms は `Form` のイベントハンドラー) に書かれている場合は、**テストを書かずに止まり**、ロジックを、ViewModel (WinForms は Presenter。またはロジック層) の、WPF (WinForms) 非依存のクラスに切り出す案を、ユーザーに示す。
  - **ViewModel 層がなく、ViewModel がアプリの中 (`ViewModels/` フォルダ) にある場合も、同じ。** そのままでは、テストできない (アプリは、WPF の exe)。ViewModel 層 (クラスライブラリ) を作って、ViewModel を移す案を示す (`references/setup.md`)。
  - 切り出し・移動の変更は、ユーザーの了承を得てから、行う。
- **ViewModel が、WPF の型 (`Window` / `MessageBox` / `Application.Current` / `Dispatcher`) を使っている場合も、そのままではテストできない** (MSTest は、STA スレッドも `Application` も、ない)。インターフェース (`IDialogService` など) に分けて、フェイクに差し替えられるようにする案を示す。

## セットアップ (層やテストが、足りないとき)
最初のソリューション・アプリ・層・テストは、`/new-solution --type wpf` / `winforms` が作る。**ここで足すのは、作ったあとで、足りないものが分かったときだけ** (`CLAUDE.md` の `- テスト:` が `なし`、対象の層のライブラリや `<名前>.Tests` がない)。その場合は、**`references/setup.md` を読んで、従う** (同梱の `add_project.py`、案を示して了承を得る、ベースラインの確認)。足りないものがなければ、読まない。
- **自分で `.csproj` や `.sln` / `.slnx` を手書きしない。既存のプロジェクトを上書きしない。ベースラインが緑になる前に、本物のテストを書かない。**
- `テスト: なし` のときは、この Skill (テスト先行) は使えない。「テストが、導入されていません。`/new-solution --tests mstest` で、後付けできます」と案内して止まる。

## 手順

### 0. 対象の層を決める
依頼の内容から、どのライブラリ (と、対応するテストプロジェクト) に書くかを、決める。

| 対象 | 置く場所 | テストの書き方 |
|---|---|---|
| 画面の状態・コマンド・表示用の変換 | ViewModel / ViewModel のテスト | WPF の型を使わない。ロジック層は、**フェイク**に差し替える。`PropertyChanged` の通知と、コマンドの `CanExecute` / `Execute` を確かめる |
| 業務ルール、計算、検証 | ロジック / ロジックのテスト | データ層は、**フェイク** (`IxxxRepository` の、メモリ上の実装) に差し替える。実ファイルや DB に触れない |
| 保存、読み出し、外部とのやり取り | データ / データのテスト | 実ファイルを使ってよいが、**一時フォルダに、テストごとに別のパスで作り、`[TestCleanup]` で必ず削除する** |
| 画面の状態・イベントへの反応・表示用の変換 (**WinForms**) | Presenter (ロジック層。ない構成では、アプリの `Presenters/`) / そのテスト | WinForms の型を使わない。**`IView` の Fake** でイベントを起こし (`RaiseXxx()`)、`IView` のプロパティと、サービス (`IDialogService` など) の Fake が受け取った値を確かめる |
| 画面 (XAML、code-behind。WinForms は `Form` / `Designer.cs`) | (テストしない) | View。ViewModel (WinForms は Presenter) への切り出し案を示して止まる |

1 つの依頼が、複数の層にまたがる場合 (例: 計算ルールの追加と、画面への表示) は、**層ごとに、下の層から順番に、この手順を回す** (データ → ロジック → ViewModel (WinForms は Presenter))。まとめて Red にしない (失敗の原因が、層をまたいで混ざるため)。

### 1. 仕様を、テストケースの一覧にする (コードを書く前)
**入力は、確定済みの仕様。** ユーザーが、先に、ブレインストーミング (`/brainstorm` など) で仕様を固めている場合は、その成果物 (仕様書のファイル、または、会話に出ている確定事項) を、読んで使う。
仕様書は、`/brainstorm` のメモ (`docs/ideas/`) を、`/update-from-ideas` が整理して作る、`docs/specs/<機能名>.md` (`状態: 確定`)。メモだけで、仕様書がなければ、`/update-from-ideas` を勧める。ユーザーが、仕様書のパスを示した場合と、`docs/specs/` に仕様書がある場合は、**それが、今回の依頼のものか、ユーザーに確認してから**使う。
仕様が固まっていない (`下書き`、`変更あり (要再確定)`、未決事項が残っている) 場合は、テストを書かずに、`/brainstorm` か `/update-from-ideas` を勧めて止まる。
(`/add-feature` から呼ばれた場合は、仕様書と計画は、すでに確認・承認済み。計画のテストケースを使う。)

仕様から、次の観点でテストケースを書き出し、**テキストで、ユーザーに見せる。** 仕様が曖昧な箇所は、推測せず、ここで質問する。
- 正常系 (代表的な入力)
- 境界値 (0、最小、最大、空、1 件、上限の直前と直後)
- 異常系 (不正な入力、範囲外、`null` や空文字、期待する失敗の仕方: 戻り値か、例外か)
- Presenter (WinForms): イベントを起こしたときの、`IView` のプロパティの値と、サービスの呼び出し (引数、回数)。入力が空・同じイベントの連続も、境界値として考える。
- ViewModel: **プロパティの変更通知 (`PropertyChanged` が、正しい名前で、上がること)**、コマンドの実行可否 (`CanExecute`)、実行後の状態
- バグ修正の場合: **そのバグを再現するテストを、最初の 1 件にする。**

ユーザーの依頼にケースが明記されている場合は、一覧の提示は短くてよい。ケースを勝手に増やさない (最大でも、1 つの機能あたり 10 件程度)。

### 2. スタブを作る (本体側。コンパイルを通すためだけ)
テストが、本体のクラスやメソッドを呼ぶので、**宣言がないとビルドで落ちる** (`CS0103` / `CS1061` / `CS0246`)。ビルドで落ちるのは、Red ではない (仕様の失敗ではなく、書き方の失敗)。
そこで、本体 (対象のライブラリ) に、**最小のスタブ**を置く。
- **バグ修正で、対象の実装が、すでにあるとき (テストが、本物の失敗で Red になるとき) は、スタブを置かない。** スタブは、**新しい型・メソッドがあるときだけ**置く (既存の実装を、スタブで置き換えると、実装を消す)。
- 型とメンバーの宣言と、仮の実装だけ。**本物のロジックを書かない。**
- 仮の実装は、「値を返すだけで、仕様を満たさない」ものにする (`return 0;`、`return "";`、`return false;`、`return default!;` など)。テストが、たまたまスタブの値で通ることがないように、**期待値と異なる値**にする。
  - `NotImplementedException` を投げるスタブは、**テストが、例外で落ちる** (アサーションの失敗ではない) ので、Red の条件を満たさない。使わない。
- ViewModel のプロパティのスタブは、**通知を上げない、固定の値を返す** プロパティにする (変更通知のテストが、アサーションで落ちる)。
- Presenter (WinForms) のスタブは、**イベントを購読して、何もしない、または、固定の (仕様と異なる) 値を、`IView` かサービスへ渡す** ハンドラーにする。`IView` に足したイベントの宣言と、Fake の実装は、コンパイルを通すために、ここで足す。
- 新しい `.cs` は、SDK 形式なので、`.csproj` に追加しなくてよい (**自動で含まれる**)。置き場所は、そのライブラリのフォルダの下。ファイル名は、型の名前と一致させる。
- **ViewModel を WPF 非依存のライブラリに置く。** `System.Windows` の型 (`Window` / `MessageBox` / `Application`) を使うと、ライブラリが、ビルドできない (`net10.0` に、ない)。
- 新しい型に `public` を付ける (`internal` のままだと、テストプロジェクトから見えない: `CS0122`。`InternalsVisibleTo` で、わざと見せているときを除く)。

### 3. テストを書く (対象の層に対応する `<名前>.Tests` 側)
- 既存のテストの書き方 (ファイルの命名 `<クラス名>Tests.cs`、`[TestClass]` / `[TestMethod]`、`using` の形) に合わせる。**規約の全文は、`~/.claude/rules/csharp-common.md` の「16 テスト規約」 (WinForms は、これに加えて、`~/.claude/rules/winforms-csharp.md` の「13 テスト規約」)。**
- 1 つのテストで、1 つのことを確かめる。名前は、`メソッド_条件_期待` (例: `Greeting_NameEmpty_AsksForName`)。Arrange / Act / Assert の順に書き、空行で区切る。
- 期待値は、**仕様から導いた値を、直接、書く。** 実装の出力を、写さない (まだ実装がない)。**`Assert.AreEqual(期待値, 実際の値)` の順** (逆にしない)。
- 浮動小数点は、許容誤差を指定する (`Assert.AreEqual(1.0, x, 1e-9)`)。例外は、`Assert.ThrowsException<T>`。非同期は、`async Task` (`async void` にしない)。
- 新しい `*Tests.cs` を作ったら、**その層のテストプロジェクトに、置く** (別の層のテストプロジェクトに、書かない)。
- ロジックのテストでは、データ層の**実装を使わない** (フェイクを使う)。ViewModel のテストでは、ロジック層の実装を使わない (フェイクを使う)。下の層の不具合が、上の層のテストに混ざらないようにする。
- ViewModel の変更通知は、`PropertyChanged` を購読して、上がった名前を、一覧に集めて、確かめる (`CollectionAssert.AreEquivalent`)。
- ファイルの文字コードと改行コードは、既存のファイルに合わせる (新規は、UTF-8 BOM 付き、CRLF)。

### 4. Red を確認する (実行)
#### 4.0 ベースライン (Red の前に、1 回)
**既存のテストが、ある場合は、新しいテストを書く前 (スタブを置く前) の状態で、`build_test_once.sh` を 1 回実行し、結果 (`tests: N passed`、失敗しているテスト名) を、記録する。** 後の「正しい Red の条件」の 3・4 (既存のテストが、新たに落ちていないか / 前から失敗していたか) は、この記録と比べて、判断する。テストが 1 件もない (層を足した直後など) ときは、省く。

`build-test-loop` の同梱スクリプトを使う。自分で flag を作ったり、待機ループを書いたりしない。

```bash
bash <build-test-loop の Skill のフォルダ>/scripts/build_test_once.sh "$SLN_DIR" 300
```

`run_in_background: true` で実行し、**完了通知が来るまで、ファイルを読まず、再実行もしない** (理由と詳細は、`build-test-loop` の「実行 (1回分)」と同じ)。**初回は、NuGet の復元と、ビルドで、長いことがある。**

結果の判断 (**ここが、このスキルの要点。**):

| 1行目 | 意味 | 次の行動 |
|---|---|---|
| `FAILED` | テスト失敗 | **失敗したテストの一覧と理由を読み、下記「正しい Red の条件」で確かめる** |
| `PASSED` | 全テスト成功 | **Red ではない。** 新しいテストが、実装なしで通っている。テストが空振りしている (期待値がスタブの値と同じ、アサーションがない)、または、機能がすでにある。**原因を調べて、ユーザーに報告する。実装には進まない** |
| `BUILD_FAILED` | ビルドエラー | テストかスタブの書き方の誤り。エラーを読んで直し、再実行する (下記の回数の上限に含める) |
| `ENV_ERROR` / `WATCHER_NOT_RUNNING` / `TIMEOUT` / `TEST_TIMEOUT` | 環境・実行の問題 | `build-test-loop` の表と同じ。ソースもテストも直さず、報告して停止。**`ENV_ERROR` の「テストが 1 件も実行されなかった」は、`[TestMethod]` が付いていない、テストプロジェクトが参照されていない、などでも起きる** (原因を、報告する) |

**新しいテストの、個別の状態は、`.claude-logs/test_summary.json` で確かめる** (画面の要約は、`tests:` が最大 5 件、`at:` が最大 3 件で切れる。`(+N more)` の分は、見えない)。**新しいテストが、偶然、スタブの値で通っていないか** (`FAILED` の中に、新しいテストの名前が、すべて、含まれること) も、ここで確かめる。

#### 正しい Red の条件 (すべて満たすこと)
1. **新しく書いたテストが、すべて、アサーションの失敗 (`Assert.AreEqual failed. Expected:<...>. Actual:<...>.`) で落ちている。** 値の食い違いが、仕様どおりの理由で出ている。
2. **例外 (`NullReferenceException` / `NotImplementedException` / `InvalidCastException` など)、クラッシュ、タイムアウトで落ちていない。** (スタブが、仕様として、例外を投げる場合を除く)
3. **既存のテストが、新たに落ちていない。** 落ちている場合は、今回の変更 (スタブの追加) が、既存の動作を壊している。直してから、やり直す。
4. 実行前から失敗していた既存のテストが、ある場合は、今回の失敗と区別して、報告する。
5. **失敗が、対象の層のテストプロジェクトだけに出ている。** 要約のテスト名 (`クラス名.メソッド名`) で、どのプロジェクトか分かる。書いていない層のテストが落ちている場合は、層をまたぐ影響なので、原因を調べて、報告する。

### 5. Red を報告し、テストを確定する
次を、簡潔に報告する。
- 書いたテストの一覧 (名前と、確かめていること)、それぞれの失敗の理由 (`Expected` と `Actual`)。
- **テストケースの一覧に出したテストを、Red の前に外したとき (スタブで通ってしまう、など) は、外したテストの名前と理由を、ここに書く** (黙って外さない。件数が、一覧と合わなくなる)。スタブで通るテストを残すときも、その旨を書く (真偽の対のテストは、片方が通ることがある)。
- 作った・変更したファイル (スタブ、テスト、`.csproj` (層を足した場合))。
- 「この Red を、仕様として確定してよいか」を、ユーザーに確認する。**テストは、仕様の表明であり、ここで、人が、中身を確かめる最後の機会になる。**

ユーザーが、「実装まで続けて」と、最初から依頼している場合は、確認を待たずに、**6. に進んでよい。** それ以外は、確認を待つ。

### 6. Green へ引き渡す

**Green の完了条件 (新しいテストが、実際に実行されたこと):** `PASSED` の 2 行目の `tests: N passed` の N が、**ベースライン (下記の 4.0) の件数 + 今回、書いたテストの件数** であり、**新しいテストの名前が、実行結果に含まれる**こと。確かめ方 (読み取りだけ): `grep -l "<新しいテストの名前>" "$SLN_DIR/.claude-logs/test-results/"*` (GoogleTest の XML / MSTest の trx)。**含まれなければ、PASSED でも、完了ではない** (`.vcxproj` / `.csproj` への足し忘れ、`-TestExePattern` に合わない exe、フィルターで外れている、など。`PASSED` は「実行されたテストが、すべて通った」の意味でしかない)。
テストが確定したら、`build-test-loop` の手順で、実装して全テストを通す。**その時点から、テストは、凍結する。**
- **テストを確定したら、Green に進む前に、基準を作る:** `python3 -I ~/.claude/skills/build-test-loop/scripts/test_guard.py snapshot "$SLN_DIR"`。実装のあと (と、報告の前) に `check` を実行し、**error は、許可なしにしてはいけない変更**なので、元に戻すか、止まって確認する。warning / review は、理由を報告する。変更されたテストファイルの一覧は、報告の先頭に書く (`build-test-loop` の「テストの改変の検査」)。ユーザーが、テストの変更を承認したときだけ、`snapshot` をやり直す。
- `build-test-loop` の規則が、そのまま適用される: **テストの変更・削除・`[Ignore]` 化・`Assert.Inconclusive` で飛ばす・アサーションを弱める、は、ユーザーの許可なしにしない。**
- **Green のあと、報告の前に、`test_guard.py audit "$SLN_DIR"`** (空洞なテストを探す)。中心の項目は、実装をわざと壊して確かめる (`build-test-loop` の `references/mutation-check.md`。了承を得て、必ず元に戻す。していなければ、「変異の確認は、していない」と報告)。
- 実装中に、テストの期待値が誤りだと分かった場合は、テストを直す前に、ユーザーに、理由 (どの仕様と矛盾するか) を添えて確認する。
- 実装のあと、**XAML / ViewModel を触ったら、`wpf-check` を実行する** (WinForms は、`Form` / `Designer.cs` / Presenter を触ったら、`winforms-check`) (バインディングのパスの誤りなど、ユニットテストでは見つからない不具合を、静的に確かめる)。
- **UI テスト (`*.UITests`。`CLAUDE.md` に「UI テスト (FlaUI)」の節がある) は、このビルド → テストの流れに、含めない。** 遅く、アプリを起動し、制限時間を長く取る必要があるため、**ユーザーが求めたとき**だけ、`uitest_once.sh` で、別に実行する (`build-test-loop` の `references/ui-tests.md`)。**画面を、プロンプトで作りながら、UI テストを書いて、繰り返し実行するときは、`/ui-test-first`** (UI テストを先に書く)。通常のテストが `PASSED` になっても、UI テストは、自動では、実行しない。
- 通ったあとの整理 (リファクタリング) は、**テストを変えずに**行い、そのたびに、テストが通ることを、確認する。

## ループのルール
1. Red を作る工程 (2.〜4.) の再実行は、**最大 3 回**まで。3 回目も、正しい Red にならなければ、状況と原因の候補を報告して停止する。
2. ソース (スタブ、テスト) を修正していない状態での、再実行はしない。
3. 無関係なリファクタリング、仕様にない機能のテストの追加は、しない。
4. 本物のロジックは、**Red が確定するまで書かない。** 先に実装して、あとからテストを書くことは、このスキルの目的に反する。
5. 修正時は、ファイルの文字コード (UTF-8 BOM の有無など) と改行コードを変えない。
6. **パッケージを足す必要が出たら** (例: テストで、モックのライブラリが欲しい)、`.csproj` を書き換えず、ユーザーに伝えて、`add-package` で足す。

## 完了時の確認 (変更の報告)
作業を終える前に (成功でも、停止でも)、変更したファイルを一覧して、報告に含める。ユーザーが、コミットの前に、`git diff` で、変更を確認できるようにするため。

1. 変更されたファイルの一覧を取る (読み取りだけ。ステージやコミットはしない)。
   ```bash
   git -c core.fileMode=false --no-optional-locks status --short
   ```
   - `-c core.fileMode=false` を付けるのは、WSL の git が、`/mnt/c` のファイルを実行権限つきと見て、ほぼ全ファイルを「変更あり」と表示してしまうため。
   - git のリポジトリでない場合や、コマンドが失敗した場合は、自分が編集したファイルの一覧で代える。
2. **このスキルでは、テストファイルを、必ず、新規作成か変更する。** 報告の先頭で、テストファイルの一覧と、ユーザーが確かめるべき点 (期待値が、仕様と合っているか) を、明示する。
3. 「コミット前に、`git diff` で変更を確認してください」と、一言添える。
4. **`git commit` と `git push` は、ユーザーの明示的な指示がない限り、実行しない。**
5. プロジェクトの設定 (`.claude/settings.json`) で、テストファイルの編集や、`git commit` に、確認が出る設定になっていることがある (`*Tests/**` `*Tests.cs` など)。
   このスキルは、テストファイルを書くので、**確認が出るのが、通常の動作。** 何を、なぜ、書くのかを、簡潔に説明する。拒否されたら、同じ操作を、別の方法 (別のツールやコマンド) で、行わない。

## 報告
- Red を確認できた: 書いたテストの数、失敗の理由の要約、変更したファイル、確認の依頼 (5.)。
- 正しい Red にならずに停止: 結果 (`PASSED` / 想定外の失敗など)、原因の候補、試した修正。
- 対象が View で、止まった: 切り出しの案。

## トークン節約
- ログは、`build_test_once.sh` の出力 (失敗テスト名の一覧と詳細、集約された要約、最大 40〜60 行) で足りる。足りないときだけ、`test_error.log` を読む。
- ソースは、必要な範囲だけを読む。既存のテストは、書き方を合わせるために、1〜2 ファイルだけ読む。
- 待機中・修正の合間に、経過の説明を書かない。
