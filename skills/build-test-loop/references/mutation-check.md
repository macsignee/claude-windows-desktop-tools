# テストの中身の点検 (`audit`) と、実装を壊して確かめる手順 (変異の確認)

> `<Skill群>` の意味は、`SKILL.md` の冒頭の「パスの書き方」を参照。

Red を確認し、Green になっても、**テストが、本当に不具合を捕まえるとは、限らない。** スタブが、たまたま、期待値と同じ値を返す、アサーションがない、期待値を実装から計算している、などで、実装が壊れても、通るテストがある。ここでは、2 段階で確かめる。

| 段階 | 何をするか | 道具 | 費用 |
|---|---|---|---|
| 1. 形の検査 | 空洞なテスト (アサーションがない、常に成功する、「null でない」だけ、期待値も実測値も呼び出しの結果) を、静的に探す | `test_guard.py audit` | ほぼゼロ (読み取りだけ。Windows もウォッチャーも不要) |
| 2. 変異の確認 | 実装を、**わざと、1 か所だけ壊し**、対応するテストが、**失敗する**ことを確かめる。確かめたら、**必ず、元に戻す** | 手順 (下) | 1 回につき、ビルドとテストを、1 回 (数十秒〜数分) |

**いつ行うか:** Green のあと、報告の前。1 は、毎回。2 は、**仕様書の中心の項目 (1〜3 件)** だけ (全項目は、行わない)。

## 1. 形の検査 (`audit`)
```bash
python3 -I <Skill群>/build-test-loop/scripts/test_guard.py audit "$SLN_DIR"
```
- **error:** アサーションがない (TQ001)、常に成功するアサーション (TQ002)。**空洞なテスト。** 直す (テストを直すときは、ユーザーに確認する。「止めどき」5)。
- **warning:** すべてのアサーションが、「等しくない」「null でない」だけ (TQ003)。
- **review:** 強いアサーションが、すべて、リテラルを含まず、呼び出しが 2 つ以上 (TQ004。期待値を、実装から計算している疑い)。ヘルパーの呼び出しだけで、アサーションが見当たらない (TQ011。ヘルパーの中に、あるか確かめる)。
- 対象外: 例外を期待するテスト (`EXPECT_THROW`、`Assert.Throws`、`[ExpectedException]`)、`[TestCategory("Preview")]` の目視確認のテスト。
- **形だけの検査。** 通っても、テストが、不具合を捕まえるとは、限らない (2. で確かめる)。

## 2. 変異の確認 (実装を壊して、テストが落ちることを見る)

**やること:** 仕様書の中心の項目 (例: 境界値、計算の結果) が、実装のどの行で決まるかを見て、**その行だけ**を、1 か所、壊す。対応するテストが、**失敗する**はず。失敗しなければ、**テストの穴**。

### 前提 (すべて満たすこと)
- Green (`PASSED`) で、`test_guard.py snapshot` の基準がある。
- **ユーザーに、実装を、一時的に壊すことを、伝えて、了承を得る** (壊す対象のファイルと行、元に戻すことを、示す)。
- 壊すのは、**実装のファイルだけ。テストは、触らない。**

### 手順 (1 つの変異ごと)
1. **バックアップ:** 壊すファイルを、コピーする。
   ```bash
   mkdir -p "$SLN_DIR/.claude-logs/mutation_bak" && cp "<実装のファイル>" "$SLN_DIR/.claude-logs/mutation_bak/"
   ```
2. **1 か所だけ壊す** (下の「壊し方」)。複数の箇所を、同時に壊さない。
3. **ビルドとテスト:** `build_test_once.sh "$SLN_DIR"`。
   - **期待: テストが失敗する** (`FAILED`。失敗したテストの名前が、壊した項目に対応する)。
   - ビルドエラーになったら、変異が不適切。**元に戻して**、別の壊し方にする (壊したことには、ならない)。
   - **`PASSED` のまま = 変異が、生き残った。テストの穴。** 報告する (下の「生き残ったとき」)。
4. **元に戻す (必ず):**
   ```bash
   cp "$SLN_DIR/.claude-logs/mutation_bak/<ファイル名>" "<実装のファイル>" && cmp "$SLN_DIR/.claude-logs/mutation_bak/<ファイル名>" "<実装のファイル>" && echo "復元した"
   ```
   `復元した` が出るまで、次に進まない。Git のリポジトリなら、`git diff` で、実装に、変更が残っていないことも、確かめる。
5. 次の変異に進む前に、1 に戻る。**全部の変異が終わったら、`build_test_once.sh` を 1 回実行して、`PASSED` (元の件数) に戻ったことを確認する。** `test_guard.py check` も、実行する (テストを、変えていないこと)。

### 壊し方 (小さく、仕様に対応する 1 か所)
| 変異 | 例 |
|---|---|
| 演算子を反転 | `a + b` → `a - b`、`&&` → `\|\|` |
| 境界を動かす | `<` → `<=`、`>=` → `>` |
| 定数を変える | `8` → `9`、`100` → `99` |
| 条件を否定する | `if (x)` → `if (!x)` |
| 戻り値を固定する | `return total;` → `return 0;` |
| 処理を飛ばす | 検証・丸め・分岐の 1 行を、コメントアウト |

仕様書の項目に、**直接、対応する行**を選ぶ (無関係な行を壊しても、意味がない)。

### 規則
- **上限: 1 回の依頼で、変異は、最大 3 件。** 変異のビルドは、`build-test-loop` の「止めどき」の合計 (15 回) に、含めない。ただし、**`TIMEOUT` / `ENV_ERROR` / `WATCHER_NOT_RUNNING` になったら、まず、元に戻して**、停止して報告する。
- **途中で止まるとき (中断、止めどき、エラー) も、先に、元に戻す。** 壊れた実装を、残して、終えない。
- 壊したままの状態で、**ほかの作業 (修正、報告) に、進まない。**
- **変異は、実装の確認であって、仕様の変更ではない。** 変異で見つけたことを、勝手に、実装やテストに、反映しない (生き残ったときは、ユーザーに確認する)。

### 生き残ったとき (テストの穴)
報告に、次を書く: 壊したファイルと行、壊し方、`PASSED` のままだったこと、**どの仕様の項目が、テストで守られていないか**。続けて、ユーザーに確認する。
- **テストを足す・直す (推奨):** ユーザーの承認を得て、そのテストを足し、`test_guard.py snapshot` をやり直す (基準の更新)。もう一度、同じ変異で、**失敗する**ことを確かめる。
- **このまま進む:** 穴として、報告に残す (`.trace.md` の判定を、`未確認` にする)。

## 報告に書くこと
- `audit` の結果 (error / warning / review の件数)。
- 変異の確認: 壊した件数と、結果 (失敗した = テストが捕まえた / 生き残った = 穴)。**復元して、`PASSED` に戻ったこと。**
- 実施しなかったとき (ユーザーが了承しなかった、時間、ウォッチャーなし) は、**「変異の確認は、していない」**と明記する。
