# 修正の方針 (`auto-build` / `build-test-loop` 共通)

ビルドエラー・警告・テスト失敗を、自動で直すときの、**修正の前の確認**、**直してよいものと、止めるもの**、**報告の項目**。止めどき (回数・同じ失敗) は、`build-test-loop` の SKILL.md の「止めどき」。

## 1. 修正の前の確認 (ユーザーの未コミットの変更を守る)
最初の修正の前に、**1 回だけ**、読み取りだけで確認する (ステージもコミットもしない)。

```bash
git -c core.fileMode=false --no-optional-locks status --short
git -c core.fileMode=false --no-optional-locks diff --stat
```
- **このセッションで、自分が編集していないファイルに、未コミットの変更がある** → それは、ユーザーの変更。触らない・戻さない・整形しない。
- **修正の対象が、そのファイルなら、修正せずに停止して報告する** (「未コミットの変更と重なるので、止めました。コミットか退避をして、もう一度、依頼してください」)。重ならなければ、そのまま進める。**確認のための質問は、しない。**
- 2 回目以降の修正で、**新しいファイルを修正の対象にするときだけ**、そのファイルについて、もう一度確認する。
- git のリポジトリでない・コマンドが失敗したときは、確認を飛ばして、その旨を報告に書く。

## 2. ビルドエラー
- **直してよい:** C / C++ / C# の構文エラー、型の不一致、未定義の識別子、明白な include の不足、プロジェクト内のコードに起因するリンクエラー、テストコードのコンパイルエラー (機械的な追従だけ。`build-test-loop` の止めどき 5)。
- **直さずに、停止して報告する:**
  - Visual Studio・Windows SDK・MFC・ATL・プラットフォームツールセットの不足。
  - NuGet・vcpkg・社内ライブラリの不足 (`add-package` Skill を案内する)。
  - 署名・証明書・ライセンス・管理者権限の問題。
  - `.vcxproj` / `.sln` / `.props` / `.targets` の大幅な変更が要るもの。
  - ABI・公開 API・データ形式に影響し得るもの。
  - 要件が曖昧なもの。
  - 同じエラーが 2 回続いたもの。
  - ユーザーの未コミットの変更と競合するもの (上の 1.)。

## 3. 警告の方針
ユーザーが、依頼の中で指定する。**指定がなければ、`report`。**

| 方針 | 動き |
|---|---|
| `ignore` | 直さない。報告もしない。 |
| `report` (既定) | 件数と主なコードを報告する。ソースは、直さない。 |
| `fix` | **安全に直せるものだけ**直して、再ビルドする。 |

- **`fix` でも、直してよいもの:** 未使用のローカル変数、明白な型変換 (`size_t` から `int` など)、代替が明白な非推奨 API、原因と修正が局所的に判断できるもの。
- **`fix` でも、直さずに、報告するもの:** ABI に影響し得るもの、外部ライブラリ・Windows SDK・MFC 起因のもの、生成コード (`*.g.cs`・ウィザードが作ったコード)、意図的な変換か判断できないもの、仕様の変更が要るもの。
- **禁止:** 警告を通すための抑制 (`#pragma warning disable`、`<NoWarn>`、`TreatWarningsAsErrors` / `/WX` の解除、アナライザの無効化)。`auto-build` のループのルール 8。

## 4. テスト失敗
- **直してよい (原因を、安全に判断できるとき):** 条件の誤り、境界値の処理、`nullptr` チェックの不足、Win32 メッセージ処理の戻り値、`WPARAM` / `LPARAM` の扱い、初期化の不足、状態の更新漏れ、明確な期待値との不一致、待機条件の誤り、テスト用ウィンドウの破棄漏れ。
- **直さずに、停止して報告する:**
  - 仕様上の期待値が不明なもの。テストと製品のコードの、どちらが正しいか判断できないもの。
  - GUI のフォーカス・DPI・ロケール・タイムゾーン・OS の状態に依存するもの。
  - フレークの疑い (同じコードで、成功と失敗が混ざる)。
  - 外部機器・ネットワーク・実行環境に依存するもの。
  - 非同期の競合で、原因が 1 つに決まらないもの。
  - 公開 API・ABI の変更が要るもの。
  - アクセス違反・クラッシュで、原因が 1 つに決まらないもの。
  - 修正のあとも、同じテストが、2 回続けて失敗するもの。
- **禁止:** テストの削除・無効化 (`DISABLED_` / `GTEST_SKIP()` / `[Ignore]`)、アサーションを弱める (`ASSERT_*` を `EXPECT_*` に変える、許容誤差を広げる)、根拠のない期待値の変更、根拠のないタイムアウトの延長、例外・クラッシュの無視。**`test_guard.py` が、機械的に確かめる** (`build-test-loop` の「テストの改変の検査」)。

## 5. 完了報告の項目
修正をした、または、停止したときは、次を、**1 項目 1 行**で報告する。成功だけで、修正なしのときは、1〜2 行 (トークン節約を優先する)。

- **環境:** ウォッチャーの版、ソリューション、構成|プラットフォーム。Visual Studio の表示名・版・場所は、分かる範囲で (ウォッチャーの画面の `[VS]` の行)。
- **実行:** スクリプトの実行回数と、各回の結果 (`SUCCESS` / `FAILED` / …)。テストがあれば、テスト exe (プロジェクト) と、件数 (成功・失敗)。
- **修正:** 変更したファイルと、理由。テストファイルの変更は、先頭で明示する (「完了時の確認」)。
- **警告:** 方針 (`ignore` / `report` / `fix`) と、件数、対応の結果。
- **ログ:** `.claude-logs/` の `build.log` / `errors.log` / `warnings.log` と、テストのログの場所。
- **停止したとき:** 理由と、ユーザーが行うこと。
