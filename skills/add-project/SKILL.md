# プロジェクトを足す (/add-project)

すでにあるソリューションに、プロジェクトを足していく**入口**。作るのは、既存のスクリプト (`add_layer.py` / `add_project.py` / `add_ui_host.py` / `new_solution.py`)。**このコマンドは、手順の案内と、足したあとの記録・確認をする。** `.vcxproj` / `.csproj` / `.slnx` を、自分で手書きしない。

**配布されていること:** `cpp-test-first` / `csharp-test-first` / `new-solution` / `build-test-loop` / `auto-build` の Skill (スクリプトは、それぞれの `scripts/`)。ウォッチャー (`run_watcher.cmd`) が、起動していること (ビルド・テストの確認のとき)。

## 前提
- カレントが、ソリューションフォルダ (`.sln` / `.slnx` があるフォルダ)。以降 `$SLN_DIR`。**なければ、`/new-solution` を案内して止まる。** 複数あれば、止まって、ユーザーに確認する。
- **作業フォルダ (`solutions.md` があり、`.sln` / `.slnx` がないフォルダ) では、使わない** (複数の候補を比べる場所。`/new-solutions`)。
- カレントにしか書き込まない (サンドボックスの制限)。

## 手順

### 1. 現状を読む (読み取りだけ)
```bash
python3 <このSkillのフォルダ>/scripts/solution_state.py "$SLN_DIR"
```
出力の読み方 (`KEY: 値` の行):

| キー | 意味 | 使い方 |
|---|---|---|
| `KIND` / `MAIN` | cpp / dotnet / mixed。メイン | どのスクリプトを使うかを、決める |
| `PROJECT` | 名前 \| 種類 \| 役割 \| テスト \| 参照 \| include だけの参照 | 層の一覧と、テストの有無 |
| `MISMATCH` | CLAUDE.md と、実際の食い違い | **先に、ユーザーに伝える** (足す前に、直すか確認) |
| `REF_ISSUES` | 層の参照の向きの違反 | **先に、ユーザーに伝える。** 違反を、さらに増やさない |
| `SUGGEST_REF` | 参照されていない層と、参照するのが自然な使う側 (`使う側 -> 層`) | 手順 5 で使う |
| `PLATFORMS` | C++ のプラットフォーム (`x64` / `Win32`。全部のプロジェクトが持つもの) | 層・テスト・画面ホストは、**このプラットフォームに、そろえて作られる** (スクリプトが、読み取る)。`platform` の追加に使う |
| `ADDABLE` | 足せるもの。例のコマンド (`--dry-run`) | 手順 2・3 で使う |

終了コード 2 (ソリューションなし) / 3 (複数) は、止まって、ユーザーに伝える。

### 2. 何を足すかを決める (質問は、1 回に 1 つ)
**層を足すときの質問は、この順にする:** 名前 → 役割 → 種類 → 参照する層 (`--uses`) → テスト → 使う側。**名前を聞かずに、既定の名前で案を出さない** (既定の名前 (`LogicLayer` など) でよいか、別の名前にするか、を先に聞く。**質問のツールが失敗したときも、既定の名前で黙って進まず、チャットの文章で、名前を聞く。**実機の確認 AR3・AR3b で、最初の案が既定の名前で出て、名前を 3 回変えた)。
引数 (`layer` / `tests` / `ui-host` / `ui-tests`、名前) があれば、そのとおり。なければ、`ADDABLE` から、選択肢を作って、質問する (AskUserQuestion が使えるなら、選択肢で)。

| 足すもの | 決めること | 使うスクリプト |
|---|---|---|
| **層** (`layer`) | 名前、役割 (データ / ロジック / ViewModel / その他)、種類 (C++: `dll` / `lib` / `mfc-ext-dll` / `mfc-std-dll`。.NET: `lib` / `data` / `logic` / `viewmodel`)、テストの有無、**参照する層 (`--uses`)** | C++: `cpp-test-first` の `add_layer.py`。.NET: `csharp-test-first` の `add_project.py` |
| **テストの後付け** (`tests-for:<名前>`) | どの層か (`ADDABLE` の項目) | 同上の `--tests-only` |
| **画面を持つ DLL + 画面ホスト** (`ui-host`。C++ だけ) | 名前、種類 (標準 / 拡張)、ロジック層 (`--logic`)、UI テストの有無 | `cpp-test-first` の `add_ui_host.py` |
| **UI テストの後付け** (`ui-tests:<アプリ>`) | どのアプリか | `new-solution` の `new_solution.py --ui-tests flaui` |
| **プラットフォームの追加** (`platform:Win32` / `platform:x64`。C++ だけ) | どのプラットフォームか (`ADDABLE` に出たもの。**質問は、これだけ**) | この Skill の `add_platform.py` (全部の `.vcxproj` と `.slnx` / `.sln` に、構成を足す) |
| **MSBuild の共通設定の後付け** (`common`。C++ も .NET も) | 決めることは、なし (`ADDABLE` に `common` が出たときだけ。**質問は、しない**)。外の正本の場所は、`CLAUDE.md` の「- MSBuild 共通: <パス>」→ 環境変数 `MSBUILD_COMMON_DIR` → 配布用のコピー の順。型 (参照型 / コピー型) は、すでにある薄いファイルの型を保つ。ないときは、場所が前の 2 つなら参照型、配布用のコピーならコピー型。`--common copy|reference` で、切り替えもできる | この Skill の `add_common.py` (Claude は、正本の中身を決めず、読んで置く) |

- **質問のツールは、選択肢が 2 つ以上のときだけ使う** (1 つしかないと、`Invalid tool parameters` で失敗する。自由入力の質問も、失敗した。実機の確認 AP2・AP3b・AR5 で 3 回)。選択肢が 1 つなら、その 1 つで進める案を、手順 3 の案の中で示して、承認を得る。自由入力が要る質問 (名前など) は、質問のツールではなく、**チャットの文章で聞く**。
- **C++ の層の役割の選択肢は、「データ」「ロジック」「画面 (UI)」「その他」。** 「画面 (UI)」を選ばれたら、層の追加ではなく、`ui-host` の流れ (`add_ui_host.py`) に進む (下の表の 3 行目。参照の向きの違反は、起きない: 画面の層が、ロジック層を使う向き)。ViewModel の役割は、.NET の層だけ。
- **選択肢に、「やめる」と「進める」を混ぜない** (例: 「やめる (推奨)。ReportData2 の作成のみを進める」)。依頼を取り下げる選択肢は、何も作らないことだけを意味する。
- **層の名前は、既定のままでよい** (`LogicLayer` / `DataLayer` / `ViewModels`。変更は、作成後にもできる。`DLL-LAYOUT.md`)。作るのは、ユーザーが望んだときだけ。
- **参照の向きを守る:** メイン → 画面 → ViewModel → ロジック → データ。**下の層は、上の層を参照しない。** `--uses` に、上の層を指定する依頼は、その場で指摘する。
- **MFC 拡張 DLL (`mfc-ext-dll`) は、メインが MFC のときだけ。** MFC の DLL の選び方は、`cpp-test-first` の `DLL-LAYOUT.md`。
- **C++ のテスト (`gtest`) の入れ方** (`--gtest auto|vcpkg|source`) は、`new-solution` の「GoogleTest」と同じ。迷ったら `auto`。
- **UI 層はテストしない** (画面のテストは UI テスト)。UI DLL に、`tests-for` を出さない。
- **プラットフォームの追加 (`platform`)**: x64 だけのソリューションに Win32 を足す (または、その逆)。**全部の C++ の `.vcxproj` と、`.slnx` (`<Platform Name="x86" />`) / `.sln` が、変わる。** すでにあるプラットフォームは、何もしない。**`.vcxproj` の形が想定と違うものが 1 つでもあれば、何も書かずに止まる** (終了コード 2。「!」の行を、ユーザーに伝える)。.NET (`AnyCPU`) は対象外。

### 3. 案を示して、承認を得る (**必ず止まる**)
`ADDABLE` の例の `--dry-run` を、実際の引数で実行し、出力を要約して見せる。
- 作るプロジェクトとファイル、参照 (`--uses`)、テスト、GoogleTest / MSTest の状態 (`GTEST_MODE` / `NOTE`)、ソリューションへの登録。
- **参照の案 (使う側 → 新しい層) も、一緒に示す。** 使う側は、`solution_state.py` の `SUGGEST_REF` と同じ規則で決める (新しい層の役割の、**すぐ上の層。なければ、メイン**)。テストを足すときは、そのテストが対象の層を参照する (`add_layer.py` / `add_project.py` が、すでに書く)。ユーザーが、別の使う側 (例: 画面を介さず、メインが、直接使う) を指定してもよい。
- **使う側が決まらない層 (役割が「その他」。`SUGGEST_REF` は、メインを案として出す) も、使う側の既定は、メイン** (「いまはどこからも参照しない」は、ユーザーが選んだときだけ)。
- **切り出し: アプリの中に、新しい層と同じ名前のフォルダ (同じ名前空間) があるとき** (例: WPF のアプリの `ViewModels/` に `MainViewModel.cs` などがあるときに、`ViewModels` の層を足す)。そのままでは、名前空間が衝突して (CS0104)、ビルドが通らない。案に、次を、**範囲外の変更として、別に書く:** (a) 削除するアプリ側のファイルの一覧、(b) 書き換えるファイル (例: `.xaml` の `xmlns:vm` に `;assembly=<層の名前>`)。**削除は、承認された案に書いてあるときだけ。作成のあと、削除の前に、アプリ側のファイルが、生成された同名のファイルと同一かを、`diff` で確かめる** (内容・BOM・改行)。**同一でないファイル (ユーザーが編集したもの) が 1 つでもあれば、どのファイルも削除せず、止まって、ユーザーに聞く** (一部だけ削除して、中途半端な状態を作らない)。選択肢は、「編集のあるファイルを、新しい層へ移す (案に、移す内容と、アプリ側の書き換えを書いて、あらためて承認を得る)」「名前を変える」「残して、層の追加を中止する」。**「移す」を選んだあとは、移した ViewModel に対して、層の側に生成されたサンプルのテスト (`MainViewModelTests` など) が、失敗することがある** (編集した ViewModel が、サンプルの動きと違うため)。失敗しても、**テストを、黙って直さず、弱めない。** どのテストが、なぜ失敗したかを、ユーザーに伝えて、直し方 (テストを、移した ViewModel の仕様に合わせて書き換える / 移すのをやめる) を、確認する。**利用者の編集を捨てて、上書きする選択肢は、出さない。** 編集の有無は、作成の前の読み取りで調べてよい (案の前に、分かる)。
- **変わるのは、新しいプロジェクトと、ソリューション (`.slnx` / `.sln`)、`CLAUDE.md` (手順 6)、そして、承認された参照の、使う側のプロジェクト (`.vcxproj` / `.csproj`。手順 5) だけ**であることを、明記する。それ以外の既存のプロジェクトは、書き換えない。**例外は 2 つ。** (1) 上の「切り出し」の、アプリ側のファイルの削除と書き換え。(2) **`ui-host` は、指定したロジック層に `Greeting.h` / `Greeting.cpp` を足し、そのテストに `TestGreeting.cpp` を足す** (その 2 つの `.vcxproj` / `.filters` も変わる)。案には、例外の中身を、必ず書く。
- **`platform` のとき:** `add_platform.py ... --dry-run` の出力 (`+` が、書き換えるファイル、`=` が、すでにあるもの、`!` が、想定外の形式) を、そのまま見せる。**変わるのは、全部の C++ の `.vcxproj` と、`.slnx` / `.sln` だけ** (`CLAUDE.md` の `- プラットフォーム` の記述があれば、手順 6 で合わせる)。
- **`common` のとき:** `add_common.py ... --dry-run` の出力 (正本の場所と決めた元、置き方 (参照型 / コピー型)、`+` が、足すもの、`~` が、書き換えるもの、`=` が、すでに同じもの、`!` が、止まる理由) を、そのまま見せる。**書き換えるのは、以前の `/new-solution` が作った `Directory.Build.props` (`Nullable` などを直接書くもの。設定は、共通ファイルの `Dotnet.props` に移る。効果は同じ)、型を切り替えるときの薄いファイル、古い版の `build\common\`、`CLAUDE.md` の自動生成の節だけ。手で書いた `Directory.Build.props` / `.targets` は、書き換えず、止まる** (`!` の行の、Import の行を、ユーザーに伝える)。**参照型のときは、案に出る NOTE (Windows 側の環境変数 `MSBUILD_COMMON_DIR` の設定。Visual Studio の再起動、ウォッチャーの起動し直し) を、ユーザーに伝える。**
- 「この内容で、足してよいですか?」と聞いて、返事を待つ。**承認が出るまで、何も作らない。** **承認は、はっきりした肯定の返事 (「はい」「進めて」「承認します」など) だけ。** 案への質問・修正や、ほかの質問への答え (例: 「参照する層: LogicLayer」) は、承認ではない。そのときは、案を直して (または答えを案に入れて)、もう一度、承認を求める (実機の確認で、別の質問への答えを承認として、削除まで進めた)。
- 終了コード 3 (すでにある) は、何も書かれていない。**既存のものを、上書きしない。** 終了コード 2 は、組み合わせや入力の問題。内容を、ユーザーに伝える。

### 4. 作る
承認された引数で、`--dry-run` を外して、実行する。**手で、`.vcxproj` や `.csproj` を書かない。**
- C++ のテストを足したとき: 出力の `GTEST_MODE` で、仕上げを行う (`new-solution` の A. の 5.。`GTEST_VCPKG: no-baseline` のときは、`package_once.sh` で baseline の固定と取得)。
- .NET: NuGet の復元は、ウォッチャーのビルドが行う (`/restore`)。

### 5. 参照 (使う側から、新しい層へ)
**手順 3 で承認された参照だけを、`add_reference.py` で足す** (使う側ごとに、1 回ずつ。手書きしない)。
```bash
python3 <このSkillのフォルダ>/scripts/add_reference.py "$SLN_DIR" --from <使う側> --to <新しい層> --dry-run   # 内容を確かめてから
python3 <このSkillのフォルダ>/scripts/add_reference.py "$SLN_DIR" --from <使う側> --to <新しい層>
```
- **足すもの:** .NET は、使う側の `.csproj` に `ProjectReference` を 1 行。C++ は、使う側の `.vcxproj` に `ProjectReference` (DLL はインポートライブラリ、静的ライブラリは `.lib` が、リンクされる。ビルド順も決まる) と、全構成のインクルードパス (新しい層と、それが参照している層。テスト exe と同じ形)。
- **ヘッダ (インターフェース) だけを使う層** (実装には、リンクしない) は、`--include-only` (C++ だけ。`add_layer.py` の `--uses` と同じ)。
- **断られたとき (終了コード 2):** 理由を、そのまま、ユーザーに伝える。**向きの違反** (下の層が、上の層を参照する)、**循環**、**MFC 拡張 DLL を、`UseOfMfc` のない使う側から参照する** (先に、使う側の MFC の設定を直す。`mfc-check` の DLL008) は、勝手に回避しない。終了コード 3 (すでにある) は、何も書かれていない。
- **足したあと:** `solution_state.py` を、もう一度実行し、**`SUGGEST_REF` と `REF_ISSUES` が、残っていないこと**を確認する。残っているものは、報告に書く (ユーザーが、承認しなかった参照、断られた参照)。
- 新しい層が、`--uses` で他を参照している場合は、`add_layer.py` / `add_project.py` が、すでに書いている (新しい側から、下の層への参照)。

### 6. CLAUDE.md を、実際の構成に合わせる
**書き換えるのは、次の場所だけ** (`- 層:` の行、層の表または「追加した層」の行、`- テスト:` の行。ほかの節は、触らない)。`CLAUDE.md` がなければ、作らず、ユーザーに伝える。
- **`- 層:` の行:** 役割で足す。既定の名前 (`DataLayer` / `LogicLayer` / `ViewModels`) なら、役割だけ (`data,logic`)。既定でない名前は、`logic:OrderLogic` の形。**名前に役割の語 (`Logic` / `Data` / `ViewModel` / `Ui` `View`) がない層 (例: `ExtLayer`) も、ユーザーが選んだ役割で、`logic:ExtLayer` の形で書く** (書かないと、`solution_state.py` / `mfc-check` / `add_reference.py` が、名前だけから「その他」と判定し、層の検査が効かない。実機の確認 AR3 で発見)。行が `なし` のときは、`なし` を、足す層に置き換える。役割が「その他」の層だけ、この行に書かず、下の表に書く。**書いてある層は、消さない・並べ替えない。**
- **層の表 (「## 層と依存の向き」):** 1 行足す (プロジェクト、種類、テスト)。表がなければ、「- 追加した層: 名前 (種類)。<役割>。テストあり / テストなし。<参照>」の箇条書きを、その節の末尾に足す。**テストの有無を、必ず書く。**
- **ViewModel の層を作ったとき (アプリの `ViewModels/` を切り出したとき):** 「アプリの構成」の行の「`ViewModels/` (ViewModel 層がないとき)」と、「ViewModel 層を作っていないので、ViewModel は、アプリの `ViewModels/` フォルダにある…」の行も、実態に合わせて直す (後者は、消してよい)。
- **「追加した層」の行の名前は、`` ` `` で囲まない** (`- 追加した層: ExtLayer (MFC 拡張 DLL)。…`。`solution_state.py` は、名前の直後を読んで、テストの有無の食い違いを調べる。囲んであっても読めるが、書式は、そろえる)。
- **テストを後付けしたとき (`tests-for`):** **その層の行 (表があれば、その行の「テスト」の列。なければ、「追加した層」の行) の「テストなし」を、`テストあり (<名前>Test)` に直す。** 層を足した記録が、実際と食い違わないようにするため (`solution_state.py` は、「追加した層」の行のテストの有無の食い違いを、`MISMATCH` に出す)。
- **`- テスト:` の行:** 最初のテストを足したとき、`なし` を `あり (GoogleTest)` / `あり (MSTest)` に直す。
- 画面を持つ DLL + 画面ホストは、`add_ui_host.py` が、自分で CLAUDE.md に節を足す (二重に足さない)。

直したあと、`solution_state.py` を実行して、**`MISMATCH` が出ないこと**を確認する。

### 7. 確かめる (ベースライン)
- **ビルド:** `auto-build` の手順 (`build_once.sh`)。`SUCCESS` になるまで。 **`common` を足したときも、ビルド (テストがあれば `build-test-loop`) で確かめる** (`.csproj` / `.vcxproj` は、変わらないが、薄いファイルが、すべてのプロジェクトに効く)。**`platform` を足したときは、足したプラットフォームでも、ビルドする:** ウォッチャーは、Platform を、**起動の引数**で決める (引数なしは x64)。Win32 のビルドは、`run_watcher.cmd <フォルダ> "" Win32` で、ウォッチャーを起動し直してもらう (起動時の表示 `Build : <構成>|<Platform>` を確かめる。**Win32 のままで、x64 のソリューションをビルドすると、`MSB4126` (構成が無効) になる**)。
- **テストを足したとき:** `build-test-loop` の手順 (`build_test_once.sh`)。`PASSED` (追加分の 1 件のテストを含む) になること。
- **静的な検査:** MFC は `mfc-check` (層の依存、DLL の設定)、WPF は `wpf-check`、WinForms は `winforms-check`。**指摘が 0 件**であること (生成物は、指摘が出ないように作ってある。出たら、生成の誤り)。
- 失敗したら、それぞれの Skill の規則で直す。**環境の問題 (`ENV_ERROR`、ウォッチャー未起動) は、直さずに報告する。**

### 8. 報告して、終わる
作ったもの (プロジェクト、テスト、ソリューションへの登録)、`CLAUDE.md` で直した行、**足りない参照 (`SUGGEST_REF`)**、ビルド・テスト・静的検査の結果、**確認できていないこと** (実機の画面など) を、短く示す。自動で、次に進まない。**`git commit` / `git push` は、ユーザーの指示があるときだけ。**
- ユーザーに、Visual Studio で `.slnx` を開いて、問題がないか確認してもらうとよい、と添える。

## しないこと
- 承認なしの作成。既存のスクリプトを使わない、プロジェクトファイルの手書き。
- 既存のプロジェクトの、無断の書き換え (書き換えてよいのは、手順 3 で承認された参照の、使う側のプロジェクトだけ)。
- `add_reference.py` が断った参照 (向きの違反、循環、MFC の設定) の回避。
- 参照の向きを逆にする (下の層から、上の層への参照)。
- ソリューションの新規作成 (`/new-solution`)、機能のコード、仕様書の作成 (`claude-spec-workflow`)。
- カレントの外への書き込み。`git commit` / `git push` / `git init`。
