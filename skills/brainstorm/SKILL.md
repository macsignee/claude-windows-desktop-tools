# 壁打ちで仕様を固める (/brainstorm)

作りたいものを、ユーザーと対話しながら、**テストに落とせる具体さ**まで固める。成果物は、仕様書 1 枚。
**このコマンドでは、コードもテストも、プロジェクトも作らない。** 書いてよいのは、仕様書のファイルだけ。

用途は、プロトタイプと、TDD の練習。大きく作り込まない。**1 回の仕様は、1 つの小さな機能**にする (テストが 5〜10 件で収まる大きさ)。

引数 (`$ARGUMENTS`) に、作りたいものの一言があれば、そこから始める。なければ、「何を作りたいですか?」と聞く。

## 進め方

1. **現状を、軽く確認する (読み取りだけ)。** カレントに `.sln` / `.slnx` があるか、既存のプロジェクト (層) と、`docs/specs/` の既存の仕様書を、見る。長く調べない。
2. **質問は、1 回に 1 つ。** 選択式にできるものは、選択肢 (2〜3 個) と、**推奨案とその理由**を添える。ユーザーが迷っていたら、具体例で示す。
   - AskUserQuestion が使えるときは、それを使ってよい。
3. **次の順で、固める** (答えが出ている項目は、飛ばす)。
   1. **目的:** 何のための機能か (1〜2 文)。
   2. **どの層に置くか:** 業務ルール・計算 → ロジック層 / 保存・読み出し → データ層 / 画面 → UI 層。**テストするのは、ロジック層とデータ層だけ**。UI にロジックが混ざりそうなら、切り分けを提案する。
   3. **具体例を先に:** 入力 → 期待する出力の例を、3〜5 件。**例が、そのまま、テストケースの種になる。**
   4. **ルール (一般化):** 例から、規則を言葉にする (計算式、丸め方、検証の条件)。
   5. **境界値と異常系:** 0、最小・最大、空、上限の前後、不正な入力のときの振る舞い (戻り値か、例外か、無視か)。
   6. **インターフェース案:** 関数・クラス名と、引数・戻り値 (名前は仮でよい)。データ層との境界 (インターフェース) が要るかも。
   7. **やらないこと (スコープ外):** 今回は作らないものを、明示する。
4. **要約して、確認する。** 固まったら、仕様の要約を示して、「この内容で合っていますか?」と聞く。
5. **確定の合図があってから、仕様書を書く。** ユーザーが「確定」「OK」などと言うまで、状態は `下書き` にする。

## 仕様書

保存先: `docs/specs/<機能名 (英小文字とハイフン)>.md` (フォルダがなければ作る)。UTF-8、BOM なし、改行は LF。

```markdown
# <機能名>

- 状態: 下書き | 確定 | 変更あり (要再確定)
- 日付: YYYY-MM-DD

## 目的
## 置く層
(ロジック層 / データ層 / UI 層。テスト対象と、そうでないものを区別する)

## 具体例
| 入力 | 期待する出力 | 補足 |
|---|---|---|

## ルール
## 境界値と異常系
| ケース | 振る舞い |
|---|---|

## インターフェース案 (仮)
## スコープ外
## 未決事項
(あれば。**未決事項が残っている間は、状態を「確定」にしない**)

## 変更履歴
(確定後の変更は、`/update-from-ideas` が追記する)
```

## 終わり方
- 仕様書を保存したら、パスと、1〜3 行の要約を示す。
- 状態が `確定` なら、**「`/add-feature docs/specs/<名前>.md` で、計画 → テスト先行 → 実装 → 検証に進めます」**と案内する。自動で、次に進まない。
- 状態が `下書き` なら、残っている質問を示して、続けるか確認する。
- 確定後に、思いつきや変更案が出たら、`/update-from-ideas` で、仕様書に反映する (`docs/ideas.md` に貯めておいてもよい)。

## しないこと
- コード、テスト、`.vcxproj` の作成や変更。
- ユーザーが言っていない要件の追加 (提案は、してよいが、決めるのは、ユーザー)。
- 一度に、複数の質問を投げること。
- `git commit` / `git push`。
