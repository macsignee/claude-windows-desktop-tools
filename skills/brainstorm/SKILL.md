# 壁打ちで、考えを広げる (/brainstorm)

作りたいものを、ユーザーと対話しながら、**テストに落とせる具体さ**に近づける。成果物は、**ブレインストーミングのメモ** 1 枚。
**正式な仕様書は、ここでは作らない。** メモを整理して、仕様書にするのは、次の **`/update-from-ideas`** (そのあとに `/add-feature`)。

```
/brainstorm (考えを出す) → /update-from-ideas (整理して、正式な仕様書にする) → (/new-solution) → /add-feature (実装)
```

**このコマンドでは、コードもテストも、プロジェクトも作らない。** 書いてよいのは、メモのファイルだけ。

用途は、プロトタイプと、TDD の練習。大きく作り込まない。**1 回のメモは、1 つの小さな機能**にする (テストが 5〜10 件で収まる大きさ)。

引数 (`$ARGUMENTS`) に、作りたいものの一言があれば、そこから始める。なければ、「何を作りたいですか?」と聞く。

## 進め方

1. **現状を、軽く確認する (読み取りだけ)。** (`solutions.md` があるフォルダは、複数の候補を比べる作業フォルダ。`docs/` は、全候補に共通の正本。) カレントに `.sln` / `.slnx` があるか、`CLAUDE.md` の設定 (`- 層:` / `- テスト:`)、既存のプロジェクト、`docs/specs/` と `docs/ideas/` の既存のファイルを、見る。長く調べない。
   - **ソリューションがなくても、そのまま進めてよい。** ソリューションの作成 (`/new-solution`) は、仕様が整理されたあとで、構成案を出してから行える (仕様が先)。器を先に作りたいと言われたら、`/new-solution` を案内する。
2. **質問は、1 回に 1 つ。** 選択式にできるものは、選択肢 (2〜3 個) と、**推奨案とその理由**を添える。ユーザーが迷っていたら、具体例で示す。
   - AskUserQuestion が使えるときは、それを使ってよい。
3. **次の順で、広げて、固める** (答えが出ている項目は、飛ばす。**決まらない項目は、無理に決めずに、「未決」としてメモに残す**)。
   1. **目的:** 何のための機能か (1〜2 文)。
   2. **どの層に置くか:** 業務ルール・計算 → ロジック層 / 保存・読み出し → データ層 / 画面 → UI 層。**テストするのは、ロジック層とデータ層だけ**。UI にロジックが混ざりそうなら、切り分けを提案する。
   3. **具体例を先に:** 入力 → 期待する出力の例を、3〜5 件。**例が、そのまま、テストケースの種になる** (`テスト: なし` のソリューションでは、**手動の確認項目**になる)。
   4. **ルール (一般化):** 例から、規則を言葉にする (計算式、丸め方、検証の条件)。
   5. **境界値と異常系:** 0、最小・最大、空、上限の前後、不正な入力のときの振る舞い (戻り値か、例外か、無視か)。
   6. **インターフェース案:** 関数・クラス名と、引数・戻り値 (名前は仮でよい)。
   7. **やらないこと (スコープ外):** 今回は作らないものを、明示する。
   8. **ほかのアイデア・気になる点:** 出てきたが、今回の機能に、入れるか決めていないもの。
4. **要約して、確認する。** 区切りのよいところで、メモの要約を示して、「ここまでで、メモに残してよいですか?」と聞く。
5. **メモを保存する。** ユーザーの了承があったら、メモを書く (下書きでよい。**状態の「確定」は、ここでは、扱わない**)。

## メモ

保存先: `docs/ideas/<機能名 (英小文字とハイフン)>.md` (フォルダがなければ作る)。UTF-8、BOM なし、改行は LF。
**決まったことと、決まっていないことを、分けて書く** (整理するときに、仕様書へ、そのまま移せるように)。

```markdown
# <機能名> (ブレインストーミングのメモ)

- 日付: YYYY-MM-DD
- 整理: 未   (`/update-from-ideas` が、仕様書にしたら、「済 (→ docs/specs/<名前>.md)」にする)

## 目的
## 置く層の候補
## 具体例
| 入力 | 期待する出力 | 補足 |
|---|---|---|

## ルールの候補
## 境界値と異常系の候補
| ケース | 振る舞い |
|---|---|

## インターフェースの案 (仮)
## スコープ外 (今回は、作らない)
## ほかのアイデア・気になる点
- 
## 未決 (まだ、決まっていないこと)
- 
```

## 終わり方
- メモを保存したら、パスと、1〜3 行の要約、**未決の件数**を示す。
- **「`/update-from-ideas docs/ideas/<名前>.md` で、整理して、正式な仕様書にできます」**と案内する。自動で、次に進まない。
- 続けて、広げたい場合は、そのまま壁打ちを続ける (メモは、追記する)。

## しないこと
- 正式な仕様書 (`docs/specs/`) の作成・変更 (それは、`/update-from-ideas`)。
- コード、テスト、`.vcxproj` の作成や変更。
- ユーザーが言っていない要件の追加 (提案は、してよいが、決めるのは、ユーザー)。
- 一度に、複数の質問を投げること。
- `git commit` / `git push`。
