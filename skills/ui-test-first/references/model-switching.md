# Model (リポジトリ) の Fake ↔ 本物と、結合

`ui-test-first` の SKILL.md の手順 1 で、画面が使う **Model が、まだ本物でない (これから作る)** ときに、**先に**読む。本物ができたあとの、結合の手順も、ここ。

## 「Model」とは何か、画面のデータは、どこに置くか
- **Model = リポジトリ的なもの** (データベース・API などの違いを隠す。MVVM の Model と、同じ意味)。**Fake と本物があり、契約テストの対象で、計画の「依存する Model」の表に載るのは、これだけ。**
- **画面が使う画面モデル** (ViewModel に相当。状態・操作と実行可否・検査・変更の通知・結果。`rules/winforms-view-model.md` の 2 章) は、Model ではない。**ただし、Fake と契約テストの対象** (下の「画面モデルの Fake と、その存在時間」)。
- **ダイアログ・画面が使う、データのクラス** (入力値のまとめ、ダイアログが返す結果、表示用の行など) は、**Model ではない。** Fake・契約テスト・「依存する Model」の表の、対象外。
- **置き場所:** **基本は、ロジック層** (UI の型を使わない。単体テストで確かめる)。**ダイアログの動作と、べったり結びつき、View 層から離すと、かえって不自然なとき (UI の型・部品の状態に強く依存するとき) だけ、View 層に置く。** データ層 (Model の層) には、置かない。
- 迷ったら、ロジック層。View 層に置いたときは、設計の記録 (`docs/design`) に、理由を 1 行書く。

## 計画に足す表 (手順 1)

- **依存する Model (データベース・API などの違いを隠す、リポジトリのようなもの):** 画面が使う Model が、**まだ本物でない (これから作る)** ときは、計画に、**表 (Model (インターフェース) / 実装 (Fake / 本物) / 契約テスト (クラス名) / 状態 (Fake のみ / 本物あり / 結合済み))** を足す。**UI テストは、Fake (メモリ上の実装) で回す** (下の「Model の差し替え」)。本物の Model は、`csharp-test-first` / `cpp-test-first` の流れで、別に作り、結合は、下の「結合 (Fake → 本物)」で行う。

## Model の差し替え (Fake ↔ 本物)

画面が使う **Model** (データベース・API の違いを隠す、リポジトリのようなもの) は、**まだ、本物がない**ことが多い。UI テストは、**Fake** (メモリ上の実装) で回し、本物ができてから、結合する。
- **インターフェースに、依存する。** ViewModel / Presenter は、Model の**インターフェース**だけを知る (`new` しない。コンストラクターで受け取る)。Fake と本物は、同じインターフェースを実装する。**Fake は、メモリ上の、小さな実装** (決まった値、保存したら覚える。遅延・失敗は、必要なときだけ)。
- **切り替えは、起動の環境変数 `APP_MODEL` (`fake` / `real`)。** アプリの、**組み立てる場所** (WPF: `App.xaml.cs`、WinForms: `Program.cs`、MFC: `InitInstance`) で、読んで、選ぶ:
  ```csharp
  IOrderRepository repo = Environment.GetEnvironmentVariable("APP_MODEL") == "fake"
      ? new InMemoryOrderRepository(/* 初期データ */) : new SqlOrderRepository(connectionString);
  ```
  **Release のビルドでは、`APP_MODEL` を読まない** (`#if DEBUG`。Fake が、製品に、紛れ込まないため)。MFC は、`getenv("APP_MODEL")` を、`_DEBUG` のときだけ。
- **UI テストが、`APP_MODEL` を、アプリに渡す。** `UiTestBase` が、起動の前に設定する (`ModelMode`)。**値は、環境変数 `UITEST_MODEL` > `uitest.settings` の `model=` > `fake` (既定)。** 読まないアプリには、影響しない。`ui-trace.txt` の先頭に、`model: fake` と出る。
- **Fake は、アプリの側 (または、データ層) に置く** (テストのプロジェクトに置かない。exe が、起動したときに、使えるため)。名前: `InMemory<名前>Repository`。
- **Fake が、本物と、ずれないように:** Fake は、インターフェースの、決めた意味 (計画の「依存する Model」) だけを、まねる。**本物の振る舞いを、推測で、足さない。** **Fake と本物は、契約テスト (同じテストを、両方に通す) で、合わせる** (`csharp-test-first/CONTRACT-TESTS.md`、C++ は `cpp-test-first/CONTRACT-TESTS.md`)。契約テストを書いて、Fake で Green にしてから、UI テストを回す。

## 結合 (Fake → 本物)

本物の Model ができて、**その単体テストが `PASSED`** になったら、結合する。**UI テストを、本物でも通す** (Fake で通っていたテストを、そのまま)。
1. **関門:** 本物の Model の単体テストと、**契約テスト (Fake と本物の両方) が `PASSED`** (`build_test_once.sh`)。計画の「依存する Model」の状態が、「本物あり」。
2. **本物に切り替える:** `<アプリ>.UITests/uitest.settings` の `model=fake` を `model=real` に直す (または、`UITEST_MODEL=real`)。**UI テストのコードは、変えない。** 本物の接続先 (開発用のデータベース・API) の準備は、ユーザーに確認する (**本番の接続先で、実行しない**)。
3. **同じ UI テストを、再実行する** (`uitest_once.sh`、同じ `--filter`)。**Green → 結合済み。** 状態を「結合済み」に直す (設計の記録・計画の表)。
4. **Red になったら、原因を分ける:** (a) **Fake が、本物と、違う** (戻り値・順序・エラーの形) → Fake と、インターフェースの意味を直す (Model の単体テストが、先)。(b) **本物の不具合** → 本物を直す (単体テストが、先)。(c) **データ・時間の違い** (本物は、遅い、データが残る、並びが違う) → テストを、データに依存しない形にする (**アサーションを、弱めない**。仕様が変わったときだけ、ユーザーの承認で)。**どれも、`test_guard.py check` の対象** (UI テストの、削除・`Ignore`・弱めは、許可なしにしない)。
5. **結合したあとも、Fake を、捨てない。** 普段の UI テストは、`model=fake` (速く、安定) に戻す。**本物での UI テストは、主要な流れだけ**に絞り、結合の確認のときに、`model=real` で、回す。

## 画面モデルの Fake と、その存在時間

画面が使う画面モデルにも、Fake (Fake 画面モデル) を置ける。**Model (リポジトリ) の Fake とは、別のもの** (フォームが直接使うのが画面モデル、画面モデルが使うのがリポジトリ)。
- **通常の UI テストは、本物の画面モデル + Fake リポジトリ** で回す。Fake 画面モデルで通っても、本物の画面モデルの規則で壊れる余地が残るため。
- **Fake 画面モデルは、次の 2 つに限る:** (a) 本物の画面モデルが、まだ存在しないときの、つなぎ (UI 先)。(b) 本物では作りにくい状態の再現 (エラー表示、無効状態、長い一覧)。
- **存在時間 (UI 先):** UI テスト (Red) を書くときに生まれる → 画面モデルの契約テストを、Fake で Green → 本物の画面モデルを作り、同じ契約テストを通す (併存) → **UI テストを、本物の画面モデル + Fake リポジトリに切り替えて、同じテストが通ったときに、役目を終える** → 既定は削除。(b) の用途で残すときは、契約テストを通し続け、残す理由を `docs/design` に 1 行書く。
- **ロジック先 (本物の画面モデルが、すでにある):** 契約テストを、先に書き、本物で Green にしてから、Fake を作る (本物を読んで Fake を書くと、偶然の挙動まで写す)。通常は、Fake 画面モデルを作らない (b が必要になったときだけ)。
- **置き場所:** アプリ側 (exe の起動時に使う。テストのプロジェクトには置かない)。**契約テストは、`<画面モデル名>ContractTests`** で、本物 (Fake リポジトリを注入) と Fake の両方に通す。
- **切り替え (決定。ひな形・`UiTestBase` の実装は、まだ):** 画面ごとに選ぶ。アプリへ渡す環境変数 **`APP_FAKE_SCREENS`** (Fake にする画面名のカンマ区切り。`画面名:シナリオ名` も可。例: `Greeting,NameEdit:InvalidName`)。テスト側は、環境変数 `UITEST_FAKE_SCREENS` > `uitest.settings` の `fake_screens=` > 空 (すべて本物)。アプリは、`APP_MODEL` と同じ場所で、**Debug のときだけ**読む。`ui-trace.txt` の先頭に `fake_screens: ...` と記録する。`APP_MODEL` とは独立 (Fake 画面モデルを選んだ画面は、リポジトリを使わない)。**一覧にあるのに Fake がないときは、Debug の起動時に、エラーで止める。** 画面モデルは、インターフェース経由で使い、組み立てる場所で、画面名から実装を選ぶ。**実装が済むまでは、本物の画面モデル + Fake リポジトリで回す。**
- **Fake リポジトリの失敗の再現:** 単体テストは、Fake の専用メソッド (`FailNext(種別)`、`FailWhen(操作, 種別)`。インターフェースにはない)。UI テスト (別プロセス) は、**`APP_MODEL=fake:<シナリオ名>`** (例: `APP_MODEL=fake:SaveConflict`。Fake が、シナリオに応じて失敗する)。

## UI 層の文言のテスト (現状と移行後)
- **現状 (画面モデルが、`IMessageFormatter` で、日本語の文章を作る):** 画面モデルの単体テストは、**文言ではなく、種別と引数で検査する** (業務の生成文は、文言で検査する)。UI テストは、画面に出る文章を、`IMessageFormatter` の既定の実装 (日本語の表) から引いた期待値と比べる。**期待値を引く補助は、欠落 (空、キー名そのまま) を検出して、テストを失敗させる** (期待値も画面も空で、通ってしまうのを防ぐ)。主要なエラー 2 件に限り、日本語の直書きを併用する。完全性のテスト: 列挙の全値に、日本語の表の行がある。
- **移行後 (UI 層のリソースを引く formatter に差し替えたあと):** 期待値は、リソースから引く。言語の指定 (`UITEST_CULTURE` > `uitest.settings` の `culture=` > `ja-JP` を、アプリへ `APP_CULTURE` で渡し、Debug のときだけ読む。表示言語と書式の両方)、擬似ローカライズ (第 1 段階は、画面モデル由来の文字だけ)、MFC の `STRINGTABLE` を読むテスト補助、完全性のテストのリソース版は、**このときに実施する** (国際化は、優先度が低い)。
- Form の固定文字列は、リソースにしない。国際化の範囲は、画面モデル由来の文章だけ。
