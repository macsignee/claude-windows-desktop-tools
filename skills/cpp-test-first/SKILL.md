# C++ テストファースト (Red を作る)

実装の前に、仕様をテストとして書き、**正しい理由で失敗すること (Red)** を確かめるところまでを行う。
実装して通す (Green) 工程は、`build-test-loop` が行う。実行の仕組み (ウォッチャー、フラグ、結果の読み方) は、そちらと同じ。

## 前提
- ユーザーが対象ソリューションのフォルダで `run_watcher.cmd` を起動済みであること。
- ソリューションフォルダを `$SLN_DIR` とする (**`.slnx` / `.sln` のファイルのパスではなく、それを含むフォルダ**。スクリプトの第 1 引数も、このフォルダ)。Claude Code は、このフォルダをカレントにして起動されている。
- **作業フォルダ (`solutions.md` があり、`.sln` / `.slnx` がないフォルダ) で起動しているとき** (複数の候補のソリューションを、比べているとき): `$SLN_DIR` は、カレントではなく、対象の候補。`SLN_DIR=$(python3 ~/.claude/skills/new-solution/scripts/new_solutions.py resolve "$PWD" [<候補名>])` で決める (終了コード 2: 候補が複数 → 一覧を示して、ユーザーに質問する。3: 対象がない)。以降の `CLAUDE.md` や `docs/` は、`$SLN_DIR` の下 (その候補のコピー)。**他の候補は、読まない・書かない。** ウォッチャーは、その候補のフォルダで、起動されている必要がある。
- **ソリューションは、次の 3 層 + テストの構成であること。** (プロジェクトの作り方と規約は、同梱の `DLL-LAYOUT.md`)

  | 層 | プロジェクト | 種類 | MFC | テスト |
  |---|---|---|---|---|
  | UI | メインの exe | exe | 使う/使わない | 下記「exe の種類による判断」による |
  | ロジック | `<Name>Logic` 等 | **DLL** | 使わない | 対応する `<DLL名>Test` (GoogleTest の exe) |
  | データ | `<Name>Data` 等 | **DLL** | 使わない | 対応する `<DLL名>Test` (GoogleTest の exe) |

- **テストは、DLL 単位で作る。** ロジック DLL のテストは、そのテスト exe に、データ DLL のテストは、そのテスト exe に書く。
  テスト exe は、対応する DLL をプロジェクト参照している。ウォッチャーは、`*Test.exe` を、すべて実行する。
- **テスト対象は、ロジック DLL とデータ DLL のクラス・関数だけ。** ダイアログ、ビュー、`CWnd` 派生、メッセージハンドラは、対象にしない。
  - 対象が UI 層に書かれている場合は、**テストを書かずに止まり**、ロジックを、ロジック DLL の MFC 非依存の関数・クラスに切り出す案を、ユーザーに示す。
  - 切り出しの変更は、ユーザーの了承を得てから、行う。

### exe の種類による判断 (メインの exe をテストするかどうか)
メインの exe の `SubSystem` (`Windows` か `Console`) で、方針が変わる。

- **Windows (GUI、`CWinApp` + メッセージループあり):** ウィンドウが開き、手動で閉じるまで終了しない。GoogleTest の「実行して終了コードと出力を見る」という前提に合わないため、通常の単体テスト (ロジック/データ DLL と同じ枠組み) は**しない** (UI 層として、上の「対象が UI 層に書かれている場合」の扱いにする)。
  - このため、ウォッチャーの既定のテスト検出パターン (`*Test.exe`) にメインの exe の名前が偶然一致しても (例: プロジェクト名が `...Test` で終わる場合)、それは除外して、GoogleTest として実行しない (ホスト側ツールの対応は `watch_and_build.ps1` 側で行う)。
  - **ただし、別カテゴリの「UI 自動化テスト」としてなら、GUI exe もテストできる。** 本番コードにテスト専用のフックを足さず、**実際に存在するコマンド** (コマンドライン起動でのファイルを開く、`ID_FILE_SAVE` などの標準コマンド ID を `WM_COMMAND` で送る) と、保存されたファイルを外部から読むことで検証する。
    クリックの模倣は、`SendMessage` で `WM_LBUTTONDOWN` を直接送るとドッキング UI 等のアクティブ化処理に吸収されて届かないことがあるため、`SendInput` (実際のマウス入力と同じ経路) を使う。ビューの HWND は `GetDlgItem(hwndFrame, 0xE900 /* AFX_IDW_PANE_FIRST */)` で取得できる。
    これは、通常の DLL 単体テストより重く (別プロセスを起動し、実際にマウスを動かす)、exe ごとに個別の実装が要る。**ユーザーが明示的に望んだときだけ**行う。
- **Console (メッセージループなし、`main()` が実行されて自然に終了する):** 通常の CLI プログラムと同じなので、**ロジック層・データ層と同じ感覚で、そのままテストしてよい** (GoogleTest の exe として書く、または実際に実行して標準出力・終了コードを確かめる)。
  - ただし、対応は、ユーザーに「この exe (Console) もテストしますか」と確認してから行う (構成によっては、exe 本体ではなく、やはりロジック/データ DLL に切り出す設計を、ユーザーが選ぶこともある)。
- 対応する DLL やテスト exe が、まだない場合は、下記「セットアップ」で作る (**ユーザーの了承を得てから**)。

## セットアップ (層やテストを、あとから足すとき)

**最初のソリューション・メインのプロジェクト・層・テストは、`/new-solution` が作る** (層 `--layers` と、テスト `--tests` を、別々に指定できる)。
この Skill が、セットアップに関わるのは、**作ったあとで、足りないものが分かったとき**だけ。

1. **設定を読む:** `$SLN_DIR` の `CLAUDE.md` の `- 層:` と `- テスト:` の行 (なければ、構造から判定: `*Test` プロジェクトと GoogleTest の有無)。
   - **`テスト: なし` の場合、この Skill (テスト先行) は、使えない。** 「テストが、導入されていません。`/new-solution --tests gtest` で、後付けできます」と案内して止まる (ユーザーが望めば、そのコマンドへ)。
2. **足りないものを確認する (読み取りだけ):** 対象の層の DLL と、`<DLL名>Test` が、あるか。
   - **DLL はあるが、テスト exe がない:** `/new-solution --tests gtest` (後付け) の対象。案内する。
   - **対象の層の DLL がない** (例: `層: logic` で、データ層が必要になった): 次の 3. で、層を足す。
3. **案を示して、了承を得て、同梱のスクリプトで足す。** 自分で `.vcxproj` や `.sln` を手書きしない。
   ```bash
   python3 <このSkillのフォルダ>/scripts/add_layer.py "$SLN_DIR" DataLayer --tests gtest
   python3 <このSkillのフォルダ>/scripts/add_layer.py "$SLN_DIR" LogicLayer --tests gtest --uses DataLayer
   ```
   - `--tests gtest` (既定): DLL と、`<Name>Test` を足す。`--kind lib`: 静的ライブラリ。`--tests-only`: すでにある DLL に、テストだけを足す。
   - GoogleTest は、**すでにあるソリューションと、同じ方式**で足される (`--gtest auto`。`gtest` プロジェクトがあれば source、それ以外は **vcpkg**。旧 NuGet 方式 (nuget) は、v2.31.0 で廃止。`packages\` に旧方式のテストがあっても、新しいテストは vcpkg で、出力に `NOTE: … 旧 NuGet 方式 …` が出る)。vcpkg 方式では、`vcpkg.json` に gtest が入り、テスト exe に `main.cpp` が置かれる。
   - 名前の既定は `DataLayer` / `LogicLayer`。終了コード 3 (すでに存在) は、何も書かれていない。**既存のプロジェクトを、上書きしない。**
   - 層を足したら、`CLAUDE.md` の `- 層:` の行も、実際の構成に合わせる。
   - 出力の `GTEST_VCPKG: no-baseline` (vcpkg 方式): ウォッチャー経由で、`package_once.sh "$SLN_DIR" --timeout 1800 "vcpkg baseline" "vcpkg install"` を実行する (`add-package` Skill。初回のみ。2 回目以降は、キャッシュで速い)。
   - 出力の `GTEST_SOURCE: to-fetch` (source 方式): ウォッチャー経由で、取得する (`new-solution` Skill の `scripts/gtest_once.sh`。手順は、`/new-solution` の「GoogleTest の仕上げ」と同じ)。
4. **ベースラインを確認する (下記「手順」の 4. と同じ実行方法で、`build-test-loop` のスクリプトを使う):** ビルドが通り、**`PASSED`** になること。
   - `BUILD_FAILED`: エラーを読んで直す。ベースのアプリ自体の、もともとのエラーなら、直さずに、報告する。
   - `ENV_ERROR`: 出力先 (`x64\Debug\`)、GoogleTest の復元を確認して、ユーザーに報告する。
   - **ベースラインが緑になる前に、本物のテストを書かない。**
5. **メインから DLL を使う配線 (ProjectReference、インクルード) は、ここでは、しない。** 必要になったときに、ユーザーの了承を得て行う。

## 手順

### 0. 対象の層を決める
依頼の内容から、どの DLL (と、対応するテスト exe) に書くかを、決める。

| 対象 | 置く場所 | テストの書き方 |
|---|---|---|
| 業務ルール、計算、検証 | ロジック DLL / ロジックのテスト exe | データ層は、**フェイク** (`IxxxRepository` の、メモリ上の実装) に差し替える。実ファイルや DB に触れない |
| 保存、読み出し、外部とのやり取り | データ DLL / データのテスト exe | 実ファイルを使ってよいが、**一時フォルダに、テストごとに別のパスで作り、終了時 (`TearDown`) に必ず削除する** |
| 画面、メッセージ処理 | (テストしない) | UI 層。ロジックの切り出し案を示して止まる |

1 つの依頼が、複数の層にまたがる場合 (例: 計算ルールの追加と、保存形式の変更) は、**層ごとに、順番に、この手順を回す。** まとめて Red にしない (失敗の原因が、層をまたいで混ざるため)。

### 1. 仕様を、テストケースの一覧にする (コードを書く前)
**入力は、確定済みの仕様。** ユーザーが、先に、ブレインストーミング (`/brainstorm` など) で仕様を固めている場合は、その成果物 (仕様書のファイル、または、会話に出ている確定事項) を、読んで使う。
仕様書は、`/brainstorm` のメモ (`docs/ideas/`) を、`/update-from-ideas` が整理して作る、`docs/specs/<機能名>.md` (`状態: 確定`)。メモだけで、仕様書がなければ、`/update-from-ideas` を勧める。ユーザーが、仕様書のパスを示した場合と、`docs/specs/` に仕様書がある場合は、**それが、今回の依頼のものか、ユーザーに確認してから**使う。
仕様が固まっていない (`下書き`、`変更あり (要再確定)`、未決事項が残っている) 場合は、テストを書かずに、`/brainstorm` か `/update-from-ideas` を勧めて止まる。
(`/add-feature` から呼ばれた場合は、仕様書と計画は、すでに確認・承認済み。計画のテストケースを使う。)

仕様から、次の観点でテストケースを書き出し、**テキストで、ユーザーに見せる。** 仕様が曖昧な箇所は、推測せず、ここで質問する。
- 正常系 (代表的な入力)
- 境界値 (0、最小、最大、空、1件、上限の直前と直後)
- 異常系 (不正な入力、範囲外、null や空文字、期待する失敗の仕方: 戻り値か、例外か)
- バグ修正の場合: **そのバグを再現するテストを、最初の1件にする。**

ユーザーの依頼にケースが明記されている場合は、一覧の提示は短くてよい。ケースを勝手に増やさない (最大でも、1つの機能あたり 10 件程度)。

### 2. スタブを作る (本体側。コンパイルを通すためだけ)
テストが、本体の関数やクラスを呼ぶので、**宣言がないとビルドで落ちる。** ビルドで落ちるのは、Red ではない (仕様の失敗ではなく、書き方の失敗)。
そこで、本体 (xxx) に、**最小のスタブ**を置く。
- **バグ修正で、対象の実装が、すでにあるとき (テストが、本物の失敗で Red になるとき) は、スタブを置かない。** スタブは、**新しい関数・クラスがあるときだけ**置く (既存の実装を、スタブで置き換えると、実装を消す)。
- 宣言 (ヘッダ) と、仮の実装だけ。**本物のロジックを書かない。**
- 仮の実装は、「値を返すだけで、仕様を満たさない」ものにする (`return 0;`、`return {};`、`return false;` など)。
  テストが、たまたまスタブの値で通ることがないように、**期待値と異なる値**にする。
- 新しい `.cpp` / `.h` を作った場合は、そのプロジェクトの `.vcxproj` (と `.filters`) への追加が必要。**追加しないと、ビルドに含まれない。**
  `.vcxproj` を編集するときは、既存の文字コード (BOM の有無)・改行コードを変えず、該当する行だけを追加する。
- **DLL の場合: 新しいクラス・関数に、公開マクロ (`<NAME>_API`) を付ける** (既存のヘッダの、`class XXX_API Foo` の形に合わせる)。
  **付け忘れると、テスト exe のビルドが、リンクエラー (`LNK2019`) になる。** これは Red ではなく、スタブの不備。付けて、やり直す。
  - 公開マクロを付けるのは、テスト exe や UI から、直接使うクラス・関数だけ。ヘッダだけで完結するインターフェース (純粋仮想クラス) には、不要。

### 3. テストを書く (対象の層に対応する `<DLL名>Test` 側)
- 既存のテストの書き方 (ファイルの命名、`TEST` / `TEST_F`、`#include` の形) に合わせる。
- 1 つのテストで、1 つのことを確かめる。名前は、振る舞いが分かるようにする (例: `CalcTotal_Price100_Returns110`)。
- 期待値は、**仕様から導いた値を、直接、書く。** 実装の出力を、写さない (まだ実装がない)。
- 浮動小数点は、`EXPECT_DOUBLE_EQ` / `EXPECT_NEAR` を使い、許容誤差は、仕様から決める。
- 新しい `Test*.cpp` を作った場合は、**その層のテスト exe の** `.vcxproj` に追加する (2. と同じ注意)。別の層のテスト exe に、書かない。
- ロジックのテストでは、データ層の**実装 DLL を使わない** (フェイクを使う)。データ DLL の不具合が、ロジックのテストに混ざらないようにする。
- ファイルの文字コードと改行コードは、既存のファイルに合わせる。

### 4. Red を確認する (実行)
#### 4.0 ベースライン (Red の前に、1 回)
**既存のテストが、ある場合は、新しいテストを書く前 (スタブを置く前) の状態で、`build_test_once.sh` を 1 回実行し、結果 (`tests: N passed`、失敗しているテスト名) を、記録する。** 後の「正しい Red の条件」の 3・4 (既存のテストが、新たに落ちていないか / 前から失敗していたか) は、この記録と比べて、判断する。テストが 1 件もない (層を足した直後など) ときは、省く。

`build-test-loop` の同梱スクリプトを使う。自分で flag を作ったり、待機ループを書いたりしない。

```bash
bash <build-test-loop の Skill のフォルダ>/scripts/build_test_once.sh "$SLN_DIR" 300
```

`run_in_background: true` で実行し、**完了通知が来るまで、ファイルを読まず、再実行もしない** (理由と詳細は、`build-test-loop` の「実行 (1回分)」と同じ)。

結果の判断 (**ここが、このスキルの要点。**):

| 1行目 | 意味 | 次の行動 |
|---|---|---|
| `FAILED` | テスト失敗 | **失敗したテストの一覧と理由を読み、下記「正しい Red の条件」で確かめる** |
| `PASSED` | 全テスト成功 | **Red ではない。** 新しいテストが、実装なしで通っている。テストが空振りしている (期待値がスタブの値と同じ、アサーションがない)、または、機能がすでにある。**原因を調べて、ユーザーに報告する。実装には進まない** |
| `BUILD_FAILED` | ビルドエラー | テストかスタブの書き方の誤り。エラーを読んで直し、再実行する (下記の回数の上限に含める) |
| `ENV_ERROR` / `WATCHER_NOT_RUNNING` / `TIMEOUT` / `TEST_TIMEOUT` | 環境・実行の問題 | `build-test-loop` の表と同じ。ソースもテストも直さず、報告して停止 |

**新しいテストの、個別の状態は、`.claude-logs/test_summary.json` で確かめる** (画面の要約は、`tests:` が最大 5 件、`at:` が最大 3 件で切れる。`(+N more)` の分は、見えない)。**新しいテストが、偶然、スタブの値で通っていないか** (`FAILED` の中に、新しいテストの名前が、すべて、含まれること) も、ここで確かめる。

#### 正しい Red の条件 (すべて満たすこと)
1. **新しく書いたテストが、すべて、アサーションの失敗 (`Expected` / `Which is`) で落ちている。** 値の食い違いが、仕様どおりの理由で出ている。
2. **クラッシュ、例外、アクセス違反、タイムアウトで落ちていない。** (スタブが、例外を投げる場合を除く)
3. **既存のテストが、新たに落ちていない。** 落ちている場合は、今回の変更 (スタブの追加) が、既存の動作を壊している。直してから、やり直す。
4. 実行前から失敗していた既存のテストが、ある場合は、今回の失敗と区別して、報告する。
5. **失敗が、対象の層のテスト exe だけに出ている。** 出力は、テスト exe ごとに、`=== xxxTest.exe ... ===` の見出しで区切られる。
   書いていない層のテスト exe が落ちている場合は、層をまたぐ影響 (例: インターフェースの変更が、別の層を壊した) なので、原因を調べて、報告する。

### 5. Red を報告し、テストを確定する
次を、簡潔に報告する。
- 書いたテストの一覧 (名前と、確かめていること)、それぞれの失敗の理由 (`Expected` と `Which is`)。
- 作った・変更したファイル (スタブ、テスト、`.vcxproj`)。
- 「この Red を、仕様として確定してよいか」を、ユーザーに確認する。**テストは、仕様の表明であり、ここで、人が、中身を確かめる最後の機会になる。**

ユーザーが、「実装まで続けて」と、最初から依頼している場合は、確認を待たずに、**6. に進んでよい。** それ以外は、確認を待つ。

### 6. Green へ引き渡す

**Green の完了条件 (新しいテストが、実際に実行されたこと):** `PASSED` の 2 行目の `tests: N passed` の N が、**ベースライン (下記の 4.0) の件数 + 今回、書いたテストの件数** であり、**新しいテストの名前が、実行結果に含まれる**こと。確かめ方 (読み取りだけ): `grep -l "<新しいテストの名前>" "$SLN_DIR/.claude-logs/test-results/"*` (GoogleTest の XML / MSTest の trx)。**含まれなければ、PASSED でも、完了ではない** (`.vcxproj` / `.csproj` への足し忘れ、`-TestExePattern` に合わない exe、フィルターで外れている、など。`PASSED` は「実行されたテストが、すべて通った」の意味でしかない)。
テストが確定したら、`build-test-loop` の手順で、実装して全テストを通す。**その時点から、テストは、凍結する。**
- **テストを確定したら、Green に進む前に、基準を作る:** `python3 -I ~/.claude/skills/build-test-loop/scripts/test_guard.py snapshot "$SLN_DIR"`。実装のあと (と、報告の前) に `check` を実行し、**error は、許可なしにしてはいけない変更**なので、元に戻すか、止まって確認する。warning / review は、理由を報告する。変更されたテストファイルの一覧は、報告の先頭に書く (`build-test-loop` の「テストの改変の検査」)。ユーザーが、テストの変更を承認したときだけ、`snapshot` をやり直す。
- `build-test-loop` の規則が、そのまま適用される: **テストの変更・削除・`DISABLED_` 化・アサーションを弱める、は、ユーザーの許可なしにしない。**
- **Green のあと、報告の前に、`test_guard.py audit "$SLN_DIR"`** (空洞なテストを探す)。中心の項目は、実装をわざと壊して確かめる (`build-test-loop` の `references/mutation-check.md`。了承を得て、必ず元に戻す。していなければ、「変異の確認は、していない」と報告)。
- 実装中に、テストの期待値が誤りだと分かった場合は、テストを直す前に、ユーザーに、理由 (どの仕様と矛盾するか) を添えて確認する。
- **UI テスト (`*.UITests`。`CLAUDE.md` に「UI テスト (FlaUI)」の節がある) は、このビルド → テストの流れに、含めない。** 遅く、アプリを起動し、制限時間を長く取る必要があるため、**ユーザーが求めたとき**だけ、`uitest_once.sh` で、別に実行する (`build-test-loop` の `references/ui-tests.md`)。**画面を、プロンプトで作りながら、UI テストを書いて、繰り返し実行するときは、`/ui-test-first`** (UI テストを先に書く)。通常のテストが `PASSED` になっても、UI テストは、自動では、実行しない。
- 通ったあとの整理 (リファクタリング) は、**テストを変えずに**行い、そのたびに、テストが通ることを、確認する。

## ループのルール
1. Red を作る工程 (2.〜4.) の再実行は、**最大3回**まで。3回目も、正しい Red にならなければ、状況と原因の候補を報告して停止する。
2. ソース (スタブ、テスト) を修正していない状態での、再実行はしない。
3. 無関係なリファクタリング、仕様にない機能のテストの追加は、しない。
4. 本物のロジックは、**Red が確定するまで書かない。** 先に実装して、あとからテストを書くことは、このスキルの目的に反する。
5. 修正時は、ファイルの文字コード (UTF-8 BOM の有無など) と改行コードを変えない。

## 完了時の確認 (変更の報告)
作業を終える前に (成功でも、停止でも)、変更したファイルを一覧して、報告に含める。ユーザーが、コミットの前に、`git diff` で、変更を確認できるようにするため。

1. 変更されたファイルの一覧を取る (読み取りだけ。ステージやコミットはしない)。
   ```bash
   git -c core.fileMode=false --no-optional-locks status --short
   ```
   - `-c core.fileMode=false` を付けるのは、WSL の git が、`/mnt/c` のファイルを実行権限つきと見て、ほぼ全ファイルを「変更あり」と表示してしまうため。
   - git のリポジトリでない場合や、コマンドが失敗した場合は、自分が編集したファイルの一覧で代える。
2. **このスキルでは、テストファイルを、必ず、新規作成か変更する。** 報告の先頭で、テストファイルの一覧と、ユーザーが確かめるべき点 (期待値が、仕様と合っているか) を、明示する。
3. 「コミット前に、`git diff` で変更を確認してください」と、一言添える。
4. **`git commit` と `git push` は、ユーザーの明示的な指示がない限り、実行しない。**
5. プロジェクトの設定 (`.claude/settings.json`) で、テストファイルの編集や、`git commit` に、確認が出る設定になっていることがある。
   このスキルは、テストファイルを書くので、**確認が出るのが、通常の動作。** 何を、なぜ、書くのかを、簡潔に説明する。拒否されたら、同じ操作を、別の方法 (別のツールやコマンド) で、行わない。

## 報告
- Red を確認できた: 書いたテストの数、失敗の理由の要約、変更したファイル、確認の依頼 (5.)。
- 正しい Red にならずに停止: 結果 (`PASSED` / 想定外の失敗など)、原因の候補、試した修正。
- 対象が UI 層で、止まった: 切り出しの案。

## トークン節約
- ログは、`build_test_once.sh` の出力 (失敗テスト名の一覧と詳細、最大60行) で足りる。足りないときだけ、`test_error.log` を読む。
- ソースは、必要な範囲だけを読む。既存のテストは、書き方を合わせるために、1〜2 ファイルだけ読む。
- 待機中・修正の合間に、経過の説明を書かない。
