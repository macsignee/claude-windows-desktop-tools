# アイデアを、正式な仕様書へ反映する (/update-from-ideas)

思いつきや変更案を、**仕様書に、整理された形で、取り込む。** 仕様書は、テストの元になるので、**勝手に書き換えない。** 仕分けと変更案を示して、承認を得てから、更新する。
**このコマンドでは、コード・テスト・プロジェクトは、変更しない。** 書いてよいのは、`docs/specs/` 配下のファイルと、`docs/ideas.md` だけ。

## アイデアの入口 (どれか)
1. **引数 (`$ARGUMENTS`) のテキスト:** パス以外の文字列は、アイデアとして扱う。
2. **`docs/ideas.md` (アイデアの受け皿):** 箇条書きで、思いついたことを、貯めておくファイル。ユーザーが、書き足してもよい (`- [ ] 税率を、設定から変えたい`)。
3. **この会話の中で出たアイデア:** 直前までの、やりとり (`/brainstorm` や `/add-feature` の途中で出たもの)。

どこから読むか、迷う場合は、ユーザーに確認する。アイデアが、見つからなければ、「反映するアイデアがありません」と伝えて、終わる。

## 手順

### 1. 対象の仕様書を決める
- 引数にパスがあれば、それ。なければ、`docs/specs/` の仕様書を一覧して、**どれに反映するか、ユーザーに確認する** (1 つだけなら、「これでよいか」)。
- 仕様書を読む。**状態 (`下書き` / `確定`)** と、**実装済みか** (同名の `.plan.md` がある、対応するテストが、ソリューション内にある) を、確認する。

### 2. アイデアを、仕分ける
アイデア 1 件ごとに、次のいずれかに分類して、**理由を 1 行**添える。

| 分類 | 意味 | 扱い |
|---|---|---|
| **取り込む** | この機能の仕様として、追加・変更する | 仕様書の、どの節を、どう変えるかを示す |
| **保留** | 面白いが、今回は、決めきれない・時期尚早 | 仕様書の「未決事項」か、`docs/ideas.md` に残す |
| **別機能** | この機能の範囲を超える | `docs/ideas.md` に残す (`/brainstorm` で、別の仕様書に) |
| **却下** | すでに仕様と矛盾する・不要 | 理由を添えて、記録しない (ユーザーが、記録を望めば、スコープ外に書く) |

- **1 つの仕様は、小さく保つ** (テストが 5〜10 件の大きさ)。取り込むと大きくなりすぎる場合は、「別機能」を勧める。
- **既存の仕様と、矛盾するアイデア**は、そのことを明示して、どちらを採るか、ユーザーに確認する。

### 3. 変更案を示して、承認を得る (**必ず止まる**)
次の形で、画面に示す。**承認が出るまで、ファイルを、何も変えない。**

```
## 反映の案: <機能名> (docs/specs/xxx.md、状態: 確定 / 実装済み)

取り込む:
 1. <アイデア> → [具体例] に 1 件追加: 「100円 x 3, 税率 8% → 324」
 2. <アイデア> → [境界値と異常系] を変更: 「数量 0 → 例外」→「数量 0 → 無視」
保留: ...  別機能: ...  却下: ...

影響 (実装済みの場合):
 - 変更するテスト: TestOrderService.cpp の Total_... (期待値が変わる)
 - 追加するテスト: ...
 - 変更する実装: OrderService::Total
```

「この内容で、仕様書を更新してよいですか?」と聞いて、**返事を待つ。** (AskUserQuestion が使えるなら、「承認 / 修正 / 中止」を選択肢にしてよい。)

### 4. 仕様書を更新する
承認された内容だけを、仕様書に反映する。
- **変更は、該当する節だけ。** 仕様書の、ほかの部分を、書き換えない。形式は、`/brainstorm` の仕様書の形のまま。
- 末尾の **`## 変更履歴`** に、1 行追加する: `- YYYY-MM-DD: <変更の要点> (<取り込んだアイデア>)`。節がなければ、作る。
- **状態:**
  - 実装前の仕様 (`下書き`) → そのまま。
  - **`確定` の仕様に、取り込む変更が入った → 状態を `変更あり (要再確定)` にする。** 内容を要約して、ユーザーに、**再確定してよいか聞く。** 「確定」の返事があれば、`確定` に戻す。
  - 未決事項が残っている間は、`確定` に戻さない。
- 保留と別機能のアイデアは、`docs/ideas.md` に残す (取り込んだものは、`- [x]` にして、行き先を添える)。ファイルがなければ、作る。
- UTF-8、BOM なし、改行は LF。

### 5. 実装済みの仕様の場合: 次の行動を示す
**コードやテストは、ここでは、変更しない。** 仕様書の変更で、影響を受けるテストと実装を、一覧にして示し、
**「`/add-feature docs/specs/<名前>.md` で、変更分を、テスト先行で、実装できます」**と案内する。自動で、進まない。
(変更分の計画は、`/add-feature` が、仕様書の変更履歴と、既存のテストとの差分から作る。)

## 終わり方
- 更新した仕様書のパスと、変更の要点 (取り込んだ件数、保留・別機能・却下の件数) を、短く示す。
- 状態が `確定` なら、次の `/add-feature` を案内する。`変更あり (要再確定)` / `下書き` なら、残っている確認事項を示す。

## しないこと
- 承認なしの、仕様書の更新。
- コード、テスト、`.vcxproj` の変更。
- アイデアの、勝手な追加・拡大解釈 (ユーザーの言葉を、そのまま、仕様の形に直す。足りない点は、質問する)。
- 仕様書の、無関係な部分の書き換え。
- `git commit` / `git push`。
