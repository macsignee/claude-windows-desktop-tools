# アイデアを、整理して、正式な仕様書にする (/update-from-ideas)

```
/brainstorm (メモ) → /update-from-ideas (整理して、正式な仕様書) → (/new-solution) → /add-feature (実装)
```

思いつきやメモを、**テストの元になる、正式な仕様書**に、整理して取り込む。仕様書は、実装とテストの根拠なので、**勝手に書かない。** 仕分けと案を示して、承認を得てから、書く。
**このコマンドでは、コード・テスト・プロジェクトは、変更しない。** 書いてよいのは、`docs/specs/` と `docs/ideas/` 配下のファイルと、`docs/ideas.md` だけ。

## 入力 (どれか。複数でもよい)
1. **`docs/ideas/<機能名>.md`:** `/brainstorm` のメモ。**メモから、仕様書を、新しく作る**のが、主な使い方。
2. **引数 (`$ARGUMENTS`) のテキスト:** パス以外の文字列は、アイデアとして扱う。
3. **`docs/ideas.md` (アイデアの受け皿):** 箇条書きで、思いついたことを、貯めておくファイル (`- [ ] 税率を、設定から変えたい`)。
4. **この会話の中で出たアイデア:** 直前までの、やりとり。

どこから読むか、迷う場合は、ユーザーに確認する。アイデアが、見つからなければ、「反映するアイデアがありません」と伝えて、終わる。

## モードの判定

| 状態 | モード |
|---|---|
| メモ (`整理: 未`) があり、対応する仕様書が、まだない | **A. 新規作成** (メモ → 仕様書) |
| 仕様書がすでにある + アイデア | **B. 更新** (アイデア → 仕様書の変更) |

## A. 新規作成 (メモ → 正式な仕様書)

1. **メモを読む。** 複数あれば、**どれを整理するか、ユーザーに確認する** (1 つだけなら、「これでよいか」)。`整理: 済` のメモは、対象にしない (ユーザーが、明示した場合を除く)。
2. **仕分ける。** メモの項目を、次のとおりに、分ける。理由を 1 行添える。

   | 分類 | 意味 | 扱い |
   |---|---|---|
   | **取り込む** | この機能の仕様にする | 仕様書の、該当する節に書く |
   | **保留** | 決めきれない・時期尚早 | 仕様書の「未決事項」に書く (**未決が残る間は、`確定` にしない**) |
   | **別機能** | この機能の範囲を超える | `docs/ideas.md` に残す (`/brainstorm` で、別のメモに) |
   | **却下** | 矛盾する・不要 | 理由を添えて、記録しない |

   - **1 つの仕様は、小さく保つ** (テストが 5〜10 件の大きさ)。大きくなりすぎる場合は、「別機能」を勧める。
   - メモの内容が、矛盾している (例: 具体例が、ルールと合わない) 場合は、指摘して、どちらを採るか、確認する。**足りない点は、推測で埋めず、質問する** (1 回に 1 つ)。
3. **仕様書の草案を示して、承認を得る (必ず止まる)。** 下の「仕様書」の形で、**草案の全文**を、画面に示す。**承認が出るまで、ファイルを、何も作らない。**
   - 草案には、**具体例・境界値・異常系が、テストケース (テストなしなら、手動の確認項目) に落とせる具体さか**を、点検した結果を添える (曖昧な項目は、指摘する)。
   - 「この内容で、仕様書を作ってよいですか?」と聞いて、返事を待つ (AskUserQuestion が使えるなら、「承認 / 修正 / 中止」)。
4. **仕様書を書く:** `docs/specs/<機能名>.md`。状態は、`下書き`。
   - **未決事項が 0 件で、ユーザーが「確定」と言ったら、`確定` にする。** 未決が残っていれば、`下書き` のまま、残りの質問を示す。
   - メモの `整理:` の行を、`済 (→ docs/specs/<名前>.md)` に更新する。メモは、削除しない。
   - 別機能・保留のうち、仕様書に入れないものは、`docs/ideas.md` に残す。
5. **ソリューションがない場合: 構成案を出す** (下の「構成案」)。

## B. 更新 (アイデア → 既存の仕様書)

1. **対象の仕様書を決める。** 引数にパスがあれば、それ。なければ、`docs/specs/` を一覧して、ユーザーに確認する。**状態** (`下書き` / `確定`) と、**実装済みか** (同名の `.plan.md`、対応するテストが、ソリューション内にある) を、確認する。
2. **アイデアを、仕分ける** (A. の 2. と同じ分類。矛盾するものは、どちらを採るか、確認する)。
3. **変更案を示して、承認を得る (必ず止まる)。** 承認が出るまで、ファイルを、何も変えない。
   ```
   ## 反映の案: <機能名> (docs/specs/xxx.md、状態: 確定 / 実装済み)

   取り込む:
    1. <アイデア> → [具体例] に 1 件追加: 「100円 x 3, 税率 8% → 324」
    2. <アイデア> → [境界値と異常系] を変更: 「数量 0 → 例外」→「数量 0 → 無視」
   保留: ...  別機能: ...  却下: ...

   影響 (実装済みの場合):
    - 変更するテスト: TestOrderService.cpp の Total_... (期待値が変わる)   ※ テストなしなら、「変えるべき手動確認項目」
    - 追加するテスト: ...
    - 変更する実装: OrderService::Total
   ```
4. **仕様書を更新する。** 承認された内容だけを、**該当する節だけ**に反映する。
   - 末尾の **`## 変更履歴`** に、1 行追加する: `- YYYY-MM-DD: <変更の要点> (<取り込んだアイデア>)`。節がなければ、作る。
   - **`確定` の仕様に、取り込む変更が入った → 状態を `変更あり (要再確定)` にする。** 要約して、**再確定してよいか聞く。** 「確定」の返事で `確定` に戻す。未決事項が残っている間は、戻さない。
   - 保留と別機能は、`docs/ideas.md` に残す (取り込んだものは、`- [x]` にして、行き先を添える)。
5. **実装済みの仕様の場合:** **コードやテストは、ここでは、変更しない。** 影響を受けるテストと実装を、一覧にして示し、「`/add-feature docs/specs/<名前>.md` で、変更分を、実装できます」と案内する。自動で、進まない。

## 仕様書

保存先: `docs/specs/<機能名 (英小文字とハイフン)>.md` (フォルダがなければ作る)。UTF-8、BOM なし、改行は LF。**`/add-feature` は、この形を前提に、読む。**

```markdown
# <機能名>

- 状態: 下書き | 確定 | 変更あり (要再確定)
- 日付: YYYY-MM-DD
- 元: docs/ideas/<名前>.md (メモから作った場合)

## 目的
## 置く層
(ロジック層 / データ層 / UI 層。テスト対象と、そうでないものを区別する)

## 具体例
| 入力 | 期待する出力 | 補足 |
|---|---|---|

## ルール
## 境界値と異常系
| ケース | 振る舞い |
|---|---|

## インターフェース案 (仮)
## スコープ外
## 未決事項
(あれば。**未決事項が残っている間は、状態を「確定」にしない**)

## 構成案 (ソリューションがまだないときだけ)
(**`/new-solution --spec` が読む。下の 7 行の形を、守る。** `--spec` は、**仕様書そのもの (と、「元:」のメモ)** を、新しいソリューションの `docs/` に取り込み、**「具体例」「境界値と異常系」の表から、テストケースの種 `docs/specs/<名前>.cases.md` を作る** (表の行が、そのまま、テストの元になる。**表が空だと、種も空になる**)。 値は、最初の空白までの 1 語。後ろは、根拠。決まっていない項目は、`未定` と書く)
- メインの種類: console (画面が要らないため)
- 層: logic,data (計算と保存がある)
- 層の種類: dll
- テスト: 未定 (ユーザーに確認する。TDD の練習なら gtest)
- 名前空間: tdd
- UIテスト: none (画面がない、または、画面の操作の自動確認は、まだ要らない)
- TFM: 未定 (.NET のときだけ。決まっていなければ、既定の net10.0)

## 変更履歴
(確定後の変更は、このコマンドが追記する)
```

## 構成案 (ソリューションがない場合。新規作成のとき)

**仕様が先。** 仕様書ができたあとに、その仕様に合った構成を、提案する。**ソリューションは、ここでは作らない** (作成は、`/new-solution`)。

| 項目 | 決め方 |
|---|---|
| メインの種類 | 仕様に、**画面が要るか**で決める。画面なし → コンソールか DLL / 静的ライブラリ。画面あり → **WPF (MVVM、.NET)**、**WinForms (MVP、.NET)**、MFC (SDI / MDI / ダイアログベース)、Win32 のどれか。画面なしで .NET なら **C# クラスライブラリ (`csharp-dll`)**。**WPF / WinForms / MFC のどれかは、ユーザーが決める** (既存の資産、チームの技術、配布の条件。仕様からは決まらない)。MFC は、ドキュメントを 1 つ扱う → SDI、複数を同時に開く → MDI、ドキュメントなし (設定・ツール型) → ダイアログベース |
| 層 | 仕様の「置く層」から。ロジック・データの、どちらを使うか (**WPF は、画面の状態・コマンドがあれば、`viewmodel` も**。テストしたい ViewModel は、WPF 非依存のライブラリに置く。**WinForms と `csharp-dll` は、`logic` と `data` だけ**。`viewmodel` は書かない)。層の名前を決めるなら、`logic:OrderLogic,data:OrderData` のように、**空白なし**で書く |
| テスト | **仕様からは、決まらない。** ユーザーに確認する (TDD の練習が目的なら、C++ は `gtest`、.NET (WPF / WinForms / C# DLL) は `mstest` を勧める) |
| UI テスト | 画面あり (WPF / WinForms) で、**画面の操作を自動で確かめたい**ときだけ `flaui`。それ以外は `none`。ユーザーに確認する (`csharp-dll` には、使えない) |
| TFM | .NET のみ。決まっていなければ、書かない (既定の `net10.0`)。 |
| 名前空間 | フォルダ名の頭文字は、読みにくいことがある。短い名前 (例: `tdd`) を、提案する |

- 案と根拠を示し、仕様書の「構成案」の節に書く (承認を得てから)。**節の形は、上の仕様書の様式のとおり** (`- メインの種類:` / `- 層:` / `- 層の種類:` / `- テスト:` / `- 名前空間:`。`/new-solution --spec` が、機械的に読む)。
  メインの種類の値: `wpf` / `winforms` / `csharp-dll` / `mfc` (SDI) / `mfc-mdi` / `mfc-dialog` / `win32` / `console` / `dll` / `lib`。層: `none` / `logic` / `data` / `logic,data` (**`wpf` のときは、`viewmodel` も、組み合わせられる**。例: `data,logic,viewmodel`。`winforms` / `csharp-dll` は `logic` / `data` だけ)。層の種類: `dll` / `lib` (C++ のみ。.NET では、書かない)。テスト: `none` / `gtest` (C++) / `mstest` (.NET) / `未定`。UIテスト: `none` / `flaui` (`wpf` / `winforms`、と C++ の GUI)。TFM: `net10.0` など (.NET のみ。C++ では、書かない)。
- **テストは、ユーザーが決めたら、その値を書く。** 決まっていなければ `未定` (`/new-solution` が、質問する)。
- **そのまま実行できる、`/new-solution --spec docs/specs/<名前>.md` のコマンドを示す** (引数で、明示して上書きもできる)。自動で、実行しない。
- ソリューションがすでにある場合は、この節は、出さない。

## 終わり方
- 書いた仕様書のパスと、要点 (取り込んだ件数、保留・別機能・却下の件数、未決の件数) を、短く示す。
- 状態が `確定` なら: ソリューションがなければ、**`/new-solution` (構成案のコマンド)**、あれば、**`/add-feature docs/specs/<名前>.md`** を案内する。
- `下書き` / `変更あり (要再確定)` なら、残っている確認事項を示す。

## しないこと
- 承認なしの、仕様書の作成・更新。
- コード、テスト、`.vcxproj`、ソリューションの作成や変更。
- アイデアの、勝手な追加・拡大解釈 (ユーザーの言葉を、そのまま、仕様の形に直す。足りない点は、質問する)。
- 仕様書の、無関係な部分の書き換え。
- `git commit` / `git push`。
