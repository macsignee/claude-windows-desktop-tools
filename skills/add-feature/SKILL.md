# 機能の追加 (/add-feature): 計画 → 承認 → テスト先行 → 実装 → 検証

`/brainstorm` で確定した仕様を、TDD で実装する、司令塔のコマンド。
実際のテストの書き方・Red の判定は **`cpp-test-first`**、実装して通す工程は **`cpp-build-test-loop`** の手順に従う (ここには、書き直さない)。
このコマンドは、**どこで止まって、ユーザーに確認するか (ゲート)** と、順番を決める。

用途は、プロトタイプと、TDD の練習。小さく、1 サイクルずつ、進める。

## 前提
- カレントが、ソリューションフォルダ (`.sln` / `.slnx` があるフォルダ) であること。以降、これを `$SLN` とする。
- ユーザーが、`run_watcher.cmd` を起動済みであること (なければ、ビルドの段階で `WATCHER_NOT_RUNNING` になる。その時点で、起動を依頼する)。

## 手順

### 0. 仕様書を特定する
- 引数 (`$ARGUMENTS`) にパスがあれば、それを読む。なければ、`docs/specs/` の、`状態: 確定` の仕様書を一覧して、**どれか、ユーザーに確認する** (1 つだけなら、「これでよいか」と聞く)。
- **仕様書がない、または `状態: 下書き` / `変更あり (要再確定)` / 未決事項が残っている場合は、実装に進まない。** `/brainstorm` か `/update-from-ideas` で、固めるよう案内して、止まる。
- 仕様書に `変更履歴` があり、**すでに実装・テストがある場合**は、変更分 (変更履歴と、既存のテストの差) だけを、計画にする。全部を、作り直さない。
- 仕様書を読んで、**どの層に、何を作るか**を把握する (ロジック層 / データ層 / UI 層)。

### 1. 現状を確認する (読み取りだけ)
- 必要な DLL とテスト exe (`<DLL名>` と `<DLL名>Test`) が、あるか。ないものは、計画に、`cpp-test-first` の「セットアップ」を含める。
- すでにあるコード (関連するクラス・インターフェース) を、必要な範囲だけ読む。長く調べない。

### 2. 計画を作って、ユーザーに見せる
**この時点では、ファイルを、何も作らない・変えない。** 計画は、次の形で、画面に示す。

```
## 計画: <機能名>   (仕様書: docs/specs/xxx.md)

セットアップ: (必要なら) DataLayer / DataLayerTest の作成 ... / なし

タスク (依存される側から。データ層 → ロジック層 → UI):
 1. [データ層] <何を作るか>
    - テストケース: (仕様書の具体例・境界値・異常系との対応)
    - 公開するもの (シグネチャ): ...
    - 触るファイル: ...
 2. [ロジック層] ...
 3. [UI 層] (仕様に、画面があれば) ...  ※ テストはしない。ビルドと、目視の確認

やらないこと: (仕様書のスコープ外 + 今回は触らないファイル)
確認の方法: 全テスト PASSED + (UI があれば) 手動で、○○を確認
```

- 1 タスクは、**1 つの層で、テスト 3〜8 件**を目安にする。大きければ、分ける。
- 計画は、`docs/specs/<機能名>.plan.md` にも保存してよい (承認後に、保存する)。

### 3. 承認のゲート (**必ず止まる**)
計画を見せたら、**「この計画で進めてよいですか?」**と聞いて、**返事を待つ。** (AskUserQuestion が使えるなら、「承認 / 修正 / 中止」を選択肢にしてよい。)
- **承認が出るまで、プロジェクト・テスト・ソースを、作らない・変えない。**
- 修正の指示があれば、計画を直して、再び見せる。
- ここでの承認は、**計画に書いた範囲の、ファイルの作成と編集**に対するもの。計画にないものは、実行中に、改めて確認する。

### 4. セットアップ (計画に含めた場合だけ)
`cpp-test-first` の「セットアップ」に従う。**ベースライン (ビルド成功 + `PASSED`) が緑になるまで、次へ進まない。**
(NuGet の復元など、ユーザーの作業が必要なときは、依頼して、待つ。)

### 5. タスクごとに、Red → 確認 → Green (計画の順に、1 タスクずつ)
各タスクで、次の順に進める。**1 つのタスクが終わるまで、次のタスクに、手をつけない。**

1. **Red (テスト先行):** `cpp-test-first` の手順 1〜5 に従う (テストケースの一覧は、計画のものを使う。スタブ、テスト、Red の判定)。
2. **テストの確認のゲート (止まる):** Red の結果 (書いたテストと、失敗の理由) を示して、**「このテストが、仕様どおりか」を、ユーザーに確認する。**
   - 計画の承認とは別に、**テストの中身は、必ず、確認を待つ** (テストは、仕様の表明。間違いに気づける、最後の機会)。
   - 修正の指示があれば、テストを直して、Red を、やり直す。
3. **Green (実装):** 確認が出たら、`cpp-build-test-loop` の手順で、実装して `PASSED` にする。**テストは、凍結する** (許可なしに、変更・削除・無効化しない)。
4. **リファクタリング (必要なときだけ):** テストを変えずに整理し、そのたびに、`PASSED` を確認する。
5. **サイクルの記録 (練習用):** 1〜2 行で、「Red: どのテストが、どう失敗したか / Green: 何を実装して通ったか」を、メモしておく (最後の報告に使う)。

UI 層のタスクは、テストをしない。計画した最小の配線 (例: ProjectReference、メニューやボタンからの呼び出し) だけを行い、**ビルドが通ること**を確認して、ユーザーに、手動での確認を依頼する。

### 6. 検証 (全体)
1. `cpp-build-test-loop` のスクリプトで、**ソリューション全体のビルドと、全テスト exe の実行**を行い、`PASSED` を確認する (ベースの MFC アプリも含む)。
2. **仕様書と突き合わせる:** 仕様書の、具体例・境界値・異常系の、**1 件ごとに、対応するテストがあるか**を、一覧にする。対応がないものは、報告する (追加するか、ユーザーに確認)。
3. 確認できていないこと (UI の目視、実行時の動作) を、明示する。**「検証した」と言えるのは、実際に実行して、結果を見たものだけ。**

### 7. 報告して、終わる
- 作った・変更したファイル (**テストファイルを、先頭で明示**)、タスクごとのサイクルの記録 (Red → Green)、検証の結果、仕様書との対応表、未確認のこと。
- 「コミット前に、`git diff` で、変更を確認してください」と添える。
- **`git commit` / `git push` は、ユーザーの明示的な指示がない限り、しない。**
- 次の機能に進む場合は、`/brainstorm` から。

## ルール
- **ゲートは、飛ばさない:** 計画の承認 (3.)、テストの確認 (5.2) の 2 つ。ユーザーが「ゲートなしで、最後まで」と、明示した場合だけ、省略してよい (その場合も、最後の報告は、省略しない)。
- **計画にないことを、しない。** 必要になったら、止まって、ユーザーに確認する (計画を、直す)。
- **仕様が変わるときは、実装を止めて、仕様書を直す** (`/update-from-ideas`。大きく変わるなら `/brainstorm`)。コードやテストだけを、先に変えない。
- **実装中に出た、思いつき・拡張案は、実装しない。** `docs/ideas.md` に、1 行で書き留めて、今のタスクを続ける (あとで、`/update-from-ideas` で、仕分ける)。
- **失敗で止まるとき:** 5 回直しても通らない、環境エラー (`ENV_ERROR`)、ウォッチャー未起動、などは、`cpp-build-test-loop` の規則どおり、止まって、報告する。
- ファイルの文字コードと改行は、既存に合わせる。無関係なリファクタリングは、しない。
- 待機中・修正の合間に、経過の説明を書かない (ゲートの質問と、最後の報告だけ、しっかり書く)。
