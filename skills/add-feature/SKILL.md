# 機能の追加 (/add-feature): 計画 → 承認 → テスト先行 → 実装 → 検証

`/brainstorm` (メモ) → `/update-from-ideas` (整理して、正式な仕様書) で、確定した仕様を、実装する、司令塔のコマンド。**テストがあるソリューションでは TDD、ないソリューションでは、ビルド確認で進める。**
実際のテストの書き方・Red の判定は **`cpp-test-first`**、実装して通す工程は **`cpp-build-test-loop`** の手順に従う (ここには、書き直さない)。
このコマンドは、**どこで止まって、ユーザーに確認するか (ゲート)** と、順番を決める。

用途は、プロトタイプと、TDD の練習。小さく、1 サイクルずつ、進める。

## 前提
- カレントが、ソリューションフォルダ (`.sln` / `.slnx` があるフォルダ) であること。以降、これを `$SLN` とする。
- **ソリューションがない場合は、実装に進まない。** `/new-solution` で、先に作るよう案内して止まる。
- **`CLAUDE.md` の設定を読む** (`- 層:` / `- テスト:`)。なければ、構造から判定する (`*Test` プロジェクトと GoogleTest の有無)。判定できなければ、ユーザーに確認する。

  | 設定 | 進め方 |
  |---|---|
  | `テスト: あり (GoogleTest)` | 計画 → 承認 → **テスト先行 (Red) → テストの確認 → 実装 (Green)** → 検証 |
  | `テスト: なし` | 計画 → 承認 → **実装 → ビルド確認 → 手動確認** → 報告 (Red / Green は、ない) |

- ユーザーが、`run_watcher.cmd` を起動済みであること (なければ、ビルドの段階で `WATCHER_NOT_RUNNING` になる。その時点で、起動を依頼する)。

## 手順

### 0. 仕様書を特定する
- 引数 (`$ARGUMENTS`) にパスがあれば、それを読む。なければ、`docs/specs/` の、`状態: 確定` の仕様書を一覧して、**どれか、ユーザーに確認する** (1 つだけなら、「これでよいか」と聞く)。
- **仕様書がない、または `状態: 下書き` / `変更あり (要再確定)` / 未決事項が残っている場合は、実装に進まない。** **`/brainstorm` のメモ (`docs/ideas/`) だけがあって、仕様書がない場合は、`/update-from-ideas` で、整理して、仕様書にするよう案内する。** メモがない場合は、`/brainstorm` から。
- 仕様書に `変更履歴` があり、**すでに実装・テストがある場合**は、変更分 (変更履歴と、既存のテストの差) だけを、計画にする。全部を、作り直さない。
- 仕様書を読んで、**どの層に、何を作るか**を把握する (ロジック層 / データ層 / UI 層)。

### 1. 現状を確認する (読み取りだけ)
- **改行コードの規則 (`.gitattributes`) の確認 (1 回だけ。作業を止めない):** `new-solution` Skill の `scripts/new_solution.py "$PWD" --check-git` を実行する (読み取りだけ)。
  **`GITATTRIBUTES: propose` のときだけ**、短く提案する (追加する / 今回は見送る / 今後も見送る)。ほかの状態では、何も言わない。手順の詳細は、`/new-solution` の「C. 改行コードの規則の確認と追加」。
  **追加するなら、機能の作業を始める前に行う** (あとから足すと、報告の `git diff` に、改行だけの差分が混ざるため)。git のステージ・コミットは、しない。
- 仕様が置く層 (ロジック / データ) の DLL が、あるか。**ない場合は、計画に「層の追加」を含める** (ユーザーに確認。名前は既定の `LogicLayer` / `DataLayer`)。
- **テストあり:** 各 DLL に、`<DLL名>Test` があるか。ない DLL は、計画に、`cpp-test-first` の「セットアップ」(層・テストの追加) を含める。
- **テストなし:** テストの確認はしない。仕様が、テストを必要とするなら、`/new-solution --tests gtest` を案内する (勝手に、導入しない)。
- すでにあるコード (関連するクラス・インターフェース) を、必要な範囲だけ読む。長く調べない。

### 2. 計画を作って、ユーザーに見せる
**この時点では、ファイルを、何も作らない・変えない。** 計画は、次の形で、画面に示す。

```
## 計画: <機能名>   (仕様書: docs/specs/xxx.md)

モード: テストあり (TDD) / テストなし (ビルド確認)
セットアップ: (必要なら) 層の追加 (DataLayer ...) と、そのテスト / なし

タスク (依存される側から。データ層 → ロジック層 → UI):
 1. [データ層] <何を作るか>
    - テストケース (テストあり) / 手動の確認項目 (テストなし): (仕様書の具体例・境界値・異常系との対応)
    - 公開するもの (シグネチャ): ...
    - 触るファイル: ...
 2. [ロジック層] ...
 3. [UI 層] (仕様に、画面があれば) ...  ※ テストはしない。ビルドと、目視の確認

やらないこと: (仕様書のスコープ外 + 今回は触らないファイル)
確認の方法: (テストあり) 全テスト PASSED / (テストなし) ビルド成功 + 手動で、○○を確認  + (UI があれば) 手動で、○○を確認
```

- 1 タスクは、**1 つの層で、テスト 3〜8 件 (テストなしなら、確認項目 3〜8 件)** を目安にする。大きければ、分ける。
- 計画は、`docs/specs/<機能名>.plan.md` にも保存してよい (承認後に、保存する)。

### 3. 承認のゲート (**必ず止まる**)
計画を見せたら、**「この計画で進めてよいですか?」**と聞いて、**返事を待つ。** (AskUserQuestion が使えるなら、「承認 / 修正 / 中止」を選択肢にしてよい。)
- **承認が出るまで、プロジェクト・テスト・ソースを、作らない・変えない。**
- 修正の指示があれば、計画を直して、再び見せる。
- ここでの承認は、**計画に書いた範囲の、ファイルの作成と編集**に対するもの。計画にないものは、実行中に、改めて確認する。

### 4. 層・テストの追加 (計画に含めた場合だけ)
同梱の `add_layer.py` (`cpp-test-first` の「セットアップ」) で、層を足す。**テストあり** なら `--tests gtest` (DLL + `<DLL名>Test`)、**テストなし** なら `--tests none` (DLL だけ)。`CLAUDE.md` の `- 層:` の行も、合わせる。
**ベースライン (ビルド成功、テストありなら `PASSED`) が緑になるまで、次へ進まない。** (NuGet の復元など、ユーザーの作業が必要なときは、依頼して、待つ。)

### 5. タスクごとに、Red → 確認 → Green (テストあり。計画の順に、1 タスクずつ)
各タスクで、次の順に進める。**1 つのタスクが終わるまで、次のタスクに、手をつけない。**

1. **Red (テスト先行):** `cpp-test-first` の手順 1〜5 に従う (テストケースの一覧は、計画のものを使う。スタブ、テスト、Red の判定)。
2. **テストの確認のゲート (止まる):** Red の結果 (書いたテストと、失敗の理由) を示して、**「このテストが、仕様どおりか」を、ユーザーに確認する。**
   - 計画の承認とは別に、**テストの中身は、必ず、確認を待つ** (テストは、仕様の表明。間違いに気づける、最後の機会)。
   - 修正の指示があれば、テストを直して、Red を、やり直す。
3. **Green (実装):** 確認が出たら、`cpp-build-test-loop` の手順で、実装して `PASSED` にする。**テストは、凍結する** (許可なしに、変更・削除・無効化しない)。
4. **リファクタリング (必要なときだけ):** テストを変えずに整理し、そのたびに、`PASSED` を確認する。
5. **サイクルの記録 (練習用):** 1〜2 行で、「Red: どのテストが、どう失敗したか / Green: 何を実装して通ったか」を、メモしておく (最後の報告に使う)。

### 5b. テストなしの場合: タスクごとに、実装 → ビルド確認 → 手動確認
**テスト先行は、しない。** Red / Green も、ない。1 つのタスクが終わるまで、次に進まない。
1. **実装する** (計画に書いた範囲だけ)。新しい `.cpp` / `.h` は、`.vcxproj` (と `.filters`) に追加する。DLL の公開 (`<NAME>_API`) を付ける。
2. **ビルドする:** `cpp-auto-build` の手順で、`SUCCESS` になるまで、直す。
3. **手動の確認項目 (ゲート。止まる):** 仕様書の、具体例・境界値・異常系を、**確認項目の一覧**にして、ユーザーに、実際に動かして確認してもらう。
   **ビルドが通ることは、仕様を満たすことの証明ではない。** 確認できていない項目は、「未確認」として残す。
4. 確認で見つかった不具合は、直して、2. からやり直す。

UI 層のタスクは、テストをしない。計画した最小の配線 (例: ProjectReference、メニューやボタンからの呼び出し) だけを行い、**ビルドが通ること**を確認して、ユーザーに、手動での確認を依頼する。

### 6. 検証 (全体)
1. **テストあり:** `cpp-build-test-loop` のスクリプトで、**ソリューション全体のビルドと、全テスト exe の実行**を行い、`PASSED` を確認する (メインも含む)。
   **テストなし:** `cpp-auto-build` で、ソリューション全体のビルドが `SUCCESS` であることを確認する。
2. **仕様書と突き合わせる:** 仕様書の、具体例・境界値・異常系の、**1 件ごとに、対応するテスト (テストなしなら、手動確認の結果) があるか**を、一覧にする。対応がないものは、報告する (追加するか、ユーザーに確認)。
3. 確認できていないこと (UI の目視、実行時の動作) を、明示する。**「検証した」と言えるのは、実際に実行して、結果を見たものだけ。**

### 7. 報告して、終わる
- 作った・変更したファイル (**テストファイルを、先頭で明示**)、タスクごとのサイクルの記録 (Red → Green)、検証の結果、仕様書との対応表、未確認のこと。
- 「コミット前に、`git diff` で、変更を確認してください」と添える。
- **`git commit` / `git push` は、ユーザーの明示的な指示がない限り、しない。**
- 次の機能に進む場合は、`/brainstorm` (メモ) → `/update-from-ideas` (仕様書) から。

## ルール
- **ゲートは、飛ばさない:** 計画の承認 (3.)、テストの確認 (5.2。テストなしなら、手動確認 5b.3) の 2 つ。ユーザーが「ゲートなしで、最後まで」と、明示した場合だけ、省略してよい (その場合も、最後の報告は、省略しない)。
- **計画にないことを、しない。** 必要になったら、止まって、ユーザーに確認する (計画を、直す)。
- **仕様が変わるときは、実装を止めて、仕様書を直す** (`/update-from-ideas`。大きく変わるなら `/brainstorm`)。コードやテストだけを、先に変えない。
- **実装中に出た、思いつき・拡張案は、実装しない。** `docs/ideas.md` に、1 行で書き留めて、今のタスクを続ける (あとで、`/update-from-ideas` で、仕分ける)。
- **失敗で止まるとき:** 5 回直しても通らない、環境エラー (`ENV_ERROR`)、ウォッチャー未起動、などは、`cpp-build-test-loop` の規則どおり、止まって、報告する。
- ファイルの文字コードと改行は、既存に合わせる。無関係なリファクタリングは、しない。
- 待機中・修正の合間に、経過の説明を書かない (ゲートの質問と、最後の報告だけ、しっかり書く)。
