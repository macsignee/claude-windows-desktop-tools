# C++ 自動ビルド & エラー修正ループ

サンドボックスから msbuild を直接実行できないため、ホスト側の `run_watcher.cmd`
(watch_and_build.ps1) がフラグファイルを監視してビルドする。Claude はフラグを置いて結果を読むだけ。

## 前提
- ユーザーが対象プロジェクトで `run_watcher.cmd` を起動済みであること。
- プロジェクトフォルダ(.sln または .slnx があるフォルダ)を `$PROJ` とする。

## ビルド実行 (1回分)

必ず同梱スクリプトを使う。自分で flag を作ったり待機ループを書いたりしない。

```bash
bash <このSkillのフォルダ>/scripts/build_once.sh "$PROJ" 180
```

**重要 (トークン節約と打ち切り防止):** Bash ツールの既定タイムアウトは120秒で、180秒待つスクリプトが
途中で打ち切られる。次のどちらかで呼ぶ。待機中に ls や cat で状況確認をしない (1回の呼び出しで完結する)。
- `run_in_background: true` で実行し、完了通知を待つ (推奨。待機中は何も消費しない)。
- フォアグラウンドなら Bash の `timeout` を 200000 以上にする。

スクリプトは古い `build_result.txt` / `build_error.log` を消し、`trigger_build.flag` を作り、
`build_result.txt` の出現を待つ。1行目が結果、終了コードも対応する。

| 1行目 | rc | 意味 | 次の行動 |
|---|---|---|---|
| `SUCCESS` | 0 | ビルド成功 | ループ終了。1〜2行で報告 |
| `FAILED` | 1 | コンパイル/リンクエラー | 2行目以降のエラーを読んで修正し、再ビルド |
| `ENV_ERROR` | 4 | 環境エラー (VS/vswhere/引数など) | **ソースを直さず**、内容を報告して停止 |
| `WATCHER_NOT_RUNNING` | 3 | フラグが回収されない | 停止し、`run_watcher.cmd` の起動をユーザーに依頼 |
| `TIMEOUT` | 5 | 完了マーカーが出ない | 停止して報告 (長いビルドなら timeout を延ばして1回だけ再試行可) |

## ループのルール
1. ソースを修正したら `build_once.sh` を実行する。修正していない状態での再実行はしない。
2. `FAILED` なら、エラー行 (`file(line,col): error Cxxxx`) の箇所を修正する。無関係なリファクタリングはしない。
3. **最大5回**まで。5回目も失敗なら、残りのエラーと試した修正を報告して停止する。
4. **同じエラー (同じファイル・行・コード) が修正後も出る場合**は、2回目で止めて原因を調べる。
   ファイルが外部 (エディタの再保存など) で書き戻されている可能性を疑い、ユーザーに確認する。
5. `.claude-logs/` の `build.log` は詳細が必要なときだけ読む。通常は `build_error.log` で足りる。
6. 修正時はファイルの文字コード (UTF-8 BOM の有無など) と改行コードを変えない。

## トークン節約
- 成功時は `build_error.log` や `.claude-logs/` を読まない。報告も1〜2行。
- 失敗時のエラー出力は、スクリプトが最大40行・1行400文字に制限している。足りないときだけ `build_error.log` を読む。
- ソースは、エラー行の前後だけを読む (ファイル全体を読み直さない)。
- 待機中・修正の合間に、経過の説明を書かない。

## 完了時の確認 (変更の報告)
作業を終える前に (成功でも、停止でも)、変更したファイルを一覧して、報告に含める。ユーザーが、コミットの前に、`git diff` で、変更を確認できるようにするため。
**このセッションで、自分がファイルを編集していない場合は、実行せず、「変更なし」と報告する。**

1. 変更されたファイルの一覧を取る (読み取りだけ。ステージやコミットはしない)。
   ```bash
   git -c core.fileMode=false --no-optional-locks status --short
   ```
   - `-c core.fileMode=false` を付けるのは、WSL の git が、`/mnt/c` のファイルを実行権限つきと見て、ほぼ全ファイルを「変更あり」と表示してしまうため。
   - git のリポジトリでない場合や、コマンドが失敗した場合は、自分が編集したファイルの一覧で代える。
2. **テストファイル (`Test*.cpp`、`Test*.h`、`*Test/` 配下) を編集した場合は、そのことを、報告の先頭で明示する** (ビルドエラーの修正で、触れた場合など)。
3. 「コミット前に、`git diff` で変更を確認してください」と、一言添える。
4. **`git commit` と `git push` は、ユーザーの明示的な指示がない限り、実行しない。**
5. プロジェクトの設定 (`.claude/settings.json`) で、テストファイルの編集や、`git commit` に、確認が出る設定になっていることがある。
   確認が出たら、何を、なぜ、行うのかを、簡潔に説明する。拒否されたら、同じ操作を、別の方法 (別のツールやコマンド) で、行わない。

## 報告
- 成功: 回数と結果を1〜2行で。差分ビルドで「すべての出力が最新」でも正常。続けて、「完了時の確認」の、変更ファイルを、1行で。
- 失敗で停止: 最後のエラー、試した修正、停止理由。変更したファイルも、同様に報告する。

## ホスト側の構成 (参考)
- `trigger_build.flag`: Claude が作る。ウォッチャーが検知して削除する。
- `build_result.txt`: ビルド終了時にウォッチャーが `SUCCESS` / `FAILED` を書く (完了マーカー)。
- `build_error.log`: 失敗時のみ作成。環境エラーは先頭が `[ENVIRONMENT ERROR - not a source code problem]`。
- `.claude-logs/`: `build.log` / `errors.log` / `warnings.log`。
