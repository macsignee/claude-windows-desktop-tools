# UI デザインガイドライン (ui-design-review)

> **パスの書き方:** `<Skill群>` = この Skill のフォルダ (Base directory) の 1 つ上。ほかの Skill も、そこにある。コマンドでは、実際のパスに置き換える。

画面を、**ガイドライン (`references/UI-Design-Guidelines.md`。v2.10、草案)** に沿って、設計し、レビューする。
ガイドラインは、**利用者に見える結果と振る舞い**の規範 (ボタンの並び、キーボード、色、DPI、メッセージ、アクセシビリティなど)。**テストの手法は、含まない** (UI テストは `/ui-test-first`)。

- 規則には ID (`UI-CTL-110` など) と、強さ (**必須** / 推奨 / 任意 / 廃止) がある。**必須は、ユーザーの承認 (付録 C の例外申請) なしに、破らない。**
- 単位は、論理単位 = DIP = epx (**同値とみなす**。本文 §6.2、付録 A.6)。
- 本文は、WPF / WinForms / MFC の表を持つ。WinUI 3 は、付録 A (枠のみ。記入前)。

## ガイドラインの読み方 (全文を読まない)

本文は、約 1,200 行ある。**全文を読まない。** 章を探して、必要な範囲だけ読む。

```bash
G=<Skill群>/ui-design-review/references/UI-Design-Guidelines.md
grep -n '^## \|^### ' "$G"        # 章・節の位置
grep -n 'UI-CTL-110' "$G"          # 規則 ID の位置 (本文と、付録 F のチェックリスト)
sed -n '<開始>,<終了>p' "$G"       # その範囲だけを読む
```

- 構成: 1〜2 章 (適用範囲、使い方、用語)、3〜17 章 (規則)、付録 A (WinUI 3)、B (参考資料)、C (例外申請の様式)、D (改訂履歴)、E (仕様書テンプレート)、F (レビュー用チェックリスト)。
- 規則の末尾や直下に、**〔適用: MFC〕** (その技術だけ)、**適用除外** (規則の対象外になる条件。例外申請は要らない)、**受入条件 (AC-n) と確認方法**、**〔出典〕** が付くことがある。
- **`[廃止]`** の規則は、統合先の ID が書いてある。そちらを読む。

## 使う場面

### 1. 画面を作る前 (設計。`/ui-test-first` や `/add-feature` の計画で)

決まった画面の設計 (部品、操作と期待、守る規則 ID、選んだ案) は、`docs/design/<画面>.md` に残す (`/ui-test-first` が、承認のあとに保存する)。**あれば、先に読む。**

1. **付録 E (仕様書テンプレート)** の項目のうち、その画面に該当するものを、計画に含める (特に、5 コントロール一覧、6 キーボード、8 画面の状態、9 ボタンの動作、12 処理 (想定処理時間の区分)、15 アクセシビリティ)。
2. 作るものに応じて、次の章だけを読む。

| 作るもの | 読む章 |
|---|---|
| ダイアログ (OK / キャンセル) | 4.1 (ウィンドウ種別)、5 の UI-LAY-006 / 007 / 009、8 (キーボード)、9.2 (UI-CTL-010〜014)、9.11 (既定値)、12.2 (確認) |
| 入力画面 | 9.3〜9.6 (入力、チェック、選択)、11 (入力検証)、14 (アクセシビリティ) |
| 一覧・表 | 9.7 (表)、10 (画面の状態)、9.10 / 9.11 |
| 長い処理がある画面 | 13 (想定処理時間の区分、進捗、キャンセル) |
| すべての画面 | 6 (DPI・文字)、7 (色・テーマ)、8 (キーボード)、14、16 (ローカライズ) |

3. **計画 (承認を取る表) に、守る規則 ID を書く** (例: 「UI-CTL-091: 『削除』は既定のボタンにしない」)。

### 2. 作った画面 (または、既存の画面) のレビュー

`$SLN_DIR` は、ソリューションのフォルダ (カレント)。作業フォルダ (`solutions.md` があり、`.sln` / `.slnx` がない) で起動しているときは、`/ui-test-first` と同じく、`python3 <Skill群>/new-solution/scripts/new_solutions.py resolve "$PWD" [<候補名>]` で対象を決める。

1. **静的検査を実行する** (読み取りだけ。Windows もウォッチャーも不要):
   ```bash
   python3 -I <Skill群>/ui-design-review/scripts/ui_guideline_check.py "$SLN_DIR" [--all] [--json <ファイル>] [--fail-on-warning]
   ```
   既定は、warning (必須の規則への指摘) だけを出す。`--all` で、info (推奨の規則への指摘と、人の確認を促すもの (UIG-CTL101)) も出す。
2. **各 warning を、規則の本文で確かめる。** 静的検査は、推測 (下の「誤検出と限界」)。誤検出は、報告に、理由つきで書く。
3. **付録 F (レビュー用チェックリスト) で、該当する章を判定する。** 判定は、適合 / 不適合 / 対象外 / 確認不能 (付録 F.1)。受入条件 (AC-n) のある規則は、確認方法 (仕様書 / 画面 / 実装 / 支援技術の確認) に従う。**画面を見て確かめる項目** (コントラスト、DPI の倍率での文字切れ、タッチ領域、フォーカスの順序) は、静的検査では判定できない。`/ui-test-first` のプレビュー (`Snap` / `HoldForViewing`) で画面を撮る、または、ユーザーに見せて確認する。
4. **付録 F.2 の様式で、報告する (次の欄を、そのまま埋める。表の形に、変えない)。** 必須の不適合は、修正するか、例外申請 (付録 C) を、ユーザーに提案する。推奨の不適合は、理由を記録する。**適合も、「確認した項目」に、1 行ずつ書く** (説明は要らない)。

```text
画面名:
対象技術:
適用した付録:
レビュー者:
レビュー日:
仕様書の版:

確認した項目:
  規則 ID(受入条件の番号) / 確認方法 / 証跡(画面、ファイル、仕様書の箇所)
  例) UI-WIN-022 / 実装の確認 / Views/MainWindow.xaml: MinWidth="320" MinHeight="180"
  例) UI-ACC-001 AC-1 / 実装の確認 / Views/MainWindow.xaml(21): TextBox に AutomationProperties.Name がない (不適合)

不適合:
  規則 ID / 内容 / 修正内容、または例外 ID

確認不能:
  規則 ID / 必要な資料
```

**「適用した付録」** は、**技術別の付録** (WinUI 3 を扱うなら付録 A) を書く。WPF・WinForms・MFC の本文だけなら、「なし」。付録 F (チェックリスト) は、書かない。

**「確認方法」の使い分け:** **「画面の確認」は、実際の画面を、起動して、操作・表示して、確かめたときだけ**書く。ソース・リソース・設定を読んだだけなら、**「実装の確認」**。画面を操作できなかった項目は、**確認不能**にして、必要な資料に、「画面の確認」と書く。

### 3. 規則の意味の確認

`grep -n '<規則 ID>' "$G"` で、本文と、付録 F の位置を見る。規則の引用は、ID を添える。

## 静的検査の対象

| コード | 規則 | 対象 | 重大度 | 内容 |
|---|---|---|---|---|
| UIG-KEY006 | UI-KEY-006 | WPF / WinForms / MFC | warning | アクセスキーが、同じ画面 (ダイアログ) で重複している (メニューは、メニューごとの範囲) |
| UIG-CTL091 | UI-CTL-091 | WPF / WinForms / MFC | warning | 破壊的な操作 (削除・消去・破棄・初期化・上書など) と思われるボタンが、既定のボタン (`IsDefault` / `AcceptButton` / `DEFPUSHBUTTON`) になっている |
| UIG-LAY007 | UI-LAY-007 | WPF / MFC | info | 既定のボタンが、1 つの画面に複数ある |
| UIG-CTL003 / UIG-CTL003T | UI-CTL-003 | WPF / WinForms | warning | アイコンだけのボタンに、アクセシブル名 (UIG-CTL003)・ツールチップ (UIG-CTL003T。WPF のみ) がない |
| UIG-ACC001 | UI-ACC-001 | WPF | warning | `TextBox` / `PasswordBox` / `ComboBox` / `DatePicker` に、`AutomationProperties.Name` / `LabeledBy` がない (`Label` の `Target` と `TextBlock` は、アクセシブル名にならない。実機の Narrator で確認済み) |
| UIG-LAY005 | UI-LAY-005 | WPF | warning | `Canvas` で、コントロールを座標 (`Canvas.Left` など) で配置している |
| UIG-TYP001 | UI-TYP-001 | WPF | warning | 独自のフォントを指定している (Segoe UI・日本語の標準フォント・アイコン用フォントは、対象外) |
| UIG-LOC001 | UI-LOC-001 | WPF | warning | XAML の表示文字列の直書き (全体で 1 件の指摘に、件数をまとめる) |
| UIG-DPI001 | UI-DPI-001 | WinForms | warning | `AutoScaleMode.None` |
| UIG-DPI002 | UI-DPI-002 | WPF / WinForms / MFC | warning | DPI 認識モードの宣言 (`dpiAware` / `ApplicationHighDpiMode` など) が、プロジェクトに見つからない |
| UIG-CTL100 / UIG-CTL100V / UIG-CTL100U | UI-CTL-100 | MFC | warning | Common Controls 6.0 以降のマニフェストの記述がない / 版が 6.0 未満、または混在 / Unicode 文字セットでない |
| UIG-CTL101 | UI-CTL-101 | MFC | info | MFC の DLL に、ダイアログがある (ユーザー DLL のマニフェスト ID 2 は、手作業で確認) |

**重大度の方針:** 必須の規則への指摘は warning、推奨は info。**例外は `UIG-CTL101` だけ** (必須の規則だが、静的に違反かを判定できず、人の確認を促すだけなので、info)。

| 終了コード | 意味 | 次の行動 |
|---|---|---|
| 0 | 完了 (指摘があっても 0。`--fail-on-warning` のときは、warning があれば 1) | 指摘を、読んで、判断する |
| 2 | 引数が不正 | フォルダを確認する |
| 3 | 検査する対象 (XAML / `*.Designer.cs` / MFC の `.rc`・`.vcxproj` / WPF・WinForms の `.csproj`) がない | UI のプロジェクトではない。報告して終わり |

## ループのルール
1. **画面・リソース・プロジェクトを編集したら、編集のあとで、実行する。** 編集していない状態で、再実行しない。
2. warning は、**自分が今回編集した画面に関係するもの**だけ直し、ほかは、報告に 1 行で添える (無関係な修正はしない)。
3. **指摘を消すために、画面の機能を減らさない。** ボタンの名前だけを変える、`AutomationProperties.Name` に意味のない文字列を入れる、といった、見かけだけの修正をしない。直すのは、実際の振る舞い (既定のボタン、名前、キー、配置)。
4. 直したら、再実行して、warning が減ったことを確認する。**最大 3 回。** 同じ指摘が残るなら、停止して、原因 (誤検出の疑いを含む) を報告する。
5. 必須の規則を、満たせないときは、**自分で例外にしない。** 付録 C の様式で、ユーザーに、例外申請を提案する。
6. **`Name` / `AutomationId` / コントロール ID を変えたら、UI テスト (`*.UITests`) の `Find` も、同時に直す** (`/ui-test-first`)。
7. ガイドラインの本文は、このリポジトリで管理する。配布先 (`<Skill群>/ui-design-review/references/`) を、直接編集しない。

## 誤検出と限界
- **静的解析 (字面と構造の推測)。** 実行はしない。**通ったことは、規則を満たすことを意味しない。**
- UIG-CTL091 は、ラベル・名前・コマンドの語 (削除、Delete など) で、破壊的かを推測する。**取り消せる削除は、破壊的操作ではない** (ガイドライン §2.6)。誤検出は、理由つきで報告する。
- UIG-ACC001 は、`AutomationProperties.Name` / `LabeledBy` だけを見る (`Label` の `Target` は、アクセスキー用で、名前を与えない)。スタイルやカスタムコントロールが名前を与える場合は、誤検出になる (`DataTemplate` / `ControlTemplate` / `Style` の中は、対象外)。
- UIG-DPI002 は、宣言の**有無**だけを見る (どのモードにするかは、人が決める。UI-DPI-002 は、DPI 非対応にしないことを求める)。**WPF は、宣言がなくても、既定で、システム DPI 対応** (DPI 非対応ではない)。モニターごとの DPI には、マニフェストでの宣言が要る (dotnet/wpf Issue #859。Microsoft の WPF-Samples の PerMonitorDPI)。**「既定で PerMonitorV2 相当」と書かない。**
- XAML は、XML として解析する。**解析できない XAML は、黙って飛ばす。** `*.Designer.cs` は、VS が書く形 (`x.Text = "..."`) の字句解析。
- **見た目・操作・表示は、判定できない** (コントラスト、各倍率での文字切れ、タッチ領域の大きさ、タブ順、スクリーンリーダーでの読み上げ、メッセージの文面)。付録 F の手動確認で行う。
- **`/new-solution` が作る、新規のソリューション (v2.27.0 以降) は、UI-DPI-002 / UI-CTL-100 (MFC) / UI-ACC-001 (WPF) を、ひな形で満たしている** (実機のビルドと実行は、未確認。TEST-PLAN 2-10)。**残る既知の指摘は、UI-LOC-001 (WPF の XAML の文字列)** だけ (**ローカライズを、ひな形の既定にしない、と決定済み** (2026-10-31)。生成直後の WPF の `UIG-LOC001` は、毎回、報告し直さず、既知として扱う。ローカライズが要る画面では、本来の指摘として扱う)。v2.27.0 より前に作ったソリューションの、生成直後の指摘は、ひな形の未対応であって、画面の設計の誤りではない。
- **実プロジェクトでの検証 (2026-10-30、UG2):** 既存の 12 フォルダ (WPF・WinForms・MFC) で、異常終了なし。誤検出は、見つかっていない。**XAML のスタイルが名前を与える画面は、未確認。** UIG-DPI002 は、ほぼすべてのプロジェクトで出る (VS のウィザードで作った MFC を含む)。
- **「OS に追従するか」は、色指定やスタイルの有無では判定できない** (UI-CLR-005: OS のライト / ダーク設定への追従、UI-DPI-005: OS のテキストのサイズ設定への追従など)。独自の色指定がないことは、追従することを意味しない。追従するかは、フレームワークと版による。**画面で確かめられないときは、確認不能にする** (確認した項目 (適合) に入れない)。
- **規則の引用は、本文を `grep` で確かめてから書く** (記憶で節番号を書かない。存在しない節を引用した例がある)。破壊的操作かの判断は、§2.6 の定義 (取り消せない形で、削除・上書き・外部へ送信・公開する操作。Undo できる操作は含まない) に、根拠を置く。定義にない言い回し (「Undo 不要域」など) で、根拠を書かない。
- ガイドラインは、**草案 (v2.10)**。文書管理の欄 (承認者など) は、未記入 (他部署の承認後に設定される)。
