# Windows Desktop UI Design Guidelines

**対象:** WPF / Windows Forms / MFC（Dialog、CFormView）  
**拡張対象:** WinUI 3（付録 A に記載。追記・参照可能）  
**版:** 2.10（草案）  
**制定日:** 2026-10-29  
**改訂日:** 2026-10-29  
**目的:** Windows デスクトップアプリケーションの UI を、利用者にとって一貫性があり、分かりやすく、操作しやすく、誰にとっても使える形に統一する。

本書は UI の設計規範を中心に扱う。UI の一貫性、アクセシビリティ、操作性を保証するために必要な範囲で、UI 実装上の要件(実装要件)も規定する。実装要件の範囲と基準は、§1.4 に定める。テスト手法、テスト用識別子、自動化ツールの運用、セキュリティ要件、性能要件そのものは本書の対象外とし、別文書で定める。関連文書は、次の「文書管理」に示す。

## 1. 適用範囲

### 1.1 対象

- 新規開発する画面と、改修する画面
- ウィンドウ、ダイアログ、メッセージ、ファイル選択、進捗表示、通知

### 1.2 技術ごとの扱い

| 技術 | 扱い |
|---|---|
| WPF、Windows Forms、MFC | 本文(第 3 章から第 17 章)を直接適用する |
| WinUI 3 | 本文の原則を適用し、固有の指針は付録 A で補う |
| その他の技術 | 付録を新設して追加する(§2.4) |

本文の技術別の表は、本文の対象技術(WPF、Windows Forms、MFC)だけを扱う。付録で扱う技術の読替えは、その付録に書く。

### 1.3 OS 標準の優先

- OS 標準のダイアログとコントロールを、独自実装より優先する。
- 独自実装する場合は、理由を記録する。

### 1.4 実装要件

本書は、UI の設計規範を中心に扱う。実装やビルドに踏み込む規則(実装要件)は、次の条件をすべて満たす場合に限り、本書に置く。

- 利用者に見える結果を守るために必要である。
- 守る結果を、規則ごとに、次の表に書く。

| 規則 ID | 実装要件 | 守る結果 |
|---|---|---|
| UI-CTL-100 | MFC アプリケーションに、Common Controls 6.0 以降のマニフェストを、リソース ID 1 で組み込む | 標準コントロールが、OS の現行のビジュアルスタイルで表示される |
| UI-CTL-101 | 画面を持つ MFC ユーザー DLL に、同じマニフェストを、リソース ID 2 で組み込む | DLL の画面の標準コントロールが、同じスタイルで表示される |
| UI-DPI-002 | DPI 認識モードを、マニフェストなどで明示し、DPI 非対応にしない | 高 DPI の環境で、表示がぼやけない |
| UI-LOC-001 | 表示文字列を、コードに埋め込まず、リソースにする | 表示文字列を、コードを変更せずに、言語ごとに差し替えられる |
| UI-LOC-002 | 文字列の結合で文章を組み立てず、翻訳できる単位でリソース化する | 翻訳した文章が、その言語の語順で、正しく表示される |
| UI-PRG-004 | UI スレッドをブロックしない | 処理中も、画面が操作に応答する |
| UI-WIN-004 | MFC の CFormView の、Document/View、フレーム、ビューの寿命、コマンドルーティングを、仕様化する | 画面の生成、破棄、コマンドの動作が、仕様どおりになる |
| UI-VAL-007 | 画面側と処理側で、矛盾した検証規則を持たない | 画面で受け付けた入力が、処理側で、別の理由により拒否されない |

実装要件は、この表の規則に限る。追加する場合は、この表に、守る結果を書く。実装の手順や API の詳細は、関連文書(文書管理の表)で定めてよい。

## 2. 文書の使い方

### 2.1 規則 ID

すべての規則に ID を付ける。形式は `UI-<分野>-<連番>` とする。

```text
例: UI-KEY-003
```

ID は、指摘、例外申請、付録からの参照に使う。いったん付けた ID は、再利用も再採番もしない。廃止または統合する場合は、規則の強さの位置に「[廃止]」と書き、統合先の規則 ID を書いて残す。

**適用技術。** 規則の強さの直後に〔適用: …〕がある規則は、その技術だけに適用する。記載のない規則は、本文の対象技術のすべてに適用する。付録の規則(例: `UI-WUI-…`)は、その付録の技術だけに適用する。

**分野コード。** 分野コードは、次の一覧で管理する。新しい分野を追加する場合は、この一覧に追加する。コードは大文字 3 文字とし、いったん割り当てたら再利用しない。

| コード | 分野 | 章 |
|---|---|---|
| PRN | 設計原則 | 3 |
| WIN | ウィンドウと画面構成 | 4 |
| LAY | レイアウト | 5 |
| TYP | 文字、文字列 | 6 |
| DPI | DPI と拡大率 | 6 |
| CLR | 色、テーマ、アイコン | 7 |
| KEY | キーボードとフォーカス | 8 |
| CTL | コントロール | 9 |
| NAV | ナビゲーション | 9.10 |
| STA | 画面の状態 | 10 |
| VAL | 入力検証とエラー表示 | 11 |
| MSG | メッセージと通知 | 12 |
| PRG | 長時間処理 | 13 |
| ACC | アクセシビリティ | 14 |
| SAV | データの保存と終了 | 15 |
| LOC | ローカライズ | 16 |
| INP | 入力デバイス | 17 |
| WUI | WinUI 3 | 付録 A |

### 2.2 規則の強さ

| 表記 | 意味 |
|---|---|
| **[必須]** | 従わなければならない。判定者が変わっても同じ結果になる、客観的に判定できる規則に限る。満たせない場合は、付録 C の例外申請により承認を得る |
| **[推奨]** | 特別な理由がなければ従う。判断を要する規則は、ここに置く |
| **[任意]** | プロジェクトの判断で採用する |

**必須の条件。** 規則を **[必須]** にするのは、「満たすか満たさないか」を、数値、有無、または仕様で定めた事項と照合して判定できる場合に限る。「適切に」「意味のある」「過剰な」など、判定者の判断に依存する語を含む規則は、**[推奨]** とする。

**適用除外。** 規則に条件つきの除外がある場合は、規則の末尾に「適用除外」(**[推奨]** の規則では「この規則を適用しない場合」)として、閉じた一覧で書く。一覧に該当する場合は、その規則の対象外であり、例外申請は要らない。一覧に該当しない場合は、例外申請(付録 C)を行う。「原則として」「必要に応じて」のような曖昧な語で、除外を暗示しない。

**出典。** 外部の基準に由来する規則には、末尾に〔出典: …〕を付ける。出典の記載は、改訂のたびに順次追加する。記載のない規則は、出典の有無が未確認であることを表し、独自の規則とは限らない。

### 2.3 優先順位

1. 法令、契約、アクセシビリティ要件
2. 本ガイドライン
3. 製品固有の規約
4. 既存画面との整合性

既存画面との整合性が本ガイドラインに反する場合、新規画面では本ガイドラインを優先する。既存画面は、改修の機会に段階的に改善する。

### 2.4 付録による拡張

- 技術固有の指針は付録として追加する。本文は書き換えない。
- 付録は、本文の規則 ID を参照して、次のいずれかを行う。
  - **読替え:** 本文の規則を、その技術の用語や API に置き換える。
  - **追加:** 本文にない規則を、付録内の ID(例: `UI-WUI-001`)で加える。
  - **例外:** 本文の規則が当てはまらない点を明記する。
- 付録は、本文の **[必須]** 規則を弱めてはならない。
- WinUI 3 の付録は付録 A とする。他の技術は付録 G 以降に追加する。
- 本文の技術別の表に、付録で扱う技術の行を追加しない。付録で扱う技術の読替えは、その付録に書く(§1.2)。

### 2.5 例外

従えない場合は、付録 C の様式で記録し、承認を得る。

### 2.6 用語

| 用語 | 定義 |
|---|---|
| 破壊的操作 | 利用者のデータを、取り消せない形で削除、上書き、または外部へ送信・公開する操作。Undo できる操作は含まない |
| 重要な通知 | 処理の失敗、データの損失または未保存、および、利用者の対応を要する通知 |
| 主要操作 | その画面の目的を達成するために、利用者が通常の作業で必ず使う操作 |
| 行頭・行末 | 文章を書き始める側が行頭、終わる側が行末。左から右に書く言語では、行頭が左、行末が右。右から左に書く言語では、逆になる |
| 仕様書 | 画面ごとの UI 仕様書。記載する項目は、付録 E に示す |
| 既定のボタン | Enter キーで実行されるボタン。1 つのウィンドウに 1 つだけ指定できる |

### 2.7 受入条件と確認方法

規則のうち、判定が分かれやすいものには、受入条件と確認方法を付ける。

- **対象:** 適用除外を持つ規則、複数の条件を持つ規則、数値基準を持つ規則。v2.9 では、必須の 16 規則である(付録 F の副項目として表示される)。
- **対象外:** それ以外の規則は、規則の第 1 文で判定する。判定がぶれた規則があれば、受入条件を追加する。
- **書式:** 受入条件は、「AC-1」「AC-2」のように番号を付け、1 つの条件を 1 文で書く。
- **性質:** 受入条件は、規則の要求を細かくしたものであり、新しい要求を加えない。規則と食い違う場合は、規則を優先する。

確認方法は、次の語から選ぶ。

| 確認方法 | 内容 |
|---|---|
| 仕様書の確認 | 仕様書(付録 E)の記載を確認する |
| 画面の確認 | 実際の画面を操作して、確認する |
| 実装の確認 | ソースコード、リソース、ビルドの設定を、確認する |
| 支援技術の確認 | スクリーンリーダーなどの支援技術で、確認する |

確認した結果は、レビュー記録(付録 F.2)に、確認方法と証跡を付けて残す。証跡は、画面の確認ではスクリーンショットや操作の手順、実装の確認では確認した箇所(ファイル、設定)、仕様書の確認では仕様書の該当箇所である。

## 3. 設計原則

**UI-PRN-001 [推奨]** 画面は、データ構造ではなく、利用者の作業単位で構成する。

**UI-PRN-002 [必須]** クラス名、DB 列名、例外の型名など、実装上の識別子を、利用者向けの表示に使わない。

**UI-PRN-003 [推奨]** 利用者が、現在の状態、結果、次にできる操作を判断できるようにする。

**UI-PRN-004 [推奨]** 同じ意味の操作には、同じ用語、配置、アイコン、ショートカットを使う。

**UI-PRN-005 [推奨]** 通常作業に必要な情報を優先して表示し、詳細設定や診断情報は必要なときに展開できる形にする。重要なエラーや判断材料は、折りたたみ領域だけに置かない。

**UI-PRN-006 [必須]** 破壊的操作(§2.6)を実行する前に、対象と影響を明示する。

**UI-PRN-007 [推奨]** 取り消せる操作では、確認ダイアログより Undo を優先する。

**UI-PRN-008 [廃止]** UI-CTL-090 と UI-CTL-091 に統合した(v2.4)。

**UI-PRN-009 [推奨]** 利用者が使うフレームワークの違いを、利用者に意識させない。

**UI-PRN-010 [推奨]** 内部用語や、利用者に通じない略語を、表示しない。

## 4. ウィンドウと画面構成

### 4.1 ウィンドウ種別

**UI-WIN-001 [推奨]** モーダル画面は、呼出元の操作を完了しないと継続できない場合に限る。

**UI-WIN-002 [必須]** モードレス画面は、二重起動、所有関係、アクティブ化、終了時の処理を定義する。

**UI-WIN-003 [推奨]** 単純な確認や短い入力はダイアログにし、継続作業は通常のウィンドウまたはビューにする。

**UI-WIN-004 [必須]**〔適用: MFC〕 MFC の CFormView を使う画面では、Document/View、フレーム、ビューの寿命、コマンドルーティングを仕様化する。

### 4.2 タイトル

**UI-WIN-010 [推奨]** タイトルは、画面の目的を短く具体的に示す。

**UI-WIN-011 [推奨]** 「画面」「フォーム」「ダイアログ」といった内部的な語を付けない。

**UI-WIN-012 [推奨]** 編集対象がある場合は、対象名を含める。

**UI-WIN-013 [必須]** 未保存状態を記号だけで示さない。支援技術からも分かる形にする。

### 4.3 サイズと配置

**UI-WIN-020 [必須]** 画面外に表示させない。マルチモニター構成と、所有ウィンドウとの位置関係を考慮する。

**UI-WIN-021 [必須]** 前回の位置とサイズを復元する場合は、現在のモニター領域内に補正する。

**UI-WIN-022 [必須]** リサイズ可能な画面は、最小サイズと、各コントロールの伸縮規則を定義する。

**UI-WIN-023 [推奨]** 固定サイズは、翻訳、フォント変更、DPI 変更でも内容が欠けない場合に限る。

**UI-WIN-024 [推奨]** 初回表示位置は、所有ウィンドウの中央、または直前の操作位置の近くにする。

## 5. レイアウト

**UI-LAY-001 [推奨]** 関連項目をグループ化し、見出しまたは枠で意味を示す。

**UI-LAY-002 [必須]** ラベルと入力欄の位置関係を、画面内で統一する。

**UI-LAY-003 [推奨]** 主要操作は、視線とキー操作の自然な終点に置く。

**UI-LAY-004 [推奨]** 余白と間隔には、アプリケーション内で一貫した間隔体系を用い、関連の強い項目ほど近づける。新規画面では、技術ごとの論理単位で 4 を基本単位とする。ただし、文字サイズ、標準コントロールの既定寸法、および既存の MFC ダイアログの DLU 配置を、この規則に合わせるためだけに変更しない。

**UI-LAY-005 [必須]** (a) UI-WIN-022 で定めた最小サイズ以上のウィンドウサイズ、(b) 仕様書に記載した対象言語の表示文字列、(c) OS 既定の UI フォントの、いずれの条件でも、文字切れ、重なり、操作不能が起きないレイアウト方式を使用する。DPI は、UI-DPI-001 に従う。次の表は、実現手段の例である。

| 技術 | 使用する機構 |
|---|---|
| WPF | Grid、StackPanel、DockPanel など |
| Windows Forms | TableLayoutPanel、FlowLayoutPanel、Anchor、Dock |
| MFC | ダイアログ単位（DLU）を基礎とし、必要に応じて動的レイアウトまたはリサイズ処理を実装して DPI 変化に追従する |

受入条件:

- **AC-1** UI-WIN-022 で定めた最小サイズのウィンドウで、文字切れ、重なり、操作不能が起きない。
- **AC-2** 最小サイズより大きい範囲で、ウィンドウサイズを変えても、文字切れ、重なり、操作不能が起きない。
- **AC-3** 仕様書に記載した対象言語のそれぞれの表示文字列で、文字切れ、重なり、操作不能が起きない。
- **AC-4** OS 既定の UI フォントで、文字切れ、重なり、操作不能が起きない。

確認方法: 画面の確認(最小サイズ、リサイズ、対象言語の文字列、既定のフォント)。DPI は、UI-DPI-001 の受入条件で確認する。

**UI-LAY-006 [推奨]** ダイアログの標準ボタンは、ウィンドウ下端の行末側にまとめ、次の順序で並べる。順序は、行頭から行末へ向かう順で示す(行頭・行末は §2.6)。

| 場面 | 順序(行頭 → 行末) |
|---|---|
| 確定、否定、取消、適用、ヘルプ | 確定(OK、はい、または具体的な確定ボタン)、否定(いいえ、実行しない)、キャンセル、適用、ヘルプ。あるものだけを、この順に並べる |
| ウィザード | 戻る: ウィンドウ上端の行頭側(タイトルバー)。下端の行末側: 次へ(または具体的な確定ボタン)、キャンセル |

この規則を適用しない場合:

- OS 標準のダイアログ(ファイル選択、印刷など)を使う場合は、OS の配置に従う。
- 使用する部品が、ボタンの配置を固定している場合は、部品の配置に従う。例: MFC の `CPropertySheet` のウィザードモード(ボタンは、戻る、次へまたは完了、キャンセル、ヘルプ。配置は部品が決める)。付録で扱う技術の部品は、その付録に書く(WinUI 3 は付録 A.4)。
- 設定を即時に反映する画面など、標準ボタンを置かない場合(UI-CTL-010)。

〔出典: Microsoft Learn「Windows 7 Dialog Boxes (Design basics)」(確定ボタンの順序と配置)、「Wizards」(ウィザードの戻る)。これらは Windows 7 向けの指針で、新しい Windows 向けには更新されていない。MFC のウィザードモードのボタン構成は、Microsoft Learn「CPropertySheet Class」。確認: 2026-10-29(付録 B)〕

**UI-LAY-007 [推奨]** ダイアログには、既定のボタン(§2.6)を 1 つ置く。ボタンの強調表示(アクセントなど)は、既定のボタンにだけ使う。〔出典: Microsoft Learn「Command Buttons in Windows 7」(Default values)。確認: 2026-10-29〕

**UI-LAY-008 [推奨]** 画面の情報密度は、利用者の習熟度と作業頻度に合わせる。

**UI-LAY-009 [必須]** 同じアプリケーションの中で、同種のダイアログ(確認、設定、ウィザードなど)の標準ボタンは、位置と順序を同一にする。

**UI-LAY-010 [必須]** 右から左に書く言語に対応する画面では、行頭と行末を入れ替え、レイアウトの左右、ボタンの並び、Tab 順を、鏡像にする。座標を手作業で反転せず、フレームワークの機構で行う。

| 技術 | 使用する機構 |
|---|---|
| WPF | `FlowDirection`。アプリケーションのカルチャーからは自動で設定されないため、明示的に設定する |
| Windows Forms | `RightToLeft` と `RightToLeftLayout` の両方を有効にする。`RightToLeftLayout` は子コントロールに継承されない。オーナードローは、鏡像化と併用できない |
| MFC | `WS_EX_LAYOUTRTL` などの拡張ウィンドウスタイル。シェルの言語が、右から左に書く言語に対応している場合に有効 |

〔出典: Microsoft Learn の `FrameworkElement.FlowDirection`、`Form.RightToLeftLayout`、Extended Window Styles。確認: 2026-10-29〕

受入条件:

- **AC-1** 右から左に書く言語で、レイアウトの左右が、鏡像になる。
- **AC-2** 右から左に書く言語で、ボタンの並びが、鏡像になる。
- **AC-3** 右から左に書く言語で、Tab 順が、鏡像になる。
- **AC-4** 座標を手作業で反転せず、表の機構で鏡像にしている。

確認方法: 画面の確認(最初の 3 つ。右から左に書く言語で表示する)と、実装の確認(最後の 1 つ)。この規則は、右から左に書く言語に対応する画面にだけ適用する。

## 6. 文字、DPI、拡大率

### 6.1 フォント

**UI-TYP-001 [必須]** 独自の固定フォントを強制せず、Windows 標準の UI フォントに従う。

**UI-TYP-002 [推奨]** 本文の文字サイズは、Windows および使用する標準コントロールの既定値を基準にする。固定値を指定する場合も、通常本文には、12 論理単位(DIP。9 pt に相当、§6.2)未満の文字を使用しない。

**UI-TYP-003 [推奨]** 文字サイズだけで重要度を表さない。

**UI-TYP-004 [推奨]** 見出し、本文、補足の 3 段階程度に、書式を絞る。

### 6.2 DPI と拡大率

本文で寸法を示す場合は、物理ピクセルではなく、DPI スケーリング後も同程度の見かけの大きさになる論理単位を用いる。本文ではこれを「論理単位」と呼び、技術ごとに次のように読み替える。

| 技術 | 本文の「論理単位」の読替え |
|---|---|
| WPF | デバイス非依存ピクセル（DIP、1/96 インチ基準） |
| Windows Forms | 96 DPI 基準のピクセル(DIP と同じ大きさ)。`AutoScaleMode` により、実行時の DPI へスケーリングされる |
| MFC | ダイアログ単位(DLU)。ダイアログのフォントに依存するため、DIP への換算は一定でない |

画像資産の解像度や画面キャプチャなど、物理ピクセルを意味する場合だけ「物理 px」と明記する。

**単位の関係。** 文字の大きさと寸法の単位は、次の関係で読み替える。

| 単位 | 定義 | 換算 |
|---|---|---|
| pt(ポイント) | 1/72 インチ。WinForms と MFC のフォント指定、および WCAG の「大きな文字」の基準で使う | 1 pt = 4/3 DIP |
| DIP(論理単位) | 1/96 インチ。WPF の寸法とフォントサイズで使う。100% 表示では 1 物理 px | 1 DIP = 3/4 pt |
| DLU | MFC のダイアログ単位。ダイアログのフォントに依存する | 一定の換算なし。100% 表示の px に直して比較する |

- 本文の数値は、論理単位(DIP)で示す。pt で示す場合は、「pt」と明記する。
- 主な換算: 9 pt = 12 DIP、14 pt ≒ 18.7 DIP、18 pt = 24 DIP。
- MFC の画面で、本文の数値(例: 24 論理単位)を判定する場合は、100% 表示の px に換算して比較する。
- WinForms は、フォントを pt、寸法を 96 DPI 基準の px で指定する。単位を混ぜない。
- 付録で扱う技術の単位の読替えは、その付録に書く。WinUI 3 の epx は、DIP と同値(1 epx = 1 DIP)とみなす。この取り決めは、以降の版でも維持する(付録 A.6)。

**UI-DPI-001 [必須]** 100%、125%、150%、200% の倍率で、文字切れ、重なり、操作不能が起きないようにする。

受入条件:

- **AC-1** 100%、125%、150%、200% のそれぞれの倍率で、全画面について、文字切れが起きない。
- **AC-2** 100%、125%、150%、200% のそれぞれの倍率で、全画面について、重なりが起きない。
- **AC-3** 100%、125%、150%、200% のそれぞれの倍率で、全画面について、操作不能が起きない。

確認方法: 画面の確認(4 つの倍率のそれぞれで、画面を表示して確認する)。

**UI-DPI-002 [必須]** アプリケーションの DPI 認識モードを、マニフェストなどで明示する。アプリケーション自身が決める場合は、DPI 非対応(DPI Unaware。OS がビットマップとして拡大し、表示がぼやける)にしない。プラグインや DLL など、ホストプロセスが DPI 認識モードを決める構成では、前提となるホストの DPI 認識モードを仕様に記録する。

**UI-DPI-003 [推奨]** 画像とアイコンは、倍率に応じた解像度を用意する。ビットマップの拡大で代用しない。

**UI-DPI-004 [推奨]** ウィンドウを別 DPI のモニターへ移動したとき、レイアウトが崩れないようにする。対象 OS と使用するフレームワークが対応する場合は、モニターごとの DPI の変化に追従する。追従しない場合は、別 DPI のモニターへ移動したときの制約と動作を、仕様に記録する。

**UI-DPI-005 [推奨]** OS の「テキストのサイズ」設定への追従は、技術によって対応状況が異なる。追従できる技術では追従し、追従しない技術では、その旨を仕様に記録する。

**UI-DPI-006 [廃止]** UI-DPI-004 に統合した(v2.6)。

### 6.3 文字列

**UI-TYP-010 [推奨]** 文字列領域には、翻訳や表記変更による伸びを見込む。

**UI-TYP-011 [推奨]** 省略表示には、ツールチップや詳細表示の手段を付ける。

**UI-TYP-012 [必須]** 数値、日付、時刻、通貨、桁区切りは、カルチャーに従う。

**UI-TYP-013 [推奨]** 全角・半角の強制変換は、業務上必要な場合に限る。変換した場合は、結果を利用者に示す。

## 7. 色、テーマ、アイコン

**UI-CLR-001 [必須]** 色だけで、状態、エラー、必須、選択を伝えない。形、文字、アイコンを併用する。

**UI-CLR-002 [必須]** 文字と背景のコントラスト比は、通常の文字で 4.5:1 以上、大きな文字で 3:1 以上にする。大きな文字とは、18 pt(24 DIP)以上、または 14 pt(約 18.7 DIP)以上の太字をいう(§6.2)。〔出典: WCAG 2.2 達成基準 1.4.3(レベル AA)。大きな文字の定義は、CJK フォントでは「同等の大きさになるサイズ」とされている。適用除外の「高コントラストテーマ」は、本ガイドライン独自。ウェブ以外では、1 pt を 1.333 CSS ピクセルとして扱う(WCAG2ICT)〕

適用除外:

- 無効状態のコントロールの文字
- 装飾だけを目的とし、情報を持たない文字
- ロゴタイプ(商標としての文字)
- 高コントラストテーマの有効時(色は OS のテーマに従う)

受入条件:

- **AC-1** 通常の文字(大きな文字以外)と背景のコントラスト比が、4.5:1 以上である。
- **AC-2** 大きな文字(18 pt 以上、または 14 pt 以上の太字)と背景のコントラスト比が、3:1 以上である。
- **AC-3** 上の 2 つを満たさない文字は、適用除外(無効状態、装飾、ロゴタイプ、高コントラストテーマ)のいずれかに該当する。

確認方法: 画面の確認(文字と背景の色を測り、コントラスト比を計算する。画面が表示するテーマごとに行う)。

**UI-CLR-003 [必須]** 操作対象の境界と、状態を示すグラフィック(アイコン、チェックマーク、フォーカス表示など)の色は、隣接する色に対して 3:1 以上にする。〔出典: WCAG 2.2 達成基準 1.4.11(レベル AA)。適用除外の「高コントラストテーマ」は、本ガイドライン独自〕

適用除外:

- 無効状態のコントロール
- 大きさや色などのスタイルを変更せず、OS 標準の描画のまま使うコントロール
- 特定の見た目が情報の本質であるグラフィック(ロゴ、写真、地図など)
- 高コントラストテーマの有効時(色は OS のテーマに従う)

受入条件:

- **AC-1** 操作対象の境界の色が、隣接する色に対して 3:1 以上である。
- **AC-2** 状態を示すグラフィック(アイコン、チェックマーク、フォーカス表示など)の色が、隣接する色に対して 3:1 以上である。
- **AC-3** 上の 2 つを満たさないものは、適用除外のいずれかに該当する。

確認方法: 画面の確認(色を測る)。OS 標準の描画のまま使うコントロールは、スタイルを変更していないことを、実装の確認で確かめる。

**UI-CLR-004 [必須]** 高コントラストテーマで、情報が失われないようにする。

**UI-CLR-005 [推奨]** OS のライト/ダーク設定に追従する。追従しない場合は、理由を記録する。

**UI-CLR-006 [推奨]** 固定色の使用は、必要最小限にする。可能なら、システムの色リソースを使う。

**UI-CLR-007 [推奨]** アイコンは、一貫した意味で使う。意味が不明な場合は、テキストを併記する。

**UI-CLR-008 [推奨]** 点滅、過剰なアニメーション、自動スクロールを避ける。アニメーションを使う場合は、OS の「アニメーションを表示する」設定に従う。

**UI-CLR-009 [推奨]** 無効状態のコントロールでも、文字が読める程度のコントラストを保ち、有効状態と区別できるようにする。OS 標準の無効表示を、変更せずに使う場合は、この規則を満たすものとして扱う。

## 8. キーボードとフォーカス

**UI-KEY-001 [必須]** すべての主要操作を、キーボードだけで実行できるようにする。

**UI-KEY-002 [必須]** Tab 順は、読み順(行頭から行末、上から下。§2.6)、または作業順に一致させる。右から左に書く言語に対応する画面では、鏡像になる(UI-LAY-010)。

**UI-KEY-003 [必須]** 装飾要素と、操作もコピーもできない表示要素に、タブ停止を設定しない。選択やコピーができる読取専用の値(UI-CTL-022)には、タブ停止を設定する。

**UI-KEY-004 [廃止]** UI-CTL-091 に統合した(v2.4)。

**UI-KEY-005 [必須]** フォーカス位置を、視覚的に識別できるようにする。標準のフォーカス表示を消さない。

**UI-KEY-006 [必須]** アクセスキーは、画面内で重複させず、ラベルと対象コントロールを関連づける。

**UI-KEY-007 [必須]** 標準キーの意味を変えない。

| キー | 役割 |
|---|---|
| Tab / Shift+Tab | フォーカス移動 |
| Enter | 既定操作(複数行入力中は改行) |
| Esc | キャンセル、または一時的な UI を閉じる |
| Space | チェック、選択、ボタン実行 |
| 矢印キー | 一覧、タブ、ラジオ、メニュー内の移動 |
| F1 | ヘルプ(提供する場合) |

受入条件:

- **AC-1** Tab と Shift+Tab が、フォーカスを移動する。
- **AC-2** Enter が、既定操作を実行する(複数行入力中は改行する)。
- **AC-3** Esc が、キャンセルする、または一時的な UI を閉じる。
- **AC-4** Space が、チェック、選択、ボタン実行を行う。
- **AC-5** 矢印キーが、一覧、タブ、ラジオ、メニュー内を移動する。
- **AC-6** F1 を使う場合は、ヘルプを開く。

確認方法: 画面の確認(各キーの動作)。

**UI-KEY-008 [必須]** 独自ショートカットは、OS や標準の編集操作と競合させない。

**UI-KEY-009 [推奨]** 頻繁に使う操作には、ショートカットを提供し、メニューやツールチップに表示する。

**UI-KEY-010 [推奨]** 初期フォーカスは、最初に操作すべきコントロールに置く。破壊的操作を実行するボタンは、UI-CTL-091 に従う。

**UI-KEY-011 [必須]** キーボードフォーカスを受けた操作対象が、画面の作り手が配置した表示(固定表示のパネル、通知、浮動するツールバー、ツールチップなど)によって、完全に隠れないようにする。〔出典: WCAG 2.2 達成基準 2.4.11(レベル AA)。確認: 2026-10-29〕

## 9. コントロールの選択と使い方

### 9.1 ボタン

**UI-CTL-001 [推奨]** ボタンの名称は、動詞または結果が分かるものにする。「実行」は、処理が明らかな場合に限る。「OK」「キャンセル」など、OS 標準の名称は、UI-CTL-010 に従う。

**UI-CTL-002 [推奨]** 無効なボタンの理由が分からない場合は、説明を表示する。

**UI-CTL-003 [必須]** アイコンだけのボタンには、名前とツールチップを付ける。

**UI-CTL-004 [必須]** 連打による二重処理を防ぐ。

### 9.2 OK、適用、キャンセル、閉じる

**UI-CTL-010 [必須]** 次のボタンを使う場合は、次の意味で統一する。設定を即時に反映する画面では、これらのボタンを置かなくてよい(UI-CTL-014)。

| ボタン | 意味 |
|---|---|
| OK | 変更を確定して閉じる |
| 適用 | 変更を確定するが閉じない |
| キャンセル | 未確定の変更を破棄して閉じる |
| 閉じる | 閲覧画面を閉じる(編集画面では、保存の有無を曖昧にしない) |

受入条件:

- **AC-1** OK を置く画面で、OK が、変更を確定して閉じる。
- **AC-2** 適用を置く画面で、適用が、変更を確定し、画面を閉じない。
- **AC-3** キャンセルを置く画面で、キャンセルが、未確定の変更を破棄して閉じる。
- **AC-4** 閉じるを置く画面で、閉じるが、閲覧画面を閉じる。編集画面では、保存の有無が、画面上で明確である。

確認方法: 画面の確認(各ボタンの動作)と、仕様書の確認(UI-CTL-011 のボタン動作の定義)。

**UI-CTL-011 [必須]** ウィンドウ右上の閉じる操作、Esc、キャンセルボタンの動作を、画面ごとに定義し、同じ画面の中で食い違わせない。

**UI-CTL-012 [必須]** 適用後にキャンセルした場合の動作(適用済みの変更を残すか、戻すか)を仕様で定め、画面の動作と一致させる。

**UI-CTL-013 [推奨]** 適用ボタンは、設定画面(プロパティシート、コントロールパネルに相当する画面)だけで使う。単純な選択や入力のダイアログには置かない。〔出典: Microsoft Learn「Windows 7 Dialog Boxes (Design basics)」。確認: 2026-10-29〕

**UI-CTL-014 [推奨]** 設定を即時に反映する画面(OK や適用のボタンを置かない画面)では、変更が反映されたことを、画面上で分かるようにする。閉じる操作は、反映済みの変更を取り消さない。利用者が変更前の状態へ容易に戻せない場合は、Undo、既定値に戻す、または同等の回復手段を提供する。この規則は、本ガイドライン独自である。

### 9.3 テキスト入力

**UI-CTL-020 [必須]** ラベル、入力形式、単位、必須性を明示する。

**UI-CTL-021 [必須]** プレースホルダーを、ラベルの代用にしない。

**UI-CTL-022 [推奨]** 読取専用と無効を使い分ける。コピーが必要な値は、読取専用にする。

**UI-CTL-023 [必須]** 入力長や許容文字を、実際の仕様と一致させる。

**UI-CTL-024 [必須]** パスワードなどの機密値は、画面上で伏せ字にする。

### 9.4 数値、日付、時刻

**UI-CTL-030 [推奨]** 数値入力、スピン、日付選択を、用途に応じて使い分ける。

**UI-CTL-031 [必須]** 最小値、最大値、単位、丸め規則を定義する。

**UI-CTL-032 [推奨]** 入力途中の状態を許容し、1 文字ごとに不要なエラーを出さない。

**UI-CTL-033 [必須]** 曖昧な日付形式(例: 03/04/05)を避ける。

### 9.5 チェックボックスとラジオボタン

**UI-CTL-040 [必須]** チェックボックスは、独立した真偽、または複数選択に使う。ラジオボタンは、相互排他の選択に使い、グループ化する。

**UI-CTL-041 [推奨]** 否定形や二重否定のラベルを避ける。

**UI-CTL-042 [推奨]** 三状態を使う場合は、未確定状態の意味を明記する。

### 9.6 コンボボックス、リスト、ツリー

**UI-CTL-050 [推奨]** 選択のみか、自由入力も可能かを、利用者が分かるようにする。

**UI-CTL-051 [推奨]** 項目数が多い場合は、検索や絞り込みを提供する。

**UI-CTL-052 [必須]** 選択の変更だけで、破壊的操作(§2.6)や、仕様書で「進捗」以上の区分(UI-PRG-002)と定めた処理を実行しない。

**UI-CTL-053 [推奨]** ツリーは、階層が利用者にとって意味を持つ場合に限る。

### 9.7 表・グリッド

**UI-CTL-060 [必須]** 表のすべての列に、列見出しを付ける。

**UI-CTL-061 [推奨]** ソート中の列と方向を、視覚的に示す。

**UI-CTL-062 [推奨]** 行選択、セル選択、複数選択の方式を、アプリ内で統一する。

**UI-CTL-063 [必須]** データなし、読込中、取得失敗を、空白だけで表現しない。

**UI-CTL-064 [必須]** 編集可能セル、エラーセル、変更済みセルを、色だけで区別しない。

**UI-CTL-065 [推奨]** 列見出しに、意味の分からない省略を使わない。

### 9.8 タブ

**UI-CTL-070 [推奨]** タブは、同じ対象に関する並列のカテゴリに使う。手順の強制には、ウィザードを検討する。

**UI-CTL-071 [必須]** エラーが別のタブにある場合は、タブ見出しでも示し、そこへ移動できるようにする。

### 9.9 メニュー、ツールバー

**UI-CTL-080 [推奨]** ツールバーには、よく使う操作だけを置く。

**UI-CTL-081 [必須]** 必須の操作を、コンテキストメニューだけに置かない。

**UI-CTL-082 [推奨]** メニューの階層を、深くしすぎない(原則 2 階層まで)。

**UI-CTL-083 [必須]** メニューやツールバーの有効/無効の状態を、実際に実行できるかどうかと一致させる。

### 9.10 ナビゲーション

**UI-NAV-001 [推奨]** 利用者が、現在の画面、選択中の対象、および必要に応じて上位の位置を判断できるようにする。

**UI-NAV-002 [推奨]** 同じ意味の操作による画面遷移、戻る操作、閉じる操作は、アプリ内で一貫させる。

**UI-NAV-003 [推奨]** 主要な作業へ少ない操作で到達できるようにし、不要に深い画面階層を避ける。

**UI-NAV-004 [廃止]** UI-SAV-003 に統合した(v2.7)。

### 9.11 既定値

**UI-CTL-090 [推奨]** 既定値は、最も一般的で安全な選択肢とする。利用者ごとに異なる値を、根拠なく推測して設定しない。誤操作を誘発する既定値を設定しない。

**UI-CTL-091 [必須]** 破壊的操作(§2.6)を実行する選択肢やボタンを、既定値、初期選択、初期フォーカス、Enter で実行される既定のボタンのいずれにもしない。確認ダイアログでも同様とする。〔出典: Microsoft Learn「Command Buttons in Windows 7」(Default values)。確認: 2026-10-29〕

受入条件:

- **AC-1** 破壊的操作を実行する選択肢やボタンが、既定値または初期選択になっていない。
- **AC-2** 破壊的操作を実行するボタンに、初期フォーカスがない。
- **AC-3** 破壊的操作を実行するボタンが、Enter で実行される既定のボタンになっていない。
- **AC-4** 確認ダイアログでも、上の 3 つを満たす。

確認方法: 画面の確認(ダイアログを開いた直後のフォーカスと、Enter の動作)と、実装の確認(既定のボタンの指定)。

### 9.12 技術固有の前提

**UI-CTL-100 [必須]**〔適用: MFC〕 MFC アプリケーション(実行ファイル)には、Common Controls(ComCtl32.dll)バージョン 6.0 以降を使用することを示すマニフェストを、リソース ID 1 で組み込む。Common Controls は Unicode 文字セットだけに対応するため、Unicode 文字セットでビルドする。〔出典: Microsoft Learn「Build Requirements for Windows Common Controls」(MFC)、「Enabling Visual Styles」、「Support for Activation Contexts in the MFC Module State」。確認: 2026-10-29〕

Visual Studio の IDE で新規に作成した MFC アプリケーションには、IDE がマニフェストを自動で宣言する。Visual Studio 2005 以前から移行したプロジェクトには、自動では追加されない。この場合は、プリコンパイル済みヘッダーに、次のコンパイラ指令を手作業で書く。

組み込み方は、次のどちらかとする。

- アプリケーションマニフェストを、`RT_MANIFEST` リソースとして組み込む。
- Visual C++ 2005 以降では、ソースにコンパイラ指令を書く。

```cpp
#ifdef UNICODE
#if defined _M_IX86
#pragma comment(linker,"/manifestdependency:\"type='win32' name='Microsoft.Windows.Common-Controls' version='6.0.0.0' processorArchitecture='x86' publicKeyToken='6595b64144ccf1df' language='*'\"")
#elif defined _M_IA64
#pragma comment(linker,"/manifestdependency:\"type='win32' name='Microsoft.Windows.Common-Controls' version='6.0.0.0' processorArchitecture='ia64' publicKeyToken='6595b64144ccf1df' language='*'\"")
#elif defined _M_X64
#pragma comment(linker,"/manifestdependency:\"type='win32' name='Microsoft.Windows.Common-Controls' version='6.0.0.0' processorArchitecture='amd64' publicKeyToken='6595b64144ccf1df' language='*'\"")
#else
#pragma comment(linker,"/manifestdependency:\"type='win32' name='Microsoft.Windows.Common-Controls' version='6.0.0.0' processorArchitecture='*' publicKeyToken='6595b64144ccf1df' language='*'\"")
#endif
#endif
```

マニフェストの依存関係は、次のとおりとする。

| 項目 | 値 |
|---|---|
| type | `win32` |
| name | `Microsoft.Windows.Common-Controls` |
| version | `6.0.0.0` |
| processorArchitecture | `*`(または、対象に応じた `x86`、`amd64`) |
| publicKeyToken | `6595b64144ccf1df` |
| language | `*` |

コンパイラ指令(`#pragma comment(linker, ...)`)を使う場合の、リソース ID:

- コンパイラ指令は、リンカーが生成するマニフェストの `<dependency>` に、依存関係を加えるだけである。リソース ID は、指令では決まらず、マニフェストをバイナリに組み込む方法で決まる。
- リンカーの `/MANIFEST:EMBED` で組み込む場合、ID の既定値は、実行ファイルが 1、DLL(`/DLL` を指定したビルド)が 2 である。マニフェストツール(`mt.exe`)で組み込む場合は、`-outputresource` に、実行ファイルでは `;1`、DLL では `;2` を指定する。いずれも、UI-CTL-100 の 1、UI-CTL-101 の 2 と一致する。
- Visual Studio では、Manifest Tool の `Embed Manifest` を有効にする。無効にすると、マニフェストは、バイナリと同じフォルダーの外部ファイルになり、組み込みにならない。
- 同じ依存関係を、コンパイラ指令、`Additional Manifest Dependencies`、手書きのマニフェストなど、複数の場所で、異なる内容で指定しない。リンカーは、重複する項目を除くが、内容が衝突すると、マニフェストが壊れ、アプリケーションが起動しない。
- 組み込まれたマニフェストは、最終的なバイナリを、Visual Studio でファイルとして開くと、確認できる。

〔出典: Microsoft Learn「/MANIFEST」、「/MANIFESTDEPENDENCY」、「Understanding manifest generation for C/C++ programs」。確認: 2026-10-29〕

理由: マニフェストがない場合、アプリケーションは ComCtl32.dll バージョン 5 のコントロールを使い、ビジュアルスタイルが適用されない。バージョン 6 は再頒布できず、これを含む Windows でだけ使える。

受入条件:

- **AC-1** 実行ファイルに、Common Controls の依存関係(name が `Microsoft.Windows.Common-Controls`、version が 6.0 以降)を持つマニフェストが、組み込まれている。
- **AC-2** そのマニフェストが、`RT_MANIFEST` のリソース ID 1 である。
- **AC-3** Unicode 文字セットでビルドされている。
- **AC-4** 同じ依存関係が、異なる内容で、複数の場所に指定されていない。

確認方法: 実装の確認(最終的なバイナリのマニフェストとリソース ID、ビルドの文字セットの設定、依存関係の指定箇所)。

**UI-CTL-101 [必須]**〔適用: MFC〕 画面を持つ MFC ユーザー DLL(通常の DLL)には、同じマニフェストを、リソース ID 2 で組み込む。MFC は、ユーザー DLL ごとに別の activation context を作るため、DLL 自身のマニフェストで指定する。MFC 拡張 DLL は、ホストのアプリケーションまたはユーザー DLL が決める activation context に従うため、拡張 DLL 自体への組み込みは要らない。〔出典: Microsoft Learn「Support for Activation Contexts in the MFC Module State」。確認: 2026-10-29〕

### 9.13 ホバーやフォーカスで現れる表示

ツールチップやポップアップなど、ホバーまたはキーボードフォーカスで追加の表示が現れる要素に適用する。

**UI-CTL-110 [必須]** ホバーまたはキーボードフォーカスで追加の表示が現れる場合は、次の 3 つを満たす。〔出典: WCAG 2.2 達成基準 1.4.13(レベル AA)。確認: 2026-10-29〕

- **閉じられる:** ホバーやフォーカスを動かさずに、追加の表示を閉じる手段がある(例: Esc)。ただし、入力エラーを伝える表示と、他の内容を隠さず置き換えもしない表示は除く。
- **重ねられる:** ホバーで現れる表示は、ポインターを表示の上に動かしても、消えない。
- **持続する:** 追加の表示は、ホバーまたはフォーカスが外れる、利用者が閉じる、または情報が無効になるまで、表示し続ける。

適用除外: OS またはフレームワークが表示を制御する標準のツールチップを、表示の挙動を変更せずに使う場合。WCAG の「ユーザーエージェントが制御し、作り手が変更していない表示」に相当するとみなす。この読替えは、本ガイドライン独自である。

受入条件:

- **AC-1** 追加の表示を、ホバーやフォーカスを動かさずに閉じる手段がある(入力エラーを伝える表示と、他の内容を隠さず置き換えもしない表示は除く)。
- **AC-2** ホバーで現れる表示の上に、ポインターを動かしても、表示が消えない。
- **AC-3** 表示は、ホバーまたはフォーカスが外れる、利用者が閉じる、または情報が無効になるまで、続く。
- **AC-4** 標準のツールチップの適用除外を使う場合は、表示の挙動を変更していない。

確認方法: 画面の確認(最初の 3 つ。ホバーとフォーカスの両方で行う)と、実装の確認(最後の 1 つ)。

## 10. 画面の状態

**UI-STA-001 [必須]** 次の状態のうち、画面に該当するものについて、表示と操作を仕様で定める。該当しないと判断した状態は、その旨を仕様に記録する。

- 初期、通常
- 空、入力途中、入力不正
- 検索結果 0 件
- 読込中、処理中、部分完了
- 成功、失敗
- 接続切断、外部依存の停止
- 権限不足、読取専用
- 未保存変更あり

受入条件:

- **AC-1** 仕様書に、上の各状態について、画面に該当するかどうかが、記載されている。
- **AC-2** 該当する状態は、表示と操作が、仕様書に定められている。
- **AC-3** 該当しない状態は、該当しない旨が、仕様書に記録されている。
- **AC-4** 画面の表示と操作が、仕様書の記載と一致している。

確認方法: 仕様書の確認(最初の 3 つ)と、画面の確認(最後の 1 つ)。

**UI-STA-002 [必須]** 無効、非表示、読取専用を混同しない。

| 状態 | 使う場面 |
|---|---|
| 無効 | 今は操作できないが、存在は知らせたい |
| 非表示 | この利用者、またはこの状況には無関係 |
| 読取専用 | 値は見せる、コピーはできる、編集はできない |

受入条件:

- **AC-1** 無効のコントロールは、今は操作できないが、画面に表示され、存在が分かる。
- **AC-2** 非表示にする要素は、その利用者、またはその状況に無関係なものに限られる。
- **AC-3** 読取専用の値は、表示され、コピーでき、編集できない。

確認方法: 画面の確認(状態ごとの表示と操作)と、仕様書の確認(状態の条件。付録 E の項目 7)。

**UI-STA-003 [推奨]** 状態の遷移を、仕様書に記載する。

**UI-STA-004 [推奨]** 空状態や検索結果 0 件の状態では、単にデータがないことを示すだけでなく、必要に応じて、データの作成、条件の見直し、再読込など、次に行える操作を示す。

## 11. 入力検証とエラー表示

**UI-VAL-001 [必須]** 検証の実施時点(入力中、フォーカス移動時、確定時)を、項目ごとに定める。

**UI-VAL-002 [推奨]** 入力途中として妥当な状態を、即時エラーにしない。

**UI-VAL-003 [必須]** エラー文には、対象、原因、修正方法を含める。

**UI-VAL-004 [必須]** エラー箇所を、枠の色だけで示さない。文字やアイコンを併用する。

**UI-VAL-005 [推奨]** 複数のエラーがある場合は、先頭のエラーへ移動し、一覧を示す。

**UI-VAL-006 [必須]** エラーの修正後は、表示を直ちに更新する。

**UI-VAL-007 [必須]** 画面側と処理側で、矛盾した検証規則を持たない。

**UI-VAL-008 [必須]** 同じ作業の流れ(ウィザード、複数の画面にまたがる入力など)の中で、すでに入力された、または提供された情報を、再度入力させない。自動入力するか、選択できるようにする。〔出典: WCAG 2.2 達成基準 3.3.7(レベル A)。確認: 2026-10-29〕

適用除外:

- 再入力が本質的な場合
- セキュリティを確保するために必要な場合
- 以前の入力が、もう有効でない場合

受入条件:

- **AC-1** 同じ作業の流れの中で、すでに入力された、または提供された情報を、再度入力させる箇所がない。
- **AC-2** 再度の入力を求める箇所は、適用除外(再入力が本質的、セキュリティのために必要、以前の入力が無効)のいずれかに該当する。
- **AC-3** 以前の情報は、自動入力されるか、選択できる。

確認方法: 仕様書の確認(作業の流れと入力項目の対応)と、画面の確認(流れを通して操作する)。

## 13. 長時間処理

**UI-PRG-001 [必須]** I/O、通信、外部プロセスやデバイスへのアクセス、大量データの処理、計算量の大きい処理、起動時の初期化、印刷など、実行環境やデータ量によって応答時間が変動し、即時に完了しない可能性がある操作について、想定する処理時間の区分(UI-PRG-002)を仕様書に定め、その区分が求める表示を実装する。これらに当たらない操作は、区分を定めなくてよい。

**UI-PRG-002 [推奨]** 操作の想定処理時間を、次の 4 つの区分で設計する。区分の名称は、本書の他の規則(UI-PRG-001、UI-PRG-006、UI-CTL-052)が参照する。区分は設計の目安であり、実測時間だけでは適否を判定しない。実測は実行環境によって変動するため、区分は仕様書で定め(UI-PRG-001)、実測は区分の見直しに使う。UI-PRG-001 により、仕様書で定めた区分が求める表示は、必須である。区分の値の決め方は、推奨である。区分の値は、Jakob Nielsen の 0.1 秒、1 秒、10 秒の 3 つの限界に基づく。Nielsen は、1 秒未満の遅延に特別な表示を要しないとするが、本書は、処理が瞬時でない場合に受付を示す Windows のガイドラインに合わせ、約 0.1 秒を超える区分から、受付の表示を求める。上位の区分は、下位の区分の表示も含む。〔出典: Nielsen Norman Group「Response Times: The 3 Important Limits」、Microsoft Learn「Command Buttons in Windows 7」。確認: 2026-10-29〕

| 区分 | 想定処理時間 | 求める表示 |
|---|---|---|
| 即時 | 約 0.1 秒以内 | 表示は不要 |
| 受付 | 約 0.1 秒を超え、約 1 秒まで | 操作を受け付けたことを示す(ビジーポインターなど) |
| 進捗 | 約 1 秒を超え、約 10 秒まで | 受付の表示に加え、処理中であることを示す不確定の進捗 |
| 中断 | 約 10 秒を超える | 進捗の表示に加え、確定進捗(可能な場合)と、処理を中断する手段 |

**UI-PRG-003 [必須]** 進捗を表示する場合は、進捗が分かるときは確定進捗、分からないときは不確定進捗を表示する。

**UI-PRG-004 [必須]** UI スレッドをブロックして、応答不能にしない。

**UI-PRG-005 [必須]** 処理中の操作の可否を定義し、二重実行を防ぐ。

**UI-PRG-006 [推奨]** 「中断」区分(UI-PRG-002)の処理には、キャンセルを提供する。キャンセルの要求中と完了後を、区別して表示する。

**UI-PRG-007 [必須]** 完了、失敗、キャンセルの後に、UI の状態を元に戻す。

**UI-ACC-001 [必須]** すべての操作可能な要素に、支援技術から取得できる空でないアクセシブル名を持たせる。フレームワークまたは標準コントロールが適切な名前を自動的に公開する場合は、同じ名前を重ねて設定しなくてよい。視覚的なラベルがある場合は、アクセシブル名にそのラベルの文字列を含める。同種の要素が複数ある場合は、名前だけで区別できるようにする。〔出典: WCAG 2.2 達成基準 4.1.2(レベル A)、2.5.3(レベル A)〕

**UI-ACC-002 [必須]** ラベルと入力コントロールを関連づける。

**UI-ACC-003 [必須]** コントロールの役割、値、選択状態、有効状態を、支援技術に公開する。標準コントロールを優先し、カスタムコントロールでは、これらを明示的に実装する。

**UI-ACC-004 [必須]** 動的な状態変化(エラー、進捗、完了)を、支援技術に通知する。

**UI-ACC-005 [必須]** 読み上げ順を、視覚上と操作上の順序に一致させる。

**UI-ACC-006 [必須]** カスタム描画だけで、情報を伝えない。

**UI-ACC-007 [必須]** ポインター(マウス、タッチ、ペン)で操作する対象は、24×24 論理単位以上の操作領域を持たせる。〔出典: WCAG 2.2 達成基準 2.5.8(レベル AA)、WCAG2ICT。適用除外は、WCAG の 5 条件に基づく。確認: 2026-10-29〕

適用除外:

- **間隔:** 24 論理単位未満の対象の中心に、直径 24 論理単位の円を置いたとき、その円が、他の操作対象と、24 論理単位未満の他の対象に置いた円のどちらとも重ならない場合
- **同等手段:** 同じ画面に、同じ機能を持つ、24 論理単位以上の別の対象がある場合
- **文中:** 文章の中にあり、文の行間や大きさに制約される対象(文中のリンクなど)
- **OS 標準:** OS 標準のコントロールを、大きさを変更せずに使う場合
- **本質:** 特定の表示が、伝える情報にとって本質的である場合、または法令で定められている場合

受入条件:

- **AC-1** ポインターで操作する各対象が、24×24 論理単位以上の操作領域を持つ。
- **AC-2** 24 論理単位未満の対象は、適用除外(間隔、同等手段、文中、OS 標準、本質)のいずれかに該当する。

確認方法: 画面の確認(対象の大きさを測る。MFC の画面は、100% 表示の px に換算して比べる。§6.2)。

**UI-ACC-008 [推奨]** 時間制限のある操作を、避ける。必要な場合は、延長できるようにする。

**UI-ACC-009 [推奨]** Narrator などのスクリーンリーダーで、主要な作業が完了できることを、設計時に想定する。

| 技術 | 主な手段 |
|---|---|
| WPF | `AutomationProperties.Name`、`LabeledBy`、`HelpText`、AutomationPeer |
| Windows Forms | `AccessibleName`、`AccessibleDescription`、`AccessibleRole` |
| MFC | 標準コントロールの使用、アクセシブル情報の公開 |

**UI-ACC-010 [推奨]** タッチ操作を主に想定する画面では、操作対象の大きさを、物理寸法で約 7.5 mm 四方以上にする。40×40 論理単位は、135 PPI、100% 表示の場合の換算値である。頻繁に操作する対象と、誤操作の影響が大きい対象は、これより大きくし、周囲の余白も広げる。この値は Microsoft の推奨値であり、WCAG の要件ではない。〔出典: Microsoft Learn「ターゲット設定」(付録 B)〕

PPI と拡大率の組合せによって、40 論理単位の物理寸法は 7.5 mm から外れる。タッチ主体の機器では、物理寸法で確認する。

**UI-ACC-011 [必須]** 認証の手順では、記憶の再生(パスワードを覚えていることなど)や、パズルの解答といった認知機能テストを、利用者に求めない。〔出典: WCAG 2.2 達成基準 3.3.8(レベル AA)。確認: 2026-10-29〕

適用除外: その手順が、次のいずれかを提供する場合

- 認知機能テストに頼らない、別の認証方法
- 認知機能テストを助ける仕組み(パスワードマネージャーへの対応、貼り付けの許可など)
- 物体の認識だけを求めるテスト
- 利用者が自分で提供した、画像、音声などの識別だけを求めるテスト

受入条件:

- **AC-1** 認証の各手順が、記憶の再生やパズルの解答を求めない。
- **AC-2** 求める手順は、適用除外の 4 つ(別の認証方法、助ける仕組み、物体の認識だけ、利用者が提供した内容の識別だけ)のいずれかを提供する。

確認方法: 画面の確認(認証の手順を通して操作する。助ける仕組みでは、貼り付けや、パスワードマネージャーの利用を、実際に試す)と、仕様書の確認(別の認証方法)。

## 15. データの保存と終了

**UI-SAV-001 [必須]** 保存が成功するまで、保存済みとして扱わない。

**UI-SAV-002 [必須]** 保存に失敗した場合は、入力内容を保持し、再試行または別名保存などの選択肢を示す。

**UI-SAV-003 [必須]** 未保存の変更が失われる操作(画面やウィンドウを閉じる、別の画面や対象へ遷移する、アプリケーションを終了する)の前に、保存、破棄、操作の取消を選択できるようにする。確認の方針は、アプリケーション全体で統一する。

**UI-SAV-004 [推奨]** 自動保存では、保存中、最終保存時刻、失敗を、利用者が確認できるようにする。

**UI-SAV-005 [推奨]** 前回の設定値を復元する際、旧バージョンの値や不整合な値は、安全な既定値で置き換える。

## 16. ローカライズ

**UI-LOC-001 [必須]** 表示文字列を、コードに埋め込まず、リソースにする。

**UI-LOC-002 [必須]** 文字列の結合で文章を組み立てず、翻訳できる単位でリソース化する。

**UI-LOC-003 [必須]** アクセスキーの重複を、言語ごとに確認する。

**UI-LOC-004 [推奨]** 右から左へ書く言語、文字列の伸長、異なるフォントを、必要に応じて考慮する。

## 17. 入力デバイス

**UI-INP-001 [必須]** マウスだけ、またはキーボードだけの利用者を、排除しない。

**UI-INP-002 [推奨]** タッチやペンでの利用が想定される画面では、操作対象を大きくし、ホバーだけで現れる情報や操作を避ける。

**UI-INP-003 [推奨]** 右クリックでしか行えない操作を、作らない。

**UI-INP-004 [必須]** ドラッグの動作で行う機能(並べ替え、移動、サイズ変更、ドラッグ&ドロップなど)は、ドラッグを使わず、単一のポインター操作(クリック、タップ)でも実行できるようにする。〔出典: WCAG 2.2 達成基準 2.5.7(レベル AA)。確認: 2026-10-29〕

適用除外:

- ドラッグが本質的な操作(手書き、描画など)
- OS が機能を決め、変更していない場合

受入条件:

- **AC-1** ドラッグで行う各機能が、ドラッグを使わず、単一のポインター操作(クリック、タップ)でも実行できる。
- **AC-2** 上を満たさない機能は、適用除外(ドラッグが本質的、OS が機能を決め、変更していない)のいずれかに該当する。

確認方法: 仕様書の確認(ドラッグを使う機能の一覧と、代わりの操作)と、画面の確認(代わりの操作で実行する)。

### A.6 単位の読替え(本文 §6.2)

| 本文の単位 | WinUI 3 での読替え |
|---|---|
| 論理単位 | 有効ピクセル(epx) |
| DIP との関係 | **本書では、epx と DIP を、同値(1 epx = 1 DIP)とみなす。** 以降の版でも、この扱いを前提とする |

同値とみなす根拠と、注意点:

- **根拠 1:** どちらも、画面密度から独立した仮想の単位で、拡大率を掛けて、物理ピクセルに換算される。DIP は、物理ピクセル = DIP × DPI ÷ 96 である。epx は、100% から 400% の拡大率で換算される。
- **根拠 2:** W3C の WCAG2ICT は、epx を、Windows の密度非依存ピクセルとして挙げている。
- **根拠 3:** Windows の表示倍率を変更すると、アプリに DPI 変更の通知が届く。デスクトップのモニターでは、拡大率と DPI が連動する。
- **取り決めであること:** epx と DIP が同一であると、明記した資料は、確認できていない。この扱いは、本ガイドラインの取り決めである。
- **注意点:** epx は、画面密度に加え、視聴距離も考慮して正規化される(1080p のテレビは、540 epx 相当になる)。視聴距離が大きく違う機器(テレビなど)では、epx と DIP の値がずれる可能性がある。本書は、デスクトップのモニターを対象とするため、同値とみなす。
- **見直し:** Microsoft が、epx と DIP の関係を明記した場合は、この取り決めを見直す。

## 付録 F. レビュー用チェックリスト

本付録は、規則の本文から生成する。規則を改訂した場合は、再生成する。各項目は、規則の第 1 文である。受入条件(§2.7)を持つ規則は、受入条件を副項目とし、確認方法を併記する。受入条件を持たず、第 1 文に「次の」を含む規則は、続く箇条書きや表も、副項目として含む。適用除外、出典、詳細は、本文の規則を見る。廃止した規則は、含めない。

### F.1 判定の方法

| 判定 | 意味 |
|---|---|
| 適合 | 規則を満たす |
| 不適合 | 満たさない。必須の規則は、修正するか、例外申請(付録 C)を行う。推奨の規則は、理由を記録する |
| 対象外 | 適用技術の対象外、または該当する要素がない。理由を記録する |
| 確認不能 | 仕様書、画面、実機のいずれかが足りず、判定できない。必要な資料を記録する |

付録の技術の規則(`UI-WUI-…` など)は、その技術の画面で、あわせて確認する。

### F.2 レビュー記録の様式

```text
画面名:
対象技術:
適用した付録:
レビュー者:
レビュー日:
仕様書の版:

確認した項目:
  規則 ID(受入条件の番号) / 確認方法 / 証跡(画面、ファイル、仕様書の箇所)

不適合:
  規則 ID / 内容 / 修正内容、または例外 ID

確認不能:
  規則 ID / 必要な資料
```

  - [ ] **AC-3** 上の 2 つを満たさないものは、適用除外のいずれかに該当する。
  - 確認方法: 画面の確認(色を測る)。OS 標準の描画のまま使うコントロールは、スタイルを変更していないことを、実装の確認で確かめる。

- [ ] **UI-CLR-005** [推奨] OS のライト/ダーク設定に追従する。
- [ ] **UI-CLR-006** [推奨] 固定色の使用は、必要最小限にする。
- [ ] **UI-CLR-007** [推奨] アイコンは、一貫した意味で使う。
- [ ] **UI-CLR-008** [推奨] 点滅、過剰なアニメーション、自動スクロールを避ける。
- [ ] **UI-CLR-009** [推奨] 無効状態のコントロールでも、文字が読める程度のコントラストを保ち、有効状態と区別できるようにする。

  - [ ] **AC-4** 画面の表示と操作が、仕様書の記載と一致している。

#### 13. 長時間処理

- [ ] **UI-PRG-001** [必須] I/O、通信、外部プロセスやデバイスへのアクセス、大量データの処理、計算量の大きい処理、起動時の初期化、印刷など、実行環境やデータ量によって応答時間が変動し、即時に完了しない可能性がある操作について、想定する処理時間の区分(UI-PRG-002)を仕様書に定め、その区分が求める表示を実装する。
- [ ] **UI-PRG-002** [推奨] 操作の想定処理時間を、次の 4 つの区分で設計する。
  - 即時: 約 0.1 秒以内 / 表示は不要
  - 受付: 約 0.1 秒を超え、約 1 秒まで / 操作を受け付けたことを示す(ビジーポインターなど)
  - 進捗: 約 1 秒を超え、約 10 秒まで / 受付の表示に加え、処理中であることを示す不確定の進捗
  - 中断: 約 10 秒を超える / 進捗の表示に加え、確定進捗(可能な場合)と、処理を中断する手段
- [ ] **UI-PRG-003** [必須] 進捗を表示する場合は、進捗が分かるときは確定進捗、分からないときは不確定進捗を表示する。
- [ ] **UI-PRG-004** [必須] UI スレッドをブロックして、応答不能にしない。
- [ ] **UI-PRG-005** [必須] 処理中の操作の可否を定義し、二重実行を防ぐ。
- [ ] **UI-PRG-006** [推奨] 「中断」区分(UI-PRG-002)の処理には、キャンセルを提供する。
- [ ] **UI-PRG-007** [必須] 完了、失敗、キャンセルの後に、UI の状態を元に戻す。

#### 14. アクセシビリティ

- [ ] **UI-ACC-004** [必須] 動的な状態変化(エラー、進捗、完了)を、支援技術に通知する。
- [ ] **UI-ACC-005** [必須] 読み上げ順を、視覚上と操作上の順序に一致させる。
- [ ] **UI-ACC-006** [必須] カスタム描画だけで、情報を伝えない。
- [ ] **UI-ACC-007** [必須] ポインター(マウス、タッチ、ペン)で操作する対象は、24×24 論理単位以上の操作領域を持たせる。
  - [ ] **AC-1** ポインターで操作する各対象が、24×24 論理単位以上の操作領域を持つ。
  - [ ] **AC-2** 24 論理単位未満の対象は、適用除外(間隔、同等手段、文中、OS 標準、本質)のいずれかに該当する。
  - 確認方法: 画面の確認(対象の大きさを測る。MFC の画面は、100% 表示の px に換算して比べる。§6.2)。
- [ ] **UI-ACC-008** [推奨] 時間制限のある操作を、避ける。
- [ ] **UI-ACC-009** [推奨] Narrator などのスクリーンリーダーで、主要な作業が完了できることを、設計時に想定する。
- [ ] **UI-ACC-010** [推奨] タッチ操作を主に想定する画面では、操作対象の大きさを、物理寸法で約 7.5 mm 四方以上にする。
- [ ] **UI-ACC-011** [必須] 認証の手順では、記憶の再生(パスワードを覚えていることなど)や、パズルの解答といった認知機能テストを、利用者に求めない。

#### 15. データの保存と終了

- [ ] **UI-SAV-001** [必須] 保存が成功するまで、保存済みとして扱わない。
- [ ] **UI-SAV-002** [必須] 保存に失敗した場合は、入力内容を保持し、再試行または別名保存などの選択肢を示す。
- [ ] **UI-SAV-003** [必須] 未保存の変更が失われる操作(画面やウィンドウを閉じる、別の画面や対象へ遷移する、アプリケーションを終了する)の前に、保存、破棄、操作の取消を選択できるようにする。
- [ ] **UI-SAV-004** [推奨] 自動保存では、保存中、最終保存時刻、失敗を、利用者が確認できるようにする。
- [ ] **UI-SAV-005** [推奨] 前回の設定値を復元する際、旧バージョンの値や不整合な値は、安全な既定値で置き換える。

#### 16. ローカライズ

- [ ] **UI-LOC-001** [必須] 表示文字列を、コードに埋め込まず、リソースにする。
- [ ] **UI-LOC-002** [必須] 文字列の結合で文章を組み立てず、翻訳できる単位でリソース化する。
- [ ] **UI-LOC-003** [必須] アクセスキーの重複を、言語ごとに確認する。
- [ ] **UI-LOC-004** [推奨] 右から左へ書く言語、文字列の伸長、異なるフォントを、必要に応じて考慮する。

#### 17. 入力デバイス

- [ ] **UI-INP-001** [必須] マウスだけ、またはキーボードだけの利用者を、排除しない。
- [ ] **UI-INP-002** [推奨] タッチやペンでの利用が想定される画面では、操作対象を大きくし、ホバーだけで現れる情報や操作を避ける。
- [ ] **UI-INP-003** [推奨] 右クリックでしか行えない操作を、作らない。
- [ ] **UI-INP-004** [必須] ドラッグの動作で行う機能(並べ替え、移動、サイズ変更、ドラッグ&ドロップなど)は、ドラッグを使わず、単一のポインター操作(クリック、タップ)でも実行できるようにする。
  - [ ] **AC-1** ドラッグで行う各機能が、ドラッグを使わず、単一のポインター操作(クリック、タップ)でも実行できる。
  - [ ] **AC-2** 上を満たさない機能は、適用除外(ドラッグが本質的、OS が機能を決め、変更していない)のいずれかに該当する。
  - 確認方法: 仕様書の確認(ドラッグを使う機能の一覧と、代わりの操作)と、画面の確認(代わりの操作で実行する)。
