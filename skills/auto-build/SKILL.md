# 自動ビルド & エラー修正ループ (C++ / .NET)

サンドボックスから msbuild を直接実行できないため、ホスト側の `run_watcher.cmd`
(watch_and_build.ps1) がフラグファイルを監視してビルドする。Claude はフラグを置いて結果を読むだけ。

**C++ (`.vcxproj`)、.NET (`.csproj`。WPF を含む)、その混在の、どれでも、手順は同じ。** ウォッチャーが、ソリューションの中身を見て、ビルドの方法 (C++ ツール要求の有無、NuGet の復元) を決める。Skill 側で、切り替える必要はない。

## 前提
- ユーザーが対象プロジェクトで `run_watcher.cmd` を起動済みであること。
- プロジェクトフォルダ(.sln または .slnx があるフォルダ)を `$PROJ` とする。
- **作業フォルダ (`solutions.md` があり、`.sln` / `.slnx` がないフォルダ) で起動しているとき** (複数の候補のソリューションを、比べているとき): `$PROJ` は、カレントではなく、対象の候補。`PROJ=$(python3 ~/.claude/skills/new-solution/scripts/new_solutions.py resolve "$PWD" [<候補名>])` で決める (終了コード 2: 候補が複数 → 一覧を示して、ユーザーに質問する。3: 対象がない)。以降の `CLAUDE.md` や `docs/` は、`$PROJ` の下 (その候補のコピー)。**他の候補は、読まない・書かない。** ウォッチャーは、その候補のフォルダで、起動されている必要がある。

## ビルド実行 (1回分)

必ず同梱スクリプトを使う。自分で flag を作ったり待機ループを書いたりしない。
**スクリプトは、この Skill のフォルダ (`~/.claude/skills/auto-build/scripts/`) のものだけを使う。** 同じ名前の古いコピー (ホーム直下の `cpp-auto-build/` など) を、探して使わない。古い版は、エラーの要約や `.claude-logs/*_summary.json` を出さず、`.claude-logs/test-results/` も扱えない。
失敗の要約 (`N errors (M unique) ...` の行と、`.claude-logs/build_summary.json`) が出ないときは、まず、古い版を実行していないか (スクリプトのパス) を確認する。

```bash
bash <このSkillのフォルダ>/scripts/build_once.sh "$PROJ" 180
```

**重要 (トークン節約と打ち切り防止):** Bash ツールの既定タイムアウトは120秒で、180秒待つスクリプトが
途中で打ち切られる。次のどちらかで呼ぶ。待機中に ls や cat で状況確認をしない (1回の呼び出しで完結する)。
- `run_in_background: true` で実行し、完了通知を待つ (推奨。待機中は何も消費しない)。
- フォアグラウンドなら Bash の `timeout` を 200000 以上にする。

スクリプトは古い `build_result.txt` / `build_error.log` を消し、`trigger_build.flag` を作り、
`build_result.txt` の出現を待つ。1行目が結果、終了コードも対応する。

| 1行目 | rc | 意味 | 次の行動 |
|---|---|---|---|
| `SUCCESS` | 0 | ビルド成功 | ループ終了。1〜2行で報告 |
| `FAILED` | 1 | **ビルド失敗** (コンパイル/リンクエラー。`build-test-loop` では、テスト失敗の意味。ここでは `BUILD_FAILED` は出ない) | 2行目以降のエラー要約を読んで修正し、再ビルド (読み方は下記) |
| `ENV_ERROR` | 4 | 環境エラー (VS/vswhere/引数など) | **ソースを直さず**、内容を報告して停止。**`no Visual Studio with C++ x86/x64 tools found` のとき: C++ ツールのない VS では、C++ のビルドができない。自動では追加できないので、ユーザーに、Visual Studio Installer で「変更」→「C++ によるデスクトップ開発」の追加を依頼して、待つ。逆に、.NET / WPF のビルドで `MSB4236` / `NETSDK1045` / `NETSDK1141` (または `dotnet` が見つからない) のときは、「.NET デスクトップ開発」の追加 (または .NET SDK のインストール) を依頼して、待つ (`build_error.log` に、その案内の行が付く)** |
| `WATCHER_NOT_RUNNING` | 3 | フラグが 15 秒以内に回収されず、ウォッチャーが処理中の印もない | 停止し、ユーザーに、`run_watcher.cmd` の起動と、対象のフォルダが同じかの確認を依頼 |
| `TIMEOUT` | 5 | 今回の実行の完了マーカーが、待ち時間内に出ない (ウォッチャーは、まだ処理を続けている) | **停止して報告。再試行しない** (ウォッチャーが空いてから、次を実行する。`build-test-loop` の「止めどき」) |
| `BAD_ARGS` | 2 | 引数・フォルダの誤り | 引数を直して、再実行 (ソースは、直さない) |

**出力の最後に `NOTE:` の行が出たとき (WPF の XAML にメニューがある):** 結果 (1 行目) と終了コードは、変わらない。`NOTE:` の指示に従う (UI テストのプロジェクトの `uitest.settings` に `desktop=visible` を書く / 設定に従い、ユーザーのデスクトップで実行されるので、実行中は、PC に触らないよう、ユーザーに伝える。2 行目が出たら、ウォッチャーが古い可能性)。WPF のメニューは、別のデスクトップでは、開かない (`build-test-loop` の `references/ui-tests.md`を参照)。

## エラー出力の読み方 (要約形式)
`FAILED` / `BUILD_FAILED` の2行目以降は、`build_error.log` を集約した要約。
```
7 errors (4 unique) in 4 files; compile 5 / link 2
[1] C2065 'cnt': undeclared identifier  x4
    MyApp/Foo.cpp(49,5)  MyApp/Foo.cpp(50,9)  MyApp/Bar.cpp(12,3)  (+1 more)
```
- 見出し: 総数 / 種類数 / ファイル数 / コンパイルとリンクの内訳。
- `[n]` は同じ (コード, メッセージ) をまとめたもの。`xN` は件数、下の行は代表の場所 (最大3つ。`(+N more)` は省略分)。
- **最初に出たエラー順。上の `[n]` ほど原因の可能性が高い。** 下のほうは連鎖エラーのことが多いので、まず `[1]` から直し、再ビルドで確認する。
- `LNK` は定義・エクスポート・ライブラリ指定の問題。ソースの宣言だけ直しても消えない。
- .NET のコード: `CS` は C# コンパイラ、`MC` / `XDG` は XAML のコンパイル (WPF。XAML の文法、`x:Class` の不一致、未定義の型など)、`NU` は NuGet の復元、`NETSDK` は SDK、`MSB` は MSBuild。
  XAML のエラーは、`.xaml` のファイルと行を指す。`obj/` 配下の生成物 (`*.g.cs` など) は、**直接編集しない** (元の `.xaml` / `.cs` を直す)。
- `other:` は解釈できなかった行 (そのまま)。
- 同じ内容は `.claude-logs/build_summary.json` にもある。ログの再読ではなく、必要なら、これを読む。
- 要約が出ない (生ログのまま) 場合は、`python3` がないか、エラー行を解釈できなかった。生ログのとおりに読む。

## ループのルール
1. ソースを修正したら `build_once.sh` を実行する。修正していない状態での再実行はしない。
2. `FAILED` なら、要約の `[1]` から順に、場所 (`file(line,col)`) の箇所を修正する。無関係なリファクタリングはしない。
3. **最大 5 回** (スクリプトの実行の合計) まで。5回目も失敗なら、残りのエラーと試した修正を報告して停止する。`TIMEOUT` / `ENV_ERROR` / `WATCHER_NOT_RUNNING` は、再試行せず、停止して報告する (`build-test-loop` の「止めどき」)。
4. **同じエラー (同じファイル・行・コード) が修正後も出る場合**は、2回目で止めて原因を調べる。
   ファイルが外部 (エディタの再保存など) で書き戻されている可能性を疑い、ユーザーに確認する。
5. `.claude-logs/` の `build.log` は詳細が必要なときだけ読む。通常は `build_error.log` で足りる。
6. 修正時はファイルの文字コード (UTF-8 BOM の有無など) と改行コードを変えない。
7. **ライブラリの不足が原因のエラー** (`C1083` include が見つからない、外部ライブラリの `LNK2019`、`CS0246` 型・名前空間が見つからない、`NU1101` パッケージが見つからない) は、**自分で `.csproj` や `.vcxproj` を書き換えて直さず**、`add-package` Skill で追加する (名前とバージョンの確認、ホスト側での取得が要る)。
8. **ビルドを通すために、警告の抑制 (`#pragma warning disable`、`<NoWarn>`、`TreatWarningsAsErrors` の解除、アナライザの無効化) を足さない。** 必要だと思うときは、理由を添えて、ユーザーに確認する。
9. `.csproj` / `Directory.Build.props` / `global.json` (対象フレームワーク、パッケージ、SDK) の変更は、ビルドエラーの直接の原因である場合に限り、必要最小限にする。変更したことは、報告の先頭で述べる。

## トークン節約
- 成功時は `build_error.log` や `.claude-logs/` を読まない。報告も1〜2行。
- 失敗時のエラー出力は、スクリプトが集約して最大40行・1行400文字にしている。足りないときだけ `build_error.log` を読む。
- ソースは、エラー行の前後だけを読む (ファイル全体を読み直さない)。
- 待機中・修正の合間に、経過の説明を書かない。

## 完了時の確認 (変更の報告)
作業を終える前に (成功でも、停止でも)、変更したファイルを一覧して、報告に含める。ユーザーが、コミットの前に、`git diff` で、変更を確認できるようにするため。
**このセッションで、自分がファイルを編集していない場合は、実行せず、「変更なし」と報告する。**

1. 変更されたファイルの一覧を取る (読み取りだけ。ステージやコミットはしない)。
   ```bash
   git -c core.fileMode=false --no-optional-locks status --short
   ```
   - `-c core.fileMode=false` を付けるのは、WSL の git が、`/mnt/c` のファイルを実行権限つきと見て、ほぼ全ファイルを「変更あり」と表示してしまうため。
   - git のリポジトリでない場合や、コマンドが失敗した場合は、自分が編集したファイルの一覧で代える。
2. **テストファイル (`Test*.cpp`、`Test*.h`、`*Test/` 配下) を編集した場合は、そのことを、報告の先頭で明示する。** テストファイルの編集は、**機械的な追従 (`include` の追加、名前・シグネチャの変更への追従) 以外は、ビルドエラーを直すためでも、事前に、ユーザーに確認する** (`build-test-loop` の「止めどき」の 5)。
3. 「コミット前に、`git diff` で変更を確認してください」と、一言添える。
4. **`git commit` と `git push` は、ユーザーの明示的な指示がない限り、実行しない。**
5. プロジェクトの設定 (`.claude/settings.json`) で、テストファイルの編集や、`git commit` に、確認が出る設定になっていることがある。
   確認が出たら、何を、なぜ、行うのかを、簡潔に説明する。拒否されたら、同じ操作を、別の方法 (別のツールやコマンド) で、行わない。

## 警告の件数 (成功時)
成功 (`SUCCESS` / `PASSED`) のとき、警告があれば、1行目の次に、**1行だけ**件数が出る。警告がなければ何も出ない。
```
warnings: 12 (5 unique): C4244 x5, C4996 x3, C4101 x2, ... (+2 more)
```
- 警告は、ビルドの成否に影響しない。**この行が出ても、ループは終了してよい。** 報告に、そのまま1行添える。
- **警告を直すのは、ユーザーに頼まれたときだけ。** 無関係な警告の修正は、リファクタリングと同じ扱い (しない)。自分が今回編集した行に由来する警告 (未使用の変数、型の縮小など) は、報告に、そう書いて、直すかを尋ねる。
- 詳細 (コード別の件数・場所) が必要なときだけ、次を実行する (読み取りだけ。`<このSkillのフォルダ>` はスクリプトと同じ場所):
  ```bash
  python3 -I <このSkillのフォルダ>/scripts/summarize_build_log.py "$PROJ/.claude-logs/warnings.log" --severity warning --root "$PROJ"
  ```
  同じ内容は、`.claude-logs/warnings_summary.json` にもある。
- **差分ビルドでは、再コンパイルされたファイルの警告だけが出る** (「すべての出力が最新」なら、件数も出ない)。件数が出ないことは、警告がないことを意味しない。

## 報告
- 成功: 回数と結果を1〜2行で (警告の件数の行があれば、それも1行で)。差分ビルドで「すべての出力が最新」でも正常。続けて、「完了時の確認」の、変更ファイルを、1行で。
- 失敗で停止: 最後のエラー、試した修正、停止理由。変更したファイルも、同様に報告する。

## ホスト側の構成 (参考)
- `trigger_build.flag`: Claude が作る。ウォッチャーが検知して削除する。
- `build_result.txt`: ビルド終了時にウォッチャーが `SUCCESS` / `FAILED` を書く (完了マーカー)。
- `build_error.log`: 失敗時のみ作成。環境エラーは先頭が `[ENVIRONMENT ERROR - not a source code problem]` (VS / .NET SDK が見つからない `MSB4236` `NETSDK1045` `NETSDK1141`、NuGet のソースに届かない `NU1301` を含む)。
- `.claude-logs/`: `build.log` / `errors.log` / `warnings.log`。
