## 4. 落とし穴 (2026-11-25 に分かったこと)
- **自動ビルドは、常に Debug。** `watch_and_build.ps1` には `-Configuration` の引数があるが、`run_watcher.cmd` も `build_once.sh` も、渡さない。**Release の確認は、ユーザーが VS で、構成を Release にして、手でビルドする。** `--debug` は、VS の今の構成のまま動く。
- **スラッシュコマンド (`/new-solution`・`/add-project` ほか) は、Claude からは実行できない** (`disable-model-invocation`)。実機確認の依頼文に、「`/new-solution` で作って」と書かない。**ユーザーが、自分で打つ**と書く。
- **サンドボックス:** カレントの外 (`ImageSampleApp` など) には、書き込めない (`git rm`・コミットも不可。ユーザーが、コマンドを実行する)。`git pull` / `git push` は `github.com`、`gh` は `api.github.com` を、`allowed_domains` に入れる (入れ忘れると、拒否される)。`git push` のあとの「上流の設定のヒント」は、無害。
- **`solution_state.py` は、`python3 -I` では動かない** (`import add_common` が失敗する。`-I` は、スクリプトのフォルダを、検索に入れない)。SKILL のとおり、`python3 <パス>` で実行する。
- **`vs-debug` の `--inspect`:** Release の C++ では、読めない変数は `NAME = (unavailable)` (型は出ない)。**MFC の DLL のシンボルがないと、`cmdInfo` のような変数も読めない** (値の欄に、VS の文言が入る)。最適化で消えた変数は、LOCALS に出ない。`this` が `0x…0a {???}` のように、読めても壊れた値は、`(unavailable)` にならない (VS 側の挙動)。
- **実機確認の依頼文の作り方:** (1) 空の新しい確認用フォルダを使う。(2) ウォッチャーは、フォルダごとに起動し直す。(3) スラッシュコマンドは、ユーザーが打つと書く。(4) 結果は、段階ごとに貼ってもらう。(5) 期待は、**ツールの設計を読んでから**書く (MX6 では、「断られる」と期待したが、自由な依頼は、断られる経路ではなかった)。
- **教訓 (v2.105.2 の誤り):** 「`KIND: mixed` を判定できる」ことと、「混在の最初の 1 歩が通る」ことは、別。**流れが通るかは、実機 (または通しのテスト) で確かめる。** 判定の機能があるだけで、「対応済み」と書かない。
- **Token の測り方:** `python3 -I tools/token_report.py [--timeline] <セッションの .jsonl か、そのフォルダ>`。ログは `~/.claude/projects/<作業フォルダの / を - にした名前>/`。使い方は USAGE 4。
