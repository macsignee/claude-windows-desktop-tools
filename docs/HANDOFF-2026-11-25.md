## 4. 検討中の構想 (ユーザーの質問から。まだ、決まっていない。着手するかを、聞く)
**ユーザーの狙い:** (1) Windows のホストから、リアルタイムに、Claude へデータを送りたい。(2) Visual Studio のデバッグ情報を、ステップ単位で、Claude の分析に回したい。(3) UI テストの仕組みを使って、デバッグを行いたい。

### 4-1. リアルタイムのデータ送信 (localhost の通信)
- **Claude の Bash (サンドボックス) から、Windows 側のサーバーへ、localhost で直接つなぐことは、できない。** コマンドごとに、専用の隔離されたネットワークで動き、外側へは、`ECONNREFUSED` か `ENETUNREACH` になる (外へ出る通信は、フィルタつきのプロキシだけ)。逆向き (Windows から Claude のサーバーへ) も、同じ理由で届かない。
- 可能な方法:

| 方法 | 仕組み | リアルタイム性 |
|---|---|---|
| **A. ファイル + 監視 (おすすめ)** | Windows 側が、`/mnt/c/...` のログに追記し、Claude が `Monitor` ツール (`tail -f` など) で、行が増えるたびに通知を受ける | 行ごと。ただし、Claude が応答中なら、ターンの切れ目に受け取る |
| B. MCP サーバー | Windows 側に、MCP サーバー (localhost の HTTP) を立て、Claude Code 本体が、クライアントとしてつなぐ。サンドボックスの制限は、Bash にだけ効く | Claude が呼んだときに、最新のデータが返る (プル)。設定と常駐が要る |
| C. 今の設計 | ウォッチャーが結果ファイルを書き、Claude が、スクリプトで読む | ポーリング |

- **「リアルタイム」の意味:** Claude は、ターンで動く。処理中の Claude に、データを割り込ませることは、できない。
- **未検証:** A (`Monitor` で `/mnt/c` のログを監視できるか。Windows のドライブの共有は、変更の通知が不安定なことがある)、B。`Monitor` は、後から読み込む形のツール。
- B のセキュリティ: `127.0.0.1` だけで待ち受け、トークンで認証する。
- **ユーザーに聞くこと:** 何を、リアルタイムに渡したいか。(VS のデバッグ出力・ブレークの通知 → A。アプリの実行中のログの監視 → R15 と A。Claude から、いつでも問い合わせたい → B)

### 4-2. ステップ単位のデバッグ情報を、Claude の分析に回す
- **すでに、できている (`vs-debug`):** `--step over|into|out [歩数]` (1 歩ごとの場所・ソースの行・変わった変数 `CHANGED:` のトレース)、`--eval "<式>"` (読み取りだけ)、`--inspect` (例外・呼び出し履歴・ローカル変数)、`--output` (デバッグ出力)。
- 制限 (方針。変えられる): 1 回の依頼で、合計 30 歩まで。同じ場所に 3 回戻ったら止まる。Claude が、ステップごとに、コマンドを打つ (プル)。**1 歩ごとにターンが増えると、Token の費用が増える** → 歩数をまとめて呼ぶ (`--step over 10`)。
- 改善の余地: 「値が変わるまで進める」、長いトレースの要約。

### 4-3. UI テストの仕組みを使った、デバッグ
- **壁 (確認済み):** ウォッチャーは、**1 本のループで、フラグを順番に処理**する。UI テストは、その中で実行され (`Start-Process` + `WaitForExit`)、終わるまで待つ。**UI テストの実行中は、`trigger_vs.flag` (`--inspect`・`--step` など) が処理されない。** UI テストが、ブレークポイントで止まったアプリを操作すると、テストが待たされ、ウォッチャーも待たされる → Claude が `--step` を頼んでも、受け付けられない (デッドロック)。
- UI テストは、アプリを自分で起動する (`Application.Launch`。ひな形 `add_ui_tests.py` の `BASE_CS`)。**VS のデバッガーが起動したアプリに、つなぐ (`Attach`) 機能は、ない。**
- UI テストの既定は、別のデスクトップ。VS が起動したアプリは、ユーザーのデスクトップにある → 同じデスクトップ (`desktop=visible`) にする必要がある。
- 案:

| 案 | 流れ | 規模 |
|---|---|---|
| **A. 順番に動かす (おすすめ)** | (1) `--break` でブレークポイントを置く。(2) `--debug` で、VS がアプリを起動する。(3) **UI テストを「アタッチ」モードで実行**する (起動済みのアプリにつなぎ、操作を行い、最後の操作がブレークポイントで止まっても、**待たずに終了**する。待ちの時間切れを、想定内として扱う)。(4) ウォッチャーが空くので、`--inspect` と `--step` が通る | 中。UI テストのひな形に、アタッチモード (環境変数 `UITEST_ATTACH_PROCESS` など) を足す。ウォッチャーに、`attach=<プロセス名>` を足す。Skill に手順を足す |
| B. ウォッチャーを並行にする | UI テストを待たずに、次のフラグを処理する | 大。ウォッチャーのループの作り直し。結果の混線や、二重実行の対策が要る |
| C. 終了後に、状態を見る | UI テストで、操作を再現し、最後にアプリを開いたままにする (`--hold`)。そこに VS をアタッチして、`--pause` と `--inspect` で、状態を見る (`vs-ide.ps1` に、アタッチの操作を足す) | 小〜中。ステップ実行ではなく、最後の状態の分析。ただし、`--hold` の間も、ウォッチャーは、テストの終了を待つので、アタッチの依頼が、処理されない可能性がある (要確認) |

- **A の未確認の点 (実機で、小さな試作で確かめる):** (1) ブレークポイントで止まったアプリへの UIA の操作が、待たされるのか、すぐ返るのか (WPF・WinForms・MFC で違う可能性)。(2) VS が起動したアプリと、アタッチしたテストが、同じデスクトップで動くか。(3) 待ちの時間切れを、「想定内」にしても、テスト結果の扱いに、不都合がないか。
- **試作の進め方 (提案):** `MfcScope` か `PS5` の確認用フォルダで、手で行える範囲で、(1)〜(3) を確かめる。うまくいけば、A を、テストを先に書いて、正式に作る (ホスト側・ひな形・Skill)。
- **ユーザーに聞くこと:** ふだん、どの種類のバグを追いたいか。(ボタンを押したあとの、内部の値のずれ → A で足りる。UI 操作の途中で、ゆっくり進めたい → B が要るかもしれない)

## 5. 落とし穴 (2026-11-25 に分かったこと)
- **自動ビルドは、常に Debug。** `watch_and_build.ps1` には `-Configuration` の引数があるが、`run_watcher.cmd` も `build_once.sh` も、渡さない。**Release の確認は、ユーザーが VS で、構成を Release にして、手でビルドする。** `--debug` は、VS の今の構成のまま動く。
- **スラッシュコマンド (`/new-solution`・`/add-project` ほか) は、Claude からは実行できない** (`disable-model-invocation`)。実機確認の依頼文に、「`/new-solution` で作って」と書かない。**ユーザーが、自分で打つ**と書く。
- **サンドボックス:** カレントの外 (`ImageSampleApp` など) には、書き込めない (`git rm`・コミットも不可。ユーザーが、コマンドを実行する)。`git pull` / `git push` は `github.com`、`gh` は `api.github.com` を、`allowed_domains` に入れる (入れ忘れると、拒否される)。`git push` のあとの「上流の設定のヒント」は、無害。
- **`solution_state.py` は、`python3 -I` では動かない** (`import add_common` が失敗する。`-I` は、スクリプトのフォルダを、検索に入れない)。SKILL のとおり、`python3 <パス>` で実行する。
- **`vs-debug` の `--inspect`:** Release の C++ では、読めない変数は `NAME = (unavailable)` (型は出ない)。**MFC の DLL のシンボルがないと、`cmdInfo` のような変数も読めない** (値の欄に、VS の文言が入る)。最適化で消えた変数は、LOCALS に出ない。`this` が `0x…0a {???}` のように、読めても壊れた値は、`(unavailable)` にならない (VS 側の挙動)。
- **実機確認の依頼文の作り方:** (1) 空の新しい確認用フォルダを使う。(2) ウォッチャーは、フォルダごとに起動し直す。(3) スラッシュコマンドは、ユーザーが打つと書く。(4) 結果は、段階ごとに貼ってもらう。(5) 期待は、**ツールの設計を読んでから**書く (MX6 では、「断られる」と期待したが、自由な依頼は、断られる経路ではなかった)。
- **教訓 (v2.105.2 の誤り):** 「`KIND: mixed` を判定できる」ことと、「混在の最初の 1 歩が通る」ことは、別。**流れが通るかは、実機 (または通しのテスト) で確かめる。** 判定の機能があるだけで、「対応済み」と書かない。
- **ウォッチャーは、1 本のループで、フラグを順番に処理する。** 長い処理 (UI テストなど) の間は、ほかのフラグ (`trigger_vs.flag` など) が、待たされる。複数の操作を、同時に動かす構想は、この構造を、まず考える (第 4-3 節)。
- **Token の測り方:** `python3 -I tools/token_report.py [--timeline] <セッションの .jsonl か、そのフォルダ>`。ログは `~/.claude/projects/<作業フォルダの / を - にした名前>/`。使い方は USAGE 4。

```bash
cd ~/src/claude-windows-desktop-tools && for t in tests/*.sh; do bash $t || echo "FAILED: $t"; done
```
`fake_watcher_test.sh` の `FAILED` の表示は、疑似の失敗テストの想定出力。`tools/check-formats.sh` も、実行する。

## 7. 配布
- Skill・規約: `./install/install.sh --skills-only` / `--rules-only`。
- ホスト側 (`host-tools/`): `./install/install.sh --host-only` のあと、ウォッチャーを再起動する (今は、v2.105.1 の `vs-ide.ps1` まで配布済み)。
- 配布のあとは、配布先の `VERSION` で確かめる (例: `cat ~/.claude/skills/add-project/VERSION`)。
