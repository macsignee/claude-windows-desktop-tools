## 1. 作業の約束事 (旧版の第 1 節に、追加・補足)
- **コミット・push・PR は、ユーザーが指示したときだけ。** 頼まれていないのに実行すると、自動モードの判定で、止められる (今回も 1 回、起きた)。「コミットして」でコミット、「push して」で push、「PR を作って」で PR。マージは、ユーザーが GitHub で行う。**1 回の「コミットして push して PR を作って」で、3 つとも行ってよい。**
- **コミットの前に、`git branch --show-current` で、ブランチを確かめる。** 今回、`git switch -c` が効かず、コミットが `main` に乗ったことがあった (`git branch -f main origin/main` で戻した)。
- **`git add -A` を使わない。** 元から未追跡の `.claude/` `.mcp.json` `poc/` `q` `docs/HANDOFF-2026-11-17.md` を巻き込む。**変更したファイルを、名前で `git add` する。**
- **GitHub に触れるコマンドは、`allowed_domains` に `github.com` と `api.github.com`** (`git push` / `git pull` / `gh pr create`)。`gh pr create` は、`--head <ブランチ> --base main` を付けると確実。
- **コード・Skill・検査の変更は、先にテストを書き、失敗 (Red) を確かめてから、実装する** (`tests/`)。**コミットの前に、全件を通す:** `for t in tests/*_test.sh; do bash $t >/dev/null 2>&1 || echo "FAIL $t"; done` (`git_once_test.sh` は、約 100 秒かかる。timeout を 400000 以上に)。形式の検証は `bash tools/check-formats.sh`。
- **版:** 文書だけ・規約と Skill の文言だけの PR はパッチ。`VERSION` と `CHANGELOG.md` を、同じ PR で更新する。ホスト側 (`host-tools/`) を変えたときだけ、`host-tools/HOST_VERSION` も上げる (ウォッチャーの再配布と再起動が要る)。
- **PowerShell は、WSL のサンドボックスから、実行できない** (`powershell.exe` の呼び出しが拒否される)。ホスト側 (`host-tools/lib/*.ps1`) の変更は、静的な検査と疑似ウォッチャーのテストで確かめ、**実機の確認は、ユーザーが行う** (診断用の PowerShell を、ユーザーが `powershell.exe` で実行して、結果を貼る)。
- **サンドボックスは、`/mnt/c` に書けない。** Windows 側のフォルダの変更・生成は、ユーザーが行う。私は、結果のファイル (`build_result.txt`・`vs_output.txt`・`git_output.txt` など) を、読み取りで確かめる。
- **記憶ファイル** (`~/.claude/projects/-home-shigene-makoto/memory/`) は、Bash では書けない。**Edit / Write を使う。**
- **実機の確認の進め方 (今回、うまくいった形):** ユーザーが、確認用のフォルダで Claude Code を起動し、私が渡した依頼文を貼る。依頼文には、「fork には任せず、直接実行して。出力を省略せずに示して」を付ける。**1 つずつ**、見る点を示し、結果が貼られたら、ファイル (`/mnt/c/...`) で裏づけてから、合否を伝え、次の手順を渡す。終わったら、TEST-PLAN・REMAINING-CHECKS・NEXT-STEPS・HANDOFF に記録する (1 本の PR)。

## 6. 技術メモ (非自明なもの)
- **サンドボックスは、書き込みを禁じるファイルに、`/dev/null` を重ねる** (`mountinfo` で確認)。**影響が 2 つ:** (1) `.git/config` と `.git/config.lock`: `git_once.sh` が結果を待つ間だけ、Windows の `git` にも、`config.lock` が見え、上流 (`branch.<名>.*`) が書けない (`push -u` は、書けなくても、push が成功するので、気づけない)。対処: ウォッチャーが、結果のマーカーを書いたあとに、`git branch --set-upstream-to` を再試行する (`UPSTREAM_PENDING` → `Complete-GitUpstream`)。上流がなくても、同じ名前の `origin/<ブランチ>` で比べ、push できる。(2) `.bashrc`・`.gitconfig`・`.mcp.json`・`.vscode`・`.idea`・`.claude/*` などの空ファイルが、Claude Code のコマンドが動く間、作業フォルダに見える。**VS の「すべてコミット」で、コミットに入る。** 規約に注意書きがある (`rules/git-wsl.md` の「コミットの前に」の 4)。
- **`vs-debug` のステップ実行 (v2.101.0):** 非ブロックの `StepOver($false)` などで呼び、モードを確かめて待つ (`STEP_TIMEOUT` は 15 秒、`--continue` は 20 秒)。実機で分かった動き: `--step out` は代入の前の行に戻る。1 行の `for` は F10 のたびに同じ行に止まる。`--pause` は任意のスレッドで止まる。`--reload` は git の差分に頼る (git 管理外では `NOT_A_REPO` でスキップ)。外部コードでも場所は出る (取得したソースのコピー `.vsdbgsrc`)。`vs_once.sh` の操作の順: open → break → debug → 実行系 (指定した順) → inspect → output → status。読み取りだけ・実行系だけのときは、VS を起動しない。
- **`git-remote` (v2.102.x):** `git_once.sh <フォルダ> --status | --fetch [リモート名] | --push [--remote 名] [--set-upstream] [--allow-main]`。終了コード: 0 OK・1 FAILED・2 BAD_ARGS・3 WATCHER_NOT_RUNNING・4 ENV_ERROR・5 TIMEOUT・6 AUTH_REQUIRED・7 REJECTED。ホスト側は `host-tools/lib/git-remote.ps1`。入力待ちをしない (`GIT_TERMINAL_PROMPT=0`・`GCM_INTERACTIVE=never`)。認証が要るときは `AUTH_REQUIRED` (ユーザーが VS で 1 回サインインする)。
- **MFC のひな形:** `skills/new-solution/scripts/new_solution.py` の `MFC_FILES` (SDI)・`MFC_MDI_FILES`・`MFC_DIALOG_FILES`。標準 DLL の層のアプリクラスは `skills/cpp-test-first/scripts/add_layer.py`。`CWinApp` は `ID_FILE_NEW` / `ID_FILE_OPEN` を割り当てない (TN022。派生クラスに `ON_COMMAND` が要る)。`DECLARE_MESSAGE_MAP` だけで `BEGIN_MESSAGE_MAP` がないと、リンクエラー (`mfc-check` の MAP004)。
- **ps1 は UTF-8 BOM + CRLF、`.cmd` は CP932 + CRLF。** 規約・文書は、UTF-8 (BOM なし)・LF。コミットの前に `tools/check-formats.sh`。
- **サイズの上限 (テストで確かめる):** 規約と Skill のサイズは、テストが見ている (`rules_split_test.sh` など)。足すときは、先に `references` へ移す。
