# UI と画面モデルの開発の手引き (2026-11-16 の決定を反映。設計の記録)

WPF・WinForms・MFC のフォーム (ダイアログ・サブウィンドウ) を、**リポジトリをラップした「画面モデル」** を通して操作する形に統一し、UI テストファーストでも、ロジック先でも、同じ着地点に着くようにするための手引き。

前版の「フォーム = リポジトリを直接参照」という整理は白紙にした。既存の仕様の改訂は 8 章にまとめる。画面モデルの採用と、WinForms での Presenter との共存 (3 章) は決定済み。

## 1. 構造と用語

```
フォーム (View) ──▶ 画面モデル (インターフェース) ──▶ リポジトリ (インターフェース)
 WPF / WinForms / MFC     ロジック層                       データ層 (本物) / Fake
```

| 名前 | 役割 | 置き場所 |
|---|---|---|
| **画面モデル** | ViewModel に相当する。フォームが見る状態、フォームから呼ぶ操作、入力の検査、変更の通知を持ち、リポジトリを呼んで永続化・取得を行う。**WPF・WinForms・MFC で共通の考え方で作る** | ロジック層。UI の型を使わない |
| **リポジトリ** | データベース・API などの違いを隠す | インターフェースはロジック層かデータ層、本物はデータ層 |
| **フォーム** | 画面モデルの状態を表示し、利用者の操作を画面モデルの操作に変えるだけ。規則・判断を持たない | View 層 |
| **Presenter** (WinForms だけ。任意) | 画面モデルでは書けない、WinForms 固有のもの (ダイアログを開く、画面遷移の実行、フォーカス、UI スレッドへの戻し、Form の開閉、複数の View の調停) を担当する薄い層。**状態も規則も持たない** | WinForms の Presenter の置き場所 (既存の規約のとおり) |

フォームは、画面モデルのインターフェースだけを知る。画面モデルはリポジトリのインターフェースだけを知る。どちらも、実装はコンストラクターで受け取る (`new` しない)。

**WinForms だけ、Presenter を併存させる** (採用済み。3 章の末尾)。WPF は ViewModel が両方を兼ね、MFC はダイアログクラスが兼ねる。三つの UI で共通なのは画面モデルで、UI 固有の橋渡しだけが UI ごとに違う。

## 2. 画面モデルの契約

言語・UI の枠組みによらず、画面モデルは次の五つを公開する。これが、フォームと画面モデルの境界である。

| 項目 | 内容 | 例 |
|---|---|---|
| 状態 | フォームが表示する値。入力欄の値、表示専用の値、一覧、選択 | `Name`、`Greeting`、`Items` |
| 操作 | フォームから呼ぶもの。**操作ごとに「実行できるか」も公開する** (ボタンの有効 / 無効になる) | `Save()` と `CanSave` |
| 検査 | 入力の誤りと、その文言。フォームは表示するだけ。**検査の実行は `Validate()`、結果は `IsValid`** (決定。`Errors` / `HasErrors` の名前は使わない)。**誤りは、言語に依存しない形 (種別・対象のプロパティ・引数) で公開し、文言は持たない** (決定。国際化のため。下の「文言・メッセージの持ち主」)。公開の形は、下の「検査 (Validate / IsValid)」(決定) | `Validate()`、`IsValid` |
| 変更の通知 | 状態・検査・実行可否が変わったことを、フォームに知らせる | イベント / コールバック |
| 結果 | 確定は `Commit()` の `bool`、失敗は状態 `Failure`、取消は `Cancel()` (下の「操作の失敗」) | `Commit()`、`Failure` |

作り方の規則:
- **画面モデルは、すべての画面・ダイアログで必須 (例外なし。決定 2026-11-16)。** 表示専用の画面や、入力が 1 つだけの単純なダイアログでも、画面モデルを置く (Form が、リポジトリ・Model を直接使う構成は、採らない)。構造をそろえ、「Form がデータ層を直接参照しない」検査を、例外なしで書けるようにするため。薄い画面モデルになるのは受け入れ、ひな形が骨格を生成して、手書きを減らす。WPF・WinForms・MFC のすべてに適用する (**MFC の規約にも、必須を明記する**。規約の反映の段階)。計画には、画面モデルの行を、必ず書く。
- **UI の型を使わない** (コントロール、`HWND`、`CString` の UI 依存、メッセージボックス)。単体テストが、フォームなしで回ることが条件である。
- **MFC の例外 (決定):** MFC では、ロジック層・データ層に、次の MFC のクラスを使ってよい。
  - **使ってよい:** `CString`、`CArray` などのコレクション (`CList`・`CMap`・`CStringArray`・`CTypedPtrArray` など)。**CObject 派生のクラスも、純粋にデータを保持するもの、またはモデルの実装であれば、使ってよい** (CObject 派生は、名前空間に入れず、`DECLARE_DYNAMIC` などを書く。`rules/mfc-cpp.md`)。
  - **使わない:** ウィンドウのラッパー (`CWnd`、`CDialog`、`CEdit` など。`HWND` も)、Document/View などの MFC のフレームワーク。単体テストが、フォームなしで回る条件のため。
  - コレクションの操作に拡張が必要なときは、**別途、C++ のイテレーターの実装を足す** (今回の対象外)。
- **モーダル:** 編集中の値を画面モデルの内部に持ち、確定 (`Commit`) で初めてリポジトリへ書く。取消では何も書かない。
- **モードレス:** 入力のたびに、すぐ反映する。不正な値は反映せず、エラーを示す。
- **検査 (Validate / IsValid。決定 2026-11-16):**
  - **`Validate()`** は、現在の入力から検査を実行し、**`ValidationResult` (エラーの一覧) を返す。** 各エラーは、**種別 (列挙)・対象のプロパティ (`PropertyId`)・引数**。**純粋** (状態を持たず、副作用がない)。複数の入力欄の誤りを、一度に返せる。
  - **`IsValid`** は、**`bool`**。`CanXxx` と同じ扱い (C# はプロパティ、C++ は `const` のメソッド)。現在の入力から毎回計算する純粋な値で、意味は「`Validate()` の結果が空」。
  - **変更の通知に、`IsValid` を含める** (`CanXxx` と同様)。Form は、通知を受けて、必要なら `Validate()` を呼び直して表示する。入力欄ごとの表示は、結果を、対象のプロパティで絞る。
  - **`Commit()` は、内部で `Validate()` を行い、誤りがあれば `false` を返す** (UI が `IsValid` を呼んだかに、依存しない)。
  - **種別の列挙は、画面モデルごと** (名前の案: `<画面名>Error`)。ひな形が生成し、UI 層の対応表 (列挙 → ID) も、画面ごとに 1 つ。共通の誤り (必須、長さ超過) も、画面ごとの列挙に持つ。
  - **`ValidationResult<TError, TProperty>` の形 (決定 2026-11-16):** 種別と `PropertyId` を型引数にした共通の部品。画面ごとの別名は、ひな形が生成する。`Observable` と同じ方式で配る (実物のファイルを、ロジック層へコピー。C# 用と C++ 用で 1 ファイルずつ)。結果は、コレクションではなく、エラーの一覧を持つ薄いラッパー (`IsEmpty` つき)。
    - **C#:** `Errors` プロパティ (全件。`IReadOnlyList`。LINQ でも操作できる)、**`GetErrors(property)`** (欄で絞る補助。拡張メソッドでよい)、`IsEmpty`。
    - **C++:** **`GetErrors()`** (全件)、**`GetErrors(property)`** (欄で絞る)、`IsEmpty()`。C++ の取得には `Get` を付ける (MFC の `GetSize` / `GetCount` と、`rules/cpp-common.md` の例に合わせる)。述語は `Is` / `Can` (`IsValid()`、`CanSave()`、`IsEmpty()`)。
    - **絞り込みの呼び出しは、2 つの言語で `GetErrors(property)` にそろえる** (テストとアダプターが、共通の形で読める)。
    - **案 (C++ の状態の名前):** C# の `Name` は、C++ では `GetName()` / `SetName()`。
  - **引数 (`ValidationArg`) (決定 2026-11-16。後で見直す可能性がある):**
    - **C++:** 保持する型は 1 つ (`std::variant<long long, double, std::wstring>`)。専用のクラス `ValidationArg` で包み、コンストラクターの過負荷で、受け付ける型を広げる (整数、実数、ワイド文字列 (`std::wstring` / `std::wstring_view` / `const wchar_t*`)、`CString` 風の型 (`GetString` / `GetLength` を持つ型。コンセプトで受け付け、MFC のヘッダーに依存しない))。`bool` と `char` は、削除した過負荷にして、取り違えを防ぐ。**ナロー文字列 (`std::string` / `std::string_view` / `const char*`) は、暗黙の変換を持たせず、`FromUtf8` / `FromAnsi` で文字コードを明示する** (どちらも、この 3 つを受け付ける。**`const char*` の `nullptr` は、空文字列として扱う** (実質の意味が、空文字列と同じとみなせるため。`std::string_view` を `nullptr` から作ると動作が未定義になるので、`const char*` の過負荷は、別に持つ))。 取り出す側は、3 つの型だけを `std::visit` で整形する。**コンセプトを使うので、C++20 を前提とする。**
    - **C#:** `object` の一覧 (規約で、数値と文字列に限る)。
    - 数値は、整形済みの文字列にしない (桁区切りなどを、言語ごとに変えるため)。
  - **誤り (`ValidationError`) の形 (決定 2026-11-16):** 種別 (列挙)・**対象の欄の一覧 (`Properties`)**・引数。**一覧が空なら、欄に紐づかない画面全体の誤り** (`IsScreenLevel`)、1 件なら 1 つの欄の誤り、2 件以上なら複数の欄にまたがる誤り。`Property` を 1 つだけ持つ形、`None`、null 許容、`[Flags]` の列挙は、採らない。
    - **一覧の先頭が、主たる欄** (文言は、主たる欄の隣に表示し、残りの欄は強調だけ)。
    - **`GetErrors(property)` は、その欄が一覧のどこかに含まれる誤りを、すべて返す。** 欄のない誤りは、`GetScreenErrors()` (名前は仮) で取り出す。
    - 同じ問題を、欄ごとに複数件出さない (まとめの表示で、二重に並ぶため)。
    - 一覧の比較 (テスト) は、順序を含める。
  - **操作の失敗 (決定 2026-11-16。簡略化した形)。** 入力が正しくても、実行してみないと分からない失敗 (保存時のデータベースのエラー、同時更新の衝突、接続の失敗など) は、`Validate()` / `ValidationResult` に入れない (`Validate()` は、現在の入力だけから決まる純粋な関数で、混ぜると `IsValid` の意味が崩れる)。
    - **`Commit()` は `bool` を返す** (`true` = 確定、`false` = 検査の誤り、または失敗)。**理由は、戻り値ではなく、状態で読む:** 検査の誤りは `Validate()` / `IsValid`、失敗は **`Failure` (C# は `Failure? Failure`、C++ は `std::optional<Failure> GetFailure() const`)**。結果の型 (`CommitResult<...>`) は作らない (正常系で、使わない中身が付いてくるノイズを避ける)。`false` のときの表示は、`Commit()` の中で通知を出し (検査の誤りなら `All`)、いつもの更新の経路 (`OnModelChanged`) で行う。最初の誤りの欄へフォーカスを移したいときは、UI が `Validate()` を呼ぶ。区別が必要になったときは、戻り値を 3 区分の列挙 (`Committed` / `Invalid` / `Failed`) に変えられる (呼び出し側の修正が要る)。
    - **`Failure` は、種別と引数だけ** (型引数なし。対象の欄は持たない。欄に関係する失敗 (`Duplicate` など) も、まず画面全体の誤りの一覧に表示する。必要になったら、`Properties` を任意の項目として足す)。**直近の失敗を保持し、次の編集、または次の `Commit()` の開始で消す** (消す規則を忘れると、古い失敗が残って見える)。変更の通知に `Failure` を含める。
    - **失敗の種別の列挙は、ソリューションに 1 つ** (生成するファイル。画面固有の値は、開発者が、同じ列挙に直接足し、値の名前に画面名をつけて区別する。2 つの列挙の `variant` にしない)。初期の値 (案): `Unavailable` (接続できない)、`Timeout`、`Conflict` (同時更新の衝突)、`NotFound` (他の人が削除した)、`Duplicate` (一意の制約に違反)、`Unexpected`。日本語の表は、`MessageFormatter` の既定の実装 (ロジック層。ひな形が生成)。
    - **失敗の流れ:** データベースの例外 → 本物のリポジトリが、種別つきの例外 **`RepositoryException`** に変換して投げる (リポジトリの責任。契約テストで確かめる) → 画面モデルが捕まえて `Failure` にする。**画面モデルが変換するのは、リポジトリが定義した例外 (`RepositoryException`) だけ。それ以外 (プログラムの誤りの例外) は、握りつぶさず、そのまま伝え、アプリ全体の未処理の例外の受け口で扱う。** UI 層は、リポジトリの例外の型を知らない。失敗したら、画面モデルの状態は変えずに残す (再試行できる)。
    - **Fake リポジトリの失敗の再現:** 単体テストは、Fake の専用メソッド (インターフェースにはない): `FailNext(種別)`、`FailWhen(操作, 種別)`。UI テスト (別プロセス) は、**`APP_MODEL` の値を `fake:<シナリオ名>` の形に拡張する** (例: `APP_MODEL=fake:SaveConflict`。`APP_FAKE_SCREENS=NameEdit:InvalidName` と同じ書き方)。契約テストは、本物でも再現できる失敗 (`Duplicate`、`NotFound`) を含め、再現できない失敗 (`Unavailable`) は、Fake だけのテストとして別に書く。
    - **表示:** 失敗の文章は、画面全体の誤りの一覧 (`ScreenErrorTexts` など) に出し (`MessageFormatter` が作る)、重大なものは、`IDialogService` 越しのメッセージボックスも可。
    - **取消:** `Commit()` の結果ではなく、`Cancel()` (結果なし) か、利用者が閉じる操作。2 章の契約の「結果」の項の「確定・取消・失敗」は、ダイアログの終了の結果 (OK / キャンセル) と、`Commit()` の戻り値と `Failure` の読み方、として整理し直した。
    - 非同期の `Commit()` (保存に時間がかかる画面。実行中の状態の公開が要る) は、今回は決めない。
  - **`PropertyId` は、通知の識別と、誤りの対象の欄で兼ねる (決定 2026-11-16)。** 画面ごとに列挙は 1 つ (UI 層の「欄 → コントロール」の対応を、通知の更新と誤りの表示で共用できる)。**取り違え (誤りの対象に `CanSave` や `All` を入れる) への対策:** ひな形が、入力欄かどうかを判定する補助 (`IsInputField(id)`) を生成し、画面モデルの単体テストで、`Validate()` が返す誤りの対象が、入力欄だけであることを確かめる。
  - **並び順・等価・名前 (決定 2026-11-16):** (1) **誤りの並び順は、検査の規則を書いた順** (画面の表示とテストが安定する)。(2) **等価の比較:** C# は `record struct`、C++ は `operator==`。(3) **.NET の既存の `ValidationResult` (`DataAnnotations`) とは、名前空間で分ける:** 名前は `ValidationResult` のままにし、**ソリューションの名前空間の配下** に置く (配下のサブ名前空間の名前は、ひな形の段階で決める)。
  - **未決 (ValidationResult):** なし (操作の失敗の詳細も、上のとおり決定済み)。
- **文言の扱い (決定 2026-11-16。以下の、リソースに関する決定は、「移行後の姿」に位置づけ直す):**
  - **現状:** 画面モデル (`ScreenModel` / `ViewModel`) は、**画面に出す文章を、状態に持ってよい** (制限を緩和。国際化のニーズが高くなく、文章を持たせない実装は、コストが高いため)。ただし、「準備」として、文章を作る処理を **`MessageFormatter` に集約する。**
  - **`MessageFormatter`:** C# は `IMessageFormatter`、C++ は `MessageFormatterInterface`。`Format(種別, 引数)` が、文章を返す。**既定の実装は、ロジック層に置く日本語の表** (列挙 → 書式文字列。ひな形が、列挙の全値の行を生成する)。画面モデルは、日本語のリテラルを直接書かず、formatter から文章を得る。**文章を持つ状態の名前は、`〜Text` / `〜Message` に統一する** (あとで検索して、廃止できる)。**文章の元の値 (件数など) も、数値の状態として公開する** (UI 層が、将来、自前で整形できる)。検査の誤りは、決定済みの形 (種別 + 対象の欄の一覧 + 引数) のまま。
  - **移行 (文章を持たせない実装へ。必要になったとき):** UI 層が、リソース (`.resx` / `STRINGTABLE`) を引く `MessageFormatter` の実装を作り、組み立てる場所で差し替える。`〜Text` の状態は廃止して、UI が、種別と引数から、直接 formatter を呼ぶ。画面モデルの本体は、変わらない。
  - **案内文と業務の生成文の線引き (決定):** 基準は、「**文章が画面の外に出るか。言語を決めるのは、操作者か、業務か**」。**案内文** (検査の誤り、失敗、確認、状態の表示) は、操作者の UI の言語で決まり、画面モデルは種別・対象・引数を返す (移行後は、UI 層のリソース)。**業務の生成文** (挨拶文、帳票の文面、メール本文、エクスポートされるテキスト) は、業務の要件で決まる (例: 英語の操作者が、日本語の顧客へ送る請求書は、言語が顧客で決まる)。ログは、開発言語 (日本語)。**業務の生成文は、当面、ロジック層に日本語で書く。** 多言語の出力が業務の要件になったら、出力する言語を引数に取る、業務の機能にする (UI 層のリソースを使わない)。業務の生成文は、文字列の状態として持ってよく、単体テストでも、文言で検査する (言語が、業務の仕様で決まっているため)。
  - **先に決めた、リソースに関する項目 (期待値をリソースから引く、`APP_CULTURE`、MFC の `STRINGTABLE` を読むテスト補助、擬似ローカライズ、完全性のテストのリソース版) は、「移行のときに実施」に移す。** 現状の完全性のテスト: 列挙の全値に、日本語の表の行があることを、単体テストで確かめる。
  - **WPF (決定。別案):** `INotifyDataErrorInfo`・変換器・見た目のテンプレートは使わない。ViewModel の基底クラス (生成) が、`ErrorTexts` (欄の名前 → 文章。`MessageFormatter` で作る。`Item[]` の変更を通知する) と、`ScreenErrorTexts` (欄のない誤り) を公開し、XAML は普通のバインディング (`<TextBlock Text="{Binding ErrorTexts[Name]}"/>`)。キーは `PropertyId` の列挙の名前。国際化への移行は、`MessageFormatter` の差し替えだけ。通知の細部は、試作で確認が要る (優先度を下げて、後回し)。
- **文言・メッセージの持ち主 (決定。国際化のため。※移行後の姿。現状は上の「文言の扱い」):** 画面モデルは、検査の誤りや案内を、**種別 (列挙) + 対象のプロパティ + 引数** で返し、**文言を持たない。文言は、リソースに持つ** (WPF・WinForms は `.resx`、MFC は `STRINGTABLE`。言語ごとのリソースで切り替える)。**列挙から ID (キー) を引き、リソースから文言を引くのは、UI 層** (引数は、書式文字列 `{0}` / `%d` で埋め込む)。**MFC では、ダイアログ側に「列挙 → `IDS_...`」の対応表を置き、画面モデルはリソース ID を知らない** (操作の受け方と同じ規定)。フォームは、リソースから引いて表示するだけ。画面モデルの単体テストは、文言ではなく、種別 (コード) で確かめる。
- **UI 層の文言のテスト (決定: 期待値は、リソースから引く。※移行後に実施。現状は上の「文言の扱い」):** UI テスト (FlaUI) の、画面に表示された文言の期待値は、テストの中でも、同じ種別とリソースから求める (言語を変えても同じテストが通り、文言の修正で壊れない)。翻訳の質は、機械ではテストせず、人がレビューする。**以下は、未決:** (a) **期待値を取り出す補助は、欠落 (空、キー名そのまま) を検出して、テストを失敗させる (必須。決定 2026-11-16)。主要なエラー 2 件に限り、既定の言語 (日本語) の直書きを併用する (決定)** (期待値も画面も空になって、テストが通る事態を防ぎ、画面が日本語の文言を実際に表示していることを、独立に確かめるため)。(b) **実行する言語の指定の仕組み (決定 2026-11-16):** `UiTestBase` が、起動の前に、アプリへ環境変数 `APP_CULTURE` を渡す。値は、環境変数 `UITEST_CULTURE` > `uitest.settings` の `culture=` > `ja-JP` (テストを実行するマシンの OS の言語ではなく、日本語に固定)。アプリは、**Debug のときだけ** `APP_CULTURE` を読み (`APP_MODEL` と同じ。Release のアプリが環境変数で意図せず言語を変えるのを避ける)、**表示言語と書式の両方** を設定する (WinForms・WPF は `CurrentUICulture` と `CurrentCulture`、MFC は `SetThreadUILanguage` と `SetThreadLocale`。MFC の切り替えは実機で確認が要る)。`ui-trace.txt` の先頭に `culture: ...` と記録する。**この仕組みと、言語を変えた UI テストは、重要性を低くする** (国際化は高負荷な作業で、発生頻度は低いと考えられるため。実装の優先度を下げ、既定の UI テストの実行には含めない。必要になったときに、実装・実行する)。(c) **擬似ローカライズ (印をつけて長くした擬似言語) は、段階導入 (決定 2026-11-16): まず第 1 段階 (`ScreenModel` 由来の文字 (誤りの文言、案内文、状態の表示) だけを対象に、画面に出る文字 (UIA の名前) に印のないものがないか、を確かめる) から着手する。** 擬似リソースは、基の言語のリソースから、スクリプトで自動生成する案。システムが出す文字 (`MessageBox` のボタン、システムメニュー) は、除外の一覧に持つ。第 2 段階 (画面全体へ広げる) は、Form の固定文字列をリソース化する場合だけ意味を持つ。下の「文言の方針」のとおり、その方向ではないので、当面は予定しない。(d) 対応表とリソースの完全性のテスト (種別の全値に、言語ごとの文言と、同じ数の引数があるか) は、**実際に検証する (決定。MFC だけでなく、WinForms も)。** 置くプロジェクトは、案は UI 層のテストのプロジェクト。MFC の `STRINGTABLE` の読み取りは、実機での検証が要る。**MFC の期待値は、exe の `STRINGTABLE` を、テストの補助 (`LoadLibraryEx` でデータファイルとして読み、`LoadString`) で引く (決定 2026-11-16)。** `IDS_...` の数値は、コントロール ID と同じく、`Resource.h` で調べて、テストに書く。**WPF のリソースの扱いは、別途検討** (XAML での扱いが面倒なため)。
- **文言の決定 (2026-11-15。※リソースに関する部分は、移行後の姿):** (1) 種別は、**列挙** (文字列のキーにしない)。**列挙から ID を引くのは UI 層** (画面モデルは、ID もリソースも知らない)。(2) **ログは、開発言語の依存とする** (ここでは日本語。ログの文言は、リソースにしない)。出力は、極力 **UTF-8 (BOM 付き)** を試みる。このため、ロジック層に自前のリソースを持たせる案は、不要。(3) **ひな形で、列挙の追加と、対応表 (列挙 → ID) の雛形を生成する。** (4) 対応表とリソースの完全性のテストは、実際に検証する (MFC だけでなく、WinForms も)。
- **未決 (文言。検討中・別途):** (a) (決定済み: 上の「文言の扱い」の、案内文と業務の生成文の線引き。)(b) **Form の日本語の固定文字列は、リソースにしない方向** (VS のデザイナーが、現在のカルチャの文字列を、そのまま埋め込むのが標準で、リソース化はオーバーな対応との判断。確定ではない)。この方向だと、国際化の範囲は、`ScreenModel` 由来の動的な文言だけになり、言語を切り替えると、画面の見出しは日本語のまま、誤りの文言だけが切り替わる状態になる。画面全体の国際化が必要になったときは、あとから、WinForms は `Localizable` (言語ごとの `.resx`)、MFC は言語ごとのリソースで、段階的に広げられる (要確認)。
  - **メモ (2026-11-16): MFC のボタンなどの固定文字列は、Satellite Resource DLL (言語ごとのリソース DLL) の方法で解消できるが、テストコストを上げる可能性がある。** 簡単な評価: 標準的な方法で、`.rc` のダイアログのテンプレートと `STRINGTABLE` を、まとめて言語ごとに差し替えられ、コードの変更が要らない (コントロール ID は言語によらず同じなので、ID で探す UI テストは、そのまま動く)。一方、コストが増える点は、(1) 言語 × ダイアログの数だけ、UI テストを繰り返す、(2) 基の言語と、言語ごとのリソース DLL の ID の同期 (抜けや食い違いは、気づかれずに空表示や既定の言語への後退になる。静的な検査で防げる見込み)、(3) 文字が長くなったときのレイアウトの崩れは、自動では判定しにくい、(4) 期待値を引く補助が、exe ではなく、言語ごとの DLL を読む必要がある、(5) テストの環境へ、DLL を配置する手間、(6) 擬似言語の DLL の生成。**当面は、予定しない** (国際化の優先度が低いため)。あとから採れるよう、期待値を引く補助は、文字列の出どころ (exe か、言語ごとの DLL か) を隠す形にしておき、UI テストは、文字ではなく ID で探す。(c) WPF のリソースの扱い (XAML での扱いが面倒なため)。

## 3. 三つの UI での受け方

画面モデルの契約は共通で、受け方だけが違う。

| | 状態の表示 | 操作 | 実行可否 | 変更の通知 |
|---|---|---|---|---|
| **WPF** | データバインディング | `ICommand` (画面モデルが公開) | `CanExecute` + `CanExecuteChanged` | `INotifyPropertyChanged` |
| **WinForms** | `BindingSource` による `DataBindings`、または、フォームが画面モデルの通知を受けて、コントロールへ代入 | ボタンの `Click` から、画面モデルのメソッドを呼ぶ (フォームは 1 行) | 通知を受けて、`Enabled` に `CanXxx` を代入 | `INotifyPropertyChanged` (WPF と同じ型) |
| **MFC** | 標準は `UpdateData(FALSE)`。個別更新は `OnModelChanged(PropertyId)` (下の MFC の項) | ID ごとのハンドラ → 画面モデルのメソッド | (再整理中) | (再整理中) |

- **WinForms と MFC に `ICommand` は要らない。** 操作はメソッド、実行可否は `CanXxx` というプロパティにする (WPF だけ、同じものを `ICommand` で包む)。画面モデルのコードを三つの UI で共有したいときは、メソッド + `CanXxx` + 変更通知の形を共通にし、WPF 用の `ICommand` は、薄い包みとして、WPF の側に置く。
- **MFC の操作の受け方 (決定済み。`rules/mfc-cpp.md`):** ID ごとにハンドラを置き、ハンドラは画面モデルのメソッドを呼ぶ数行だけにする。`switch (nID)` で 1 つにまとめない (メッセージマップとの対応が見えなくなり、`mfc-check` の整合の検査も効かなくなる)。まとめてよいのは、同じ意味の ID の並び (ラジオ群、数字キー) だけで、`ON_COMMAND_RANGE` 系で受け、`nID - ID_FIRST` を操作の引数にする。画面モデルはリソース ID を知らず、ID と操作の対応はダイアログ側が持つ。計画には、ハンドラの表 (ID / 通知 / ハンドラ / 画面モデルの操作 / 実行可否 / 更新の方法) を書く。`WM_NOTIFY` や `WM_HSCROLL` も同じ扱い。
- **MFC の更新の経路 (決定済み。`rules/mfc-cpp.md`):**

  | 画面 | 画面 → 画面モデル | 画面モデル → 画面 |
  |---|---|---|
  | モーダルなダイアログ | OK のとき `UpdateData(TRUE)`、続けて `Commit()` | `OnInitDialog` と通知のとき `UpdateData(FALSE)` |
  | `CFormView` | DDX。操作は ID ごとのハンドラ | 通知 → `UpdateAllViews` → `OnUpdate` |

  **例外 (個別更新):** モードレスの即時反映、部分更新、DDX で書けないものは、次の 3 つを守れば許す。(1) 更新を `OnModelChanged(PropertyId)` の 1 か所に集める。通知は、変わったプロパティの識別を持つ。(2) 経路は、コントロール → 画面モデル → 通知 → コントロール。ハンドラが別のコントロールを直接書き換えない。(3) `SetWindowText` が `EN_CHANGE` を起こす再入を、更新中のフラグで防ぐ。
- **MFC の通知の部品 (採用。暫定: リリースまで検証を繰り返す):** 画面モデルの通知は、`Observable<PropertyId>` で行う。`Subscribe(handler)` が `ModelSubscription` を返し、破棄・`Reset()` で解除する。`Raise(PropertyId)` は、ハンドラの一覧をコピーして呼ぶ (通知中の解除に耐える)。ロジック層の共通ヘッダー 1 つ (`std::function` だけで書け、MFC のクラスを許容するロジック層でも、MFC に依存させない)。ダイアログは、メンバー `ModelSubscription m_sub`、`OnInitDialog` で登録、`OnDestroy` で `m_sub.Reset()`、更新は `OnModelChanged(PropertyId)` に集める (画面ごとに書くのは、`PropertyId` とコントロールの対応づけだけ)。基底ダイアログクラスにはしない (`CDialog` / `CFormView` / `CPropertyPage` で基底が違い、MFC のメッセージマップとテンプレートの基底が合わないため)。**WPF の ViewModel と同様に、新しい MFC のソリューションへ、ひな形として自動で組み入れる** (実装が重いので、段階的に検証する)。
- **配布の方法 (案):** Python の文字列にせず、**実物のヘッダーを、Skill のフォルダに置き、生成スクリプトがコピーする。** `Observable` は MFC 非依存で、ロジック層に置く。vcpkg のポート (git レジストリ) への移行は、複数のソリューションで共有する必要が出てからにする (ヘッダーを自己完結にし、名前空間を付け、インクルードのパスを安定させておく)。
- **MFC の通知の決定 (2026-11-16):**
  1. **確定時:** `UpdateData(TRUE)` からの `ScreenModel` への反映中は、**更新中のフラグ (RAII) で `OnModelChanged` を抑える** (コントロールの値を読んでいる最中に、同じコントロールへ書き戻す再入を防ぐ)。`Commit()` が検査の誤りで戻ったときだけ、`OnModelChanged(All)` を 1 回呼んで、表示を更新する。
  2. **通知の粒度:** **`ScreenModel` の操作の終わりに、まとめて上げる。** 操作の途中の変更を集め (範囲を指定する RAII のスコープ)、状態がそろってから、**変わった識別を、重複なし・決まった順で、識別ごとに 1 回ずつ**通知する。ハンドラーは `void(PropertyId)` のまま。途中の中途半端な状態は、ハンドラーから見えない。
  3. **別スレッド (決定 2026-11-16):** **`ScreenModel` は、UI スレッドからだけ呼ぶ** (別スレッドの処理は、結果を UI スレッドへ引き渡してから、`ScreenModel` を呼ぶ)。`ScreenModel` は、呼び出されたスレッドで通知を上げ、UI を知らない。**ダイアログ側のリスナーが、UI スレッドでなければ、`PostMessage` (独自の `WM_APP` 系のメッセージ。`WPARAM` に `PropertyId`) で `OnModelChanged` を引き渡す。** この定型は、ひな形が生成する。**UI スレッドからだけ呼ぶ規約のもとでは、この `PostMessage` の経路は、規約に反して別スレッドから通知が上がった場合の保険**であり、`WPARAM` に識別を載せる方式のままとする (貯めて 1 回だけ投函する受信箱 `ModelChangeInbox` は、採らない)。`OnScreenModelChanged` は、閉鎖済み (リスナーの解除後) なら、何もしない。
     - **メッセージ番号 (決定 2026-11-16):** メッセージは 1 つ (`WPARAM` に識別を載せる方式でも、番号は 1 つで足りる)。名前は `UWM_SCREEN_MODEL_CHANGED`、**値は `WM_APP + 256`。ツール群の予約範囲は、`WM_APP + 256` から** (既存のシステムに統合するとき、既存のコードが、`WM_APP` の 0 付近から使っている可能性が高く、衝突を避けるため)。基点は、生成するヘッダーの定数 1 つで、プロジェクトごとに変えられる。定義は UI 側のヘッダー (ロジック層には置かない)。
  4. **有効・無効:** `OnModelChanged` のどの識別でも、最後に「**全 `CanXxx` を `EnableWindow` に適用する関数**」を 1 回呼ぶ (`CanXxx` は複数のプロパティに依存するため、更新漏れを防ぐ)。`ON_UPDATE_COMMAND_UI` は、メニューとツールバー用に限る。
  5. **`PropertyId` の形:** 画面ごとの列挙 (通知と誤りの対象で兼用)。上の「PropertyId の兼用」のとおり。
- **通知の範囲を指定するスコープ (決定 2026-11-16。MFC の `Observable<PropertyId>`):**
  - **名前:** クラスは **`ChangeScope`**、取得の関数は **`BeginChange()`** (`Observable` の保護されたメンバー)。コピーも移動もできない型にし、`[[nodiscard]]` を付ける (名前をつけない一時オブジェクトが、その行で壊れて、スコープがないのと同じになる書き間違いを、警告で見つけるため)。使い方: `auto change = BeginChange();`。
  - **仕組み:** 変わった識別を貯める入れ物 (重複なし、昇順)、スコープの深さの数、スコープのオブジェクトの 3 つ。スコープは、作ると深さを +1、壊れると -1 し、**0 に戻ったときだけ、貯めた通知を出す。**
  - **入れ子:** 深さを数え、**いちばん外側のスコープが閉じるときだけ**通知する。
  - **スコープの外での `Raise`:** **その場で 1 件を通知する** (暗黙の 1 回限りのスコープ)。1 つの値だけを変える単純な `Set` は、スコープを書かなくてよい。規則: **複数の値を変える操作、またはほかの操作を呼ぶ操作は、スコープを開く。**
  - **通知の順序:** **列挙の宣言順** (値の昇順)。呼ばれた順にしない。ひな形が、「入力欄、表示、`CanXxx`、`IsValid`、`All`」の順で列挙を生成する。
  - **`All` の集約:** 貯めたものに `All` があれば、ほかの個別の通知は出さず、`All` だけを 1 回通知する。
  - **ハンドラーの中での `Raise`:** いま出している束が終わってから、次の束として処理する。デバッグ時は、繰り返しの回数に上限を設け、無限ループを検出する。
  - **例外のとき:** 操作の途中で例外が出ても、**デストラクターが、貯めた通知を出す** (途中まで変わった状態を、画面が反映するため)。デストラクターは例外を出さず、**ハンドラーが出した例外は、ログに残して続ける。**
  - **スレッド:** スコープと入れ物は、スレッドセーフにしない。呼び出す側が、1 つのスレッドから使う (別スレッドの通知は、ダイアログ側が `PostMessage` で引き渡す。上の「MFC の通知の決定」)。
  - C# (WinForms の `ScreenModel`、WPF の `ViewModel`) は、`INotifyPropertyChanged` を使うので、このスコープは、C++ だけのもの。C# で、複数のプロパティの変更をまとめる必要があるかは、決めていない。
- **未決 (MFC):** `Observable` の実装の詳細と検証 (「リリースまで検証を繰り返す」)。(閉じたあとのメッセージの扱いと、スレッドの方針は、上のとおり決定済み。)
- **Document/View は、今回の対象外** (`CFormView` は、例外的に Document/View なので、上の表に載せている)。

### WinForms: 画面モデルと Presenter の共存

```
Form ──(状態は直接読む)──▶ 画面モデル ──▶ リポジトリ
  │                          ▲
  └─(IView)─ Presenter ──────┘
        ダイアログ・遷移・フォーカス・UI スレッド
```

| 層 | 担当 |
|---|---|
| 画面モデル | 状態、規則、実行可否、検査、変更の通知、リポジトリの呼び出し。UI 非依存 |
| Presenter | WinForms の型がないと書けないものだけ。ダイアログ (`IDialogService` 越し)、画面遷移の実行、フォーカス、UI スレッドへの戻し、Form の開閉 |
| `IView` | 上の用途に必要な最小の窓口 (`ShowMessage`、`Close`、`SetFocus` など)。**状態のプロパティを持たない** |

境界の判断基準は二つだけである。**WinForms の型・機能がないと書けない → Presenter。別の UI でも同じ内容になる → 画面モデル。** 画面遷移は、「判断」(どこへ進むか) が画面モデルの結果、「実行」(開く) が Presenter である。

守る規則:
1. **状態は、画面モデルだけが持つ。** `IView` に写さない。Form は、画面モデルの状態を直接読む (`BindingSource`、または通知を受けて代入)。
2. **規則は、Presenter に置かない。** 検査・実行可否・状況で変わる文言は、画面モデルが決める。
3. **Presenter は、WinForms の型を使わない** (`winforms-check` の WFL002 を維持)。
4. **ダイアログ・`MessageBox` は、`IDialogService` 越しに開く** (画面モデル・Presenter から直接開かない)。
5. **Presenter は、必要なときだけ置く。** バインドと操作の呼び出しだけで足りる単純なダイアログは、Form が画面モデルに直接つなぐ。遷移・フォーカス・ダイアログ呼び出しが出てきたときに足す。
6. **UI スレッド:** 画面モデルは、呼び出されたスレッドで通知を上げる。UI スレッドへの戻しは、Form か Presenter が行う。

## 4. Fake が必要な場所は、二つある

画面モデルが入ったことで、Fake を置ける位置が、二つに分かれる。フォームが直接使うのは、画面モデルである。

| Fake | 何を置き換えるか | 使う場面 |
|---|---|---|
| **Fake リポジトリ** (メモリ上) | リポジトリ | **本物の画面モデル + Fake リポジトリ** で、UI テストを回す。画面モデルの規則も、実際に通る |
| **Fake 画面モデル** | 画面モデルそのもの | 画面モデルが**まだ存在しないとき** (UI 先で画面の動作だけを固める)、または、フォームの表示の確認 (エラー表示、無効状態、長い一覧など、本物では作りにくい状態) |

使い分けの原則:
- **通常の UI テストは、本物の画面モデル + Fake リポジトリ** で回す。Fake 画面モデルで通っても、本物の画面モデルの規則で壊れる余地が残るためである。
- **Fake 画面モデルは、本物の画面モデルがないあいだの、つなぎ** と、**作りにくい状態の再現** に限る。本物ができたら、通常の UI テストは本物に切り替える (表示の再現用の Fake は残してよい)。
- **画面モデルの規則そのものは、フォームなしの単体テスト** (本物の画面モデル + Fake リポジトリ) で確かめる。UI テストは、開く・閉じる・主要な流れに絞る。速く、壊れにくい。

### Fake 画面モデルの存在時間

Fake 画面モデルは、**UI 先では、本物の画面モデルが結合されるまでの、一時的なもの** である。流れは次のとおり (6 章の番号)。

| 時点 | Fake 画面モデルの状態 |
|---|---|
| 3. UI テスト (Red) を書くとき | **生まれる。** 画面から導いたインターフェースを、メモリ上の小さな実装で満たす。UI テストはこれで回る |
| 4. 契約テストを書くとき | 契約テストで、インターフェースの意味を固定する。Fake はこのテストを通ること |
| 5. 本物の画面モデルを作るとき | **併存する。** 本物にも同じ契約テストを通す。ここまで、Fake は、インターフェースの正本の代わりをしている |
| 6. UI テストを本物 + Fake リポジトリへ切り替え、通ったとき | **役目を終える。** 通常の UI テストは、本物の画面モデルで回る |
| その後 | 既定は**削除**。残すのは、本物では作りにくい状態 (エラー表示、無効状態、長い一覧) の再現に、Fake が必要なときだけ。残す場合は、契約テストを通し続け、残す理由を設計の記録 (`docs/design`) に 1 行書く |

- **「確定」の単位:** ダイアログの「確定 (OK)」とは別の話で、ここでの確定は、**本物の画面モデルへ切り替えて、同じ UI テストが通ったとき** を指す。それまで、UI テストの Green は、フォームの動作の確認にとどまり、画面モデルの規則の確認にはならない。
- **置き場所と切り替え:** Fake 画面モデルは、アプリ側に置く (exe の起動時に使うため。テストのプロジェクトには置かない)。切り替えの仕組みは、下の「Fake 画面モデルの切り替え (決定)」。

### Fake 画面モデルの切り替え (決定 2026-11-16)
画面ごとに、Fake と本物を選べる。アプリには画面が複数あり、本物ができた画面と、まだ Fake の画面が混在するため、`APP_MODEL` のようなアプリ全体の 2 値では足りない。また、状態の再現 (エラー表示、失敗など) のために、Fake の中身 (シナリオ) を、テストごとに選びたい。

| 項目 | 内容 |
|---|---|
| アプリに渡す環境変数 | **`APP_FAKE_SCREENS`**: Fake にする画面の名前のカンマ区切り。`画面名:シナリオ名` の形も可 (例: `Greeting,NameEdit:InvalidName`) |
| テスト側 | 環境変数 **`UITEST_FAKE_SCREENS`** > `uitest.settings` の **`fake_screens=`** > 空 (すべて本物)。`UiTestBase` が、起動の前に、`APP_FAKE_SCREENS` をアプリへ渡す |
| アプリが読む場所 | `APP_MODEL` と同じ (WinForms は `Program.cs`、WPF は `App.xaml.cs`、MFC は `InitInstance`)。**Debug のときだけ読む** |
| 記録 | `ui-trace.txt` の先頭に、`fake_screens: Greeting, NameEdit:InvalidName` と出す |
| `APP_MODEL` との関係 | 独立。`APP_MODEL` はリポジトリを、`APP_FAKE_SCREENS` は画面モデルを選ぶ。Fake 画面モデルを選んだ画面は、リポジトリを使わない |
| 一覧にあるのに Fake がないとき | **Debug の起動時に、エラーで止める** (黙って本物に切り替えない) |
| Release への Fake の混入 | `APP_MODEL` と同じ扱い: **Release では読まない** (Fake のクラス自体は、バイナリに残りうる。条件コンパイルで除くことは、決めていない) |

- **インターフェースに依存する:** Form・ダイアログは、画面モデルの**インターフェース** (C++ は `GreetingScreenModelInterface`、C# は `IGreetingScreenModel`、WPF は `IGreetingViewModel`) だけを知る。
- **組み立てる場所 (composition root) に、画面名から実装を選ぶ関数を 1 つ置く:** `APP_FAKE_SCREENS` に名前があれば Fake、なければ本物を返す。MFC は、ダイアログを開く側が、コンストラクターへ渡す画面モデルを、この関数から得る (Debug のときだけ読む補助 `ScreenModelSelector` を、UI 側の共通ヘッダーに置く案)。
- テストの書き方 (案): `UseFakeScreen("NameEdit", scenario: "InvalidName");` (`UiTestBase` が、起動の前に環境変数を設定する)。
- **実装の優先度は、ひな形の実装の中で決める** (UI 先では、すぐに使う場面がある。ロジック先では、通常は使わない)。
- **残してはいけない場合:** 契約テストを通していない Fake、本物とずれた Fake。ずれたまま残すと、通常の UI テストが、本物と違う振る舞いに対して通る。
- **ロジック先では、そもそも生まれないことがある。** 本物の画面モデルがすでにあるので、通常は本物 + Fake リポジトリで UI テストを回し、Fake 画面モデルは、状態の再現が必要になったときに作る (7 章の段階 B の 6)。

## 5. 整合性の確認: 契約テスト

Fake と本物のずれは、**同じテストを両方に通す契約テスト** で検出する。契約テストは二つの境界にある。

1. **リポジトリの契約テスト:** `<リポジトリ名>ContractTests`。Fake リポジトリと本物のリポジトリに通す (既存の仕組み)。
2. **画面モデルの契約テスト:** `<画面モデル名>ContractTests`。**Fake 画面モデルと、本物の画面モデル (Fake リポジトリを注入) に通す。** 状態・操作・実行可否・検査・通知・確定 / 取消の意味を、書く。

書き方の規則:
- 契約は、**インターフェースの意味だけ** を書く (実装の内部、並び順は決めたときだけ)。
- **ロジック先 (画面モデルがすでにある) では、契約テストを先に書き、本物で Green にしてから Fake 画面モデルを作る。** 本物を読んで Fake を書くと、偶然の挙動まで写すためである。
- 契約を変えるときは、承認を取り、テストと両方の実装に反映する。

## 6. UI 先の流れ

画面が出発点なので、画面からインターフェースを導く。

1. **画面の計画** (部品、識別の名前、操作と期待) を書く。
2. **画面モデルのインターフェースを導く:** 部品を、2 章の五つに当てはめる (入力欄 → 状態、ボタン → 操作 + 実行可否、エラー表示 → 検査)。計画に、画面モデルの表を足す。
3. **Fake 画面モデル + UI テスト (Red) → フォーム (Green)。** この時点では、画面モデルは Fake である。
4. **画面モデルの契約テストを書く** (Fake 画面モデルで Green)。
5. **本物の画面モデルを、ロジック層で作る** (単体テストが先。Fake リポジトリを注入)。契約テストを、本物にも通す。
6. **UI テストを、本物の画面モデル + Fake リポジトリへ切り替える。** 同じテストが通れば、結合済み。
7. **本物のリポジトリは、別に作り** (リポジトリの契約テストが先)、主要な流れだけを `model=real` で通す。

## 7. ロジック先の流れ (コードのテストファーストから、UI へ)

画面が出発点でないので、**UI に向けた準備を、ロジックの段階で済ませておく** ことと、**UI の段階で、画面の定義を、利用者の作業から起こす** ことの、二つが要る。公開面から機械的に画面を起こすと、公開メンバーの数だけ部品が並ぶ。公開面は実装の都合で決まっており、利用者の作業の単位と一致しないためである。

### 段階 A: ロジック (画面モデルとリポジトリ)。UI より前

1. **作業を書く:** 利用者がやりたいことを、動詞で 1〜3 行書く (この段階から。後の段階 B の入力にもなる)。
2. **画面モデルのインターフェースを、テストから導く:** 2 章の五つ (状態・操作 + 実行可否・検査・変更の通知・結果) を、**最初から、契約に含める。** 実行可否・検査・通知を後回しにすると、UI の段階で、インターフェースの変更が必要になる。モーダルかモードレスかも、この時点で決める (2 章)。
3. **リポジトリのインターフェース + 契約テスト + Fake リポジトリ:** 契約テストを先に書き、Fake で Green にする。本物のリポジトリは、あとでよい。
4. **画面モデルの単体テスト (Red → Green):** Fake リポジトリを注入して、規則・状態の遷移・実行可否・検査・通知を確かめる。**フォームも UI の型も、要らない。**
5. **画面モデルの契約テスト** (Fake 画面モデルを作る可能性があるときだけ)。本物で Green にしてから、Fake を作る。

### 段階 B: UI。ここから画面を定める

1. **作業を確認する (A の 1)。** 決まらなければ、ユーザーに聞く。画面モデルを見るより先に行う。
2. **画面モデルの公開面を棚卸しする** (読むだけ)。2 章の五つで分けて、「使う / 使わない」を決める。画面に出さないメンバーが残るのは正常である。

   | 公開メンバー | 画面での受け皿 |
   |---|---|
   | 読み書きできる状態 | 入力欄 (型で選ぶ: 文字列 → テキストボックス、真偽 → チェックボックス、選択肢 → コンボボックス) |
   | 読み取り専用の状態 | ラベル・一覧 |
   | 操作 + 実行可否 | ボタン・メニュー (実行可否 → 有効 / 無効) |
   | 検査 | エラー表示 |
   | 通知がある状態 | 即時の更新 (モードレスで特に必要) |
3. **差分を分類する:** (a) 作業に必要で、画面モデルにある → 使う。(b) **作業に必要で、画面モデルにない → フォームの中で補わず、段階 A の 4 に戻って、画面モデルに足す** (単体テストが先。インターフェースを変えるなら、契約テストと Fake も更新し、承認を取る)。(c) 作業に不要 → 出さない。
4. **画面の計画を書く:** `ui-test-first` の形 (部品、識別の名前、操作と期待。ダイアログなら、種類・開き方・閉じ方・開く前提)。見た目は、スケッチがあれば、それに沿う。計画に、画面モデルの表 (棚卸しの結果) を入れる。
5. **UI テスト (Red) → フォーム (Green):** 本物の画面モデル + Fake リポジトリで回す。部品を名前つきで置き、次に動作をつなぐ。フォームは、表示と、操作の呼び出しだけを持つ。UI テストは、開く・閉じる・主要な流れに絞る (規則は、A の 4 で確かめ済み)。
6. **Fake 画面モデル (必要なときだけ):** エラー表示・無効状態・長い一覧など、本物では作りにくい状態を再現するときに作る。契約テストを通す。
7. **本物のリポジトリを結合する:** リポジトリの契約テストを本物で Green にし、`model=real` で、主要な流れだけを通す。

### 戻りの規則
段階 B で画面モデルの不足が見つかったら、フォームの中で補わず、**必ず、段階 A (単体テスト) に戻る。** 戻る回数を減らすには、A の 2 で、実行可否・検査・通知を、最初から契約に含めておく。

### 決定した名前と命名 (補足)
- **名前 (決定 2026-11-16): WinForms と MFC の画面モデルは `<画面名>ScreenModel`。** 理由: `ViewModel` は、宣言的なデータバインディング (WPF、ASP.NET Core MVC) を連想させるが、WinForms と MFC は、更新を明示的に書く (`OnModelChanged`、`UpdateData`) ため。`Model` (リポジトリ)・`ViewModel`・`Presenter` のどれとも、名前が衝突しない。「データモデル」は、データベースの設計を指す言葉と衝突し、操作・検査・通知を持つ中身も言い表さないため、採らない。副次の利点: `ScreenModels/` と `*ScreenModel*.cs` を、WinForms 規約の読み込み条件に入れられる (`ViewModel` は WPF の規約の読み込み条件と同じ名前で、入れられなかった)。日本語の概念名は「画面モデル」。**WPF は、`ViewModel` のまま** (既存の WPF 規約・`wpf-check`・`ViewModels/` の読み込み条件が、`ViewModel` の名前に依存するため)。手引き・規約・ひな形では、「画面モデルという役割を、WPF では `ViewModel`、WinForms と MFC では `ScreenModel` と呼ぶ」と、一度書く。
- **C++ のインターフェース (純粋仮想クラス) の命名 (決定 2026-11-16):** **`I` 接頭辞は付けない。基本は `XXXInterface`、軽いもの (1 つの能力を表す小さなインターフェース) には `XXXable`** (`Observable<PropertyId>`、`Validatable` など)。**本物の実装は、役割の名前そのまま** (`GreetingScreenModel`)、インターフェースは `GreetingScreenModelInterface`、Fake は `FakeGreetingScreenModel`。ダイアログのコンストラクターは、`GreetingScreenModelInterface&` を受け取る。リポジトリも同じ規則 (`GreetingRepositoryInterface`、Fake は `InMemoryGreetingRepository`、本物は技術名の `SqlGreetingRepository`)。`Base` は、実装を持つ基底クラス (共通の実装) のために、とっておく。`〜Contract` は、契約テストの exe の名前 (`<インターフェース名>Contract`) と衝突するので、使わない。**C# は、`csharp-common.md` の既存の規約どおり、`I` 接頭辞のまま** (`IGreetingScreenModel`)。2 つの言語で名前が違うのは、言語の慣習の違い。`cpp-common.md` への反映は、規約の反映の段階。

## 9. 最小のチェックリスト

- [ ] フォームが、画面モデルのインターフェースだけを知る (リポジトリを直接呼ばない)
- [ ] 画面モデルが、UI の型を使わない (単体テストが、フォームなしで回る。MFC は、`CString`・コレクション・データやモデルの CObject 派生を許容。ウィンドウのラッパーと Document/View は不可)
- [ ] 検査は `Validate()` / `IsValid` で公開している
- [ ] 操作ごとに、実行可否を公開している
- [ ] 通常の UI テストは、本物の画面モデル + Fake リポジトリ。Fake 画面モデルは、つなぎと状態の再現に限る
- [ ] 契約テストが、リポジトリと画面モデルの両方にある (本物と Fake の両方に通す)
- [ ] ロジック先では、利用者の作業を先に書き、足りないものはフォームの中でなく画面モデルに足した
- [ ] モーダルは確定まで書かず、モードレスは即時に反映している
- [ ] (WinForms) 状態は画面モデルだけが持ち、`IView` に状態のプロパティがない
- [ ] (WinForms) Presenter に規則がなく、WinForms の型を使わない。単純なダイアログには、Presenter を置いていない
