# 設計メモ

このリポジトリの成果物 (ホスト側ツールと Skill) が「なぜこの形か」を残す。
ファイルを読めば分かることは書かず、**判断の理由・取り下げた案・守るべき約束 (契約)** を中心に書く。

## 1. 目的と前提

**目的:** Claude Code (WSL) が、C++ (Visual Studio / MSBuild) と .NET (WPF など) のコードを修正し、ビルドとテストを行い、
エラーや失敗を読んで自分で直す、というループを、人手を介さずに回せるようにする。

**制約:** Claude Code は、サンドボックスで動いており、Windows 側の `msbuild.exe` やテスト exe、
開発者用環境変数 (`vcvarsall.bat` など) に直接アクセスできない。

**環境の前提:** デバッグは Visual Studio で行う。ビルドする PC には、**C++ ワークロード入りの Visual Studio** が入っている。
`build-windows.cmd` は、`Features` に `cpp` を含めないとき (.NET のみのソリューション)、C++ ツールを要求しない (`MSBuild` だけの VS でも動く設計) が、**C++ ツールのない環境での動作は、確認していない** (前提に含まない。TEST-PLAN の U14 は「対象外」)。

**解決策:** Windows 側に、フラグファイルを監視するウォッチャーを常駐させる。
Claude は、ファイルを置いて、ファイルを読むだけ。ファイルが、両者の唯一の接点になる。

```
Claude Code (WSL)                              Windows
  trigger_build.flag / trigger_test.flag  ──▶  watch_and_build.ps1 (ウォッチャー)
                                               ├─ build-windows.cmd ─▶ MSBuild
                                               └─ (テスト時) xxxTest.exe (GoogleTest) / dotnet test (MSTest)
  build_result.txt / test_result.txt      ◀──  完了マーカー (最後に書く)
  build_error.log  / test_error.log       ◀──  失敗時のみ
```

## 2. 構成と責務

| 部品 | 場所 | 責務 |
|---|---|---|
| `run_watcher.cmd` | host-tools | 入口。引数を整え、ps1 を起動する |
| `run_watchers.cmd` | host-tools | (任意) 作業フォルダの候補ごとに、別のウィンドウで `run_watcher.cmd` を起動する (v2.25.0) |
| `watch_and_build.ps1` | host-tools | フラグ監視、ビルド/テスト実行、結果ファイルの書き出し |
| `build-windows.cmd` | host-tools | VS の環境を読み込み、MSBuild を実行する (単体でも使える)。C++ ツールの要求と NuGet の復元は、第 6 引数 (`Features`) で切り替える (4.24) |
| `auto-build` | skills | ビルドのみのループ (`trigger_build.flag`)。C++ / .NET 共通 (4.24) |
| `build-test-loop` | skills | ビルド + テスト (GoogleTest / MSTest) のループ (`trigger_test.flag`)。C++ / .NET 共通 (4.24) |
| `csharp-test-first` | skills | WPF のテスト先行 (Red)。`PROJECT-LAYOUT.md` と、プロジェクト生成 `add_project.py` (`new-solution` も使う) (4.27) |
| `add-package` | skills | パッケージの追加 (NuGet / vcpkg / ソースの取り込み)。ホスト側に、`trigger_package.flag` で実行させる (4.26) |
| `wpf-check` | skills | WPF の静的検査 (バインディング・リソース・`InitializeComponent`・層)。読み取りだけ。Windows 不要 (4.25) |
| `winforms-check` | skills | WinForms の静的検査 (`InitializeComponent`・`Designer.cs` の Name・層・スレッド)。読み取りだけ。Windows 不要 (4.30) |
| `cpp-test-first` | skills | テストを先に書き、スタブで Red (正しい理由での失敗) を確認する。実行は `build-test-loop` のスクリプトを使う (スクリプトは持たない) |
| `build_once.sh` / `build_test_once.sh` | skills/*/scripts | フラグを置き、完了マーカーを待ち、結果を1行目と終了コードで返す |

ウォッチャーは、`build-windows.cmd` を**毎回別プロセスで**呼ぶ。VS の環境変数が持ち越されず、
Platform や Configuration を変えても環境が汚れない (起動時に1回だけ読み込む方式は、環境が固定されるため不採用)。

## 3. 契約 (ホスト側ツール ⇔ Skill)

すべて `<ソリューションフォルダ>` に置かれる。**これを変えるときは、ホスト側ツールと Skill を同じコミットで直す。**

### ファイル

| ファイル | 作る人 | 内容 |
|---|---|---|
| `trigger_build.flag` | Claude | 空。ビルドのみを依頼 |
| `trigger_test.flag` | Claude | 空。ビルド + テストを依頼 (両方あればこちらが優先) |
| `build_result.txt` | ウォッチャー | `SUCCESS` / `FAILED` (ビルドのみの完了マーカー) |
| `build_error.log` | ウォッチャー | ビルド失敗時のみ。エラー行 |
| `test_result.txt` | ウォッチャー | テストの完了マーカー (後述の値) |
| `test_error.log` | ウォッチャー | テスト失敗・タイムアウト・環境エラー時のみ |
| `trigger_gtest.flag` | Claude | **GoogleTest のソース取得を依頼** (ビルド・テストとは独立)。1 行目に、タグ (例 `v1.17.0`) を書ける。空なら、ウォッチャーの `-GtestTag` |
| `gtest_result.txt` | ウォッチャー | 取得の完了マーカー: `OK` / `FAILED` (最後に書く) |
| `gtest_error.log` | ウォッチャー | `FAILED` のときのみ。先頭は `[ENVIRONMENT ERROR - not a source code problem]` |

| `trigger_package.flag` | Claude | **パッケージの操作を依頼** (NuGet / vcpkg / ソースの取り込み。ビルド・テストとは独立)。各行が 1 操作 (4.26) |
| `package_output.txt` / `package_error.log` / `package_result.txt` | ウォッチャー | 操作の出力 / 失敗時のみ (環境の問題は先頭が `[ENVIRONMENT ERROR ...]`) / 完了マーカー `OK` / `FAILED` (最後に書く) |
| `.claude-logs/` | ウォッチャー | `build.log` `errors.log` `warnings.log` `test.log` (フルパスのまま) |
| `.claude-logs/test-results/` | ウォッチャー | **テストランナーの、機械可読な結果 (4.24)。** `<exe名>.xml` (GoogleTest の `--gtest_output=xml`)、`<プロジェクト名>.trx` (`dotnet test --logger trx`)。テストの開始時に、前回分を消す。`test_result.txt` より前に書かれる |
| `.claude-logs/build_summary.json` | Skill のスクリプト | ビルド失敗の要約 (4.22)。ウォッチャーではなく、WSL 側の `summarize_build_log.py` が書く |
| `.claude-logs/test_summary.json` | Skill のスクリプト | テスト失敗の要約 (4.22、4.24)。WSL 側の `summarize_test_log.py` が、`test-results/` の XML / trx を、共通の形式 (schema 2) に変換して書く |
| `.claude-logs/warnings_summary.json` | Skill のスクリプト | 成功時の警告の要約 (4.22)。`summarize_build_log.py --severity warning` が書く |

### `test_result.txt` の値

| 値 | 意味 | 詳細の場所 |
|---|---|---|
| `PASSED` | ビルド成功・全テスト成功 | |
| `FAILED` | テスト失敗 (または異常終了) | `test_error.log` |
| `TIMEOUT` | テストが制限時間内に終わらない | `test_error.log` (`Hung test ...`) |
| `BUILD_FAILED` | ビルド失敗でテスト未実行 | `build_error.log` |
| `ENV_ERROR` | テストが見つからない (GoogleTest の exe も、.NET のテストプロジェクトもない)、`[  PASSED  ]` が出力にない、`dotnet` がない、.NET のテストが 1 件も実行されない (trx がない / `executed=0`) 等 | `test_error.log` |

環境エラーのログの先頭は、必ず `[ENVIRONMENT ERROR - not a source code problem]`。
Skill は、これを見て「ソースもテストも直さずに、報告して止まる」。

### Skill のスクリプトの出力 (1行目と終了コード)

| 1行目 | rc | 意味 |
|---|---|---|
| `PASSED` / `SUCCESS` | 0 | 成功 |
| `FAILED` | 1 | テスト失敗 (`build_once.sh` ではビルド失敗) |
| `BAD_ARGS` | 2 | 引数不正 |
| `WATCHER_NOT_RUNNING` | 3 | フラグが 15 秒回収されない = ウォッチャー未起動 |
| `ENV_ERROR` | 4 | 環境エラー |
| `TIMEOUT` | 5 | 完了マーカーが出ない (既定: ビルド 180 秒、ビルド+テスト 300 秒) |
| `BUILD_FAILED` | 6 | ビルド失敗 (`build_test_once.sh` のみ) |
| `TEST_TIMEOUT` | 7 | ホスト側のテストの制限時間超過 (`build_test_once.sh` のみ) |

### `build-windows.cmd` の終了コード
`0` 成功 / `1` ビルド失敗 / `2` 引数不正 / `10` vswhere なし / `11` 必要な構成要素入りの VS なし (`cpp` なら C++ ツール、そうでなければ MSBuild) /
`12` VsDevCmd なし / `13` VsDevCmd 失敗 / `14` MSBuild.exe (`cpp` なら cl.exe も) が PATH にない

引数: `<target> <Platform> [Configuration] [MSBuildTarget] [LogDir] [Features]`。`Platform` は `x64` / `Win32` / `x86` / `ARM64` / `AnyCPU`。
`Features` は、カンマ区切りで `cpp` (C++ ツールを要求し、cl.exe を確認する。**省略時の既定**) と `restore` (`/restore`。`Clean` では付けない)。**省略時は、従来と同じ動作。**

## 4. 設計判断とその理由

### 4.1 フラグファイル方式
Claude が、Windows 側のコマンドを直接実行できない以上、「共有フォルダ上のファイルを介する」以外の
手段は、実質的にない。ホストから Claude へ通知を送る標準の仕組みもない。
そのため、Claude 側が、完了マーカーの出現を待つ (ポーリング) 方式にした。

### 4.2 完了マーカーを別に用意した
「フラグが消えた」は「ビルドを開始した」だけで、終わったとは限らない。
「`build_error.log` がない」は、成功か、まだ実行中かの区別がつかない。
そこで、ウォッチャーが、**結果ファイルとエラーログを書いた後に、最後にマーカーを書く**。
マーカーが現れた時点で、ログは必ず読める状態にある。

### 4.3 待機で、トークンを消費しない
待機は、`build_once.sh` / `build_test_once.sh` の中の `sleep` ループで行う (1回のコマンド)。
Claude 側から、何度もファイルを読みに行く方式は、ターンとトークンを消費するため不採用。
Bash ツールの既定タイムアウト (120 秒) より長く待つため、`run_in_background: true` で実行する。
**待機中は、ファイルを読まない・再実行しない** (前回の古い結果を読んで誤判断したため。Skill に明記)。

### 4.4 結果ファイルは、毎回、実行の開始時に消す
古い結果の誤読を防ぐ。スクリプト側 (Claude の実行前) と、ウォッチャー側 (ビルド開始時) の両方で消す。
ただし、実行が重なると (前の実行が終わる前に、次のフラグを置く) 古い結果を拾う可能性が残る。
→ **Claude 側の再実行による重なりは、未対策。** フラグに一意の ID を書き、ウォッチャーが結果に書き戻す案があるが、実装していない。
(ウォッチャーが、2 つ動いて、フラグを奪い合う場合は、4.13 の二重起動の防止で、防いでいる。)
Skill で「実行中に再起動しない」と規定して、回避している。

### 4.5 `PASSED` の判定を厳しくした
古い GoogleTest は `--gtest_brief` を知らず、ヘルプだけを表示して**終了コード 0** で終わる。
テストが1件も走らないのに `PASSED` になった実例がある。
→ 終了コード 0 **かつ** 出力に `[  PASSED  ]` の行がある場合だけ成功とみなす。
なければ `ENV_ERROR`。`-TestArgs` の既定は `--gtest_color=no` のみ。

### 4.6 エラーログのパスを、相対パスにする
MSBuild と GoogleTest は、絶対パス (`C:\...`) で出力する。WSL の Claude は、そのままでは開けず、
変換にトークンと誤りの余地がある。ウォッチャーが、ソリューションフォルダ以下を、
`xxx/yyy.cpp(49)` の形 (相対・`/` 区切り) に変換して、`build_error.log` / `test_error.log` に書く。
フルパスの詳細ログは `.claude-logs/` に残る。

### 4.7 テスト失敗の扱い (Skill の方針)
テストは、仕様の表明として扱う。
- 原則として、**ソース (xxx) 側を直す。**
- テストの期待値が誤りと思われる場合は、**変更前にユーザーに確認する** (根拠を添える)。
- テストの削除、`DISABLED_` 化、`GTEST_SKIP()`、アサーションを弱める、許容誤差を広げる、
  期待値を実装の出力に合わせる、は、許可なしにしない。
- 複数の失敗は、共通の原因を先に探す (1つの不具合が、複数のテストを落とすことが多い)。
- `ENV_ERROR` では、ソースもテストも触らない。

### 4.8 テストのタイムアウト
テスト exe は、制限時間 (既定 120 秒) で、子プロセスごと強制終了する (`taskkill /T /F` + `Process.Kill()`)。
待ち時間にも上限を付けた (無期限に待つと、ウォッチャー全体が止まる)。
タイムアウト時は、`[ RUN ]` だけで `[ OK ]` が続かなかったテストを、`Hung test` として先頭に出す。
**ただし、制限時間が、全体の実行時間より短いだけの場合も、通常のテスト名が出る。**
Skill は、「直前にソースを変更していない場合、または2回続けて `TEST_TIMEOUT` の場合は、直さず報告して止まる」。

### 4.9 クイック編集モードの無効化
コンソール内をクリックすると、出力が一時停止し、ウォッチャーが止まる (Enter/Esc で再開)。
実際に、ビルドが数分止まった。起動時に、`SetConsoleMode` で無効化する (失敗しても監視は続ける)。

### 4.10 ビルド順 (xxx → xxxTest)
`xxxTest` が `xxx` をプロジェクト参照していれば、ソリューションのビルドで、MSBuild が依存順に解決する。
Skill は、順序を指定しない。参照がない構成は、対象外。

### 4.11 テストの対応範囲: GoogleTest (C++) と MSTest (.NET)
C++ のネイティブテストは、GoogleTest のみ。**C++ の `CppUnitTestFramework` (VS 付属。DLL を `vstest.console.exe` が読み込む方式) は、対象外のまま**にしている (4.24 の、検討と、採らなかった理由)。
.NET のテストは、MSTest (v3 以降、VSTest モード = `Microsoft.NET.Test.Sdk`) を、標準とする。ウォッチャーは、`dotnet test` を、`--logger trx` で実行するので、xUnit / NUnit も、同じ経路で動く見込みだが、**検証するのは、MSTest だけ。**
ホスト側の実行 (`Invoke-TestExe` / `Invoke-DotnetTest`) は、関数に分かれている。

### 4.12 プレビュー版 VS は、対象外
`vswhere` に `-prerelease` を付けない。リリース版の最新だけを使う。

### 4.13 ウォッチャーの二重起動の防止
同じプロジェクトフォルダで、ウォッチャーが 2 つ動くと、同じフラグを奪い合い、結果が混ざる。
ウォッチャー自身が、二重起動を拒否する。手動で起動した場合も、守られる。
- プロジェクトフォルダの、フルパス (小文字) の SHA1 から、名前付きミューテックス `Local\claude-windows-desktop-tools-watcher-<hash>` を作る (v2.42.0 で、旧名 `Local\cpp-claude-build-tools-watcher-<hash>` から変更。4.58)。
  取得できなければ (すでに動いている)、メッセージ (`ERROR: a watcher is already running for this folder`) を出して、**終了コード 3** で終了する。
- ロックファイルは使わない。ミューテックスは、プロセスの終了時 (異常終了を含む) に、OS が解放するため、古いロックが残らない。
  プロジェクトのフォルダに、ファイルを作らないので、`.gitignore` の追記も、不要。
- 範囲は、同じ Windows ユーザーのセッション内 (`Local\`)。別のフォルダのウォッチャーとは、干渉しない。
- 検討して、採用しなかった方法:
  - **フラグを、消せたウォッチャーだけが、処理する方式:** 仕組みは、1〜2 行で済むが、2 つ目が、止まらずに待機し続け、
    設定 (Platform など) が違う 2 つが動くと、どちらが処理するか不定になる。古い版のウォッチャーが残っていても、気づけない。
  - **cmd のファイルロック (`run_watcher.cmd` でファイルを開いたままにする):** 書き方が分かりにくく、ビルドの終了コードを、
    「すでに動いている」と、誤判定する落とし穴がある。ps1 を直接起動すると、守れない。

### 4.15 変更の確認: 指示 (Skill) と 強制 (権限設定) の使い分け
Claude が編集したコードは、ウォッチャーによって、Windows 側で、ビルドされ、テストが実行される。テストファイルの意図しない変更を、人が見逃さない仕組みが要る。
- **Skill (指示):** 完了時に、変更したファイルの一覧 (`git status --short`) と、テストファイルの変更の有無を、報告する。`git commit` / `git push` はしない。
  モデルへの指示なので、強制ではない。変更がない場合は、実行しない (トークン節約)。
- **権限設定 (強制):** プロジェクトの `.claude/settings.json` の `permissions.ask` で、テストファイルの編集 (`Edit(**/Test*.cpp)` など) と、`git commit` に、確認を付ける。
  Skill は、権限を制限できない (`allowed-tools` は事前承認で、制限ではない) ため、強制は、設定で行う。詳細と限界は、`docs/RECOMMENDED-SETTINGS.md`。
- **フックは採用しない:** 失敗時に素通りする (フェイルオープン)。確認ダイアログに、理由が表示されるかも、未確認。
- **最後の砦は、人:** コミットの前に、`git diff` で、変更 (特にテストファイル) を、確認する。権限の `ask` は、許可すれば編集されるため、禁止ではない。

### 4.16 `cpp-test-first`: テストを先に書く Skill を、別にした理由と、設計判断
`build-test-loop` は「既存のテストを通す」(Green) ループで、テストは仕様として、変えない。
「先にテストを書く」(Red) は、**テストを新しく作る工程**で、規則が逆になる (テストを書いてよい)。同じ Skill に入れると、規則が衝突するため、別にした。
- **Red の定義を、「アサーションで失敗」にした。** テストが、本体の関数を呼ぶので、宣言がないと、ビルドで落ちる (`BUILD_FAILED`)。これは、仕様の失敗ではない。
  そこで、**最小のスタブ** (期待値と異なる値を返すだけ) を、本体に置き、ビルドを通した上で、`FAILED` を見る。
- **`PASSED` を、異常として扱う。** 実装なしで通るテストは、空振りしている (期待値がスタブと同じ、アサーションがない) か、機能がすでにある。Green に進まない。
- **正しい Red の条件** (新しいテストが、すべて、アサーションで落ちる / クラッシュしない / 既存のテストを壊さない) を、Skill に明記した。
- **実行は、`build-test-loop` の `build_test_once.sh` を使う。** 契約を、1 か所に保つため、スクリプトを複製しない。契約を変えるときの、直す場所が増えない。
- **Red のあと、テストを確定する前に、人が確かめる。** テストは仕様の表明で、間違ったテストは、間違った実装を、正しく見せる。ユーザーが「実装まで続けて」と依頼した場合だけ、待たずに進む。
- **Green に入ったら、テストを凍結する。** `build-test-loop` の規則 (許可なしに、テストを変えない) が、そのまま適用される。
- **対象は、MFC 非依存のロジック DLL とデータ DLL だけ。** UI 層のコードが対象の場合は、書かずに止まり、切り出しの案を示す (3 層分離が前提)。
- **テストは、DLL 単位 (`<DLL名>Test.exe`)。** 想定する構成は、MFC アプリ (UI) + ロジック DLL + データ DLL + 各 DLL のテスト exe。構成と規約は、Skill 同梱の `DLL-LAYOUT.md` に分けた (SKILL.md を、手順に絞るため)。
  - 層ごとに、テストの書き方が違う: ロジックは、データ層を**フェイク**に差し替える。データは、**一時フォルダの実ファイル**を使い、`TearDown` で必ず消す。
  - **ウォッチャーの変更は、不要。** `Find-TestExes` は、既定パターン `(Test|Tests)\.exe$` に一致する exe を、すべて実行し、出力を `=== xxxTest.exe ===` で区切る。
    テスト exe が複数あっても、結果は、1 つの `test_result.txt` にまとまる (どれか 1 つでも落ちれば `FAILED`)。Skill は、見出しで、どの層が落ちたかを判断する。
  - 複数の層にまたがる依頼は、**層ごとに、順番に Red → Green を回す** (失敗の原因が、層をまたいで混ざらないように)。
  - **DLL 特有の落とし穴を、Skill に書いた:** 公開マクロの付け忘れ (`LNK2019`、これは Red ではない)、DLL を exe と同じフォルダに出すこと (起動失敗)、CRT の不一致。
  - 対応するテスト exe がない場合は、「セットアップ」で、ユーザーの了承を得て作り、**ベースラインが緑になってから**、Red に進む。
- **セットアップの出発点:** ユーザーが、Visual Studio で、ソリューションとベースの MFC アプリを作る。Claude Code は、ソリューションフォルダをカレントにして起動する。
  データ層 → ロジック層の順に、DLL とテスト exe を、Claude が作る。**ソリューションは、作らない。**
  - **生成は、同梱の `scripts/add_layer.py` で行う (手書きしない)。** `.vcxproj` と `.sln` / `.slnx` の編集は、ミスが出やすく、毎回の出力が揺れるため。
    スクリプトは、疑似ソリューションで、`tests/add_layer_test.sh` で検証している。**ただし、ビルドは、実機でしか確かめられない** (TEST-PLAN の F0)。
  - **x64 の Debug / Release だけ対応。** 検証済みの範囲 (6 章) に合わせた。`.sln` の x86 構成には、対応付けない。
  - 出力先 (`$(SolutionDir)x64\Debug\`) は、**各 `.vcxproj` に書く** (`Directory.Build.props` は使わない)。VS が作った既存プロジェクトに、影響を与えないため。
  - ビルド確認用の、小さな公開関数と 1 件のテストを入れる: DLL の公開・インポートライブラリのリンク・実行時の DLL の読み込みを、本物の機能の前に、確かめるため。
  - ベースの MFC アプリから DLL を使う配線は、セットアップでは、しない (UI が必要になったときに、了承を得て行う)。
  - **ウォッチャーは NuGet を復元しない** ので、GoogleTest の `packages\` がなければ、ユーザーに、Visual Studio での復元を依頼する。
- 新しい `.cpp` を作ったら、`.vcxproj` に追加する。追加しないと、ビルドに含まれず、テストが走らないまま `PASSED` になる、という落とし穴を、Skill に書いた。
- `permissions.ask` (`docs/RECOMMENDED-SETTINGS.md`) で、テストファイルの編集に確認が出るのは、この Skill では、通常の動作。Skill に、そう明記した。

### 4.17 `/brainstorm` と `/add-feature`: 仕様から検証までの、コマンドの流れ
プロトタイプと TDD の練習が目的。Superpowers のような、大きなワークフローの一式は入れず、**2 つの Skill (スラッシュコマンド) だけ**を、このリポジトリに持つ。
- **流れは 3 段: `/brainstorm` (メモ) → `/update-from-ideas` (整理して、正式な仕様書) → `/add-feature` (実装)。** 新規プロジェクトでは、`/update-from-ideas` のあとに、`/new-solution` (構成案から) が入る (**仕様が先**)。
- **`brainstorm` (`/brainstorm`):** 壁打ちで考えを広げ、**メモ** (`docs/ideas/<機能名>.md`) に残す。**正式な仕様書は、作らない。コードもテストも書かない。** 質問は 1 回に 1 つ、具体例を先に (例が、そのままテストケースの種になる)。**決まらない項目は、無理に決めず、「未決」として残す。**
  役割を分けた理由: 「考えを出す」ことと、「正式な仕様にする (矛盾の点検、テストに落とせる具体さの点検、承認)」ことは、別の作業。前者に、確定の重さを持ち込むと、発想が止まる。
- **`add-feature` (`/add-feature`):** 確定した仕様書から、計画 → 承認 → (セットアップ) → タスクごとに Red → テスト確認 → Green → 検証 → 報告。**司令塔で、手順の中身は、`cpp-test-first` と `build-test-loop` に任せる** (重複して書かない)。
- **ゲートは 2 つ:** 計画の承認と、テストの確認。計画の承認だけでは、テストの中身までは、承認されない (テストは仕様の表明。間違いに気づける、最後の機会のため)。
- **どちらも `disable-model-invocation: true`:** ユーザーが `/` で呼んだときだけ動く。承認のゲートを持つ、重いワークフローが、会話の流れで、勝手に始まらないように。
- **仕様書は、`状態: 確定` でなければ使わない。** 未決事項が残っている仕様で、実装を始めない。仕様が変わるときは、実装を止めて、仕様書を直す。
- **依存される側から:** データ層 → ロジック層 → UI の順にタスクを作る。UI 層は、テストせず、ビルドと目視 (ユーザー) で確認する。
- **検証で、仕様書の例・境界値・異常系と、テストの対応表を作る:** 「テストが通った」ことと、「仕様を満たした」ことは、別。対応がないものは、報告する。
- **`update-from-ideas` (`/update-from-ideas`): アイデアを、整理して、正式な仕様書にする。**
  - **2 つのモード:** A. 新規作成 (メモ → 仕様書。メモの `整理:` を `済` に更新。メモは、削除しない) / B. 更新 (アイデア → 既存の仕様書)。
  - **A のゲート:** 仕様書の**草案の全文**を見せて、承認を得てから書く。草案には、**テストケース (テストなしなら手動の確認項目) に落とせる具体さか**の点検結果を添える。足りない点は、推測で埋めず、質問する。
  - **未決が残る間は、`確定` にしない。** `確定` にするのは、未決が 0 件で、ユーザーが明示したとき。
  - **構成案 (ソリューションがないとき):** 仕様書ができたあとで、メインの種類 (画面が要るか)、層 (仕様の「置く層」)、テスト (仕様からは決まらない。ユーザーに確認。練習なら `gtest` を勧める)、名前空間を提案し、`/new-solution` のコマンドを示す。**作成は、`/new-solution`。**
  - アイデアの入口は、3 つ: 引数のテキスト、`docs/ideas.md` (思いつきを貯める受け皿)、会話の中で出たもの。
  - **仕分け:** 取り込む / 保留 / 別機能 / 却下。理由を 1 行添える。仕様を小さく保つため、大きくなる場合は「別機能」を勧める。矛盾するものは、ユーザーが選ぶ。
  - **承認のゲート:** 変更案 (どの節を、どう変えるか) を見せて、承認後に、更新する。コード・テストは、変更しない。
  - **状態の遷移:** `確定` の仕様に変更が入ると、`変更あり (要再確定)` になり、ユーザーが、再確定するまで、`/add-feature` は、使えない。変更は、`変更履歴` に残る。
  - **実装済みの仕様:** 影響を受けるテストと実装を一覧にして、`/add-feature` に渡す。変更分だけを、テスト先行で、実装する。
  - `/add-feature` の実装中に出た思いつきは、実装せずに、`docs/ideas.md` に書き留める (スコープが、広がり続けるのを防ぐ)。
- Superpowers との併用は、採用しなかった (README の前の議論): 並列サブエージェントと git worktree が、ウォッチャーの前提 (1 フォルダ・1 実行) と衝突し、練習の目的に対して、大きすぎる。

### 4.18 `/new-solution`: 層とテストを、独立した 2 つの軸にする
**初期の設計の誤り:** 層 (DLL) の指定を「テストあり」のときだけ聞く案にしていた。層構成 (3 層分離) と、テストの有無は、別の関心事。
最初の「3 層分離 + ビルド確認だけ (TDD なし)」の構成も、テストなしで、層だけがある状態。→ **`--layers` と `--tests` を、独立した軸にした。**
- **指定は、引数でも質問でも。** 引数で指定した項目は、質問しない。省略した項目は質問する。**`--tests` は、省略されたら、必ず質問する** (黙った既定値は、TDD かビルド確認だけかを、決めてしまうため)。
- **フォルダ名 = ソリューション名 = メインのプロジェクト名。** カレントのフォルダを対象にする (サンドボックスが、カレントにしか書き込めないため。フォルダの作成は、起動前に、ユーザーが行う)。
  `App` などのサフィックスは、付けない。メインは exe とは限らず、DLL の場合もある。
- **メインが `Test` で終わる exe の場合の衝突:** ウォッチャーは、`*Test.exe` を、テストとして実行する。`MFCTDDTest.exe` のようなアプリが、テストとして起動されるのを防ぐため、
  **テストを作るときだけ**、メインに `<TargetName>$(ProjectName)_Main</TargetName>` を足す (プロジェクト名は、変えない)。テストなしなら、ウォッチャーは、ビルドだけなので、起きない。
  (ウォッチャーの命名規約を変える案は、契約の変更になるため、採らなかった。)
- **矛盾する組み合わせは、エラー:** メインが exe で `--layers none` のとき、`--tests gtest` は、テスト対象 (DLL) がない。メインが DLL なら、メイン自身がテスト対象。
- **設定は、`CLAUDE.md` の 3 行 (`メイン:` / `層:` / `テスト:`) に記録する。** `/brainstorm` / `/add-feature` / `/update-from-ideas` が読む。なければ、構造 (`*Test` プロジェクトと GoogleTest) から判定する。手で書き換えられると、ずれる可能性がある (ずれを見つけたら、確認する)。
- **テストの後付け:** すでにソリューションがあるフォルダで `--tests gtest` を再実行すると、テストのない DLL に、`<DLL名>Test` を足す。DLL の名前空間・参照 (`--uses` 相当) は、既存のファイルから読み取る。
- **GoogleTest は、既存の `packages\` のコピーだけ (現状)。** 兄弟フォルダ (`../*/packages/`) か `--gtest-from`。ネットワークは使わない。なければ、`missing` と報告し、ユーザーに、コピー元の指定か、Visual Studio での復元を依頼する。
  **ホスト側で、ソースを取得する方式は、4.19 に追加した** (`--gtest source`)。
- **層の名前:** 既定は `LogicLayer` / `DataLayer`。**変更は作成後でもよい**が (`DLL-LAYOUT.md` に、直す箇所の一覧)、作成時に `--layers logic:OrderLogic,data:OrderData` で指定することもできる (既定の動きは、変わらない。`CLAUDE.md` の `層:` には、既定でない名前だけ、`key:名前` で記録する)。
- **`--spec <仕様書>`:** 仕様書の `## 構成案` の、`- メインの種類:` `- 層:` `- 層の種類:` `- テスト:` `- 名前空間:` の行を読んで、省略した引数の既定値にする (**明示した引数が優先**)。
  値は、最初の空白までの 1 語 (後ろは、根拠の説明)。**未定・未決・空の項目は、読み飛ばす** (呼び出し側が、ユーザーに質問する。特に `テスト:` は、仕様からは決まらないので、「未定」にしておく運用)。値が不正なら、止まる。
  構成案の様式は、`/update-from-ideas` が、この形で書く。**案を見せて、了承を得る手順は、残る。**
- **`/new-solution` は、`cpp-test-first` の `add_layer.py` を読み込んで使う** (`new_solution.py` が、隣の Skill のフォルダを参照)。重複を避けるため。両方が、配布されている必要がある。
- **メインの種類に、静的ライブラリ (`lib`) を含める。** DLL と同じく、メイン自身がテスト対象になる (テスト exe が、`ProjectReference` で、リンクする)。公開マクロは、不要。
  **層 (`--layers`) の種類は、`--layer-kind dll|lib` で選べる** (既定 `dll`。全部の層に、同じ種類)。
- **層の DLL の既定は、MFC を使わない通常の DLL。** MFC 拡張 DLL にする場合は、生成後に、手で直す (`DLL-LAYOUT.md`)。

### 4.19 GoogleTest の入れ方: nuget (コピー) と source (ホスト側で取得)
**2 つの方式。** `--gtest auto|nuget|source` (既定 `auto`)。

| 方式 | 中身 | 要るもの |
|---|---|---|
| `nuget` | NuGet のパッケージ (1.8.1.8) を、`packages\` に**コピー** (兄弟フォルダ `../*/packages/` か `--gtest-from`)。テスト exe が、`.targets` で、リンクする | コピー元 (ネットワーク不要) |
| `source` | **ソース** (`ThirdParty\googletest\`) を、ソリューション内の静的ライブラリ `gtest` として、ビルドする。テスト exe は、`gtest` を `ProjectReference` する (NuGet 不要) | **ウォッチャー (Windows 側) が、GitHub に届くこと** |

- **`auto` の優先順位:** ① すでに `gtest` プロジェクトがある → `source` (一貫性) / ② パッケージがある、またはコピーできる → `nuget` / ③ すでに `ThirdParty\googletest` がある → `source` / ④ どれもない → `source` (取得が必要: `to-fetch`)。
  既定は「コピー」を優先する (オフラインで、確実で、実績がある)。コピー元がないときだけ、ホスト側の取得に進む。
- **取得は、ホスト側 (ウォッチャー) の仕事。** Claude (WSL) は、ネットワークも、カレント外への書き込みもできない。Windows 側のウォッチャーなら、GitHub に届き、フォルダにも書ける。
  → **フラグの契約に、3 つ目を足した** (`trigger_gtest.flag` / `gtest_result.txt` / `gtest_error.log`)。ビルド・テストとは独立で、同じループで、先に処理する。Skill 側のスクリプトは、`gtest_once.sh`。
  - **取得:** `git clone --depth 1 --branch <タグ>`、なければ zip のダウンロード (`Invoke-WebRequest` + `Expand-Archive`)。`include\` `src\` `LICENSE` だけを置く。`VERSION.txt` に、タグを書く。**同じタグがあれば、何もせず OK (冪等)。**
  - **タグの検証:** `^(v|release-)\d+\.\d+(\.\d+)?$` だけを許可する (コマンドの引数と URL に渡るため)。既定は `v1.17.0` (`-GtestTag` で変更可)。**タグの存在は、ネットワークで確認できていない (実機で確認する)。**
  - **失敗は `FAILED` + `[ENVIRONMENT ERROR ...]`** (ネットワーク、プロキシ、タグ名、git の不在など。ソースの問題ではない)。Skill は、報告して止まり、手動のコピー (`ThirdParty/googletest/{include,src}`) か、`nuget` 方式への切り替えを案内する。
- **ウォッチャーは、ソリューションがないと、起動できない** (起動時に `.sln` / `.slnx` を探すため)。したがって、`source` 方式の流れは、**作成 → ウォッチャーを起動 → `gtest_once.sh` で取得 → ベースライン** の順になる。取得前は、`gtest` のビルドが、ソースがなくて失敗する。
- **`gtest.vcxproj` の設計:** 静的ライブラリ。`gtest-all.cc` と `gtest_main.cc` を、同じライブラリに入れる (テスト exe に `main` がなければ、リンカーが `gtest_main` を取り込む)。サードパーティなので、警告は、すべてオフ (`TurnOffAllWarnings`)。
  動的 CRT (`/MD`) は、ソリューション内の他のプロジェクトと、同じ設定でビルドされるので、**ランタイムの不一致が起きない。** C++17 以上が必要 (`stdcpp20`)。
- **新しい GoogleTest が使える** (`nuget` の 1.8.1.8 には、`GTEST_SKIP` がない)。ただし、**ビルド時間は、増える** (初回の、`gtest-all.cc` のコンパイル)。
- **`ThirdParty/googletest/` は、`.gitignore` に入れる** (取得し直せる。クローンし直したら、再取得する)。

### 4.20 ビルドの出力は、ウォッチャーの画面に流す (専用の、表示しないコンソールで実行する)
**症状:** `build-windows.cmd` の出力が、ウォッチャー (テストの出力が出る画面) ではなく、**別のコンソールに表示される**。
**原因の候補** (実機で再現できていない。変更の根拠は、「どの経路でも、別のコンソールが出ない」ことを、構造で保証する点):
- 以前は、`& build-windows.cmd ... 2>&1 | ForEach-Object { Write-Host $_ }` で、ウォッチャーのコンソールを、バッチに共有していた。
  既定のターミナルが Windows Terminal などの場合に、コンソールアプリの起動が、別のウィンドウ / タブになる環境が、ありうる。
- バッチ内の `chcp 65001` / `chcp 932` は、**共有しているコンソール**の文字コードを、変える。ウォッチャーの画面の、表示 (日本語) が、乱れうる。
**対策:** ウォッチャーが、`cmd.exe /c` を、`System.Diagnostics.Process` で起動する (`CreateNoWindow = $true`、標準出力をパイプで受け取る、標準エラーは `2>&1` で標準出力にまとめる)。
- 子プロセスは、**専用の、表示しないコンソール**で動く。別のウィンドウやタブは、開かない。`chcp` は、その専用のコンソールにだけ効く。
- ウォッチャーは、出力を、**1 行ずつ、自分の画面に流す** (テストの出力と同じ画面)。出力は UTF-8 として読む (バッチが、MSBuild の前後だけ `chcp 65001` にするため)。
- 終了コードは、`Process.ExitCode`。`build-windows.cmd` 自体は、変えていない (単体でも、従来どおり使える)。
- **これは、ビルドの経路そのものの変更で、手書きの PowerShell。実機での確認が、必須** (TEST-PLAN の H6〜H8)。症状が、直らなければ、画面の様子 (どのウィンドウに、何が出るか) を、教えてもらう。

### 4.21 改行コードと `.gitattributes`
**問題:** WSL の git (Claude の操作) と、Windows の Git (+ Visual Studio) が、同じ作業フォルダ (`/mnt/c`) を触る。Visual Studio は CRLF で保存し、WSL の git は、**既定では変換しない** (`core.autocrlf` 未設定)。
Windows の Git は、`autocrlf=true` が既定のことが多く、LF に直す。同じファイルが、別の規則で扱われ、差分が全行変更に見える。**「Linux だから LF」とはならない** (git は、シェルではなく、ファイルのバイトを見る)。
**採った方針:** 規則を、**リポジトリ (`.gitattributes`) に固定する** (設定 `core.autocrlf` より優先され、どの git でも同じ結果になる)。**拡張子は、列挙しない。**
```
* text=auto eol=crlf     # 中身から、テキスト / バイナリを自動判定。保存は LF、作業フォルダは CRLF
.gitattributes text eol=lf
*.sh text eol=lf         # LF でないと動かないものだけを、例外として足す
```
- **管理の手間が、ほぼない:** 新しい拡張子が増えても、更新は不要 (自動判定)。人が追記してもよい (後ろの行が優先される)。バイナリと UTF-16 (`.rc` など) は、自動で変換されない。
- **`/new-solution` が、新規作成のときに、作る** (すでにあれば上書きしない)。後付けでは、作らない。**既存のリポジトリには、自動で足さない:** 追加すると、既存の CRLF のファイルが、一斉に「変更あり」に見える (`git add --renormalize .` と 1 回のコミットが要る) ため、ユーザーに提案する。
- **Claude の改行ミスの影響が、小さくなる:** 作業フォルダに LF のファイルが混ざっても、保存時に LF へ正規化される。
- **C# など、ほかの言語でも、同じ問題と同じ解決策** (複数行の文字列リテラルの中身が、改行コードで変わる点も、`.gitattributes` で統一できる)。このツール群は、現状 C++ 専用だが、`.gitattributes` の部分は、言語に依存しない。
- 検証: `tests/new_solution_test.sh` が、実際の git で、保存が LF になること、新しい拡張子も判定されること、バイナリが変換されないことを、確認している。
- **既存のプロジェクトの、検出と提案 (実装済み):** `new_solution.py --check-git` (**読み取りだけ**)。`git check-attr` で、規則の有無を調べ (追跡中の最大 20 ファイルのどれかに、`text` の属性があれば `ok`)、なければ `git ls-files --eol` で、CRLF の件数を数える。
  - **状態:** `ok` / `propose` / `lf-only` / `declined` / `not-a-repo` / `unknown`。**提案が要るのは、`propose` (規則がなく、CRLF のファイルがある) だけ。** LF のみなら、提案しない (問題が起きていない)。
  - **提案は、`/add-feature` の最初の読み取り確認で、1 回だけ、作業を止めずに行う。** 選択肢: 追加する / 今回は見送る / 今後も見送る (`CLAUDE.md` の `- 改行コードの提案: 見送り` に記録。以降は `declined`)。
  - **`--add-gitattributes` は、ファイルを作るだけ。git のステージ・コミットは、しない** (`git add --renormalize .` と、1 回のコミットは、ユーザーが行う)。
  - **自動では、作らない:** 既存のリポジトリへの追加は、保存が CRLF のファイルを、一斉に「変更あり」に見せるため。
- **このリポジトリ (claude-windows-desktop-tools。旧名 cpp-claude-build-tools) は、別の規則のまま:** `.cmd` / `.ps1` は、CP932 と BOM のバイトを守るため `-text` (4.x 参照)。

### 4.22 ビルドエラーは、集約した要約で渡す (`summarize_build_log.py`)
**問題:** `build_once.sh` は、`build_error.log` の先頭 40 行を、そのまま出していた。同じエラー (ヘッダの宣言漏れなど) が、多数のファイルで繰り返されると、40 行が同じエラーで埋まり、別の原因が見えない。件数や、コンパイルとリンクの区別も、分からない。
**採った方針:** Skill のスクリプト (WSL 側) が、`build_error.log` を読んで、**同じ (コード, メッセージ) を 1 つにまとめた要約**を出す。
```
7 errors (4 unique) in 4 files; compile 5 / link 2
[1] C2065 'cnt': undeclared identifier  x4
    MyApp/Foo.cpp(49,5)  MyApp/Foo.cpp(50,9)  MyApp/Bar.cpp(12,3)  (+1 more)
```
- **最初に出た順に並べる。** 連鎖エラーの原因は、たいてい先頭側にある。Skill には、「上の `[n]` から直し、再ビルドで確認する」と書く (`SKILL.md`)。重要度のスコアや、連鎖の推定はしない (外れたときに、誤った順で直させるため)。
- **情報を落とさない:** 解釈できない行は、最大 5 行を `other:` として残す。同じ場所の重複は 1 つにする。出力は、最大 40 行・1 行 400 文字 (従来と同じ上限)。
- **`.claude-logs/build_summary.json` にも、同じ内容を書く** (コード・種類 `compile` / `link`・メッセージ・件数・場所・プロジェクト)。ログの再読ではなく、必要なら、これを読む。`.claude-logs/` は `.gitignore` 済み。
- **フォールバック:** `python3` がない、または、解釈できるエラー行が 1 つもない (スクリプトが rc=3 で、何も出さない) ときは、従来の生ログ表示 (`show_log`) に戻る。`ENV_ERROR` は、要約せず、生ログのまま (環境の問題は、文面そのものが手がかり)。
- **ウォッチャーではなく、WSL 側で行う理由:** 契約 (ファイル名・結果の値・終了コード) を変えず、ホスト側の再配布が要らない。ウォッチャーは、手書きの PowerShell で、実機での確認が重い。要約の規則は、Linux 上で、ログのサンプルだけで、検証できる。`build_error.log` は、従来どおり、生のエラー行 (ウォッチャーが、重複の除去と相対パス化をしたもの) のまま残る。
- **スクリプトは、2 つの Skill (`auto-build` / `build-test-loop`) に、同一のコピーを置く** (Skill ごとに配布され、片方だけが入っている環境があるため)。`tests/summarize_build_log_test.sh` が、一致を確認する。
- **テスト失敗 (GoogleTest) の要約も、同じ方針** (`summarize_test_log.py`。`build-test-loop` のみ)。`FAILED` で、`test_error.log` を、**同じメッセージの失敗ごとにまとめる** (`xN`、テスト名は最大 5、場所は最大 3)。
  「同じ原因の不具合は、1 つ直すと複数が通る」(`SKILL.md` の方針 6) を、出力の形で後押しする。**まとめる鍵はメッセージ (`Expected` / `Which is` の値を含む) で、場所は含めない** (同じ原因の失敗は、場所が違う)。値が違えば、別の組になる (誤ってまとめるより、まとめ漏れのほうが安全)。
  - **解釈の規則:** 失敗の詳細は、その後の `[  FAILED  ] 名前 (N ms)` の行の**前**にある (gtest の出力順)。`listed below` の再掲と、`[==========]` などの集計行は、数えない。MSVC 形式 (`file(line): error:`) と、Linux 形式 (`file:line: Failure`) の両方。
  - **フォールバック:** 失敗したテスト名を 1 つも解釈できない (クラッシュ。名前のない `exit code` だけの報告など)、または `python3` がないときは、従来の表示 (`Failed tests (N):` の一覧と詳細 60 行)。`TEST_TIMEOUT` / `ENV_ERROR` は、要約しない (`Hung test` などが、そのまま手がかり)。
  - **`.claude-logs/test_summary.json`:** 全テスト名・テストごとの場所とメッセージ。標準出力は、名前を省略するため、全名が要るときは、これを読む。
- **警告は、成功時に、件数の 1 行だけを出す** (`summarize_build_log.py --severity warning --oneline`)。
  - **なぜ、1 行か:** 警告は、結果を変えない。ビルドのたびに、一覧を出すと、トークンを消費し、ループで、無関係な警告を直し始める (「無関係なリファクタリングはしない」に反する)。件数と上位のコードだけで、「気づく」には足りる。詳細は、必要なときだけ、同じスクリプトで読む (`SKILL.md`)。
  - **失敗時は出さない:** エラーに集中させる。**`ENV_ERROR` / `TEST_TIMEOUT` / `FAILED` でも出さない。**
  - **相対パス化は、WSL 側 (`--root`)。** `errors.log` は、ウォッチャーが相対化するが、`warnings.log` (MSBuild のファイルロガー) は、フルパスのまま `.claude-logs/` に残る。ウォッチャーを変えない (再配布が要らない) ため、Windows のパス (`C:\...`) を、`/mnt/c/...` に直して、ソリューションからの相対にする。ドライブ文字と、フォルダの大文字・小文字は、区別しない。フォルダの外 (VS の標準ヘッダなど) は、`/` 区切りのフルパスのまま。
  - **限界:** MSBuild は、**再コンパイルされたファイルの警告だけ**を出す。差分ビルドで、何も再コンパイルされなければ、件数は出ない (警告がないという意味ではない)。`-LogDir` で、ログの場所を変えると、読めない (何も出ない)。
  - `.claude-logs/warnings_summary.json` に、同じ内容 (キーは `warnings`) を書く。
- 検証: `tests/summarize_build_log_test.sh` (集約・件数・並び・重複・上限・JSON・フォールバック)、`tests/fake_watcher_test.sh` (`BUILD_FAILED` の経路)。

### 4.23 `mfc-check`: MFC の「見えない部分」を、静的に検査する
**問題:** MFC は、メッセージマップとリソース ID の対応が、**マクロと名前でつながっている**。対応が崩れても、**コンパイルは通り**、実行したときに、「ボタンが反応しない」「メニューが効かない」という形で現れる。ビルドの要約 (4.22) では、見えない。AI は、`.rc` (ウィザード生成は UTF-16) を、読むことも、直すことも、苦手。
**採った方針:** ビルド (ウォッチャー) とは別の、**静的な検査の Skill** (`mfc-check`) にする。
- **読み取りだけ・WSL で完結・Windows 不要。** ウォッチャーの契約 (ファイル名・結果の値・終了コード) を、変えない。実行は速く、決定的で、疑似プロジェクトで検証できる (`tests/mfc_check_test.sh`)。
- **実際に起きる不具合に絞る。** (1) リソース ID の未定義・値の重複 (メッセージが別の項目に届く)、(2) メッセージマップのハンドラの、宣言・定義・登録の食い違い、(3) UI (`.rc`) との対応、(4) 層の依存 (ロジックの DLL に GUI が混ざる)。コードの書式や命名は、扱わない (`~/.claude/rules/cpp-mfc.md` と、`clang-format` の領域)。
- **重大度を 3 段階に分ける:** error = ほぼ確実な不具合 (直す)、warning = 疑わしい (自分が触った箇所だけ直す)、info = 参考 (既定では、出さない)。ウィザードが残す未使用の ID などで、ノイズにならないようにするため。
- **誤検出を減らす設計:** 標準 ID は、`afxres.h` を読まず、接頭辞で判定する。基底クラスの修飾付きハンドラ (`&CWinApp::OnFileNew`) は、検査から外す。マップの外でも使われている ID は、「コードで動的に使っている」として、UI の検査から除く。`resource.h` の `#define` 自体は、「使用」に数えない。
- **リソース定義の名前だけが未定義のときは、warning にする。** RC は、未定義の名前を、**名前付きリソース**として受け付ける (エラーにならない)。数値 ID では、参照できないだけ。実プロジェクト (`cppsamples`) の、ウィザード生成の `IDR_HELP_MENU` で、確認した。参照する側 (コントロール・メニュー項目・コード) の未定義は、RC もコンパイルもエラーになるので、error のまま。
- **ダイアログの検査 (DLG) は、「そのクラスのダイアログ」を解決してから行う。** 以前の UI003 は、「どのダイアログにもない」だけを見ていた (別のダイアログにあれば、通ってしまう)。ダイアログクラス (基底が `CDialog` 系。派生の派生も含む) の `IDD` を、`enum { IDD = ... }` か、コンストラクタの基底の初期化から読み、**そのダイアログに対して**、`DDX` の ID (DLG001)、`DDX_Control` のメンバーの型 (DLG003)、ボタンのハンドラ (DLG004) を検査する。解決できなければ、DLG の検査は行わず、UI003 に任せる (DLG001 で検査した `DDX` は、UI003 で、二重に報告しない)。
- **DLG010 (同じメンバーを、複数の `DDX_Control` に渡す) は、実機の確認から生まれた。** K7 の最初の実験で、接続済みのメンバー (`boldStyle`) に、存在しない ID を渡しても、何も起きなかった。MFC の `DDX_Control` (`wincore2.cpp`) は、`m_hWnd == NULL` のときだけ、`PrepareCtrl` でコントロールを探すため。これは、**コピー&ペーストの誤り** (メンバーを直し忘れて、別の ID に、同じメンバーを渡す) が、実行時に何も警告を出さず、2 回目が黙って無視されることを意味する。ID の存在 (DLG001) も、型 (DLG003) も、合っているので、他の検査では見逃す。**実機で確認した (K11): `DDX_Control(pDX, IDC_BRUSHCOLOR, brushColorPicker)` を `penColorPicker` に直し忘れた形にすると、Debug でも、アサートも警告も出ず、ダイアログは、表示される。ただし、そのコントロールだけが、`CMFCColorButton` に接続されず、`.rc` の素のボタンのまま (見た目が、他の色指定と違う)。**`DoDataExchange` の中で、同じメンバーが複数の `DDX_Control` に現れたら、warning にする (error ではなく warning: 分岐ごとに別の ID を渡す書き方は、`else` / `case` / `default` をまたぐものだけ除いたが、ほかの正当な書き方を、見逃している可能性があるため)。
- **`DDX_Control` の型 (DLG003) は、MFC 標準のクラスだけ判定する。** `.rc` のコントロールの種類 (キーワード、または `CONTROL` のクラス名) と、メンバーの型 (`CEdit` `CListCtrl` など) を、表で対応づける。自作の派生クラス (`CMyEdit`) は、表にないので、判定しない (誤検出を避ける。見逃しのほうを選ぶ)。
- **基底の呼び出し (DLG006 / DLG007):** `OnInitDialog` と `DoDataExchange` の定義の本体に、`X::OnInitDialog(` / `X::DoDataExchange(` の呼び出しがあるかを見る。ウィザード生成のコードは、必ず呼んでいるので、誤検出にならない。`CFormView` は `OnInitDialog` を持たないので、除く。
- **ボタンのハンドラ (DLG004) は、保守的にする:** `PUSHBUTTON` / `DEFPUSHBUTTON` (と、`BS_PUSHBUTTON` の `CONTROL`) だけ。`IDOK` / `IDCANCEL` などの標準 ID (基底が処理する) と、マップの外でコードが使っている ID (動的な処理) と、`ON_*_RANGE` があるクラスは、除く。
- **実プロジェクトでの検証で、誤検出を、4 種類見つけて、直した (`DoubleBufferSample`。最初は error が 7 件。本物の不整合は、`IDR_HELP_MENU` の名前付きリソースだけだった)。** (1) 継承したハンドラ: マップのクラスにだけ宣言を探していたのを、プロジェクト内の基底クラスまで、探すようにした。MFC の基底が持つ `ON_WM_xxx` の既定のハンドラは、宣言がなくても合法なので、指摘しない。(2) 宣言の末尾 (`final` / `override` / `= 0`) を、解釈できなかった。(3) 入れ子のクラス (`Outer::Inner`) のマップを、解釈できず、外側のクラスにも、内側の `DECLARE_MESSAGE_MAP` を数えていた。クラスごとに、入れ子のクラスの本体を除いた本体 (`own`) で、検査する。(4) `AFX_DIALOG_LAYOUT` (VS が残す、削除済みのダイアログのレイアウト) と `DESIGNINFO` を、知らなかった。メタデータとして、使用から外し、前者は、info (DLG009) にする。疑似プロジェクトでは、見つからなかった。**実プロジェクトで、ウィザードのコードに手を入れた結果を、見ることが、必要だった。** 4 種類は、すべて、`tests/mfc_check_test.sh` の「正常なプロジェクト」に、入れた (指摘が出てはならない)。
- **`.rc` の読み込み:** BOM で、UTF-16 / UTF-8 を判定する (なければ、UTF-8、だめなら CP932)。コメントと文字列を、行番号を保ったまま空白にして、BEGIN / END の入れ子を数えて、ブロックを切り出す。
- **層の判定:** プロジェクト名 (`Logic` / `Data`) と、`.vcxproj` の `ConfigurationType`。`Application` は UI。名前が違うときは、`--logic` / `--data` で指定する。テストプロジェクト (名前が `Test` で終わる) は、対象外。
- **自動では、走らせない (今回):** ビルドの成功後に、自動で走らせる案は、誤検出の量を、実機で見てから決める (件数の 1 行通知は、4.22 の警告と、同じ形で、あとから足せる)。
- **対象外 (今回):** ダイアログの、レイアウト (重なり・はみ出し・タブ順)、フォント、DPI。見た目は、スクリーンショットで観測する。起動スモークとスクリーンショット (ウォッチャー側の変更が要る)、UI Automation の操作、ミニダンプの解析。いずれも、実行の観測が必要で、Windows 側の実装になる。
- 検証: `tests/mfc_check_test.sh` (疑似プロジェクト)。実プロジェクト (`cppsamples` の 4 つの MFC プロジェクト) では、`IDR_HELP_MENU` (名前付きリソース) と、削られたウィザードのコードの残り (宣言だけで、マップにも定義にもないハンドラ) を、検出した。

### 4.24 C++ と .NET (WPF) の統合: 1 つのウォッチャー、1 組の Skill、共通のテスト結果の形式
**きっかけ:** WPF 用に、同じ仕組み (ビルドとテストのループ) が欲しくなった。`cpp-*` と `wpf-*` を別に作る案、設定で切り替える案、統合する案を、比べた。
**採った方針:** **ウォッチャーも Skill も 1 つにし、ソリューションの中身から、自動で判定する。** 理由:
- 契約 (フラグ・結果ファイル・rc・ループの規則・完了報告) は、C++ でも .NET でも同一。違うのは、「ビルドとテストの実行方法」と「ログの解釈」だけ。別の Skill にすると、同じ本文を 2 つ保守することになる。
- Skill を分けると、description が似た Skill が並び、モデルが取り違える余地が出る。**混在のソリューション** (C++ の DLL + WPF のアプリ、MFC + WPF) では、どちらを使うか、決められない。
- **`dotnet build` は、`.vcxproj` をビルドできない。** 一方、VS の MSBuild は、SDK 形式の `.csproj` を、`/restore` を付ければ、ビルドできる。ビルドの経路を MSBuild に一本化すれば、C++ のみ、.NET のみ、混在を、同じ経路で扱える。

**名前の変更 (契約ではなく、配布物の名前):** `cpp-auto-build` → `auto-build`、`cpp-build-test-loop` → `build-test-loop`。技術名を外した。**旧名の Skill が、配布先に残っていると、description が重なるので、削除する** (`install.sh` が、残っていれば知らせる)。`cpp-test-first` / `mfc-check` / `new-solution` は、技術に固有なので、名前を変えない。

**ウォッチャーの判定 (`watch_and_build.ps1`):**
- `.sln` / `.slnx` から、プロジェクトのパスを、正規表現で集める (`.vcxproj` / `.csproj` / `.vbproj` / `.fsproj`。`.slnx` は `Path="..."`、`.sln` は `Project("{...}") = "名前", "パス", ...`)。単独のプロジェクトファイルを、`-SolutionPath` に渡してもよい。
- **`-Platform auto` (新しい既定):** C++ があれば `x64`、.NET だけなら `AnyCPU`。明示した値は、そのまま使う。**混在のソリューションは、`x64` で、ソリューション構成が、.NET 側を `Any CPU` に対応づける前提。**
- **ビルドの特徴 (`build-windows.cmd` の第 6 引数 `Features`):** C++ があれば `cpp`、.NET があれば `restore`。**中身が判定できないときは、従来どおり `cpp`** (回帰を避ける)。`cpp` がなければ、VS の要求は、MSBuild だけになり、C++ ワークロードのない VS でも動く。
- **C++ だけのソリューションの MSBuild の呼び出しは、従来と実質同じ** (`/p:Platform` を、引用符で囲む点だけが違う。値は同じ)。`/restore` は、.NET があるときだけ付ける (C++ の経路に、新しい動作を持ち込まない)。
- **.NET の環境エラー:** SDK が見つからない・古い (`MSB4236` `NETSDK1045` `NETSDK1141`)、NuGet のソースに届かない (`NU1301`) は、`[ENVIRONMENT ERROR ...]` にする。**`NU1101` (パッケージが見つからない) は、環境エラーにしない** (パッケージ名の誤りは、ソースの問題で、Claude が直せるため)。
- **採らなかった案: `dotnet build` へのフォールバック (`-Builder dotnet`)。** VS のない環境の救済になるが、手書きの PowerShell が増え、実機で確かめられない分岐が増える。必要になったら、足す。

**テストの実行 (ウォッチャー):**
- **C++:** 従来どおり、`<ソリューション>\<x64|Win32|ARM64>\<Configuration>\` の `-TestExePattern` に合う exe を実行する。**`--gtest_output=xml:<test-results>\<exe名>.xml` を、引数に足す。** C++ のプロジェクトがなければ、探さない。
- **.NET:** ソリューションの `.csproj` / `.vbproj` / `.fsproj` のうち、`Microsoft.NET.Test.Sdk` / `MSTest` を参照する、`IsTestProject` が `true`、または名前が `Test` / `Tests` で終わるものを、`dotnet test <プロジェクト> --no-build -c <Configuration> --results-directory <test-results> --logger "trx;LogFileName=<名前>.trx"` で実行する。**ビルドは、ソリューションのビルドで済んでいる** (`--no-build`)。`-DotnetTestArgs` で、引数を足せる (プロジェクトの出力先が、プラットフォーム別のとき、`-p:Platform=x64` など)。
- **両方ある場合は、両方を実行する。** どちらかが落ちれば `FAILED`、どちらかがタイムアウトなら `TIMEOUT` (それ以降は実行しない)。**どちらの種類も、1 つも見つからなければ `ENV_ERROR`** (従来の「テスト exe が見つからない」を、一般化した)。C++ のプロジェクトがあっても、テスト exe がなく、.NET のテストがあれば、.NET だけを実行する。
- **「実行されなかった」を成功にしない (4.5 の、.NET 版):** `dotnet test` が終了コード 0 でも、**trx がない、または `executed` が 0** なら、`ENV_ERROR` (テスト 0 件、アダプタ未検出など)。
- `test_error.log` は、従来どおり人が読める形で書く (.NET の失敗は、trx から、`FAILED <名前>` + メッセージ + 最初のファイル行)。**構造化された解釈は、`test_error.log` ではなく、`test-results/` の XML / trx から行う** (下記)。

**テスト結果の共通の形式 (WSL 側 `summarize_test_log.py`):**
- ウォッチャーは、ランナーの機械可読な出力 (GoogleTest の XML、MSTest の trx) を、**そのまま** `.claude-logs/test-results/` に残す。**共通の形式への変換は、WSL 側のスクリプトが行う。** 4.22 と同じ理由: 契約を変えず、ホスト側の再配布が要らず、変換の規則を、Linux 上で、サンプルのファイルだけで、検証できる (手書きの PowerShell で、XML の変換を書くと、実機でしか確かめられない)。
- **共通の形式 `TestResult`:** `name` (`Suite.Case` / `完全なクラス名.メソッド名`)、`source` (exe 名 / プロジェクト名)、`framework` (`gtest` / `mstest`)、`outcome` (`passed` / `failed` / `skipped`)、`ms`、`failures` (場所とメッセージ)。
  - GoogleTest XML: `classname.name`。失敗の先頭行 `file:line` から場所を取る。`skipped` は、成功にも失敗にも数えない。
  - trx: `TestDefinitions` の `className` (`, アセンブリ名` を除く) + `name`。データ行つきのテストは、`(1,2)` を残す。場所は、スタックトレースの、**最後の ` in <パス>:line N` (日本語 OS は `場所 <パス>:行 N`)**。`NotExecuted` は、`skipped`。
  - Windows のフルパスは、`--root` で、ソリューションからの相対パスにする。
- **`test_summary.json` は schema 2:** `schema` / `structured` / `totals` (実行・成功・失敗・スキップ) / `sources` (exe・プロジェクトごとの件数と `framework`) に加え、**従来のキー (`failed` / `groups` / `tests` / `other`) を、そのまま残す** (読む側を壊さない)。
- **同じメッセージの集約は、フレームワークをまたぐ** (4.22 の方針のまま)。要約の見出しに、`[ran N: passed / failed / skipped]` が付く (構造化された結果があるとき)。
- **構造化された結果がない・読めないときは、従来のテキスト解釈 (GoogleTest の失敗行) に戻る。** クラッシュの報告 (`(no gtest failure lines ...)`、`Hung test`) は、構造化された結果があっても、`other:` に残す (クラッシュした exe には、XML がないため)。壊れた XML は、`other:` に「読めなかった」と残し、読めるものは使う。
- **古い結果の誤読を防ぐ:** ウォッチャーが、実行の開始時に `test-results/` を消す。`build_test_once.sh` も、フラグを置く前に消す (4.4 と同じ二重の防止)。

**実機で見つかった 2 つの不具合 (v2.4.1)。** WPF + MSTest の最初の実行で、`test_error.log` が、**文字化け**し、**テストが 1 件も実行されなかった**。原因は、別々だった。
- **文字化け:** `dotnet test` の出力は **UTF-8** (UTF-16 でも、CP65001 のコンソールの設定でもない。ファイルを、バイト列で調べて確認した)。ウォッチャーが、すべてのテストランナーの出力を、`Get-Content -Encoding Default` (ANSI = CP932) で読んでいたため、UTF-8 の日本語が、CP932 として解釈され、**さらに UTF-8 で書き出された** (`縺ｮ繝・せ繝・` の形。一部のバイトは、解釈できず、復元できない)。GoogleTest の exe (MSVC でビルドしたもの) は、ANSI で出すことが多いので、C++ の経路では、顕在化しなかった。**対策:** `Read-ProcessOutput` が、出力を**バイト列で読み、UTF-8 として厳密に解釈し、できなければ (不正なバイト列)、ANSI として解釈する** (BOM は除く)。**ランナーごとの決め打ちにしなかった:** GoogleTest の出力が、UTF-8 の場合も、dotnet が ANSI の場合も、動くため。CP932 の日本語は、ほぼ、UTF-8 として不正なので、判定は、実用上、曖昧にならない。構造化された結果 (trx / XML) は、XML なので、この問題の影響を受けない (WSL 側の要約は、正しいまま)。
- **テストが実行されなかった:** 出力先が `bin\auto\Debug\...` になり、`dotnet test --no-build` が、テストの DLL を、見つけられなかった。原因は、**環境変数 `Platform`**: MSBuild は、環境変数を、プロパティとして読む。`run_watcher.cmd` が、cmd の変数 `PLATFORM` (= `auto`) を作ると、大文字小文字を区別しない Windows では、環境変数 `Platform` になり、子プロセスに、継承される。ビルド (`build-windows.cmd`) は、`/p:Platform` を明示するので、影響を受けなかった (U1 の C++ は、通った)。`dotnet test --no-build` だけが、明示しないので、`Platform=auto` で、プロジェクトを評価した。**対策 (二重):** (1) `watch_and_build.ps1` が、起動時に、環境変数 `Platform` を、削除する。(2) `run_watcher.cmd` の変数名を `WATCH_PLATFORM` / `WATCH_CONFIG` に変え、環境変数として、漏れないようにする。**教訓:** 子プロセスに、MSBuild のプロパティ名と同じ環境変数 (`Platform` / `Configuration` など) を、渡さない。
- **この 2 つは、疑似ウォッチャーでは、見つからない種類の不具合** (WSL では、PowerShell も、Windows の環境変数の継承も、再現できない)。実機の確認 (U6 / U7 / WS3) の価値を示した。

**C++ のテストを `CppUnitTestFramework` (VS 付属の「MSTest」) に移して、共通化する案は、採らなかった。**
- 名前は MSTest だが、.NET の MSTest とは別物で、**ランナーが共通にならない** (`vstest.console.exe` と `dotnet test`)。共通化したかったのは、ランナーではなく、結果の形式で、それは、XML / trx の変換で、足りる。
- gmock、パラメータ化テスト、DeathTest が使えなくなる。ウォッチャーの、exe を強制終了して `Hung test` を特定する仕組みも、DLL をホストが読み込む方式では、難しくなる。
- `cpp-test-first` / `new-solution` (GoogleTest の取得) / `add_layer.py` / `summarize_test_log.py` / テストの書き直しが必要で、得るものが、少ない。

**検証の範囲 (誤解しないために):**
- **WSL 側 (検証済み):** `summarize_test_log.py` の XML / trx の変換と集約 (`tests/summarize_test_log_test.sh`、`tests/fixtures/`)、`summarize_build_log.py` の .NET の診断コード (`tests/summarize_build_log_test.sh`)、疑似ウォッチャーでの、構造化された結果の経路 (`tests/fake_watcher_test.sh`)。
- **Windows 側 (未検証):** `watch_and_build.ps1` と `build-windows.cmd` の、今回の変更は、**実機で、まだ実行していない** (WSL のサンドボックスから、PowerShell を実行できない。括弧の対応と、CP932 の `rem` 行の確認だけ、した)。C++ のソリューションで回帰がないこと、.NET (WPF + MSTest) のビルドとテストが動くことは、`docs/TEST-PLAN.md` の N 系の手順で、実機で確認する。
- **サンプルの trx / XML は、仕様から書いたもの。** 実機の `dotnet test` / GoogleTest の出力と、形が違えば、`tests/fixtures/` を、実物に差し替えて、変換を直す。

### 4.25 `wpf-check`: WPF の「見えない部分」を、静的に検査する
**問題:** WPF は、XAML と C# が、**文字列 (バインディングのパス、リソースのキー、`Source` の URI) で結ばれている**。崩れても、**コンパイルは通る**。バインディングの誤りは、例外にもならず、出力ウィンドウにログが出るだけ。AI は、実行時の画面を見られない。ビルドの要約 (4.22) では、見えない。`mfc-check` (4.23) と、同じ種類の問題。
**採った方針:** `mfc-check` と同じ形の、**静的な検査の Skill** (`wpf-check`)。読み取りだけ・WSL で完結・Windows 不要・ウォッチャーの契約は変えない。出力の形式、`--all` / `--json` / `--max-lines`、終了コード (0 / 1 / 2 / 3)、重大度の 3 段階も、同じ。

- **対象は、「コンパイルは通るが、実行時に壊れる」ものだけ。** イベントハンドラの不足、`x:Name` の重複、XAML の文法の誤り、未定義の型は、**WPF のビルドが、`MC` / `XDG` / `CS` のエラーにする**ので、検査しない (二重にしない)。取り下げた候補: イベントハンドラの検査 (EVT)、`x:Name` と code-behind の対応 (NAM)、`x:Class` と code-behind の不一致 (CLS)。いずれも、ビルドで分かる。
- **バインディングの検査 (BND) が、中心。** DataContext の型を、XAML・`DataTemplate` の `DataType`・code-behind の代入・ウィンドウを作るコードから推定し、パスの先頭 (と、辿れる限りの、入れ子) を、型のメンバーと突き合わせる。
  - **確実なときだけ error:** 型を、複数の根拠で決められ、基底クラスまで、すべて、プロジェクト内か、「プロパティを足さない」と知っている外部クラス (`ObservableObject` など) のとき。**基底が、`Window` や未知の外部クラスのときは、「ない」と言わない** (BND900 の info)。誤検出が、この Skill の信用を、最も傷つけるため。
  - **`d:DataContext` (デザイン時) だけが根拠なら、warning。** 実行時の DataContext は、別のところで決まるかもしれない。
  - **検査しない形を、明確にした:** `Source` / `ElementName` / `RelativeSource` つき、`ControlTemplate` / `Style` の中、`DataType` のない `DataTemplate` の中 (文脈が変わる)。
  - **WPF の実際の動作に合わせた:** public な**インスタンスの、プロパティ**だけがバインドされる。フィールド (BND002)・メソッド・非 public・static は、黙って失敗する。TwoWay で setter がないと、実行時に例外 (BND003)。ただし `init` は、リフレクションで設定できるので、読み取り専用に数えない。setter が public でない場合は、挙動の確信が弱いので、warning にとどめた。
  - **ソースジェネレーター (CommunityToolkit.Mvvm) を知っている:** `[ObservableProperty]` のフィールド `_name` / `m_name` / `name` → `Name`、`[RelayCommand]` のメソッド `Save` / `LoadAsync` → `SaveCommand` / `LoadCommand`。**知らないジェネレーターのメンバーは、「ない」と誤判定しうる** (ReactiveUI.Fody など。基底が外部なら、検査しないので、通常は、安全側に倒れる)。
  - **INPC の検査 (BND004):** バインドされ、setter が public で、`OneTime` でないプロパティを持つ ViewModel が、`INotifyPropertyChanged` を実装していない (継承・属性・`PropertyChanged` イベントを含めて確認) → warning。値を変えても、画面が更新されない、という、気づきにくい不具合。
- **リソースの検査 (RES) は、見える範囲を、厳密に辿る。** 祖先の `Resources` → `App.xaml` の辞書 (結合した辞書を、再帰的に)。プロジェクトの外 (NuGet のテーマなど) の辞書が混ざると、確実に言えないので、**error を warning に下げる** (誤検出より、見逃しを選ぶ)。ライブラリ (`OutputType` が `Library`) の XAML も、アプリ側の辞書で解決されうるので、同様。コードで足されるキー (`Resources["X"] = ...`) は、知っている。
  - **RES002 (前方参照) は、warning:** 辞書の項目は、遅延して読まれるので、実行時の結果が、環境で変わりうる (公式の記述を、確認できていない)。定義順を直せば、確実なので、直す価値はある。
- **`InitializeComponent()` の呼び忘れ (UI001)** は、実際に起きやすく、**例外も出ず、画面が空になる**ので、error。ただし、`this(...)` で委譲するコンストラクターがあるので、「どれか 1 つでも呼んでいれば」指摘しない。
- **層の検査 (LAY) は、`mfc-check` の LAY001〜003 と同じ考え方。** 層は、名前 (`Logic` / `Domain` / `Core`、`Data`、`ViewModels`) と、`.csproj` の `UseWPF` / `OutputType` で推定し、`--logic` / `--data` / `--viewmodel` で、上書きできる。ViewModel が `MessageBox` / `Application.Current` を使うのは、warning (動くが、テストしにくい。MSTest は、STA スレッドも `Application` もない。これは、`build-test-loop` の、.NET のテストで、実際にぶつかる)。
- **XAML は、expat で、自前で読む。** `xml.etree` は、行番号と、属性の順序を保てない。名前空間の対応 (`clr-namespace:` と `assembly=`) と、要素の開始位置 (属性の行を求めるため) を、自前で持つ。**属性の行は、開始タグの、引用符を考慮した範囲から、探す** (複数行にまたがる要素で、行が、ずれないように)。
- **C# は、軽い字句解析。** コメントと文字列 (`@"..."`、`$"..."`、raw 文字列を含む) を空白にし、深さ 0 の宣言を切り出して、型・メンバー・基底クラス・コンストラクターの本体を、取り出す。完全な構文解析 (Roslyn) は、WSL に .NET を要求するので、採らなかった。**限界:** プリプロセッサ (`#if`) で、宣言が分岐するコード、ソースジェネレーターが作る型は、見えない。
- **検証の範囲 (誤解しないために):** `tests/wpf_check_test.sh` (疑似プロジェクト) で、正常なプロジェクトに指摘が出ないこと (CommunityToolkit.Mvvm・`DataTemplate`・外部の辞書・結合した辞書・`d:DataContext`・BOM + CRLF を含む)、不具合を 1 か所ずつ入れて、狙いのコードが出ることを確認した。**実プロジェクトでは、まだ検証していない。** `mfc-check` の経験 (実プロジェクトで、誤検出を 4 種類見つけた) からすると、**実プロジェクトで、誤検出が見つかる可能性が高い**。TEST-PLAN の W1 で、実機の WPF プロジェクトに、実行して、確かめる。
- **自動では、走らせない (今回):** ビルドの成功後に、自動で走らせる案は、誤検出の量を、実プロジェクトで見てから決める (4.23 と同じ)。

### 4.26 パッケージの追加 (`add-package`): NuGet / vcpkg / ソースの取り込みを、1 つのフラグで
**問題:** Claude (WSL) は、NuGet も vcpkg も、実行できない (サンドボックスのネットワークと、Windows 側のツールに、届かない)。`.csproj` を手で編集して `PackageReference` を足す案は、**名前とバージョンを推測で書く**ことになり、実在しない名前や、紛らわしい名前 (似た名前の別のパッケージ) を入れてしまう。C++ には、そもそも、標準の手段がなかった (GoogleTest だけ、個別の方式 (4.19))。
**採った方針:** GoogleTest のソース取得 (4.19) と同じ、**フラグの契約を、4 つ目として足す。** Claude は、ファイルを置いて、ファイルを読むだけ。ビルド・テスト・gtest 取得とは、独立 (ビルドの前に処理される)。

| ファイル | 作る人 | 内容 |
|---|---|---|
| `trigger_package.flag` | Claude | 各行が 1 つの操作 (空行と `#` 行は無視)。上から順に実行し、**最初の失敗で止まる** |
| `package_output.txt` | ウォッチャー | 各操作の出力 (`## <操作>` の見出し付き)。1 操作 60 行まで (全文は `.claude-logs\package.log`) |
| `package_error.log` | ウォッチャー | 失敗時のみ。環境の問題 (ネットワーク、`dotnet` / `vcpkg` がない) は、先頭が `[ENVIRONMENT ERROR - not a source code problem]` |
| `package_result.txt` | ウォッチャー | 完了マーカー: `OK` / `FAILED` (**最後に書く**。4.2 と同じ) |

**操作 (決まった形だけ):** `nuget search <語>` / `nuget versions <ID>` / `nuget add <プロジェクト> <ID> [<バージョン>]` / `nuget remove <プロジェクト> <ID>` / `vcpkg search <語>` / `vcpkg baseline` / `vcpkg install` / `fetch <owner/repo> <タグ> <名前> [<サブフォルダ>]`。Skill 側のスクリプトは `package_once.sh`。

- **引数は、コマンドに渡るので、決まった文字だけを許可し、WSL 側 (`package_once.sh`) とウォッチャーの、両方で、同じ規則で検証する** (4.19 のタグの検証と同じ考え方。**多重の防御**。WSL 側で拒否すれば、フラグを置かないので、ホストに届かない)。ID・語・リポジトリ・タグ・名前・バージョンは、英数字と `.` `_` `-` (`+`) だけ、先頭は英数字 (**`-` で始まるものは、オプションとして解釈されるので、拒否する**)。プロジェクトは、ソリューションのフォルダの下の `.csproj` / `.vbproj` / `.fsproj` で、`..` と絶対パスを拒否する (ホスト側は、さらに、正規化したパスが、ソリューションの下にあることと、存在することを、確認する)。サブフォルダは、セグメントごとに検証し、`.` と `..` を拒否する。`vcpkg install` / `baseline` は、引数を取らない (トリプレットは、ウォッチャーが、Platform から決める)。
- **取り違えへの対策 (サプライチェーン):** (1) **検索で、ID・バージョン・ダウンロード数・発行元の確認済み (`verified`) を出す**。(2) Skill の規則で、「追加する前に、実在とバージョンを確認する」「ユーザーが名指しした名前だけを追加する」「バージョンを明示して固定する」。(3) **`package_once.sh` の実行に、`permissions.ask` を付ける** (`docs/RECOMMENDED-SETTINGS.md`)。**確認は、設定でしか強制できない** (4.15 と同じ理由)。(4) 取り込んだバージョンを、報告に含め、`git diff` で、人が確認する。
- **`search` / `versions` は、nuget.org の REST API を、直接引く** (PowerShell の `Invoke-RestMethod`)。`dotnet package search` (SDK の版に依存し、出力の形式も揺れる) は、採らなかった。ダウンロード数と `verified` を出せる。**限界: 社内フィードは見えない** (`add` は、ホストの NuGet の設定どおりに動く)。
- **NuGet の `add` / `remove` は、`dotnet add/remove package` に任せる。** ID の実在、バージョンの解決、`.csproj` の書き換え (中央管理 `Directory.Packages.props` を含む) を、`dotnet` が行う。結果のバージョンは、`.csproj` (なければ、上位の `Directory.Packages.props`) から読み、`added <ID> <バージョン> -> <プロジェクト>` と返す。**失敗の分類:** ネットワーク・フィードに届かない (`NU1301` など) は環境エラー。**`NU1101` (パッケージが見つからない) は、ソースの問題** (名前の誤りは、Claude が直せる。4.24 と同じ)。
- **C++ は、vcpkg のマニフェストモードを、標準にした。**
  - **Visual Studio 同梱の vcpkg を使う** (VS 2026 Enterprise の `VC\vcpkg\vcpkg.exe` を実機のファイルで確認。2022 にも、同じ構成がある。`VsDevCmd` の `ext\vcpkg.bat` が、`VC\vcpkg` を PATH に足す)。ウォッチャーは、`-VcpkgExe` → 環境変数 `VCPKG_ROOT` → `vswhere` で見つけた VS の `VC\vcpkg\vcpkg.exe` の順に探す。なければ、環境エラー (VS の「vcpkg パッケージ マネージャー」コンポーネントの追加を案内する)。
  - **トリプレットの既定は `x64-windows-static-md`** (静的ライブラリ + 動的 CRT `/MD`)。GoogleTest のソース方式 (4.19、`/MD`) と同じ CRT なので、**ランタイムの不一致が起きない**。Win32 は `x86-...`、ARM64 は `arm64-...`。`setup --linkage dynamic|static` と、ウォッチャーの `-VcpkgTriplet` で変えられる (**両者を、同じにする責任は、ユーザー側**)。

### 4.27 WPF のソリューションの生成 (`new-solution --type wpf`) と、テスト先行 (`csharp-test-first`)、規約 (`rules/wpf-csharp.md`)
**きっかけ:** C++ / MFC で作った一式 (`/new-solution` → `cpp-test-first` → `build-test-loop`、規約 `cpp-mfc.md`) を、WPF でも、同じ流れで使えるようにする。統合 (4.24)、`wpf-check` (4.25)、`add-package` (4.26) の上に、「作る」「テストを先に書く」「書き方を揃える」を足した。

- **C++ の生成とは、別の経路にした (`add_layer.py` を、拡張しない)。** C++ の生成 (`.vcxproj`、GoogleTest の入れ方 3 方式、MFC の `.rc`) と、.NET の生成 (SDK 形式の `.csproj`、MSTest) は、共通部分が、ほとんどない。1 つのスクリプトに混ぜると、C++ の動作確認済みの経路を、壊しうる。**`new_solution.py` が、`--type wpf` / `--tests mstest` のときだけ、`csharp-test-first/scripts/add_project.py` を、読み込む** (WPF を使わない人は、`csharp-test-first` がなくても、C++ が動く)。C++ の経路の関数は、変えていない (`parse_layers` に、引数を足しただけ。既定は、従来どおり)。
- **構成: View (WPF アプリ) → ViewModel → ロジック → データ。** ViewModel・ロジック・データは、**WPF 非依存のクラスライブラリ** (`net8.0`。`UseWPF` なし)。
  - **理由は、型システムによる強制:** `net8.0` (Windows 非依存) のライブラリは、`System.Windows` の型 (`Window` / `MessageBox` / `Application`) を、**そもそも、使えない** (ビルドで落ちる)。「ViewModel が View に依存しない」を、規約ではなく、ビルドで守る。テストも、STA スレッドや `Application` なしで動く (MSTest は、これらを用意しない)。
  - **`viewmodel` を層に含めない構成も、許す** (アプリが小さいとき)。その場合、ViewModel は、アプリの `ViewModels/` フォルダに入り、**テストできない**。`/add-feature` の計画で、「ViewModel 層の追加と、既存の ViewModel の移動」を、提案する。
  - 層の依存: 上の層は、すぐ下の層を参照する (ViewModel → ロジック → データ)。アプリは、すべての層を参照する (組み立てる側)。テストは、対応するライブラリだけを参照する (ほかは、推移的に見える)。**ロジックから、データの実装への参照は、ある** (.NET では、インターフェースと実装が、同じアセンブリ。「使うのは、インターフェースだけ」という規律で守る。厳密に分けるなら、`*.Abstractions` ライブラリ。`PROJECT-LAYOUT.md`)。
  - `wpf-check` の層の判定 (名前: `Logic` / `Domain` / `Core`、`Data`、`ViewModels`) に合う、既定の名前 (`LogicLayer` / `DataLayer` / `ViewModels`)。**生成したソリューションを、`wpf-check` にかけて、指摘が 0 件であることを、テストにした** (4 つの形: 4 層 + テスト、ViewModel 層なし、アプリのみ、層の名前を変えたもの、テストの後付け)。生成の誤りが、検査で見つかる。

### 4.29 UI テストの自動化 (FlaUI): 検討と PoC (2026-10-20)

**動機:** ビルド → テストのループで、UI だけは、人が、毎回、アプリを起動して確認している。FlaUI (UI Automation を包む .NET ライブラリ。MIT) + MSTest で、フォーム (WPF / WinForms / MFC のダイアログ) の UI テストを、ある程度、自動化したい。

**PoC (段階 0。`poc/flaui/`) の実機の結果 (2026-10-20、`UiPoc`: WPF の `WpfSample` と、MFC のダイアログ `MfcDlgLayers`):**
- **WPF (UIA3):** 起動 (メインウィンドウが取れるまで) **約 1.4 秒**。`TextBox` に `ValuePattern` で文字を設定すると、**ViewModel の `PropertyChanged` が働き、挨拶の `TextBlock` が変わる**。「クリア」を `InvokePattern` で押すと、入力欄が空になる。**マウスもキーボードも使わない。** `x:Name` / `AutomationId` が付いた要素 (`NameTextBox`、`GreetingText`、`ClearButton` など) は、`AutomationId` で見える。付いていない要素 (`TitleBar` を除くウィンドウなど) は、空。`TextBlock` の `Name` は、表示の文字。
- **MFC のダイアログ:** **UIA3 と UIA2 の、どちらでも、同じように見える。** ボタンの `AutomationId` は、**コントロール ID の数値** (`IDOK` = `1`、`IDCANCEL` = `2`)、`Name` は表示の文字 (`OK` / `Cancel`)、静的テキスト (`IDC_STATIC`) は `Text` として、`Name` に文字が入る (`AutomationId` は空)。起動 **約 0.2 秒**。`Invoke` で `Cancel` を押すと、ダイアログが終了する。違いは、タイトルバーの子 (システムメニューの名前が、UIA2 は `System`、UIA3 は `システム`) だけ。
- **スクリーンショット:** `Capture.Screen()` / `Capture.Element(window)` で PNG を保存でき、**WSL の Claude が、画像として読める** (ウィンドウの内容、ボタンの状態が、目視できる)。失敗の原因調査に、使える。
- **`trigger_test.flag` で、そのまま動いた** (`PASSED` 3 件)。ただし、これは、PoC のソリューションに、UI テストしかないため。通常のテストとの併用では、分ける必要がある (UI テストは、遅く、デスクトップを占有する)。

**判断 (PoC を受けて):**
- 実現性は、確認できた。**WPF も MFC のダイアログも、AutomationId で操作できる。** MFC では、**リソースのコントロール ID が、そのまま AutomationId** になる。`IDC_STATIC` のままの要素は、ID で探せない (Name = 表示の文字で、探す)。

## 5. ファイル形式

| ファイル | 文字コード | 改行 | 理由 |
|---|---|---|---|
| `*.cmd` | CP932 (Shift_JIS)、BOM なし | CRLF | 日本語のコメントを入れるため。Windows のバッチの流儀 |
| `*.ps1` | UTF-8、**BOM あり** | CRLF | Windows PowerShell 5.1 は、BOM がないと CP932 と解釈し、日本語が化ける |
| `*.sh` | UTF-8、BOM なし | **LF** | CRLF では bash で動かない |
| `*.md` | UTF-8、BOM なし | LF | |

- `.cmd` の画面メッセージ (`echo`) は、文字化けを避けるため、英語 (ASCII) のまま。
- `.cmd` の `rem` 行には、`|` や行末の `^` と同じ値の2バイト目を持つ文字 (「ポ」など) を使わない
  (ほかのコードページで実行されたとき、コマンドとして解釈される恐れがあるため)。
  `rem` の中の `&` も使わない。`( )` のブロックの中には、`rem` を書かない。
- **`build-windows.cmd` は、MSBuild.exe 呼び出しの直前後だけ `chcp 65001` / `chcp 932` を切り替える**
  (MSBuild/cl.exe のビルド出力の文字化けを防ぐため)。この区間 (`chcp 65001` 〜 `chcp 932` の間) に、
  CP932 の日本語コメントを置かない。上の注意点 (別コードページでの誤解釈) が、まさにこの区間で起きるため。
  `watch_and_build.ps1` は、`[Console]::OutputEncoding = UTF8` を設定し、パイプで受け取る側を合わせている。
- `.gitattributes` で、`.cmd` / `.ps1` は `-text` (git の自動変換を無効)、`.sh` / `.md` は `eol=lf`。
  検証は `tools/check-formats.sh`。`install.sh` は、コピー前に必ず、これを実行する。
- `.cmd` の差分を読めるようにするには、クローンごとに、次を設定する。
  ```bash
  git config diff.cp932.textconv "iconv -f cp932 -t utf-8"
  ```

### 4.41 GoogleTest の既定を vcpkg にする (v2.21.0)

**決定:** 新しい C++ のソリューションの GoogleTest は、vcpkg (マニフェストモード、`x64-windows-static-md`) で入れる。NuGet 方式 (旧) と source 方式 (`ThirdParty\googletest`) は、残す。**根拠: 実機の PoC (2026-10-28、gtest 1.18.0、`docs/NEXT-STEPS.md`)。**

- **なぜ vcpkg か:** (1) 版が `builtin-baseline` で固定され、再現できる。(2) NuGet の gtest は 1.8.1.8 で止まっている。コピーして使う方式は、元になる `packages\` が必要で、PoC では x64 の lib が欠けていた。(3) source 方式は、`gtest` プロジェクトを自分で持ち、ビルドごとにコンパイルする。(4) vcpkg の統合が、構成ごとの `lib` を自動でリンクする。
- **条件 (PoC で判明):** `gtest_main` は `lib\manual-link\` にあり、自動ではリンクされない → テスト exe ごとに `main.cpp`。C++17 以上。ライブラリ名は `gtestd.lib` ではなく、構成ごとのフォルダの `gtest.lib`。
- **生成する場所:** テスト exe の `.vcxproj` にだけ Vcpkg の設定を入れる (DLL には入れない。マニフェストは、ソリューション直下の 1 つ)。`cpp_pkg.py setup` は、設定済みを飛ばすので、あとから `add-package` で、ほかのライブラリを足せる。
- **並列ビルド:** `/m` で複数のノードが `vcpkg install` を始めても、`--x-wait-for-lock` で待つ。インストールの実体は 1 回 (PoC で確認)。
- **高速化は、既定のバイナリキャッシュだけ:** 初回 35 秒 (vcpkg 自身は 22 秒) が、キャッシュありで 12 秒 (同 0.2 秒)。短縮は約 23 秒で、共有フォルダや事前の温めは、手間に見合わない。大きなライブラリ向けに、`VCPKG_BINARY_SOURCES` の設定を、手順書に残す。
- **取り込まなかったこと:** ウォッチャーで gtest を実行する前に、環境変数 `GTEST_*` を消す (v2.20.1、`gtest-env-clean` ブランチ)。
- **実機で確認 (2026-10-28、TEST-PLAN N3v):** 生成物で、baseline と install (初回 60 秒) → Debug / Release とも `PASSED`、キャッシュからの復元 (28 秒)、層の追加 (3 件)、`cpp_pkg.py setup` との共存。
- **未確認:** 別のソリューションからの共有キャッシュの復元 (PoC の `files` の復元までは確認)。`package_once.sh` / `gtest_once.sh` への実行 ID の照合。

### 4.42 package_once.sh / gtest_once.sh の実行 ID の照合 (v2.21.1)

v2.20.0 の批判的レビューで、`build_once.sh` / `build_test_once.sh` / `uitest_once.sh` にだけ入れ、残していた項目。`package_once.sh` の `vcpkg install` は、特に長く (`--timeout 1800` など)、`TIMEOUT` であきらめたあと、ウォッチャーが続けて書く、古い結果を、次の実行の結果と取り違える危険があった。

- **フラグの形:** 古いウォッチャーを壊さないよう、実行 ID は **コメント行** (`# run=<ID>`)。package は、各行が操作で、`#` の行は、古いウォッチャーも無視する (先頭に置く)。gtest は、1 行目がタグ (古いウォッチャーは、1 行目だけを読む) なので、ID は 2 行目。build 系は、1 行目の `run=<ID>` のまま (その 1 行目を、古いウォッチャーは、使わない)。
- **照合:** ウォッチャーは、マーカーを書く直前に、`.claude-logs\run_id.txt` に、同じ ID を書く (`Write-GtestMarker` / `Write-PackageMarker` の先頭で `Write-RunId`)。スクリプトは、ID が一致するマーカーだけを、結果とする。`run_id.txt` がない = 古いウォッチャー → 従来どおり、マーカーだけ。
- **処理中の印:** ウォッチャーは、gtest / package でも、処理の間だけ `watcher_busy.txt` を置く (v2.20.0 で、build 系にだけあった `Set-WatcherBusy` の説明は、`gtest fetch run=<ID>` / `package run=<ID>`)。スクリプトは、処理中なら、`WATCHER_NOT_RUNNING` と誤報せず、`TIMEOUT` では、回収されていないフラグを取り下げる。
- **`TIMEOUT` の扱い:** `add-package` の Skill は、v2.21.0 で「報告して止まる」に直した。スクリプトのメッセージも、同じ (ユーザーが了承すれば、`--timeout` を延ばして、もう一度)。
- **互換性の組み合わせ:** 新 Skill + 古いウォッチャー: フラグのコメントは、無視される。`run_id.txt` は、書かれない (または、古い ID のまま) → 照合なし (従来どおり)。ただし、**古い `run_id.txt` が残っていると、一致しない**ので、スクリプトは、フラグを置く前に、`run_id.txt` を消す。古い Skill + 新しいウォッチャー: ID がないので、`run_id.txt` は書かれず、従来どおり。
- **実機で確認 (2026-10-28、`GtestVcpkgGen`):** (1) `package_once.sh "vcpkg install"`: `OK`。ログの中身が、前の実行のものでなく、今回のもの。(2) 続けて、もう一度: 3 つのファイル (`package.log`、`run_id.txt`、`package_result.txt`) が、同じ秒に更新され (`run_id.txt` が、マーカーと同時か先)、実行 ID が、前回と違う。(3) `--timeout 2` で `TIMEOUT` (`busy file: present`、「Do NOT start another run」) → すぐに、通常の制限時間で、もう一度: 1 回目の処理が終わるのを待ってから、自分の結果 (`already installed`) で `OK`。1 回目の古い結果を、取り違えない。(4) `gtest_once.sh v1.17.0`: `OK` (2 回目も)。`run_id.txt` と `gtest_result.txt` が、同じ秒に更新。(5) 手で置いた、実行 ID のない空の `trigger_gtest.flag` (古い形式): `OK`。
- **確認しきれていないこと:** (3) の 1 回目の実行 ID は、`TIMEOUT` の出力に出ないので、2 回目の `run_id.txt` と、直接は比べていない (結果の中身と時刻から判断した)。ウォッチャーの画面で、`[PACKAGE] vcpkg install` が 2 回出たことは、未確認。新しい Skill と古いウォッチャーの組み合わせは、疑似ウォッチャーでの検証のみ。

### 4.43 テストの改変の検査 `test_guard.py` (v2.22.0)

Copilot の案 (「UI テストファースト開発の、ハーネスとガード」、2026-10-28) を、既存の実装と突き合わせて検討した。**案の大半は、取り入れない**: Part A のハーネスは、実装済み。ガードは、文章の規則だけで、強制する仕組みがない。完了判定 (`COMPLETED` など 5 状態) は、半分が機械で判定できず、Claude の自己採点になる。失敗分類 12 種は、機械が決める結果コード (`ENV_ERROR` / `BUILD_FAILED` / `TIMEOUT` / `FAILED`) を、主観の分類に置き換える。成果物の構造 (`artifacts/<TestRunId>/`) は、`.claude-logs/` と実行 ID に二重になる。**取り入れたのは、「ガードを、文章から、機械判定にする」こと** (Test Mutation Guard)。

- **何を守るか:** `build-test-loop` の「止めどき」5 のテスト側の禁止事項 (削除、無効化、アサーションを弱める、許容誤差・`[Timeout]` の延長、飲み込む `try/catch`、実行から外す設定)。守られたかは、人の `git diff` でしか確かめられなかった。
- **基準:** Red を確認した直後のテストファイルを、`.claude-logs/test_guard_base/` に**コピー**する (git の HEAD ではない)。ユーザーの未コミットの変更や、未追跡のテストがあっても、混ざらない。git のないフォルダでも動く。**承認 = `snapshot` のやり直し** (承認の記録は、別に要らない)。
- **判定の単位:** テスト (名前で突き合わせる)。テスト本体の、アサーションの種類と数、`catch`、`Sleep`、待ち時間、`[Timeout]`、許容誤差、`[TestCategory]` を、基準と比べる。**コメントは除く。文字列・文字リテラルの中の波括弧は、読み飛ばす** (でないと、本体の範囲がずれる)。
- **正否を決められないものは、review:** アサーション行の書き換え (期待値の変更) と、Fake・ヘルパー・Setup の変更は、変更前後を並べて、ユーザーの確認に回す。誤検出を error にしない (形骸化を避ける)。
- **限界 (SKILL に明記):** 鍵ではなく、検知器。基準のコピーを書き換えられると、すり抜ける (SKILL に「基準を、勝手に、作り直さない」)。ヘルパーへ判定を移す細工と、実装側の細工 (テストの入力値に対する固定の答え、`#ifdef TEST`) は、検出できない。
- **採らなかった案:** (1) git の HEAD を基準にする (未コミットの変更が混ざる。フォールバックとしても、入れなかった)。(2) 検査を、`*_once.sh` の出力の末尾に、自動で足す (段階 2。Claude が `check` を忘れても、目に入る形。ウォッチャーは変えずに、WSL 側のスクリプトだけで済む。**v2.24.5 で入れた**: `test_guard_note.sh`。基準があるときだけ `TEST_GUARD:` の行を出す。基準がないときに何も出さないのは、「作れ」と促すと、Green のあとの `snapshot` で、改変が、基準に取り込まれるため)。(3) 実装側の細工の検査 (基準が、ソースにも要る。段階 2)。
- **検証の範囲:** 疑似ソリューション (`tests/test_guard_test.sh`、92 項目) のみ。**実プロジェクト (大きなテストファイル、実際のアサーションの書き方) での、誤検出の確認は、未実施。** 誤検出が見つかったら、コードと書き方を記録して、`test_guard.py` と `tests/test_guard_test.sh` に反映する (`mfc-check` / `wpf-check` と同じ進め方)。

### 4.44 作業フォルダの下に、候補ごとのソリューションを作る (v2.23.0)

**要望:** 親のフォルダ (例: `...\repos\ToDo`) で `new_solution` を動かし、複数の種類のソリューションを作って、個別に検討したい。壁打ちの結果 (`docs/`) は、その親にためる。ビルドは、候補ごと。

- **用途:** 同じ題材の比較 (種類を変えて、どれが合うかを、個別に試す)。**1 つの `.slnx` に、全候補を入れる形は、採らなかった** (ウォッチャーは、ソリューション単位でビルドするので、1 つの失敗が、ほかを止める。`Directory.Build.props` と `vcpkg.json` も共有になり、比較の独立性が失われる)。

- **仕様書の取り込みと同期:** 取り込みは、`spec_import.py` (`new_solution.py --spec` と同じ。ただし、構成案の節を要求しない)。**コピーなので、作成後は、ずれる。** そのため、取り込み時のハッシュを、候補の `docs/specs/.spec-sync.json` に記録し、`sync-spec` で、**要求したときだけ**、反映する (自動で、同期しない: 検討中の候補を、勝手に変えない)。状態: 同じ / 更新 (候補側が未編集) / 再コピー (コピーがない) / 候補側だけ変更 (そのまま) / **衝突** (両方が変更、または、記録がなく、違う。上書きしない) / 記録の作り直し。`*.cases.md` は、更新しない (チェック済みを守る)。
- **`CLAUDE.md` の節:** 全候補に、「## 比較の候補」(自動生成。候補の一覧、仕様書の正本と同期の案内、「他の候補は、読まない・書かない」)。**既存の候補の `CLAUDE.md` を、書き換えるのは、この節だけ** (候補が増えたとき)。改行コード (CRLF) を保つ。
- **対象の決め方 (`resolve`):** Skill の「カレント = ソリューション」の前提を、「作業フォルダなら、`resolve` で決める」に広げた (7 本の Skill の前提に、1 項目。`$SLN` / `$PROJ` を使う書き方は、変えない)。カレントが、ソリューションなら、これまでどおり。
- **最初のモードの選び方 (v2.23.1):** `.sln` も `solutions.md` もないフォルダは、A. にも C. にも、なりうる (A. にすると、作業フォルダそのものが、ソリューションになる)。`solutions.md` は C. の中で作るため、**判定の材料にできない**。そこで、**質問して決める** (引数で内容が指定されていれば A.、ユーザーが比較を言っていれば C.)。フォルダの中身 (`docs/specs/` があるなど) は、目安にとどめ、決めつけない。
- **範囲外にしたもの:** (1) GoogleTest (vcpkg) の仕上げ (`package_once.sh` は、ウォッチャーが要り、ウォッチャーは候補ごと。候補を扱うときに行う)。(2) ウォッチャーの一括起動 (`run_watchers.cmd`。ホスト側で、WSL では検証できない。当面は、候補ごとに、手で起動する)。(3) 候補の比較結果の集約 (比較は、ユーザーが行う)。(4) Git の方針 (作業フォルダを 1 つのリポジトリにするか、候補ごとに分けるかは、利用者が決める。どちらでも動く)。

- **検証の範囲:** 疑似フォルダ (`tests/new_solutions_test.sh`) と、**実機の NS1 (2026-10-29)**: 作業フォルダで起動して、**配下に 3 候補を書き込めた** (拒否なし)。仕様書の取り込み、`CLAUDE.md` の節、`sync-spec --dry-run` (6 件「最新」)、`resolve` が、実フォルダで、設計どおり動いた。**未確認:** 複数のウォッチャーで、候補を同時にビルドできるか (NS2。`TodoWpf` には、ビルド・テストの結果のファイルが、すでにあった)、`create` の出力の Windows のパスへの変換、v2.23.1 の初回の質問 (空の作業フォルダでの経路)、NS3〜NS6 (TEST-PLAN 2-8)。

### 4.45 UI デザインガイドラインの取り込み: `/ui-design-review` (v2.26.0)

**要望:** UI デザインのガイドライン (Windows デスクトップ。WPF / WinForms / MFC。WinUI 3 は付録の枠) を、このツール群に組み込み、画面を作るときの、UI デザインのガイドラインとして使いたい。

**背景:** v2.26.x の `/ui-design-review` は、`/new-solution` で作った直後のソリューションに、いつも、同じ既知の指摘 (UI-DPI-002、UI-CTL-100 (MFC)、UI-ACC-001 (WPF)) を出していた (DESIGN 4.45、TEST-PLAN の UG1)。レビューのたびに、本当の指摘が、既知の指摘に埋もれる。

### 4.62 MFC 標準 DLL の生成 (v2.46.0)

- **問題の整理 (2026-11-04):** 拡張 DLL (4.61) の次の対応。標準 DLL (Regular DLL) は、`_USRDLL` を持つ点で、いまの「通常の DLL」(MFC なし。`_USRDLL`) と似ているが、**`UseOfMfc` と `CWinApp` 派生の `theApp` が加わり、エクスポート関数に `AFX_MANAGE_STATE` が要る**。拡張 DLL (`_AFXEXT`、`DllMain` の定型コード、`AFX_EXT_CLASS`) とは、入口・公開の仕方・呼び出し側の条件が違う。
- **決定 (ユーザー):** 名前は `mfc-std-dll` (「標準 DLL」に合わせる。`mfc-regular-dll` は、不採用)。リンク方式は、共有 MFC のみ (静的リンクの選択肢は、見送り)。実物は `MFCLibrary2`。
- **実物から読み取った設定:** `Keyword=MFCDLLProj`、`UseOfMfc=Dynamic`、`_USRDLL` (`_AFXEXT` なし)、`PrecompiledHeader=Use` + `pch.h`、`pch.cpp` が Create、`.def`、`CMFCLibrary2App : public CWinApp` と `CMFCLibrary2App theApp;`、`.cpp` の注意書き (共有 MFC のとき、エクスポート関数の先頭に `AFX_MANAGE_STATE(AfxGetStaticModuleState())`)。
- **拡張 DLL との違い (設計):** 入口は `theApp` (`dllmain.cpp` は作らない)。公開は、関数と値のクラス (`<Name>_API`)。MFC のオブジェクトは、境界で渡さない。**呼び出し側の条件が、ない** (MFC なしの exe からも使える) ので、`new_solution.py` は、メインの種類を制限しない (拡張 DLL は、MFC のメインだけ)。**テスト exe は MFC なし** (拡張 DLL は `UseOfMfc=Dynamic` が必要だった)。
- **ウィザードと変えたところ (拡張 DLL と同じ理由):** `.def` / `.rc` / `.rc2` / `Resource.h` は作らない。`<Name>.h` は、`resource.h` を include しない。`framework.h` は最小限。x64 のみ。`<NAME>_EXPORTS` と `<NAME>_API` を残した。ビルド確認用の関数に、`AFX_MANAGE_STATE` を入れた (入れ忘れの手本)。
- **既定は、変えない:** 通常の DLL と、拡張 DLL の出力は、テストで固定した。
- **実機で確認 (2026-11-04。TEST-PLAN 2-26):** (a) 生成した一式が、ビルドできた (`SUCCESS`)。(b) MFC なしのコンソールのテスト exe が、標準 DLL (共有 MFC) をロードし、`AFX_MANAGE_STATE` つきの関数を呼べた (2 件 `PASSED`)。(c) 設定は、実物 (`MFCLibrary2`) と一致 (静的比較)。**未確認 (任意):** Visual Studio のプロパティページ、`AFX_MANAGE_STATE` を外した場合の挙動。
- **観察 (生成とは無関係):** MSBuild の vcpkg 連携が VS 2022 の `vcpkg.exe` を使い、コンパイラは VS 18 (MX2 と同じ。ビルドは通る)。
- **見送り:** 静的リンク (`UseOfMfc=Static`)、設定の食い違いの検出 (`mfc-check`。拡張 DLL の分と、まとめて)、`AFX_MANAGE_STATE` の入れ忘れの検出、メインの exe からの参照の自動生成。

### 4.63 C++ の規約の分割 (v2.47.0)

- **問題:** `mfc-cpp.md` は、全部の C++ のファイルで読み込まれる (`paths`)。`/new-solution --type win32` のように、MFC を使わないプロジェクトにも、MFC の規則 (`m_hWnd` の直接アクセス、`CArray` の優先など) が入る。名前も、内容 (約半分は MFC と無関係) と合わない。v2.41.0 で、「MFC 以外の C++ プロジェクトが来たら分ける」と見送っていた。
- **決定 (ユーザー、2026-11-04):** 分割する。命名の方針 (`<言語>-common.md` = 言語の共通、`<技術>-<言語>.md` = 技術ごと) に従い、`cpp-common.md` と `mfc-cpp.md`。
- **`paths` の限界と対応:** `paths` は、ファイルの名前だけで判定し、プロジェクトの種類を判定できない。MFC のプロジェクトだけで読み込む、確実な `paths` は、書けない。→ `mfc-cpp.md` の `paths` は、MFC のウィザードが作る名前に絞る (Win32 のプロジェクトでは、まず当たらない)。**層の `.cpp` など、当たらない MFC のファイルは、生成する `CLAUDE.md` が、読むよう指示する** (MFC のメインと、`mfc-ext-dll` / `mfc-std-dll` の層のとき)。確実性は、`paths` ではなく、`CLAUDE.md` に置く。
- **移し方:** 規則の文言は、変えない。MFC の名前が出る例 (`CArchive`、`CRect`、`CDC`、`CGdiObject`) だけ、共通では、MFC なしの例 (`Render`、`SIZE`、`HDC`、`HWND`) にした。「Win32 API は `::` を付ける」は、共通のまま (MFC の同名メンバーとの衝突は、`mfc-cpp.md`)。COM は ATL (MFC 不要) なので、共通。
- **実機で確認 (2026-11-04。TEST-PLAN 2-27):** (a) Win32 のプロジェクトで `.cpp` を触ると、`cpp-common.md` だけが読み込まれた (`nested_memory`)。(b) MFC のダイアログのプロジェクトで、`SampleDlg` の編集のときに、`mfc-cpp.md` も読み込まれた。**未確認:** `*Dlg` / `*View` / `*Doc` / `MainFrm` 以外のファイル名の MFC のファイル (層の `.cpp` など) で、`CLAUDE.md` の指示により、`mfc-cpp.md` が読まれること。
- **見送り:** 配布先に残る旧い `mfc-cpp.md` (全文の版) は、`install.sh --rules-only` が、新しい版で上書きする (番号付きのバックアップを残す)。二重の読み込みは、起きない (名前が同じ)。

### 4.64 `mfc-check` の MFC の DLL の検査 (v2.48.0)

- **問題:** MFC の拡張 DLL・標準 DLL は、設定 (`UseOfMfc`、`_USRDLL` / `_AFXEXT`) と、お決まりのコード (`DllMain`、`theApp`、`AFX_MANAGE_STATE`) の組み合わせで動く。食い違っても、コンパイルは通り、実行時に、リソースが見つからない・状態が混ざる、という形で壊れる。v2.45.0 / v2.46.0 で、「設定の食い違いの検出」を見送っていた。
- **決定 (ユーザー、2026-11-04):** `mfc-check` に足す (残作業の 1 番のみ)。メイン exe から層 DLL への参照の自動生成と、標準 DLL の静的リンクは、別。
- **検査の選び方:** 「実行時にしか分からない」ものを選んだ。コンパイルやリンクで分かるもの (`UseOfMfc=false` で `afxwin.h` を使う) は、入れない。**拡張 DLL を参照する側の `UseOfMfc` (DLL008)** は、MX3 の確認で、テスト exe に `UseOfMfc=Dynamic` が要ると分かったものを、検査にした。
- **判定の材料:** `.vcxproj` の、構成ごとの `UseOfMfc` と `PreprocessorDefinitions` (`Project.cfg`)、ソースの文字列。`.props` は読まない (限界)。DLL007 は、公開のマクロ (`#define X_API __declspec(dllexport)`) を、ヘッダーから見つけ、その名前の関数の定義の、先頭の文が、`AFX_MANAGE_STATE` かを見る。静的 MFC は、不要なので出さない。自由関数だけ。
- **既存の検査の修正:** LAY002 (ライブラリの GUI ヘッダー) は、MFC の DLL の層では、意図した include なので、info にした (拡張 DLL の `dllmain.cpp` が、生成した直後に warning になっていた)。LAY001 (GUI のクラス) は、そのまま。
- **確認 (2026-11-04):** 生成した拡張 DLL・標準 DLL、実物の `MFCLibrary1`・`MFCLibrary2` で、error 0 / warning 0。各コードの検出は、疑似のプロジェクトのテストと、検査を壊す変異で確認した。**実機 (ビルドした DLL を壊して、検査と実行を見比べる) は、未確認 (TEST-PLAN 2-28)。**
