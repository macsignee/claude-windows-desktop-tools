# WinForms: 画面モデル (ScreenModel) と Presenter の規約 (ユーザー共通)

`winforms-csharp.md` (WinForms プログラミング規約) の、**画面モデル・Presenter に関する章**を、別のファイルに分けたもの。画面モデルの考え方は、WPF (ViewModel)・MFC と共通 (**役割の名前は「画面モデル」。WPF では `ViewModel`、WinForms と MFC では `ScreenModel` と呼ぶ**。`ViewModel` は、宣言的なデータバインディングを連想させるが、WinForms と MFC は、更新を明示的に書くため、別の名前にした)。**この文書は、`Presenters/` と `ScreenModels/` の下、`*Presenter*.cs`、`*ScreenModel*.cs`、`I*View.cs` を読むときに、読み込まれる。** 章の番号は、この文書の中だけで数える (`winforms-csharp.md` の章を指すときは、ファイル名をつける)。

**共通部品の状態:** 検査の結果 (`ValidationResult`)、操作の失敗 (`Failure`)、文章の生成 (`IMessageFormatter`) などの共通部品は、**ツール群の実装の段階で、ひな形が生成する** (未実装のあいだは、この文書の設計に沿って、プロジェクトごとに書く)。

## 1. 責務の分離 (画面モデル + 任意の Presenter)
```
Form ──(状態は直接読む・操作を呼ぶ)──▶ 画面モデル ──▶ リポジトリ (インターフェース)
  │                                     ▲
  └─(IView)─ Presenter (任意) ───────────┘
        ダイアログ・遷移の実行・フォーカス・UI スレッド
```
| 部品 | 役割 | 書いてよいもの | 書いてはいけないもの |
|---|---|---|---|
| **Form (View)** | 画面の表示と、入力の受け取り | コントロールの配置、画面モデルの状態の表示 (`BindingSource`、または通知を受けた代入)、画面モデルの操作の呼び出し、画面固有の処理 (タブ順、アニメーション) | 業務ロジック、入力の検査の判断、データアクセス、`new Service()` |
| **画面モデル** (`<画面名>ScreenModel`) | 画面の状態、規則、操作とその実行可否、入力の検査、変更の通知、リポジトリの呼び出し | 状態のプロパティ、操作のメソッドと `CanXxx`、検査 (`Validate()` / `IsValid`)、`INotifyPropertyChanged`、リポジトリのインターフェースの呼び出し | WinForms の型、`MessageBox`、`Application`、UI スレッドの扱い |
| **IView** (任意。Presenter があるときだけ) | Presenter から見た Form の姿。**小さな窓口** | `ShowMessage`・`Close`・`SetFocus` のようなメソッド、イベント | **状態のプロパティ**、WinForms の型 (`Control` / `Form` / `MessageBox`) |
| **Presenter** (任意) | WinForms の型がないと書けないものだけ: ダイアログ (`IDialogService` 越し)、画面遷移の実行、フォーカス、UI スレッドへの戻し、Form の開閉 | `IView`、画面モデル、`IDialogService` の呼び出し | WinForms の型、`MessageBox`、`Application`、**状態**、**規則** |
| **ロジック / データ層** | 業務ロジック、データアクセス。**画面モデルは、ロジック層に置く** | 業務の処理 | WinForms への依存 (`UseWindowsForms`、`System.Windows.Forms`、`System.Drawing`) |

- **画面モデルは、すべての画面・ダイアログで必須 (例外なし)。** 表示専用の画面や、入力が 1 つだけの単純なダイアログでも置く。Form が、リポジトリ・Model を直接使う構成は、採らない (構造をそろえ、「Form がデータ層を直接参照しない」検査を、例外なしで書けるようにするため)。計画には、画面モデルの行を、必ず書く。
- **境界の判断基準:** **WinForms の型・機能がないと書けない → Presenter。別の UI (WPF・MFC) でも同じ内容になる → 画面モデル。** 画面遷移は、「どこへ進むか」の判断が画面モデル、「開く」の実行が Presenter。
- **状態は、画面モデルだけが持つ。** `IView` に、状態のプロパティを写さない。Form は、画面モデルの状態を直接読む。
- **規則は、Presenter に置かない。** 入力の検査、実行可否は、画面モデルが決める。
- **Presenter は、必要なときだけ置く。** 表示と操作の呼び出しだけで足りる画面・ダイアログは、Form が、画面モデルに直接つなぐ。ダイアログ・遷移・フォーカスの処理が出てきたときに、足す。
- (`winforms-check` の WFL001 / WFL002 / WFL004 が検査する。**画面モデルをロジック層に置く限り、WinForms の混入は WFL001 が検査する。** `ScreenModels/` や名前の末尾 `ScreenModel` による検査は、まだない。)

## 2. 画面モデルの契約
画面モデルは、次の五つを公開する。UI の枠組みによらない (WPF・MFC の画面モデルと同じ考え方)。

| 項目 | 内容 | 例 |
|---|---|---|
| 状態 | Form が表示する値 (入力欄の値、表示専用の値、一覧、選択) | `Name`、`Greeting`、`Items` |
| 操作 | Form から呼ぶメソッド。**操作ごとに、実行できるか (`CanXxx`) も公開する** (ボタンの有効 / 無効になる) | `Save()` と `CanSave` |
| 検査 | 入力の誤り。**検査の実行は `Validate()`、合否は `IsValid`** (2.1) | `Validate()`、`IsValid` |
| 変更の通知 | 状態・検査・実行可否・失敗が変わったことを、Form に知らせる (`INotifyPropertyChanged`) | `PropertyChanged` |
| 結果 | 確定は `Commit()` の `bool`、失敗は状態 `Failure`、取消は `Cancel()` (2.2) | `Commit()`、`Failure` |

- WinForms に `ICommand` は要らない (操作はメソッド、実行可否は `CanXxx`)。
- **通知は、呼び出されたスレッドで上げる。** UI スレッドへの戻しは、Form か Presenter が行う (`winforms-csharp.md` の 8.2)。画面モデルは、UI スレッドを知らない。
- **Form の受け方:** 状態は `BindingSource` による `DataBindings`、または、通知を受けて、コントロールへ代入する。ボタンの `Click` は、画面モデルのメソッドを呼ぶ 1 行にする。実行可否は、通知を受けて `Enabled` に代入する。
- **通知の識別 (`PropertyId`) と、誤りの対象の欄は、画面ごとの 1 つの列挙で兼ねる。** 入力欄、派生した表示、`CanXxx`、`IsValid`、`Failure`、「全体」(`All`) の値を持ち、宣言の順序は、「入力欄、表示、`CanXxx`、`IsValid`、`Failure`、`All`」とする。**列挙の名前は、プロパティの名前と同じ**にする (`INotifyPropertyChanged` のプロパティ名と対応づけるため)。誤りの対象には、入力欄だけを使う。取り違えを防ぐため、ひな形が、入力欄かどうかを判定する補助 (`IsInputField(id)`) を生成し、画面モデルの単体テストで、`Validate()` の誤りの対象が、入力欄だけであることを確かめる。

### 2.1 検査 (`Validate()` と `IsValid`)
- **`Validate()`** は、現在の入力から検査を実行し、**`ValidationResult` (誤りの一覧) を返す。純粋** (状態を持たず、副作用がない)。複数の入力欄の誤りを、一度に返せる。
- **`IsValid`** は、`bool` のプロパティ。`CanXxx` と同じ扱いで、現在の入力から毎回計算する純粋な値。意味は、「`Validate()` の結果が空」。変更の通知に含める。
- **誤り (`ValidationError`)** は、**種別 (列挙)・対象の欄の一覧 (`Properties`)・引数**を持つ。**文章は持たない** (2.4)。一覧が空なら、欄に紐づかない画面全体の誤り (`IsScreenLevel`)、1 件なら 1 つの欄の誤り、2 件以上なら複数の欄にまたがる誤り。**先頭が、主たる欄** (文章は、主たる欄の隣に表示し、残りは強調だけ)。同じ問題を、欄ごとに複数件出さない。
- **`ValidationResult<TError, TProperty>`** は、`Errors` (全件。`IReadOnlyList`)、`GetErrors(property)` (その欄を含む誤りをすべて。補助でよい)、`IsEmpty` を持つ。欄のない誤りは、`GetScreenErrors()` (名前は仮) で取り出す。**誤りの並びは、検査の規則を書いた順。** 等価の比較は、`record struct` で自動に持たせ、テストで、種別と欄の一覧と引数 (順序を含める) を比べる。.NET の `DataAnnotations` の `ValidationResult` とは、**ソリューションの名前空間の配下に置いて、区別する。**
- **種別の列挙は、画面モデルごと** (`<画面名>Error`)。共通の誤り (必須、長さ超過) も、画面ごとの列挙に持つ。
- **引数は、型を保つ** (`object` の一覧。数値と文字列に限る)。**数値を、整形済みの文字列にしない** (桁区切りなどを、言語ごとに変えるため)。
- **`Commit()` は、内部で `Validate()` を行い、誤りがあれば `false` を返す** (UI が `IsValid` を呼んだかに、依存しない)。`false` のときは、通知 (`All`) を出して、誤りの表示を更新する。

### 2.2 操作の失敗 (`Failure`)
入力が正しくても、実行してみないと分からない失敗 (保存時のデータベースのエラー、同時更新の衝突、接続の失敗など) は、`Validate()` に入れない。
- **`Commit()` は `bool` を返す。理由は、状態で読む** (検査の誤りは `Validate()` / `IsValid`、失敗は `Failure? Failure`)。結果の型は作らない。最初の誤りの欄へフォーカスを移したいときは、UI が `Validate()` を呼ぶ。
- **`Failure` は、種別と引数だけ** (対象の欄は持たない。欄に関係する失敗 (`Duplicate` など) も、まず画面全体の誤りの一覧に表示する)。**直近の失敗を保持し、次の編集、または次の `Commit()` の開始で消す。** 変更の通知に含める。
- **失敗の種別の列挙は、ソリューションに 1 つ** (画面固有の値は、同じ列挙に足し、値の名前に画面名をつける)。初期の値の案: `Unavailable`、`Timeout`、`Conflict`、`NotFound`、`Duplicate`、`Unexpected`。
- **リポジトリの失敗は、種別つきの例外 `RepositoryException` で伝える** (本物のリポジトリが、データベース固有の例外を、これに変換する。契約テストで確かめる)。**画面モデルが変換するのは、`RepositoryException` だけ。** それ以外 (プログラムの誤り) は、握りつぶさず、そのまま伝え、未処理の例外の受け口 (`winforms-csharp.md` の 9.1) で扱う。失敗したら、画面モデルの状態は、変えずに残す (再試行できる)。
- **取消は、`Commit()` の結果ではなく、`Cancel()` か、利用者が閉じる操作。**
- 失敗の再現は、Fake リポジトリの専用メソッド (`FailNext(種別)`、`FailWhen(操作, 種別)`。インターフェースにはない)。UI テストは、`APP_MODEL=fake:<シナリオ名>` (`ui-test-first` の `references/model-switching.md`)。
- 非同期の `Commit()` (実行中の状態の公開が要る) は、決めていない。

### 2.3 Fake 画面モデルの切り替え
画面ごとに、Fake 画面モデルと本物を選べる。Fake 画面モデルは、つなぎ (本物ができるまで) と、状態の再現のためで、**本物へ切り替えて、同じ UI テストが通ったときに、役目を終える。** 切り替えは、環境変数 `APP_FAKE_SCREENS` (画面名のカンマ区切り。`画面名:シナリオ名` も可。**Debug のときだけ読む**)。仕組みの詳細と、テスト側の設定は、`ui-test-first` の `references/model-switching.md`。画面モデルは、インターフェース (`I<画面名>ScreenModel`) 経由で使い、組み立てる場所 (`Program.cs`) で実装を選ぶ。

### 2.4 文章の扱い (現状と移行)
- **現状:** 画面モデルは、**画面に出す文章を、状態に持ってよい** (国際化のニーズが高くないため。文章を持たない実装は、コストが高い)。ただし、**文章を作る処理は、`IMessageFormatter` に集約する** (`Format(種別, 引数)` が文章を返す。既定の実装は、ロジック層の日本語の表で、ひな形が、列挙の全値の行を生成する)。画面モデルは、日本語のリテラルを、直接書かない。**文章を持つ状態は、`〜Text` / `〜Message` に統一し** (あとで検索して、廃止できる)、**文章の元の値 (件数など) も、数値の状態として公開する。**
- **移行 (必要になったとき):** UI 層が、リソース (`.resx`) を引く `IMessageFormatter` の実装を作り、組み立てる場所で差し替える。`〜Text` の状態は廃止して、UI が、種別と引数から、直接 formatter を呼ぶ。画面モデルの本体は、変わらない。
- **案内文と業務の生成文の線引き:** 基準は、**文章が画面の外に出るか。言語を決めるのは、操作者か、業務か。** **案内文** (検査の誤り、失敗、確認、状態の表示) は、操作者の UI の言語で決まる。**業務の生成文** (挨拶文、帳票の文面、メール本文、エクスポートされるテキスト) は、業務の要件で決まる (英語の操作者が、日本語の顧客へ送る請求書は、言語が顧客で決まる)。ログは、開発言語 (日本語)。**業務の生成文は、当面、ロジック層に日本語で書く** (文字列の状態として持ってよく、単体テストでも、文言で検査する)。多言語の出力が業務の要件になったら、出力する言語を引数に取る、業務の機能にする (UI 層のリソースを使わない)。
- **Form の固定文字列** (ラベル、ボタン) は、リソースにしない (VS のデザイナーが、現在のカルチャの文字列を埋め込むのが標準のため)。国際化の範囲は、画面モデル由来の動的な文章だけになる。

## 3. ダイアログ・画面のデータ
- **ダイアログにも、画面モデルを置く。** **ダイアログ・画面が使うデータのクラス** (入力値のまとめ、ダイアログが返す結果など) は、画面モデルが公開する値として、**ロジック層に、別のファイルで置く** (UI の型は使わない。画面モデルの内側に入れ子にせず、同じ層に、別のファイルで置く)。データ層 (データベース・API の違いを隠す、リポジトリ的なもの) には、置かない。純粋な規則 (入力の検査、表示用の派生値) は、データのクラスか画面モデルが持つ。
- **モーダルなダイアログは、確定 (OK) するまで、渡されたデータを変更しない。** 編集中の値は、**画面モデルの内部**に持ち、入力中の検査は、その値で行う。**確定 (`Commit`) するまで、リポジトリにも書かない。** 取消・× では、何も変わらない。
- **モードレスなウィンドウは、OK がないので、持っているデータ (コピーでなく、共有するデータそのもの) を、入力のたびに、すぐ更新し、変更を通知する (`INotifyPropertyChanged`)。メインなど、ほかの画面も、すぐ追従する (逆向きも)。不正な値は、反映せず、エラーを示す (勝手に元に戻さない)。閉じても、変更は、取り消さない。「開く」を押し直したときは、すでにあるウィンドウを前面に出す (単一インスタンス。Presenter か、開くサービス `IXxxDialogService` が行う)。メインを閉じると、閉じる。共有するデータは、変更通知を持つクラス (ロジック層)。

## 4. 戻りの規則
画面を作っている途中で、**画面モデルに、必要なものが足りない**と分かったら、Form・Presenter の中で補わない。**ロジック層に戻り、単体テストを先に書いて、画面モデルに足す。** 足りないのは、たとえば、確定前の一時的な値、実行可否の条件、画面に出す表示用の値である。Form や Presenter に入れると、規則が、単体テストの外 (フォームを起動しないと確かめられない場所) に出る。
- 戻る回数を減らすには、最初から、画面モデルの契約 (2 章) の五つ (特に、実行可否・検査・通知) を、そろえておく。
- 画面モデルのインターフェースの意味を変えるときは、ユーザーの承認を取り、契約テストと、Fake (画面モデルの Fake があるとき) にも反映する。
- 機械で確かめられるのは、**Form が、`new XxxRepository()` などで、データアクセスを生成していないこと** (WFL004) と、層の参照の向き (WFL003) までである。**Form が、リポジトリ・データ層を、型として直接参照する検査は、まだない (予定)。** ほかは、レビュー (`winforms-csharp.md` の 15 章) と、設計の記録に残した「戻った」履歴で確かめる。

## 5. 画面モデル規約・Presenter 規約

### 5.1 画面モデル
- 名前は `<画面名>ScreenModel`、置き場所は `ScreenModels/` (ロジック層。ロジック層がない小さなアプリでは、アプリの `ScreenModels/`)。インターフェースは `I<画面名>ScreenModel`、Fake は `Fake<画面名>ScreenModel`。
- **WinForms の型を使わない** (`Control` / `Form` / `MessageBox` / `Application` / `Timer` / `Clipboard`、`System.Windows.Forms` / `System.Drawing` の `using` も)。**UI スレッド (`Invoke`) も知らない。**
- コンストラクターで、リポジトリなどのインターフェース (`IDialogService` は、画面モデルが使うときだけ) と、`IMessageFormatter` を、受け取る。**`new` で、Service を作らない。**
- **画面モデルは、UI スレッドからだけ呼ぶ** (別スレッドの処理は、結果を UI スレッドへ引き渡してから、画面モデルを呼ぶ)。
- 非同期の処理は、`async Task` で書く。実行中の状態も、状態として公開する。
- **単体テストを先に書く** (`csharp-test-first`)。リポジトリは、Fake を渡す。

### 5.2 Presenter (任意)
- **WinForms の型を使わない** (5.1 と同じ)。
- コンストラクターで、`IView`・画面モデル・必要なインターフェース (`IDialogService`) を、受け取る。**`new` で、Service を作らない。**
- 画面モデルの通知・結果に応じて、`IView` を呼ぶ (ダイアログを開く、閉じる、フォーカスを移す)。UI スレッドへの戻しは、`IView` の実装 (Form) が引き受ける (`winforms-csharp.md` の 8.2)。
- `IView` は、小さく保つ。画面の部品を露出せず、状態のプロパティも足さない (足したくなったら、画面モデルに足す。4 章)。
